초기 기준: **2026-10-07 KST**. 문서 갱신 및 마지막 토스 거래 직접 확인: **2026-10-12 KST**. 아래 10/8 17:33 대조는 당시 중간 상태이며, 10/12 재조회에서는 지정한 단건 주문 1건·10,900원만 미취소였다. 이 문서는 사용자가 운영 Mac·DB Mac에서 실행한 명령과 브라우저·이메일에서 직접 확인해 전달한 결과를 기록한다. 토스 운영 대시보드의 10/7~10/8 거래는 에이전트도 두 차례 대조했다. 에이전트가 운영 DB를 직접 재조회한 결과로 확대 해석하지 않는다. 실제 키, 카드번호, 영수증 토큰은 기록하지 않는다. 개발 서버와 개발 DB는 이번 라이브 전환에서 변경하지 않았다.

## 열린 이슈 — 간편결제 안내 메일의 `-님`

사용자가 토스 결제 안내 메일에서 다음을 확인했다.

| 결제수단·실험 | 메일 호칭 |
| --- | --- |
| 일반 카드(체크카드·하나Pay에서 선택한 신용카드), 계좌이체 | `고객님` |
| 네이버페이·카카오페이·토스페이 간편결제 | `-님` |
| 일시적으로 `customerName: ''`를 보냈던 일반 카드·네이버페이 비교 | 일반 카드는 `고객님`, 네이버페이는 다시 `-님` |

현재 고객 웹의 단건결제 호출은 두 수단 모두 `customerEmail`만 조건부로 보내고 `customerName`은 **키 자체를 보내지 않는다**. 따라서 클리퍼의 수단별 구매자명 분기나 현재 코드에서 보낸 `-`로 설명되지 않는다. [토스 공식 결제 결과 안내](https://docs.tosspayments.com/guides/v2/learn/payment-results)는 이름을 설정하지 않으면 기본적으로 `고객님`으로 이메일이 발송된다고 설명하므로, 관찰된 간편결제 호칭은 문서 설명과 다르다. 토스/간편결제 경로의 내부 처리 중 어디서 `-`가 생기는지는 아직 확정하지 않았다.

**결정:** 사용자는 아직 토스에 문의하지 않고 이 이슈만 기록하기로 했다. 구매자 실명 정책을 팀과 정하기 전까지 `customerName`을 임의로 채우지 않는다. 추가 실결제도 이 호칭만 확인하려고 반복하지 않는다. 문의를 재개할 때는 일반 카드와 간편결제의 주문번호·시각·MID를 비공개 지원 채널에서 비교해 요청한다.

## 사용자 보고 — 결제수단·결제내역 화면

1. **마이페이지 결제수단 표시:** 사용자는 케이뱅크 체크카드가 `카드사 코드 3A`, 붙여 쓴 토스 마스킹 번호, `카드 종류 체크`, `마지막 확인`으로 표시되는 것을 확인했다. 고객 웹은 API의 `cardIssuerCode`, `cardNumberMasked`, `cardType`을 그대로 이어 붙인다. [토스 기관 코드표](https://docs.tosspayments.com/codes/org-codes)에서 `3A`는 케이뱅크다. 카드번호는 토스가 일부를 마스킹해 보내므로 현재 값의 마지막 **네 자리 숫자**를 모두 알 수 있다고 가정해서는 안 된다. 수정 시 카드사 이름과 `체크카드`를 명확히 표시하고, 마스킹된 끝부분만 안전하게 보여준다. `마지막 확인`은 실제 데이터의 `verifiedAt` 의미에 맞는 표현을 검토한다.
2. **결제내역의 미결제 주문:** 사용자는 결제 직전 화면을 나간 건까지 결제내역에 `결제 확인 필요`로 보인다고 보고했다. 10/7 22:36의 추가 크레딧 400·5,900원 사례를 m2-db에서 읽기 전용으로 확인한 결과, `reconciliation_required / EXPIRED / TOPUP_PROVIDER_STATUS_INCONCLUSIVE`, 결제 키·결제 시각 없음, 주문 생성 이벤트 1건이었다. 23:09에 주문이 갱신됐다. [토스 Payment 상태 정의](https://docs.tosspayments.com/reference)에 따르면 `EXPIRED`는 결제 유효 시간이 지나 거래가 취소된 상태다. 현재 대사 코드는 `DONE`·`WAITING_FOR_DEPOSIT`·`ABORTED`를 처리하지만 `EXPIRED`는 불확실한 상태로 분류한다. 이것이 이 주문의 잘못된 고객 메시지에 직접 연결된다. 다만 23:09의 대사를 웹훅·고객 결과 조회·관리자 조작 중 무엇이 시작했는지는 웹훅 수신 기록 없이는 확정하지 않는다. 별도로 API의 사용자 결제내역 조회는 `created`·`checkout_ready` 등 결제 전 주문도 상태 제한 없이 반환한다. 결제 전 이탈/만료 주문을 고객 결제내역에서 제외하고, 실제 미확정 거래는 숨기지 않도록 구분하되 내부 운영 기록은 보존한다.

### 10/8 코드 수정과 운영 적용

- 기능 브랜치 커밋 API `c22d90f` / 고객 웹 `a27c346`을 각각 `origin/feature/toss-live-cutover-20261007`에 push하고 `git ls-remote`로 원격 SHA 일치를 확인했다. 앞선 GitHub `Internal Server Error`는 재시도 후 해소됐다. 사용자가 m4-prod에서 두 이미지를 해당 SHA로 `--build-only` 빌드하고 API·고객 웹을 `--start-only`로 다시 기동했다. 실행 컨테이너 revision label이 각각 `c22d90f3a528864c48e56750744f91c0ed602333`, `a27c3460aa2e633cfa6a2ce135e07c0947a36d2d`임을 확인했다. 외부 고객 웹 HTTP 200과 API `/health`의 user/release/admin DB `ok`도 확인했다.
- API: 주문번호·금액·키 세트가 일치하는 토스 `EXPIRED`를 `expired`로 저장하고 대사 사유를 지운다. 기존 결제 완료 주문과 불일치 응답은 만료로 바꾸지 않는다. 고객 결제내역 조회는 DB 페이지네이션 **전에** `created`·`checkout_ready`·`canceled`·`expired`를 제외한다. 승인 중·결제 처리 중·입금 대기·실제 미확정 거래와 결제 성공/실패는 보인다. 운영자 주문·감사 기록은 그대로 조회된다.
- 고객 웹: 공식 카드사 코드표에 따라 이름을 표시하고 `신용/체크/기프트`를 카드 종류로 풀어 쓴다. 카드번호는 토스가 노출한 마지막 네 **문자**만 표시한다. 예: `케이뱅크 체크카드 · 카드번호 끝자리 113*`. 네 숫자가 모두 보이지 않을 때 숫자를 추정하지 않는다.
