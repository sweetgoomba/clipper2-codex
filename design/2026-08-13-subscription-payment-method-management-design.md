# 구독 결제수단 조회·변경 설계

작성일: 2026-08-13  
대상: `clipper_web_api`, `clipper_web_client`  
관련 설계: `2026-08-12-billing-subscription-credit-policy-design.md`, `2026-08-13-subscription-renewal-grace-retry-implementation-plan.md`

## 1. 목적

로그인 사용자가 자신의 토스페이 자동결제 수단을 Clipper 마이페이지에서 안전하게 확인하고 변경할 수 있게 한다.

특히 갱신 결제가 실패한 `past_due` 구독에서는 사용자가 새 결제수단 등록 전에 미결제 금액의 즉시 재결제 사실을 명확히 확인하고 동의하게 한다. 새 결제수단이 정상 등록되면 같은 갱신 회차를 새 결제수단으로 즉시 재시도하고, 성공하면 기존 구독 복구 흐름으로 돌아간다.

## 2. 범위

이번 작업에 포함한다.

- 현재 자동결제 수단의 안전한 표시
- 토스 상태 조회를 통한 최신 결제수단 확인
- 정상 구독의 결제수단 변경
- `past_due` 구독의 결제수단 변경과 사전 고지·동의
- 새 결제수단 활성화 후 미결제 갱신금액의 즉시 재시도
- 기존 빌링키 보존, 새 빌링키 검증 후 원자적 교체
- 중단·취소·만료된 변경 요청 정리
- 기존·후보 빌링키 삭제 복구
- 자동 재시도와 결제수단 변경의 동시 실행 차단

이번 작업에 포함하지 않는다.

- 이메일, SMS, 알림톡 발송
- 토스 오류코드별 사용자 문구 체계의 전면 개편
- 복수 결제수단을 사용자가 목록으로 보관·선택하는 기능
- 예비 결제수단 자동 대체
- 관리자가 사용자의 결제수단을 변경하는 기능
- 결제수단 변경과 요금제·결제주기 변경의 결합

## 3. 확정 결정

### 3.1 표시와 변경을 분리한다

`결제수단 확인`과 `결제수단 변경`은 서로 다른 동작이다.

- 확인은 Clipper 서버가 토스 빌링키 상태 조회 API를 호출하고 안전한 표시 정보만 사용자에게 반환한다.
- 변경은 Clipper 서버가 새 후보 빌링키를 만들고 사용자를 토스 인증 화면으로 보낸다.
- Clipper 서버가 카드번호를 직접 입력받거나 기존 빌링키의 카드를 서버 API로 임의 변경하지 않는다.

### 3.2 기존 빌링키를 먼저 삭제하지 않는다

결제수단 변경은 다음 순서를 사용한다.

```text
현재 빌링키 유지
  -> 후보 빌링키 생성
  -> 사용자가 토스에서 새 결제수단 인증
  -> 후보 빌링키 ACTIVE 상태 재검증
  -> 구독의 현재 빌링키를 후보로 원자적 교체
  -> 이전 빌링키 삭제
```

사용자가 인증 화면을 닫거나 등록에 실패하면 후보 요청만 종료하고 현재 빌링키는 유지한다.

### 3.3 상태별 결제 동작

- `active`: 결제수단만 교체한다. 즉시 승인 요청을 하지 않는다.
- `past_due`: 사용자가 사전에 확인한 미결제 갱신금액을 후보 빌링키 활성화 직후 한 번 재시도한다.
- `pending`: 최초 자동결제 등록 절차이므로 별도 결제수단 변경을 허용하지 않는다.
- `cancel_at_period_end`: 다음 결제가 취소되고 빌링키 삭제가 예약된 상태이므로 결제수단 변경을 허용하지 않는다.
- `stopped`, `canceled`, `ended`: 기존 구독의 결제수단 변경을 허용하지 않고 새 구독 시작 흐름을 사용한다.

사용자가 `cancel_at_period_end`에서 다음 결제를 다시 활성화하는 기능은 별도 동작이어야 하며, 결제수단 변경으로 취소 예약을 암묵적으로 철회하지 않는다.

### 3.4 `past_due` 즉시 재결제 동의

사용자가 후보 빌링키 등록을 시작하기 전에 다음 정보를 표시한다.

- 상품명
- 미결제 갱신금액
- 새 결제수단 등록 완료 직후 해당 금액을 즉시 결제한다는 사실
- 결제 성공 시 구독이 복구된다는 사실

권장 문구:

```text
새 결제수단 등록이 완료되면 미결제된 {상품명} 갱신금액 {금액}원이 즉시 결제됩니다.
결제가 완료되면 구독이 정상 상태로 복구됩니다.
```

확인 버튼:

```text
변경하고 {금액}원 결제
```

별도 체크박스를 추가하지 않는다. 금액과 결과가 표시된 확인 버튼 클릭을 명시적 진행 동의로 기록한다.

서버는 동의 시점에 다음을 스냅샷한다.

- 사용자와 구독
- 재결제 대상 갱신 주문
- 상품명과 금액
- 동의 시각

클라이언트가 보낸 금액은 결제 권한의 기준으로 사용하지 않는다. 서버가 현재 갱신 주문의 저장된 상품·금액을 다시 읽고, 화면에 표시했던 주문·금액과 달라졌다면 변경 등록을 시작하지 않고 최신 화면을 다시 요청하게 한다.

## 4. 사용자 화면

### 4.1 정상 상태

```text
결제수단
토스페이 · 신한카드 · **** 1234
신용카드 · 정상 등록됨
마지막 확인: 2026-08-13 15:20

[결제수단 변경]
```

정상 상태의 변경 확인창에는 다음 결제일부터 새 결제수단이 사용되며 지금은 결제되지 않는다고 표시한다.

### 4.2 갱신 실패 상태

```text
등록된 결제수단으로 결제하지 못했습니다.
미결제 금액: 19,900원

[결제수단 변경] [현재 결제수단으로 다시 시도]
다음 자동 재시도: 2026-08-14
```

- `결제수단 변경`은 새 후보 등록과 동의한 금액의 즉시 재결제를 수행한다.
- `현재 결제수단으로 다시 시도`는 기존 빌링키로만 재결제하며 카드 선택 화면을 열지 않는다.

### 4.3 정보 조회 실패

토스 상태 조회 실패 때문에 마이페이지 전체를 실패시키지 않는다.

- 저장된 표시 정보가 있으면 마지막 확인 정보와 확인 시각을 보여준다.
- 저장된 정보가 없으면 `결제수단 정보를 불러오지 못했습니다`를 표시한다.
- 빌링키 또는 공급자 사용자·표시 식별자는 사용자 응답에 포함하지 않는다.

## 5. 데이터 모델

### 5.1 구독의 현재 결제수단 표시 정보

`subscriptions`는 현재 사용 중인 암호화 빌링키와 함께 다음 안전한 표시 스냅샷을 보관한다.

- 결제수단: 카드 또는 토스머니
- 카드사명
- 카드번호 끝 4자리
- 카드 종류: 신용·체크·선불
- 토스머니 연결 은행명
- 공급자 상태를 마지막으로 확인한 시각

전체 카드번호, 카드 BIN, 계좌번호는 저장하지 않는다. 카드가 아닌 결제수단의 필드는 `null`을 허용한다.

### 5.2 결제수단 변경 요청

별도 `subscription_payment_method_changes` 기록을 둔다. 최소 개념 필드는 다음과 같다.

- 변경 요청 ID와 구독 ID
- 후보 `providerDisplayId`
- 암호화된 후보 빌링키
- 상태: `created`, `checkout_ready`, `activated`, `swapped`, `canceled`, `expired`, `failed`
- 변경 시작·만료·완료 시각
- 즉시 재결제 여부
- 동의한 갱신 주문 ID·상품명·금액·동의 시각
- 교체 뒤 삭제할 이전 암호화 빌링키와 이전 `providerDisplayId`
- 이전 빌링키 삭제 상태와 마지막 오류 범주

한 구독에는 `created`, `checkout_ready` 또는 `activated` 상태의 변경 요청을 하나만 허용한다.

후보 빌링키와 이전 빌링키는 기존 `SecretCipher`로 암호화한다. 평문 빌링키는 DB, 로그, 이벤트 payload, HTTP 응답에 남기지 않는다.

## 6. API와 처리 흐름

API 계약 정본인 `clipper_web_api/docs/api/openapi.yaml`을 먼저 변경한다.

### 6.1 현재 결제수단 조회

로그인 사용자의 현재 구독을 기준으로 결제수단 상태를 조회한다.

1. 구독의 공급자 사용자·표시 식별자로 토스 상태 조회를 호출한다.
2. `ACTIVE`와 빌링키 일치를 확인한다.
3. 안전한 표시 필드를 갱신한다.
4. 사용자에게 공급자 상태, 표시 필드, 마지막 확인 시각과 최신 조회 성공 여부를 반환한다.
5. 토스 조회가 실패하면 저장된 표시 스냅샷을 반환한다.

빌링키 평문을 토스 상태 응답과 비교하더라도 HTTP 응답이나 로그에는 포함하지 않는다.

### 6.2 변경 등록 시작

1. 로그인 사용자와 구독을 잠근다.
2. 허용된 구독 상태인지 확인한다.
3. 이미 공급자 승인 결과가 미정인 갱신 주문이 있으면 `현재 결제 결과를 확인 중입니다`로 거부한다.
4. 진행 중인 결제수단 변경 요청이 있으면 새 요청을 만들지 않는다.
5. `past_due`이면 동의한 주문·금액이 현재 미결제 갱신 주문과 일치하는지 다시 확인한다.
6. 고유한 후보 `displayId`와 30분 뒤 `expiresAt`을 가진 `created` 변경 요청을 저장한다.
7. 서버가 토스 빌링키 생성 API를 호출한다.
8. 후보 빌링키는 즉시 암호화하여 변경 요청에 저장하고 상태를 `checkout_ready`로 바꾼 뒤, 클라이언트에는 토스 인증 URL과 변경 요청 식별자만 반환한다.

토스가 빌링키 생성에 성공한 직후 프로세스가 종료되어 후보 키 저장이 누락되면, 복구 작업이 저장된 후보 `displayId`로 상태를 조회하여 해당 후보를 삭제한다. 인증 URL은 후보 키 저장이 끝난 뒤에만 클라이언트에 반환한다.

토스 API Key는 브라우저에 전달하지 않는다.

### 6.3 변경 등록 완료

토스 `ACTIVATED` 콜백을 그대로 신뢰하지 않고 상태 조회로 재검증한다.

1. `displayId`로 변경 요청을 찾는다.
2. 콜백의 사용자·`displayId`·빌링키가 변경 요청과 일치하는지 확인한다.
3. 현재 시각이 `expiresAt` 미만인지 확인한다.
4. 토스 상태 조회로 후보 빌링키가 `ACTIVE`이고 같은 사용자·`displayId`·빌링키인지 확인한다.
5. 구독과 변경 요청을 잠그고 현재 빌링키를 후보 빌링키로 교체한다.
6. 현재 안전한 표시 정보를 새 결제수단 정보로 갱신한다.
7. 기존 빌링키와 기존 `displayId`를 변경 요청의 삭제 대기 정보로 이동한다.
8. 변경 요청을 `swapped`로 확정한다.

5~8은 같은 DB 트랜잭션에서 처리한다.

이 트랜잭션은 구독 advisory lock뿐 아니라 변경 요청 row도 `FOR UPDATE`로 잠근다. 따라서 사용자 취소나 30분 만료가 먼저 확정되면 교체하지 않고, 활성화·`swapped` 상태 전이가 실제로 기록된 경우에만 현재 빌링키를 변경한다.

### 6.4 교체 후 결제

- 정상 구독은 추가 승인 요청 없이 종료한다.
- `past_due` 구독은 동의 스냅샷과 현재 미결제 주문이 여전히 일치할 때 기존 직접 재결제 경로를 새 빌링키로 호출한다.
- 결제 성공 시 기존 fulfillment가 구독과 이용권을 복구하고 크레딧을 한 번만 지급한다.
- 결제 실패 시 새 결제수단은 유지하고 구독은 `past_due`로 남긴다.
- 이 직접 재결제 실패는 `D+1`, `D+2` 자동 재시도 순번을 소모하지 않는다.
- 등록 중 상품·주문·금액 또는 구독 상태가 달라졌다면 자동 승인하지 않고 최신 상태를 사용자에게 보여준다.

### 6.5 기존 빌링키 삭제

교체 트랜잭션이 커밋된 뒤 기존 빌링키 삭제 API를 호출한다.

- 삭제 성공은 변경 요청에 기록한다.
- 일시 실패는 새 결제수단 교체를 되돌리지 않고 삭제 상태만 `failed`로 남긴다.
- 복구 스케줄러가 삭제를 재시도한다.
- 과거 `displayId`의 늦은 `REMOVED` 콜백은 변경 요청의 이전 빌링키 삭제 완료로 처리하고 현재 구독을 취소하지 않는다.

## 7. 변경 진행 제한시간과 청구 보류

변경 요청은 생성 시각부터 30분 동안 유효하다. 이 시간은 구독이나 정상 빌링키의 유효기간이 아니라, 사용자가 중간에 닫은 변경 작업을 정리하기 위한 내부 작업 제한시간이다.

변경 요청이 진행 중이면 같은 구독에 새 자동·수동 승인 요청을 시작하지 않는다. 이미 공급자 호출이 시작된 갱신 주문이 있으면 변경 요청 자체를 시작하지 않는다.

30분 만료는 사용자별 지속 polling으로 확인하지 않는다.

- 변경 요청에 `expiresAt`을 저장한다.
- 콜백, 결과 조회, 변경 재시작 시 현재 DB 시각과 비교한다.
- 서버 스케줄러가 만료된 진행 요청을 1분 단위 배치로 조회한다.

만료 처리:

1. 조건부 전이로 한 worker만 진행 요청을 `expired`로 만든다.
2. 후보 빌링키 삭제를 시도한다.
3. 현재 빌링키는 유지한다.
4. 기존 자동 재시도 일정을 다시 허용한다.
5. 보류 중 지나간 재시도 시각이 있고 아직 유예기간 안이면 기존 갱신 scheduler가 현재 정책에 따라 다음 실행을 결정한다.

만료 뒤 도착한 `ACTIVATED` 콜백은 현재 구독에 연결하지 않는다. 후보 빌링키 삭제만 수행한다.

## 8. 결과 화면 상태 확인

토스 인증 화면에서 돌아온 결과 페이지는 로그인 세션으로 자신의 변경 요청 상태만 조회한다.

- 콜백 도착 순서 차이를 흡수하기 위해 2초 간격으로 최대 30초만 polling한다.
- 30분 동안 polling하지 않는다.
- 짧은 polling 안에 확정되지 않으면 `등록 결과를 확인 중입니다`와 다시 확인 동작을 제공한다.
- 로컬 상태가 계속 `checkout_ready`이면 결과 조회 API가 토스 상태 조회를 한 번 실행하여 콜백 유실을 복구한다.
- 다른 사용자의 변경 요청 ID는 조회할 수 없다.

## 9. 동시성·멱등성

- 구독별 진행 중 변경 요청은 하나다.
- 변경 시작, 후보 활성화, 현재 키 교체, 만료는 조건부 상태 전이와 구독 잠금을 사용한다.
- 후보 활성화 콜백과 결과 조회가 동시에 와도 한 worker만 `swapped` 전이에 성공한다.
- 자동 갱신 승인 선점은 진행 중 변경 요청이 있으면 실패한다.
- `past_due` 즉시 재결제는 기존 갱신 주문번호와 조건부 claim을 사용한다.
- 결제 성공과 fulfillment는 기존 멱등 규칙을 유지한다.
- 이전 빌링키 삭제 성공·실패·콜백은 현재 빌링키 교체를 되돌리지 않는다.

## 10. 오류 처리

- 토스 상태 조회 장애: 마지막 표시 스냅샷을 반환하고 최신 확인 실패를 표시한다.
- 변경 시작 중 토스 빌링키 생성 실패: 변경 요청을 `failed`로 만들고 현재 빌링키를 유지한다.
- 사용자 인증 취소·실패: 후보 요청만 종료하고 현재 빌링키를 유지한다.
- 콜백 사용자·`displayId`·빌링키 불일치: 상태를 변경하지 않고 거부한다.
- 후보 상태가 `ACTIVE`가 아님: 현재 빌링키를 유지하고 확정 상태에 따라 대기 또는 실패 처리한다.
- 후보 교체 후 즉시 갱신 실패: 새 결제수단을 유지하고 `past_due` 복구 정책을 계속 적용한다.
- 이전 빌링키 삭제 실패: 삭제만 복구 대상으로 남긴다.
- 현재 빌링키의 실제 `REMOVED` 확인: 기존 구독 중지·재등록 정책을 적용한다.

## 11. 보안과 개인정보

- Toss API Key와 평문 빌링키는 서버 내부에서만 사용한다.
- 빌링키는 기존 `SecretCipher`로 암호화한다.
- 전체 카드번호, 카드 BIN, 계좌번호를 저장하지 않는다.
- 사용자 응답은 카드사명, 끝 4자리, 카드 종류, 토스머니 은행명만 포함한다.
- callback 본문 전체를 로그나 이벤트 payload에 저장하지 않는다.
- `displayId`는 callback correlation에만 사용하고 사용자 화면에 노출하지 않는다.
- 변경 요청·결과 조회는 로그인 사용자와 구독 소유권을 검증한다.
- 결제금액은 서버 주문 스냅샷을 기준으로 한다.

## 12. 검증 기준

자동 테스트:

- 안전한 표시 필드만 반환하고 빌링키·전체 카드번호를 노출하지 않는다.
- 최신 토스 상태 조회 성공 시 표시 스냅샷을 갱신한다.
- 표시 스냅샷 갱신은 조회를 시작한 `providerDisplayId`가 아직 현재 값일 때만 반영하여, 동시 교체된 새 결제수단 정보를 이전 조회 결과로 덮어쓰지 않는다.
- 조회 실패 시 마지막 스냅샷을 반환한다.
- 정상 구독의 결제수단 변경은 즉시 결제하지 않는다.
- `past_due` 변경은 동의한 같은 주문·금액만 즉시 재결제한다.
- 등록 실패·취소·30분 만료 시 현재 빌링키를 유지한다.
- 만료 뒤 늦은 활성화 콜백은 후보를 현재 구독에 연결하지 않는다.
- 자동 재시도와 변경 요청이 동시에 새 승인을 시작하지 않는다.
- 콜백 중복·불일치·순서 역전에도 한 번만 교체한다.
- 이전 빌링키의 늦은 `REMOVED` 콜백이 현재 구독을 취소하지 않는다.
- 새 결제수단 갱신 성공 시 구독 복구와 크레딧 지급이 한 번만 수행된다.
- 새 결제수단 갱신 실패가 자동 재시도 순번을 소모하지 않는다.
- 웹 화면이 정상·실패·조회 불가·변경 진행·변경 완료 상태를 구분한다.

개발서버 수동 검증:

1. 정상 구독에서 현재 카드사와 끝 4자리를 확인한다.
2. 정상 구독의 카드를 변경하고 즉시 승인 요청이 없는지 확인한다.
3. 갱신 실패 상태에서 상품명·미결제 금액·즉시 결제 고지를 확인한다.
4. 새 카드 등록 후 해당 금액이 한 번만 승인되고 구독이 복구되는지 확인한다.
5. 토스 등록 화면을 닫고 30분 만료 뒤 기존 카드와 자동 재시도가 복구되는지 확인한다.
6. 기존 빌링키 삭제 실패를 모의하고 새 카드 교체가 유지되는지 확인한다.

## 13. 완료 조건

- 사용자는 토스 앱을 별도로 탐색하지 않고 Clipper 마이페이지에서 현재 자동결제 수단을 확인할 수 있다.
- 사용자는 Clipper에서 시작한 토스 인증 흐름으로 결제수단을 안전하게 변경할 수 있다.
- 기존 빌링키는 후보 활성화 전까지 유지된다.
- `past_due` 사용자는 금액과 즉시 재결제를 확인한 뒤에만 새 결제수단으로 청구된다.
- 변경·자동 재시도·콜백의 경쟁에도 중복 청구나 현재 키 유실이 발생하지 않는다.
- 평문 빌링키와 불필요한 카드·계좌 정보가 저장·노출되지 않는다.
