# Clipper 결제·구독·요금제·크레딧 정책 설계

작성일: 2026-08-12

상태: 사용자 승인 완료

대상 저장소:

- `.codex`
- `web/clipper_web_api`
- `web/clipper_web_client`
- `web/clipper_web_admin`
- `desktop/clipper_angular`
- `desktop/clipper_nestjs`
- 필요 시 `web/clipper_infra`

## 1. 목적

Clipper의 출시 전 무통장 입금·수동 이용권 구조를 Toss Pay 기반의 유료 구독 구조로 교체한다.

새 구조는 다음을 서로 분리한다.

- 어떤 기능과 플러그인을 쓸 수 있는가: 요금제 등급과 권한
- 얼마마다 얼마를 결제하는가: 결제 상품과 결제 주기
- 사용자가 현재 어떤 계약 상태인가: 구독
- 얼마만큼 기능을 실행할 수 있는가: 크레딧 지급 묶음과 원장
- 돈이 실제로 결제됐는가: 주문·거래·공급자 이벤트

요금제 이름, 개수, 가격, 플러그인 구성, 크레딧 수량 같은 상품 데이터가 바뀌더라도 결제와 크레딧 시스템을 다시 설계하지 않는 것이 목표다.

## 2. 현재 구현과 전환 전제

### 2.1 현재 구현

`clipper_web_api`의 현재 결제 관련 구조는 다음과 같다.

- `plans`: 이름, 이용 개월 수, 가격, 전체 크레딧 수량을 한 행에 보관한다.
- `purchase_requests`: 사용자가 무통장 입금자명을 입력해 구매 요청을 만든다.
- `licenses`: 운영자가 구매 요청을 승인하면 이용기간과 크레딧 묶음을 함께 발급한다.
- `queued` license: 활성 이용권이 있으면 새 이용권을 대기시켰다가 나중에 시작한다.
- `token_usage`: 과거 크레딧 차감 기록이다.
- `operation_policies`: 사용자 작업별 크레딧 가격을 관리한다.
- `operation_runs`: 작업 실행, 성공, 실패를 기록한다.
- `credit_ledger`: 작업 시작 차감과 작업 실패 환불을 기록한다.
- `payment_orders`, `payment_events`: Toss Pay 심사용 주문과 공급자 이벤트를 기록한다.

현재 `payment_orders`의 Toss 흐름은 심사 목적이다. 비로그인 테스트 결제 결과만 안전하게 저장하며, 실제 사용자 구독이나 이용권·크레딧을 지급하지 않는다.

### 2.2 데이터 전제

서비스 출시 전이며 기존 무통장 구매 요청, 이용권, 크레딧 및 사용 기록은 모두 테스트 데이터다. 다음 데이터는 이관하거나 보존할 필요가 없다.

- 무통장 구매 요청과 승인·반려 기록
- 기존 license와 queued license
- 기존 크레딧 잔액 및 차감 기록
- 기존 요금제 행

따라서 legacy 데이터 변환, 호환 계층, 과거 이용권 만료 대기는 만들지 않는다.

단, 이미 적용된 TypeORM 마이그레이션 파일은 수정하지 않는다. 새 전환 마이그레이션으로 테스트 데이터를 초기화하고 목표 스키마를 만든다.

## 3. 확정된 제품 원칙

### 3.1 상품과 계정

- 무료 요금제는 없다.
- 무료 체험도 우선 제공하지 않는 것으로 설계한다.
- 실제 서비스 결제는 로그인 사용자만 할 수 있다.
- 한 사용자 계정은 동시에 하나의 유료 기본 구독만 가질 수 있다.
- 요금제 등급이 높아질수록 사용할 수 있는 플러그인이 늘어난다.
- 요금제 등급과 결제 주기는 독립된 개념이다.
- 요금제 개수, 이름, 가격, 플러그인 구성, 크레딧 수량은 변경 가능한 상품 데이터로 관리한다.

예:

```text
요금제 등급: Basic / Pro / Business
결제 상품: Pro 월간 / Pro 3개월 / Pro 연간
```

실제 등급명과 제공 결제 주기는 아직 확정하지 않는다.

### 3.2 Toss Pay 심사 흐름

- 현재 비로그인 결제는 Toss Pay 심사를 위한 dev 환경 예외다.
- 심사용 주문은 사용자 구독, 플러그인 권한, 크레딧을 지급하지 않는다.
- 1개월·3개월 정기결제와 1개월·3개월·1년 단건결제 버튼은 심사 요구를 충족하기 위한 현재 capability다.
- 1년 상품을 단건으로 연결한 것은 심사 제약이며 출시 후 상품 정책을 확정한 것이 아니다.
- 실제 서비스 checkout이 완성되면 비로그인 심사 API를 끄고 로그인 사용자 checkout으로 교체한다.

## 4. 목표 도메인 구조

```text
Plan tier
  ├─ plugin entitlements
  └─ sellable products
       ├─ billing interval
       ├─ price
       └─ renewal policy

User
  ├─ one base access source
  │    ├─ paid subscription
  │    └─ admin plan grant
  ├─ effective plugin entitlements
  └─ credit grants

Payment order
  ├─ provider transaction/events
  └─ idempotent fulfillment

Credit grant
  ├─ source and expiry
  ├─ remaining balance
  └─ charge/refund/adjustment ledger
```

### 4.1 요금제 등급

요금제 등급은 기능 권한을 소유한다.

필수 개념:

- 안정적인 등급 식별자
- 표시 이름과 설명
- 등급 순서 또는 비교 가능한 수준
- 활성·판매 가능 여부
- 월별 기본 크레딧 수량
- 등급에서 사용할 수 있는 플러그인 목록

플러그인은 표시 이름이 아니라 안정적인 `pluginKey`로 연결한다. 정확한 플러그인 목록과 등급별 매핑은 나중에 상품 데이터로 입력한다.

### 4.2 결제 상품

결제 상품은 특정 요금제 등급을 어떤 조건으로 판매하는지 나타낸다.

필수 개념:

- 연결된 요금제 등급
- 결제 주기
- 결제 금액과 통화
- 자동 갱신 여부
- 판매 활성 여부
- 결제창 표시 이름

같은 요금제 등급은 여러 결제 상품을 가질 수 있다. 기간별로 기능 권한을 복제하지 않는다.

### 4.3 구독

구독은 로그인 사용자와 유료 결제 상품을 연결한다.

필수 상태:

- `active`: 정상 이용 중
- `cancel_at_period_end`: 다음 갱신 취소, 현재 기간은 이용 가능
- `past_due`: 갱신 결제 실패 후 유예 중
- `stopped`: 유예 종료 후 구독 중지
- `ended`: 정상 기간 종료 또는 즉시 종료 처리 완료

구독은 다음 날짜를 분리해 관리한다.

- 결제 기준일
- 현재 유료 이용기간 시작·종료
- 다음 결제 예정일
- 다음 월별 크레딧 지급 예정일
- 취소 예약 시각과 실제 종료 시각

결제 주기가 3개월 또는 1년이어도 크레딧 지급은 월별로 진행되므로 결제 스케줄과 혜택 지급 스케줄을 하나의 날짜로 합치지 않는다.

### 4.4 관리자 요금제 부여

내부 직원·테스트 계정에 별도 프리패스나 권한 우회 플래그를 만들지 않는다. 관리자는 실제로 존재하는 표준 요금제 등급을 사용자에게 부여한다.

관리자 요금제 부여는 결제가 없는 기본 이용 자격이며 다음을 가진다.

- 사용자
- 표준 요금제 등급
- 시작일
- 임의의 만료일 또는 만료 없음
- 지급 사유
- 처리 운영자
- 지급·회수 시각

동작:

- 시작일이 되면 해당 요금제의 플러그인 권한이 활성화된다.
- 시작 시점에 해당 요금제의 한 달분 크레딧을 전액 지급한다.
- 이후 매월 같은 기준일에 여전히 유효하면 한 달분을 전액 지급한다.
- 마지막 이용기간이 한 달보다 짧아도 크레딧을 일할 계산하거나 일부 회수하지 않는다.
- 만료 없음이면 관리자가 회수할 때까지 매월 지급한다.
- 회수하면 플러그인 권한과 미래 크레딧 지급을 중지한다.
- 이미 지급된 크레딧은 자동 삭제하지 않고 그 지급 묶음의 유효기간 정책을 따른다. 필요한 회수는 별도 관리자 조정으로 기록한다.

예:

```text
부여 기간: 2026-08-12 ~ 2026-10-20
월별 요금제 크레딧: 100,000

2026-08-12  100,000 지급
2026-09-12  100,000 지급
2026-10-12  100,000 지급
2026-10-20  요금제 권한 종료
```

유료 구독과 관리자 요금제 부여를 동시에 사용해 기본 요금제를 중첩시키는 동작은 1차 범위에 넣지 않는다. 내부·QA 계정은 유료 구독이 없는 상태에서 관리자 요금제를 사용한다. 활성 유료 고객 보상은 관리자 추가 크레딧을 기본으로 한다.

### 4.5 하나의 기본 이용 자격

사용자에게 실제 적용되는 기본 요금제 출처는 한 번에 하나다.

```text
paid subscription
or
admin plan grant
```

- 더 높은 요금제를 구매하면 두 번째 구독을 만들지 않고 업그레이드 흐름으로 보낸다.
- 더 낮은 요금제를 선택하면 다운그레이드 예약으로 보낸다.
- 관리자 요금제와 유료 구독의 동시 활성화는 서버에서 막는다.
- 추가 크레딧 구매와 관리자 추가 크레딧은 기본 이용 자격과 별도로 공존할 수 있다.

## 5. 크레딧 모델

### 5.1 지급 묶음과 출처

크레딧은 사용자별 숫자 하나가 아니라 지급 묶음 단위로 관리한다.

출처:

- `subscription`: 유료 구독 월별 지급
- `admin_plan`: 관리자 요금제 월별 지급
- `topup`: 일회성 추가 구매
- `admin_adjustment`: 관리자 추가 지급 또는 보상
- `promotion`: 향후 이벤트 지급

각 지급 묶음은 다음을 기록한다.

- 사용자
- 출처
- 최초 지급량
- 남은 수량
- 지급 시각
- 유효기간 또는 만료 없음
- 관련 구독, 관리자 부여, 결제 주문 등의 참조
- 지급 사유
- 생성 주체와 처리 운영자
- 멱등 지급 키

### 5.2 관리자 추가 크레딧

관리자는 요금제 부여와 별개로 크레딧만 지급할 수 있다.

입력:

- 사용자
- 지급 수량
- 유효기간 또는 만료 없음
- 지급 사유

관리자가 임의 수량과 유효기간을 지정하는 것은 허용한다. 이 크레딧도 별도의 우회 잔액이 아니라 일반 크레딧 지급 묶음으로 저장하고 동일한 차감·환불 원장을 사용한다.

지급·회수에는 대상 사용자, 처리 운영자, 사유, 수량, 처리 시각을 남긴다.

### 5.3 차감 순서

크레딧은 유효기간이 가장 가까운 지급 묶음부터 차감한다.

- 동일한 유효기간이면 먼저 지급된 묶음을 먼저 사용한다.
- 만료 없음은 만료일이 있는 모든 묶음 뒤에 사용한다.
- 한 작업이 여러 지급 묶음을 사용할 수 있으며, 어떤 묶음에서 얼마가 차감됐는지 기록한다.
- 작업 실패 환불은 원래 차감한 지급 묶음으로 되돌린다.
- 만료됐거나 회수된 묶음으로 환불해야 하는 특수 상황은 별도 조정 이벤트로 남기며 잔액을 조용히 변경하지 않는다.

### 5.4 사용자 표시

사용자는 총 크레딧뿐 아니라 출처별 잔액을 확인할 수 있어야 한다.

최소 표시 항목:

- 전체 사용 가능 크레딧
- 구독 또는 관리자 요금제 크레딧
- 추가 구매 크레딧
- 관리자·이벤트 지급 크레딧
- 각 지급 묶음의 만료일
- 지급·사용·환불·만료·조정 내역
- 한 작업에서 실제로 사용한 크레딧 출처

정확한 이월·소멸 정책과 추가 구매 크레딧의 기본 유효기간은 아직 확정하지 않는다. 스키마는 지급 묶음마다 유효기간 또는 만료 없음을 표현할 수 있어야 한다.

## 6. 결제와 fulfillment

### 6.1 서버 확정 원칙

브라우저 리다이렉트나 클라이언트 성공 화면만으로 구독이나 크레딧을 지급하지 않는다.

```text
Toss 결제 결과 수신
  -> Toss 상태 재검증
  -> 주문을 결제 완료로 저장
  -> 멱등 fulfillment 실행
       -> 구독 생성·갱신·업그레이드
       -> 플러그인 권한 반영
       -> 필요한 크레딧 지급
```

같은 결제 이벤트, 콜백, 재시도가 여러 번 와도 다음이 중복되면 안 된다.

- 결제 완료 처리
- 구독 기간 연장
- 월별 크레딧 지급
- 업그레이드 차액 반영
- 추가 구매 크레딧 지급

결제 성공과 혜택 지급 성공은 분리해 기록한다. 결제는 성공했지만 fulfillment가 실패한 경우 결제를 다시 시도하지 않고 혜택 지급만 재시도한다.

### 6.2 주문 목적

실서비스 주문은 최소한 다음 목적을 구분한다.

- 최초 구독 결제
- 구독 갱신 결제
- 즉시 업그레이드 차액 결제
- 향후 추가 크레딧 구매
- 환불 또는 취소와 연결되는 원거래
- Toss 심사용 익명 테스트 주문

주문에는 로그인 `userId`, 결제 상품, 당시 상품명·가격·등급·주기 스냅샷, 관련 구독, 공급자 거래 식별자를 연결한다. 심사용 주문은 별도 목적과 test 표시를 가지며 fulfillment 대상에서 제외한다.

### 6.3 결제수단과 빌링키

- 빌링키는 평문으로 저장하지 않는다.
- 실제 사용자 구독과 암호화된 빌링키를 연결한다.
- 다음 갱신 결제는 서버 스케줄러가 수행한다.
- 중복 실행을 막기 위해 같은 구독·결제회차에는 하나의 고유 주문만 허용한다.
- 네트워크 타임아웃처럼 성공 여부가 불명확하면 Toss 상태를 조회한 뒤에만 재결제한다.

## 7. 구독 생명주기

### 7.1 최초 가입

1. 로그인 사용자가 요금제 등급과 결제 상품을 선택한다.
2. 서버가 판매 가능한 상품인지 확인한다.
3. 이미 활성 기본 이용 자격이 있으면 새 구독 생성 대신 업그레이드·다운그레이드 흐름으로 보낸다.
4. Toss 결제 결과를 서버가 검증한다.
5. 구독과 최초 이용기간을 생성한다.
6. 최초 월별 요금제 크레딧을 한 번 지급한다.
7. 사용자에게 결제, 구독, 다음 결제일, 크레딧 지급 결과를 표시한다.

### 7.2 월별 크레딧 지급

- 결제 주기와 관계없이 월별 기준일에 지급한다.
- 유료 이용기간 안에 있는 지급회차만 처리한다.
- `subscriptionId + benefit period` 또는 동등한 멱등 키로 한 회차 한 번만 지급한다.
- 다음 갱신 취소 상태여도 이미 결제한 기간이 남아 있으면 지급을 계속한다.
- 즉시 종료·환불이 승인되면 미래 지급을 중단한다.

### 7.3 즉시 업그레이드

상위 요금제 플러그인을 즉시 사용하려는 경우 업그레이드는 바로 적용한다.

- 기존 결제 기준일을 유지한다.
- 남은 기간의 요금제 가격 차액을 계산한다.
- 차액 결제 성공 후 상위 요금제 권한을 즉시 활성화한다.
- 기존 크레딧은 유지한다.
- 필요하면 남은 기간에 해당하는 요금제별 크레딧 차이를 추가 지급한다.
- 다음 갱신부터 상위 요금제의 정상 가격을 청구한다.
- 차액 결제나 추가 크레딧 지급은 멱등하게 처리한다.

정확한 원 단위 반올림 규칙은 가격 정책 확정 시 정한다.

### 7.4 다운그레이드와 결제 주기 변경

- 하위 요금제 변경은 다음 갱신일부터 적용한다.
- 현재 결제기간 동안은 기존 요금제 권한과 크레딧 정책을 유지한다.
- 결제 주기 변경도 다음 갱신일부터 적용하는 것을 기본으로 한다.
- 다음 갱신 전에 예약을 취소하거나 다시 변경할 수 있는지는 후속 UX 정책으로 정한다.

### 7.5 다음 갱신 취소

- 사용자는 언제든지 다음 자동 결제를 취소할 수 있다.
- 현재 결제기간 종료일까지 권한과 예정된 월별 크레딧 지급을 유지한다.
- 기간 종료 시 구독을 끝내며 다음 결제를 만들지 않는다.
- 다음 갱신 취소는 즉시 환불을 의미하지 않는다.

### 7.6 갱신 결제 실패

갱신 결제가 실패해도 즉시 구독을 종료하지 않는다.

```text
active
  -> renewal payment failed
  -> past_due / grace period
       -> retry succeeds -> active
       -> grace expires   -> stopped
```

유예 중:

- 결제 실패와 결제수단 변경 방법을 사용자에게 알린다.
- 자동 재시도와 사용자의 직접 재결제를 지원한다.
- 실패한 새 회차의 월별 크레딧은 지급하지 않는다.
- 원래 결제 기준일은 유지한다.

복구:

- 결제가 성공하면 해당 회차 크레딧을 한 번만 지급하고 `active`로 복구한다.
- 결제 성공 후 혜택 지급만 실패하면 결제가 아니라 fulfillment만 재시도한다.

최종 실패:

- 구독을 `stopped`로 전환한다.
- 하위 요금제로 자동 변경하지 않는다.
- 현재 구독으로 얻었던 유료 플러그인 실행 권한을 종료한다.
- 계정, 프로젝트, 사용 이력, 사용자가 만든 결과물은 삭제하지 않는다.

유예기간과 재시도 횟수는 운영 설정으로 나중에 확정한다.

## 8. 해지와 환불

다음 두 기능을 사용자와 시스템에서 명확히 분리한다.

### 8.1 다음 결제 취소

- 다음 갱신만 중단한다.
- 현재 결제기간 종료일까지 이용한다.
- 자동 환불을 만들지 않는다.

### 8.2 즉시 이용 종료 및 환불 신청

- 별도의 환불 신청과 운영 처리 흐름이다.
- 환불 승인 시 유료 권한과 미래 크레딧 지급을 종료한다.
- 이미 지급·사용·만료된 크레딧과 결제기간을 반영한 환불 계산이 필요하다.
- 환불 완료와 Toss 원거래 취소 결과를 모두 기록한다.
- 환불 처리도 같은 요청을 반복해 중복 환불하지 않게 한다.

최종 환불 산식, 청약철회, 계속거래 중도해지, 위약금, 디지털콘텐츠 사용 개시 판단은 코드 설계로 임의 확정하지 않는다. 국내 전자상거래·소비자보호 관련 법령과 서비스 약관에 대한 출시 전 법률 검토 후 확정한다.

법률 검토 전에는 다음 원칙만 유지한다.

- 결제 전 총 결제금액, 결제 주기, 자동 갱신 여부를 명확히 표시한다.
- 다음 결제 취소와 즉시 종료·환불을 같은 동작으로 표현하지 않는다.
- 환불 산식과 예외를 결제 전에 고지할 수 있는 구조를 준비한다.
- 결제, 공급, 해지, 환불, 동의 이력을 감사 가능하게 보관한다.

## 9. 플러그인 권한

- 요금제 등급과 플러그인 목록을 매핑한다.
- 웹 가격 화면은 등급별 제공 플러그인을 상품 데이터에서 표시한다.
- 데스크톱은 현재 유효한 요금제 권한을 받아 플러그인 잠금·사용 가능 상태를 표시한다.
- 실제 작업 시작 시 서버가 다시 권한을 확인한다.
- 단순히 UI에서 버튼을 숨기는 것만으로 권한을 보호하지 않는다.
- 요금제 종료 후에도 사용자가 만든 프로젝트와 결과물은 보존한다.
- 종료되는 것은 해당 요금제로 부여된 플러그인 실행 권한이다.

정확한 plugin catalog, 오프라인 유예, 로컬 전용 플러그인의 권한 검증 방식은 별도 설계 대상으로 남긴다.

## 10. 기존 기능 처리

### 10.1 완전히 제거

- 무통장 구매 요청 UI와 `/app/purchase`
- 입금자명과 계좌 안내
- `purchase_requests` API와 관리자 승인·반려·재요청 기능
- 구매 요청 승인으로 license를 발급하는 흐름
- queued license와 수동 다음 이용권 시작 기능
- 기존 `plans`의 기간·가격·전체 크레딧 결합 모델
- 기존 `token_usage` 경로
- 무통장 구매 요청을 전제로 한 OpenAPI, mock, 테스트, 관리자 통계

이 제거는 실제 로그인 사용자용 Toss checkout과 관리자 지급 기능이 준비된 전환 시점에 수행한다. 심사 중인 dev 흐름이 끊기지 않도록 중간 커밋마다 실행 가능한 상태를 유지한다.

### 10.2 개념과 구현을 재사용

- Google 로그인과 사용자 식별
- `clipper_web_api`가 결제·권한·크레딧의 단일 출처라는 원칙
- Toss provider adapter와 서버 상태 재검증
- `payment_orders`, `payment_events`의 주문 스냅샷, 공급자 이벤트, 멱등 기록 개념
- `operation_policies`의 작업별 크레딧 가격
- `operation_runs`의 작업 실행 생명주기
- 작업 시작 차감과 실패 환불 방식
- 크레딧 원장 조회의 페이징·필터·세션 표시 기반
- 현재 크레딧 화면과 데스크톱 설정 화면의 기본 표시 구조

### 10.3 재설계

- `plans` -> 요금제 등급 + 결제 상품
- `licenses` -> 유료 구독 또는 관리자 요금제 부여
- license 내부 크레딧 -> 출처별 credit grant
- 작업 전용 `credit_ledger` -> 지급·차감·환불·만료·관리자 조정을 포괄하는 원장
- 심사용 익명 payment order -> 로그인 사용자와 구독 목적을 지원하는 결제 주문

## 11. 데이터와 감사 기록

각 상태 변화는 현재 값만 덮어쓰지 않고 원인을 추적할 수 있어야 한다.

반드시 추적할 항목:

- 상품의 당시 이름, 가격, 주기, 요금제 등급 스냅샷
- Toss 주문번호, 거래 식별자, 결제수단, 공급자 상태
- 구독 생성, 갱신, 취소 예약, 실패, 복구, 종료
- 업그레이드·다운그레이드 신청과 적용
- 크레딧 지급, 차감, 환불, 만료, 관리자 조정
- 관리자 요금제·크레딧 지급과 회수
- 처리 운영자와 사유
- fulfillment 재시도 및 최종 결과

API Key, 평문 빌링키, 불필요한 개인정보는 감사 payload에 저장하지 않는다.

## 12. 오류 처리와 복구

- Toss callback은 중복 전달을 정상 상황으로 간주한다.
- 주문과 결제회차에는 고유 키를 두어 중복 청구와 중복 지급을 막는다.
- 결제 결과가 불명확하면 실패로 추측하거나 즉시 재결제하지 않는다.
- 결제 완료 후 fulfillment 실패는 운영 재처리 목록에 남긴다.
- 월별 크레딧 스케줄러는 누락 회차를 다시 실행해도 한 번만 지급한다.
- 관리자 지급 요청도 중복 제출 방지를 위한 요청 식별자나 확인 절차를 둔다.
- 크레딧 차감과 원장 기록은 하나의 DB 트랜잭션으로 처리한다.
- 작업 실패 환불도 원 차감과 연결하고 반복 호출에 멱등하게 처리한다.

## 13. 전환 전략

출시 전 데이터이므로 dual-write나 legacy 데이터 이관은 사용하지 않는다.

권장 순서:

1. 목표 상품·구독·관리자 지급·크레딧 스키마를 추가한다.
2. 기존 operation 차감·환불을 새 credit grant와 ledger에 연결한다.
3. 관리자 요금제와 관리자 추가 크레딧 지급을 구현해 결제 없이 권한·크레딧 경로를 검증한다.
4. 로그인 사용자 Toss 최초 결제와 fulfillment를 연결한다.
5. 월별 크레딧 지급, 갱신 결제, 결제 실패 복구를 연결한다.
6. 업그레이드, 다운그레이드, 다음 결제 취소를 연결한다.
7. 웹·데스크톱·관리자 UI를 새 계약으로 전환한다.
8. 기존 테스트 데이터를 초기화하고 무통장·license API 및 화면을 제거한다.
9. Toss 심사가 끝나고 실제 계약 키가 준비되면 비로그인 review checkout을 비활성화한다.
10. 최종 약관·환불정책 법률 검토 후 운영 결제를 연다.

각 단계는 기존 dev 배포가 부팅 가능한 작은 변경으로 나누고, 코드 작업은 저장소별 동일한 기능 브랜치에서 진행한다.

## 14. 검증 기준

### 14.1 상품과 권한

- 같은 요금제의 월간·장기 상품이 동일한 플러그인 권한을 제공한다.
- 상위 요금제만 허용된 플러그인은 하위 요금제에서 서버가 거부한다.
- 한 사용자에게 두 개의 활성 기본 구독 또는 관리자 기본 이용 자격이 생기지 않는다.

### 14.2 결제와 구독

- 검증된 Toss 결제만 구독을 만든다.
- 같은 callback을 반복해도 구독과 크레딧이 한 번만 생성된다.
- 장기 결제 사용자도 크레딧은 월별로 한 번씩만 받는다.
- 결제 성공 후 fulfillment 실패를 재처리해도 다시 청구되지 않는다.
- 비로그인 심사 결제는 어떤 권한이나 크레딧도 지급하지 않는다.

### 14.3 관리자 지급

- 관리자가 표준 요금제를 부여한 계정은 일반 사용자와 같은 플러그인 권한 검사를 거친다.
- 임의 만료일이 월 기준일 사이에 있어도 마지막 지급회차는 전액 지급되고 일할 계산되지 않는다.
- 만료 또는 회수 후에는 미래 크레딧이 지급되지 않는다.
- 관리자 추가 크레딧은 지정한 수량과 유효기간으로 별도 지급 묶음에 기록된다.

### 14.4 크레딧

- 가장 가까운 만료 크레딧부터 차감한다.
- 한 작업이 여러 지급 묶음에서 차감될 수 있다.
- 실패 환불은 원래 차감한 지급 묶음으로 돌아간다.
- 사용자는 총잔액과 출처별 잔액·만료일·사용 내역을 확인할 수 있다.

### 14.5 갱신 실패와 해지

- 갱신 실패 즉시 하위 요금제로 내려가거나 계정을 삭제하지 않는다.
- 유예 중 새 회차 크레딧을 중복 지급하지 않는다.
- 결제 복구 후 해당 회차 크레딧을 한 번만 지급한다.
- 다음 결제 취소 후에도 이미 결제한 기간의 권한과 예정 크레딧을 유지한다.

## 15. 의도적으로 나중에 확정할 정책

다음 값은 목표 구조를 막지 않으므로 이번 설계에서 고정하지 않는다.

- 요금제 개수·이름·가격
- 등급별 플러그인 목록
- 등급별 월간 크레딧 수량
- 월간·3개월·연간 중 실제 판매할 결제 주기
- 고정 기간 단건 이용권 판매 여부
- 추가 크레딧 판매 출시 여부와 가격
- 구독 크레딧의 이월·소멸 정책
- 추가 구매 크레딧의 기본 유효기간
- 활성 기본 이용 자격이 없을 때 남은 추가 구매 크레딧의 사용 가능 범위
- 갱신 실패 유예기간과 재시도 횟수
- 업그레이드 차액과 크레딧 차이의 반올림 규칙
- 환불 산식과 최종 약관 문구
- 플러그인 오프라인 사용 유예와 로컬 권한 검증 방식

이 값들은 코드 상수에 분산하지 않고 상품·운영 설정 또는 별도 정책 모듈에서 관리한다.

## 16. 비범위

이 문서는 다음을 구현하지 않는다.

- 실제 요금제 상품값 확정
- 환불·이용약관 법률 자문 대체
- 팀·워크스페이스 단위 구독
- 여러 기본 구독의 동시 보유
- 사용량 기반 후불 청구
- 세금계산서·법인 계약·해외 통화
- 영구 소유형 플러그인 판매
- 별도의 내부 계정 프리패스

## 17. 최종 결정 요약

Clipper는 `요금제 등급 + 결제 상품 + 하나의 기본 이용 자격 + 출처별 크레딧 지급 묶음` 구조를 사용한다.

일반 사용자는 Toss 결제 성공으로 구독을 얻고, 내부·테스트 사용자는 관리자가 동일한 표준 요금제를 부여받는다. 두 경로는 결제 유무만 다르고 플러그인 권한과 크레딧 차감·환불 처리는 동일하다.

무통장 구매 요청과 기존 license 모델은 출시 전 테스트 데이터와 함께 제거한다. 기존 Toss 검증, operation pricing, 실행·실패 환불 개념은 새 구조에 재사용한다.
