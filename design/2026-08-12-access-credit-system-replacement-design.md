## 1. 목표

현재 `licenses` 한 행에 이용기간과 전체 크레딧이 함께 들어 있는 구조를 다음 구조로 완전히 교체한다.

```text
상품 등급과 플러그인 권한
+ 사용자의 유효한 기본 이용 자격
+ 출처별 크레딧 지급 묶음과 원장
+ 선불 추가 크레딧 상품
```

출시 전 테스트 데이터는 이관하지 않는다. 기존 무통장 구매 요청, `plans`, `licenses`, `token_usage`, 작업 전용 `credit_ledger`는 새 구조와 관련 클라이언트가 모두 완성된 기능 브랜치에서 제거한다. 완성 전 중간 상태는 dev에 병합하거나 배포하지 않는다.

현재 Toss 심사용 익명 결제는 유지하되 어떤 사용자 이용 자격이나 크레딧도 지급하지 않는다.

## 2. 확정 원칙

### 2.1 상품과 이용 자격

- 요금제 등급은 월별 기본 크레딧과 플러그인 권한을 가진다.
- 결제 상품은 등급, 결제 주기, 가격, 자동 갱신 여부를 연결한다.
- 한 사용자에게 유효한 기본 이용 자격은 한 번에 하나다.
- 기본 이용 자격의 출처는 유료 구독 또는 관리자 요금제 부여다.
- 여기서 `기본`은 가장 낮은 등급이라는 뜻이 아니라 플러그인 권한을 결정하는 대표 이용 자격이라는 뜻이다.
- 별도의 내부 직원 프리패스나 권한 우회 플래그를 만들지 않는다.

### 2.2 크레딧

- 크레딧은 사용자별 숫자 하나가 아니라 지급 묶음별로 관리한다.
- 출처는 `subscription`, `admin_plan`, `topup`, `admin_adjustment`, `promotion`을 지원한다.
- 유효기간이 가장 가까운 묶음부터 차감한다.
- 같은 만료일이면 먼저 지급된 묶음부터 차감한다.
- 만료 없음은 만료일이 있는 묶음 뒤에 사용한다.
- 실패 반환은 실제로 차감한 원래 지급 묶음으로 돌아간다.
- 출처와 관계없이 크레딧을 사용하려면 유효한 기본 이용 자격이 있어야 한다.

### 2.3 추가 크레딧

- 추가 크레딧 판매를 제공한다.
- 활성 기본 이용 자격이 있는 로그인 사용자만 구매를 시작할 수 있다.
- Toss 결제 성공을 서버가 확인한 후 지급하는 선불 단건결제다.
- 모든 요금제 등급이 같은 추가 크레딧 상품을 같은 수량과 가격으로 구매한다.
- 플러그인별 원가 차이는 작업별 크레딧 차감량으로 반영한다.
- 추가 크레딧은 이용기간이나 플러그인 권한을 부여하지 않는다.
- 기본 이용 자격이 끝나면 잔액은 보존하지만 사용할 수 없다.
- 기본 이용 자격이 다시 활성화되면 아직 만료되지 않은 잔액을 다시 사용할 수 있다.
- 결제 중 이용 자격이 끝났어도 결제가 성공했다면 크레딧은 지급하고 사용만 정지한다.

정확한 추가 크레딧 상품 수량·가격·유효기간은 아직 확정하지 않는다.

## 3. 목표 데이터 구조

### 3.1 상품 카탈로그

이미 구현한 상품 카탈로그 기반을 사용한다.

#### `plan_tiers`

- 안정적인 등급 코드와 표시 이름
- 월별 기본 크레딧
- 월별 크레딧 유효기간 정책
- 활성 여부와 정렬 순서

기존 카탈로그의 `monthly_credits`는 유지하고, 정책 확정 후 `monthly_credit_validity_days` 또는 동등한 설정을 추가할 수 있어야 한다. `null`은 만료 없음으로 표현할 수 있다.

#### `billing_products`

- 연결된 등급
- 결제 주기
- 가격
- 자동 갱신 여부
- 판매 활성 여부

#### `plan_plugin_entitlements`

- 등급과 안정적인 `plugin_key`의 매핑

같은 등급의 월간·3개월·연간 상품은 동일한 플러그인 목록을 사용한다.

### 3.2 추가 크레딧 상품

새 `credit_products`를 둔다.

필수 필드:

- `id`, `code`, `name`
- `credits`
- `price_krw`
- `validity_days` 또는 만료 없음
- `is_active`, `sort_order`
- 생성·수정 시각

`plan_tier_id`는 두지 않는다. 동일 상품을 모든 등급에 같은 조건으로 판매하기 때문이다.

### 3.3 사용자 기본 이용 자격

새 `user_access_grants`를 둔다.

필수 필드:

- 사용자와 요금제 등급
- 출처: `subscription` 또는 `admin_plan`
- 시작일과 종료일 또는 만료 없음
- 상태: 시작 예정, 활성, 종료, 회수, 교체
- 월별 크레딧 기준일과 다음 지급 예정일
- 관련 구독 또는 관리자 부여 식별자
- 관리자 지급 사유와 처리 운영자
- 종료·회수·교체 사유와 시각
- 생성·수정 시각

한 사용자에게 겹치는 유효 기본 이용 자격이 생기지 않도록 DB 제약과 트랜잭션 잠금을 함께 사용한다.

현재 값만 덮어써서 이력을 잃지 않도록 `access_grant_events` 또는 동등한 불변 감사 원장을 둔다. 지급, 기간 수정, 등급 변경, 종료, 회수를 기록한다.

유료 구독의 결제 상태·결제 기준일·다음 청구일·빌링키는 별도 `subscriptions`에 보관하고, 실제 플러그인 권한은 연결된 `user_access_grants`가 나타낸다.

### 3.4 크레딧 지급 묶음

새 `credit_grants`를 둔다.

필수 필드:

- 사용자
- 출처
- 최초 지급량과 현재 잔량
- 지급 시각과 만료 시각 또는 만료 없음
- 상태: 활성, 소진, 만료, 회수
- 관련 이용 자격, 구독, 결제 주문 등의 참조
- 지급 사유와 처리 운영자
- 멱등 지급 키
- 생성·수정 시각

잔량은 0 미만이 될 수 없다. 같은 월별 지급 회차, 결제 주문 또는 관리자 요청이 반복돼도 멱등 키로 한 묶음만 생성한다.

### 3.5 크레딧 원장

기존 작업 전용 `credit_ledger`를 지급 묶음 기반의 불변 원장으로 교체한다.

원장 유형:

- 지급
- 작업 차감
- 작업 실패 반환
- 관리자 회수·조정
- 결제 취소·환불 조정
- 만료

각 행은 다음을 연결한다.

- 사용자와 `credit_grant_id`
- 증감 수량과 해당 묶음의 처리 후 잔액
- `operation_run_id`, `payment_order_id`, 관리자 요청 ID 등 원인 참조
- 표시 가능한 사유와 내부 멱등 참조 키
- 처리 시각

한 작업이 여러 지급 묶음을 사용하면 묶음별 차감 행을 각각 만든다. 실패 시 이 행들을 기준으로 원래 묶음에 반환한다.

### 3.6 결제 주문

`payment_orders`, `payment_events`의 주문·공급자 이벤트·멱등 기록 개념은 유지하고 실서비스 목적을 확장한다.

주문 목적:

- 최초 구독
- 갱신
- 업그레이드 차액
- 추가 크레딧 구매
- Toss 심사용 익명 주문

주문은 당시 상품 코드·이름·가격·등급·결제 주기·크레딧 수량을 스냅샷으로 가진다. 나중에 상품이 수정되어도 이미 결제한 주문의 의미는 변하지 않는다.

심사용 익명 주문에는 fulfillment를 실행하지 않는다.

## 4. 관리자 이용 자격 동작

### 4.1 최초 지급

관리자는 사용자, 등급, 시작일, 종료일 또는 만료 없음, 사유를 입력한다.

시작 시점에:

1. 플러그인 권한을 활성화한다.
2. 해당 등급의 한 달분 크레딧을 전액 지급한다.
3. 다음 월별 지급일을 같은 기준일의 다음 달로 기록한다.

마지막 이용기간이 한 달보다 짧아도 마지막 지급회차는 전액 지급하고 일할 계산하지 않는다.

### 4.2 같은 등급 수정

- 종료일과 사유를 수정할 수 있다.
- 월별 지급 기준일은 유지한다.
- 수정 자체로 크레딧을 다시 지급하지 않는다.
- 변경 전후 값을 감사 이벤트로 남긴다.

### 4.3 다른 등급으로 즉시 변경

관리자에게는 한 번의 변경 작업으로 제공한다. 서버 내부에서는 이전 등급 종료와 새 등급 시작을 하나의 짧은 트랜잭션으로 처리한다.

상위 등급 변경:

- 기존 미사용 크레딧을 유지한다.
- 현재 월별 회차에서 `max(새 등급 월 지급량 - 이전 등급 월 지급량, 0)`만 추가 지급한다.
- 월별 지급 기준일은 유지한다.
- 다음 지급일부터 새 등급의 월 지급량을 전액 지급한다.

예:

```text
Basic 월 10,000 / Pro 월 30,000
8월 12일 Basic 10,000 지급
8월 20일 Pro 변경 -> 차이 20,000 추가 지급
9월 12일 Pro 30,000 지급
```

하위 등급 변경:

- 이미 지급한 크레딧을 회수하지 않는다.
- 추가 차액도 지급하지 않는다.
- 플러그인 권한은 즉시 하위 등급으로 바뀐다.
- 다음 월별 지급일부터 하위 등급 지급량을 적용한다.

### 4.4 회수와 만료

- 플러그인 권한과 미래 월별 지급을 중지한다.
- 이미 지급한 크레딧은 자동 삭제하지 않는다.
- 유효한 기본 이용 자격이 없어져 모든 잔액의 사용은 정지된다.
- 특정 크레딧도 회수해야 하면 별도 관리자 크레딧 회수로 기록한다.

## 5. 월별 크레딧 지급

스케줄러는 지급 예정일이 지난 유효 이용 자격을 찾는다. 전체 대상을 하나의 거대한 트랜잭션으로 묶지 않고 사용자·회차별로 짧게 처리한다.

개별 회차 트랜잭션:

1. 이용 자격을 잠그고 여전히 유효한지 다시 확인한다.
2. `이용 자격 ID + 월별 기준일` 멱등 키를 확인한다.
3. 해당 등급의 월 지급량으로 `credit_grants`를 만든다.
4. 지급 원장을 만든다.
5. 다음 지급 예정일을 진행시킨다.
6. 모두 성공하면 커밋한다.

서버가 중단됐다가 재시작되어도 누락 회차를 다시 찾는다. 같은 회차를 반복 처리해도 한 번만 지급한다.

## 6. 플러그인 권한과 작업 차감

### 6.1 권한 검사

사용자 작업 시작 전 서버가 다음 순서로 확인한다.

1. 유효한 기본 이용 자격이 있는가
2. 해당 등급이 요청한 `plugin_key`를 포함하는가
3. 사용할 수 있는 유효 크레딧이 충분한가

클라이언트가 보낸 임의의 플러그인 키를 신뢰하지 않는다. 각 서버 작업이나 작업 정책이 자신의 안정적인 `plugin_key`를 알고 있어야 한다. 데스크톱은 서버가 반환한 허용 플러그인 목록으로 잠금 상태를 표시하지만 서버도 같은 권한을 다시 검사한다.

오류 코드는 최소한 다음을 구분한다.

- `NO_ACTIVE_ACCESS`
- `PLUGIN_NOT_ENTITLED`
- `INSUFFICIENT_CREDITS`

### 6.2 작업 시작

작업 시작 시 짧은 DB 트랜잭션을 사용한다.

1. 이용 자격과 사용할 크레딧 묶음을 잠근다.
2. 권한과 잔액을 다시 확인한다.
3. 만료가 가까운 묶음부터 차감한다.
4. 묶음별 차감 원장을 만든다.
5. `operation_run`을 `running`으로 만든다.
6. 커밋한다.

외부 AI 작업은 이 트랜잭션이 끝난 뒤 시작한다. AI 작업이 30분 걸리더라도 DB 트랜잭션이나 잠금을 유지하지 않는다.

### 6.3 성공과 실패

성공 시 별도의 짧은 트랜잭션으로 실행 상태만 `succeeded`로 확정한다.

실패 시 별도의 짧은 트랜잭션으로:

1. 실행과 원 차감 행을 잠근다.
2. 반환되지 않은 차감만 찾는다.
3. 실제 차감했던 각 지급 묶음에 반환한다.
4. 묶음별 반환 원장을 만든다.
5. 실행 상태를 `failed`로 바꾼다.
6. 커밋한다.

반환 요청이 반복돼도 한 번만 반환한다. 원 지급 묶음이 이미 만료됐다면 반환 이력과 묶음 잔액은 복구하되, 만료된 잔액을 사용 가능 잔액으로 계산하지 않는다.

### 6.4 중단된 작업 복구

오래 `running`인 작업은 복구 대상이다.

- 외부 작업 식별자로 실제 상태를 확인할 수 있으면 성공 또는 실패를 확정한다.
- 외부 요청을 시작하지 못한 것이 확인되면 반환한다.
- 실제 상태를 확인할 수 없으면 시간 경과만으로 환불하지 않고 확인 필요 상태나 운영 재처리 대상으로 분리한다.

실제로 성공한 외부 작업과 크레딧 반환이 동시에 발생하지 않도록 공급자별 상태 확인 가능성을 구현 계획에서 조사한다.

## 7. 추가 크레딧 구매

### 7.1 구매 시작

1. 로그인과 유효한 기본 이용 자격을 확인한다.
2. 판매 중인 `credit_products`를 확인한다.
3. 상품 정보 스냅샷으로 단건 결제 주문을 만든다.
4. Toss 결제창을 연다.

### 7.2 결제와 fulfillment

외부 Toss 요청을 DB 트랜잭션에 포함하지 않는다.

```text
Toss 결제 확인
  -> 짧은 트랜잭션: 결제 성공과 공급자 이벤트 저장
  -> 짧은 트랜잭션: topup 지급 묶음 + 지급 원장 + fulfillment 완료
```

결제 성공 저장과 fulfillment를 분리한다. 지급 단계가 실패하면 결제는 성공으로 보존하고 지급만 재시도한다. 같은 결제 주문으로 `topup` 지급 묶음은 한 번만 생성한다.

구매 시작 후 이용 자격이 만료됐더라도 성공한 결제는 지급한다. 사용 가능 여부는 지급 시점이 아니라 현재 유효한 기본 이용 자격으로 계산한다.

## 8. 조회와 관리자 API 계약

정확한 URL과 DTO 이름은 구현 계획에서 기존 라우팅 규칙에 맞춰 확정하되 다음 capability를 제공한다.

### 8.1 사용자

- 현재 기본 이용 자격, 등급, 출처, 기간, 허용 플러그인
- 다음 월별 크레딧 지급일
- 전체 보유 잔액과 현재 사용 가능 잔액
- 출처별 잔액과 지급 묶음별 만료일
- 지급·차감·반환·만료·조정 원장
- 추가 크레딧 상품 목록과 선불 checkout

유효한 기본 이용 자격이 없고 유효 추가 크레딧 5,000이 남았다면 다음 의미를 반환할 수 있어야 한다.

```text
보유 잔액: 5,000
사용 가능 잔액: 0
사용 불가 사유: NO_ACTIVE_ACCESS
```

### 8.2 관리자

- 사용자에게 표준 요금제 등급 지급
- 같은 등급의 기간·사유 수정
- 다른 등급으로 즉시 변경
- 이용 자격 회수
- 임의 수량·유효기간의 관리자 크레딧 지급
- 남아 있는 관리자 지급 크레딧 범위 안에서 회수
- 이용 자격과 크레딧 감사 이력 조회

관리자가 사용자 총잔액을 임의 숫자로 덮어쓰는 API는 제공하지 않는다. 지급과 회수를 별도 원장 행으로 기록한다.

## 9. 짧은 트랜잭션 경계

`트랜잭션으로 처리한다`는 외부 작업 전체를 하나로 묶는다는 뜻이 아니다. 서로 일치해야 하는 DB 변경만 각각 짧게 묶는다.

| 상황 | 한 트랜잭션에 포함되는 변경 |
| --- | --- |
| 관리자 등급 변경 | 이전 등급 종료, 새 등급 시작, 감사 이벤트, 필요한 차액 크레딧 |
| 크레딧 지급 | 지급 묶음, 지급 원장, 관리자 요청 또는 회차 처리 완료 |
| 크레딧 회수 | 현재 잔량 확인, 회수, 회수 원장, 사유·처리자 |
| 작업 시작 | 권한 재검사, 차감, 차감 원장, `operation_run` 생성 |
| 작업 실패 | 원 묶음 반환, 반환 원장, `operation_run` 실패 처리 |
| 결제 fulfillment | 지급 묶음, 지급 원장, fulfillment 완료 |

외부 AI 실행과 Toss 네트워크 호출은 이 표의 트랜잭션 밖에서 수행한다.

## 10. 기존 구조 제거

최종 기능 브랜치에서 다음을 제거한다.

### API와 DB

- `plans`
- `purchase_requests`
- `licenses`
- `token_usage`
- 기존 작업 전용 `credit_ledger`
- 무통장 구매 요청·재요청·승인·반려·반환 API

이미 실행된 과거 마이그레이션 파일은 수정하지 않는다. 새 전환 마이그레이션으로 테스트 데이터를 초기화하고 기존 테이블을 제거한 뒤 목표 스키마를 만든다.

### 웹과 관리자

- `/app/purchase` 무통장 구매 요청 화면
- 구매 요청 이력과 재요청 화면
- 입금 확인·구매 요청 승인 화면
- queued 이용권 표시와 시작 동작
- 무통장 안내 문구와 관련 mock

새 상품 카탈로그, 이용 자격, 크레딧, 추가 충전 계약으로 교체한다.

### 데스크톱

- 기존 `licenses/current` 응답 의존성
- 이용권 이름과 단일 잔액만 표시하는 계약

새 이용 자격·허용 플러그인·보유 및 사용 가능 크레딧 계약으로 교체한다.

## 11. 유지할 구조

- 사용자·관리자 인증
- `operation_policies`의 작업별 크레딧 가격
- `operation_runs`의 실행 생명주기
- Toss provider adapter와 서버 재검증
- `payment_orders`, `payment_events`의 주문·이벤트 기록 개념
- 익명 Toss 심사용 checkout과 비밀 결과 조회 토큰
- 사용자가 만든 프로젝트와 결과물

익명 심사용 주문은 새 상품 카탈로그를 조회하도록 바꾸되 fulfillment는 계속 금지한다.

## 12. 오류와 복구

최소 오류 분류:

- `NO_ACTIVE_ACCESS`
- `PLUGIN_NOT_ENTITLED`
- `INSUFFICIENT_CREDITS`
- `ACTIVE_ACCESS_CONFLICT`
- `CREDIT_PRODUCT_UNAVAILABLE`
- `PAYMENT_REQUIRED`
- `DUPLICATE_REQUEST`

중복 방지 키:

- 월별 지급: 이용 자격과 지급 기준일
- 결제 지급: 결제 주문과 fulfillment 종류
- 관리자 요청: 관리자 요청 식별자
- 작업 반환: 작업과 반환 요청과 지급 묶음

결제 성공·fulfillment 실패, 누락된 월별 지급, 오래 `running`인 작업은 운영자가 식별하고 재처리할 수 있어야 한다. API Key, 평문 빌링키, 불필요한 개인정보는 감사 payload에 저장하지 않는다.

## 13. 검증 기준

### 상품과 권한

- 같은 등급의 모든 결제 주기가 같은 플러그인 권한을 사용한다.
- 상위 등급 전용 플러그인은 하위 등급에서 서버가 거부한다.
- 한 사용자에게 유효 기본 이용 자격 두 개가 생기지 않는다.

### 관리자 이용 자격

- 같은 등급 기간 수정은 크레딧을 중복 지급하지 않는다.
- 상위 등급 변경은 당월 월 지급량 차이만 한 번 지급한다.
- 하위 등급 변경은 기존 크레딧을 회수하지 않는다.
- 임의 종료일의 마지막 불완전한 회차도 한 달분을 전액 지급한다.
- 만료·회수 후 미래 월별 지급이 없다.

### 크레딧

- 가장 가까운 만료 묶음부터 차감한다.
- 한 작업이 여러 묶음에서 차감될 수 있다.
- 동시 작업과 관리자 회수로 잔액이 음수가 되지 않는다.
- 실패 반환이 원래 묶음으로 한 번만 돌아간다.
- 기본 이용 자격이 없으면 잔액이 있어도 사용할 수 없다.
- 재활성화 후 아직 유효한 잔액을 다시 사용할 수 있다.

### 추가 구매

- 모든 등급이 같은 추가 크레딧 상품을 같은 가격으로 본다.
- 기본 이용 자격 없는 사용자는 구매를 시작할 수 없다.
- 결제 성공 전에는 지급되지 않는다.
- 반복 결제 결과로 중복 지급되지 않는다.
- 결제 성공 후 지급 실패는 지급만 재시도한다.
- 이용 자격 종료 후 잔액은 보존되고 사용은 정지된다.

### 전환

- 무통장·legacy license 참조가 코드와 화면에서 제거된다.
- 새 전환 마이그레이션이 기존 테스트 데이터를 제거하고 목표 스키마를 만든다.
- 익명 심사용 결제는 어떤 이용 자격이나 크레딧도 지급하지 않는다.
- API, 웹, 관리자, Angular, Electron의 로컬 빌드와 관련 테스트가 모두 통과한 뒤에만 병합·배포한다.

## 14. 구현 단계 분해

하나의 배포 단위이지만 검토 가능한 작업 단위로 나눈다.

1. API 목표 스키마와 도메인
2. 관리자 이용 자격·크레딧 API
3. 월별 지급과 작업 차감·반환 전환
4. 추가 크레딧 상품과 로그인 선불 결제
5. 익명 심사용 결제의 새 카탈로그 전환
6. 사용자 웹·관리자 UI 전환
7. Angular·Electron 권한과 크레딧 계약 전환
8. 무통장·legacy 코드와 테이블 제거
9. 전체 로컬·통합 검증

각 저장소는 별도 기능 브랜치에서 작업한다. 전체 단계가 완성되기 전에는 dev에 병합하거나 배포하지 않는다.

- 등급별 플러그인 목록과 월 지급량

- 데스크톱 오프라인 권한 유예

추가 크레딧을 판매한다는 것, 모든 등급에 같은 상품·가격을 적용한다는 것, 이용 자격이 없으면 사용을 정지한다는 것은 확정 정책이며 이 목록의 미정 항목이 아니다.
