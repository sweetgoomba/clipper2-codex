# 정식 출시 후 데스크톱 API 하위 호환·버전 정책

> 기록 위치 정정(2026-09-17): 사용자 지시에 따라 `.codex/todos/`로 이동했다. `clipper_docs`에 신규 작성했던 것은 기록 위치 지시를 잘못 적용한 것이며, 그 저장소에 커밋·푸시하지 않았다.

> 2026-09-16. 개발서버 정식 PG 전환 사전검토에서 분리한 **출시 후 과제**다.
> 현재 전환은 정식 출시 전이므로 옛 개발판 앱을 지원 범위에 넣지 않는다. 새 통합 앱·Web API를 같은 계약으로 검증하고, 사용자는 새 빌드 설치와 1회 재로그인을 전제로 한다.

## 시작 조건

첫 정식 공개 버전이 배포되고 다음 데스크톱 버전을 준비할 때 이 문서를 다시 연다. 예: `1.2.1 -> 1.2.2`. 개발 중 내부 빌드 번호 변경에는 소급 적용하지 않는다.

## 결정할 것

- 각 데스크톱 버전의 API 지원 기간과 최소 지원 버전
- 강제 업데이트·권장 업데이트·계속 사용 가능 상태의 기준
- Web API를 `/v1`, `/v2`처럼 분리할지, 같은 endpoint에서 이전 응답 필드를 일정 기간 유지할지
- 오래된 앱이 새 응답을 이해하지 못할 때의 명시적 오류와 업데이트 안내 UX
- access/credit/operation/payment 계약 변경 시 구·신 앱 동시 지원 범위
- 요청·응답 runtime validation과 버전별 contract test/fixture
- 단계적 배포, 관측 지표, 장애 시 서버/클라이언트 rollback 방식
- 지원 종료 공지와 서버 차단 시점

## 지켜야 할 경계

- 이번 개발서버 PG 전환을 위해 옛 개발판 전용 호환 endpoint·adapter를 새로 만들지 않는다.
- 기존 개발 DB의 사용자 계정·프로젝트·작업 이력 보존은 API 하위 호환과 별개의 마이그레이션 요구다.
- Angular의 옛 license 명칭이나 도달 불가능한 UI를 향후 호환 계층으로 오인해 남기지 않는다.
- 실제 출시 뒤 호환이 필요해지면 버전·지원기간을 먼저 결정하고, 임시 필드 보존이 아니라 테스트되는 명시적 계약으로 구현한다.

## 완료 기준

- 지원 버전 표와 API 변경 규칙이 문서화됨
- 최소 2개 연속 공개 버전 조합의 contract/E2E 검증이 자동화됨
- 강제 업데이트와 호환 실패 UX가 패키지에서 검증됨
- rollout/rollback runbook과 지원 종료 절차가 준비됨
