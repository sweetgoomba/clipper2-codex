API 관련 테스트와 빌드, 인프라 검사, 고객 웹 전체 테스트와 운영 빌드 결과는 작업 ledger에 기록한다. 테스트 통과를 새 MID 연동 또는 라이브 거래 완료로 해석하지 않는다.

사용자 실행으로 m4-prod의 네 checkout을 목표 SHA에 맞췄다: 인프라 `72594b8`, 고객 웹 `d7a05f4`, 관리자 웹 `8025bc2`(`dev`), API `64a6b61`. 각 작업 폴더는 clean이고 원격 추적 브랜치와 일치한다.
후속 사용자 실행으로 m4-prod의 비공개 `stack.prod.env`에 계정 B의 일반·정기 MID별 라이브 키를 넣고 `validate-toss-payments-env.sh ... live`의 `Toss Payments environment preflight passed.`를 확인했다. 실제 값은 공유·기록하지 않았다. 이 검사는 키 형식·환경만 확인하며 실제 MID 연결 및 실거래는 미검증이다.
사용자가 m4-prod에서 `deploy-prod.sh all --build-only`를 실행해 고객 웹 `d7a05f4`, 관리자 웹 `8025bc2`, API `64a6b61`의 운영 이미지를 빌드했다. `Images built. No application or DB changes performed.`를 확인했다. 컨테이너 교체·DB 작업은 미실행이다.
사용자 제공 사후 출력에서 네 checkout은 모두 clean이며 인프라 `72594b8`, 고객 웹 `d7a05f4`, 관리자 웹 `8025bc2`, API `64a6b61`을 유지했다. 세 prod 이미지의 revision label도 각 앱 SHA와 일치한다. 심사용 앱·DB와 정식 운영 DB는 아직 그대로다.
새 테스트 키 사전 확인을 위한 m2-stage 읽기 전용 조사: 실행 Compose 프로젝트는 `clipper-dev`, 작업 경로는 `/Users/metabuzz/Desktop/project/clipper2/clipper_infra/apps`. 네 repo 모두 clean이나 인프라 `8adbfcd`, 고객 웹 `7282921`(stage의 원격 dev보다 6커밋 뒤), 관리자 웹 `bdcbae3`(7뒤), API `31f4482`(1뒤)다. 별도 최신 원격 조회에서 실제 `origin/dev`는 인프라 `d050195`, 고객 웹 `bd8fd8d`, 관리자 웹 `8025bc2`, API `1feac57`로 이전 빌드 기준에서 갱신되지 않았다. m2-stage 인프라의 `origin/dev`는 서버에서 오래된 원격 참조다. 개발 앱·DB는 아직 변경하지 않았다.
후속 m2-db 읽기 전용 조회: 개발 관리자 DB의 `subscriptions`는 `active` 4건·`canceled` 1건, `payment_orders`는 `checkout_ready` 1건·`expired` 1건·`paid` 4건이다. 컨테이너·볼륨 목록에는 `_dev`·`_prod`만 있고 별도 `_stage` DB는 없다. 기존 개발 DB와 키는 유지한다. 심사용 스택은 구 비로그인 앱·구 데이터여서 최신 UI 테스트에 재구성이 필요하다. 이번 전환은 새 테스트 키 종단 간 거래를 선행하지 않고 빈 운영 DB에서 내부 직원의 라이브 거래를 한 건씩 대조한다. 불일치 시 다음 거래를 중단한다.

사용자가 m2-db에서 운영 컨테이너 부재를 다시 검사하고 `clipper_postgres_data_user_prod`, `clipper_postgres_data_admin_prod`, `clipper_postgres_data_release_prod`만 삭제했다. 세 볼륨 모두 `docker volume inspect`에서 부재가 확인됐다. 이 시점에는 **정식 운영 DB 데이터가 삭제됐고 DB 컨테이너는 아직 재생성되지 않았다.** 개발 DB 3개와 m4-prod 심사용 DB 3개는 유지 중이다. 다음은 검증된 `clipper-db-prod` Compose 설정으로 빈 운영 DB 3개를 다시 만드는 단계다.

사용자는 두 웹훅의 상세 URL이 모두 정확하다고 확인했다. 내부 직원 계정으로 Basic 월간 5,900원의 **첫 라이브 정기결제**를 직접 실행했고, 고객 화면에서 결제·상품 지급 완료와 2026-10-07 20:34 결제 시각을 확인했다. 토스 매출전표는 카드번호 인증으로 조회됐으며 구매자란은 비어 있고, 구매자명+금액 인증은 실패했다. 실제 주문번호·영수증 URL·카드번호는 이 문서에 기록하지 않는다. 코드상 Google 프로필의 이름·이메일은 우리 User DB에 저장되지만, 정기 카드 등록 SDK 호출과 빌링키 발급·첫 승인 API 본문에는 `customerName`/`customerEmail`이 없다. 따라서 이번 매출전표의 구매자명 부재와 부합한다. 토스가 이메일을 별도 경로로 수집했는지는 미확인. 다음은 계정 B의 정기 MID `bill_cldevp14i` 상점관리자에서 승인 1건·금액을 대조하고, 고객 마이페이지의 구독·이용권·400 크레딧과 운영 DB 상태를 확인하는 단계다. 첫 자동결제는 `PAYMENT_STATUS_CHANGED` 발송 대상이 아니므로 웹훅 수신 검증 성공으로 기록하지 않는다. 단건결제·환불은 아직 실행하지 않았다.
영수증 조회 방식 추가 조사: 사용자는 이번 라이브 매출전표에 구글 이메일을 입력해도 조회할 수 없었고, 개발 서버 테스트 결제 때는 결제내역의 영수증 버튼에서 인증 없이 화면이 열렸다고 보고했다. 고객 웹의 결제결과·결제내역 버튼은 모두 서버가 저장한 토스 `receipt.url`을 그대로 연다. 테스트 결제내역은 sandbox 영수증 호스트도 허용하고, 결제결과 화면은 라이브 호스트만 허용하므로 과거에 결제내역에서만 테스트 링크를 본 정황과 맞는다. 토스 공식 문서는 테스트 키에서 영수증 URL은 생기지만 실제 매출전표 데이터가 없고 라이브에서만 실제 전표가 나온다고 명시한다. 따라서 이번에 보인 인증 화면은 앱이 새로 만든 것이 아니라 라이브 토스 영수증 화면이다. 다만 토스가 어떤 조건에서 조회 인증을 요구하는지는 공식 문서에서 확인되지 않았다. `customerEmail`은 SDK 카드등록·일반결제와 서버 빌링 승인에서 지원되는 선택 파라미터라 향후 전달 가능하지만, 추가해도 인증 단계 제거 또는 이메일 방식 조회 성공을 보장한다는 근거는 없다. 기존 결제 전표에 소급 적용되지 않는다.

이메일 전송 후속 결정: 사용자는 앞으로 토스의 결제 결과 안내 이메일을 로그인한 구글 계정 이메일로 받기를 원하며, 구매자명(`customerName`)은 팀 논의 전까지 보내지 않기로 했다. 클리퍼는 이미 회원 DB에 이메일을 보유하므로 별도의 입력란이나 DB 컬럼을 추가하지 않는다. 이번 변경은 단건 결제창, 정기 카드 등록창, 첫 정기 청구, 자동 갱신, 즉시 요금제 변경 청구에 `customerEmail`만 전달한다. 토스 공식 문서상 이메일은 100자 이하이며, 길이를 넘으면 결제 요청에서 생략한다. 상점관리자의 ‘결제내역 이메일 입력’ 토글은 현재 확인한 주문서형·결제창형 기본 UI 설정으로, 클리퍼의 API 개별 연동 결제창과 서버 자동 청구를 대신하는 근거가 없으므로 이번에는 OFF로 유지한다. 사용자가 임의의 수신 이메일을 입력하는 기능은 도입하지 않는다. 사용자가 m4-prod에서 API `89795cd`, 고객 웹 `ebce0c1` 이미지를 빌드·기동했고 API health의 user/admin/release DB `ok`, 고객 웹 공개 주소 HTTP 200을 확인했다. 단건 라이브 거래 뒤 토스 결제 안내 메일 수신은 확인했다. 다만 그 메일의 수신 주소가 SDK의 `customerEmail` 전달에서 왔는지, 선택한 간편결제의 별도 정보에서 왔는지는 이 거래만으로 확정할 수 없다. 이메일 안내는 앞서 완료된 정기결제에 소급되지 않는다.

사용자는 같은 직원 계정으로 추가 크레딧 400을 5,900원에 단건 결제했다. 고객 화면은 결제와 지급 완료를 표시했고, 토스 안내 메일은 같은 상품·금액·주문번호와 `네이버페이 - 카드` 결제수단을 담아 도착했다. 사용 가능 크레딧은 1,200으로, 무료체험·정기결제·추가 구매 각 400을 합한 값이며 아직 소진하지 않았다. 사용자가 토스 결제조회 API로 일반 MID `clidevxzdd`, 상태 `DONE`, 최초 결제금액 5,900원, 수단 `간편결제`를 확인했다. **앞서 제공한 진단 명령의 `customerEmailPresent: false`와 `customerNameState: null`은 전송되지 않았다는 뜻이 아니다.** 공식 Payment 객체 명세에 두 필드가 없고, 해당 명령은 필드 부재와 `null`/빈 문자열을 구분하지 못하므로 전송 여부를 판단할 수 없는 진단 오류다. 클라이언트 코드는 결제 요청에 이메일을 조건부로 전달하고 이름은 전달하지 않는다. 실제 메일 호칭은 `-님`으로, 공식 안내의 이름 생략 시 `고객님` 설명과 차이가 있으나 결제조회 응답으로 메일 주소·호칭의 원인을 확인할 수 없다. 사용자 결정에 따라 이름 자동 전송은 팀 논의 전까지 보류한다. 계좌이체·취소/환불·웹훅 실제 배달은 미검증이다.

- 표시 이름·레이아웃·필수 안내와 실제 토스 결제창의 수단을 내부에서 확인한다.

### 4. 라이브 실결제・환불・가상계좌

- 실결제 대상 계정·상품·금액·키/MID/환경을 구체화하고 사용자가 실행할 결제/환불 절차를 만든다. 키 발급 보고 자체는 에이전트의 결제 실행 권한이 아니다.
- 승인/확정, access·credit 지급, 원장, 취소/환불 및 자격, 중복/실패/webhook 재전송의 결과를 확인한다.
- 가상계좌는 사용자가 기존 테스트 키에서 시험하지 못한 항목이며, 현재 일반 MID의 제공된 활성 목록에도 없다. 토스의 계약·활성화 확인 후에만 발급→입금대기→입금통지→지급, 만료/취소 및 환불 계좌 흐름을 테스트/라이브 순서로 검증한다. 현재 라이브 실기 완료 기준에는 넣지 않는다.
- live 결제/환불/가상계좌의 실제 성공 결과는 아직 없으며 검증 시 test/live를 각각 기록한다.

## 작업 공간

우선 `web/clipper_web_api`, `web/clipper_web_client`, `web/clipper_infra`; 운영자 UI 변경이면 `web/clipper_web_admin`. Desktop 수정 필요 여부는 API/결제 진입 연동 조사 후 결정한다.

읽기 전용 조사 후 필요한 repo의 최신 origin/dev에서 새 브랜치·격리 worktree를 준비한다. 새 브랜치/공간은 아직 없다. 서버 접속·명령은 사용자가 실행하는 방식이다.

## 시작 순서·완료 기준

1. 먼저 현행 연동 지도·MID/키/데이터 연결과 교체 영향을 설명한다.
2. 새 키 매핑/데이터 처리/배포/검증 계획을 구체화한다.
3. 선택된 방안 구현·test 검증 → 내부 결제 UI 확인 → 구체적 live 카드/계좌이체 결제·환불 증거를 남긴다. 가상계좌는 이번 작업에서 제외한다.
4. 실제 결과, 미실행, 후속 운영 항목을 구분한다. 새 키 발급을 운영 전환 완료로 표시하지 않는다.

## 기존 운영 후속 중 함께 확인할 항목

기존 환불자격/부분환불/멱등성, 구독 즉시·예약 변경/취소, 카드 변경 후 다음 청구, worker 복구, webhook 동시성·재전송, 약관/정책은 위 전환의 관련 범위에서 최신 코드와 대조한다. runner/S3·Windows 설치·Mac 공증·모니터링 전체를 이번 PG 세션에 자동 포함하지 않는다.
