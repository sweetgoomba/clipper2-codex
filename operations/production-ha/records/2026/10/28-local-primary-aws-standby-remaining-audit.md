# 클리퍼 이중화 추천안 채택 후 남은 결정·조사·검증

기준일: 2026-10-28. 대상: `28-local-primary-aws-standby-design.md` 및 현재 저장소 코드. 회사 정전·WAN 단절을 주된 보호 장애로 유지한다. 기술 추천을 모두 따른다는 가정이며, 이미 선택한 아키텍처를 다시 사용자에게 고르게 하지 않는다.

## 1. 현재 상태와 정정

주요 제품과 정상/장애 시 역할은 선택돼 있다. 그러나 배포 입력값만 채우면 끝나는 수준은 아니다. COMMIT 취소 경고 처리, 부분 통신 장애의 대응 범위, 사용자 성공 응답 전체 경로, 복귀 자동화, 감시 배치 등에는 추가 상세 설계와 검증이 남아 있다. 이전 답변의 “핵심 기술과 장애 대응 정책을 나중에 정하는 상태로 남기지 않았다”는 표현은 이 범위를 충분히 드러내지 못했다.

이 문서는 미구현이라는 사실을 나열하지 않고, **아직 어떤 사실/정책/안전 조건이 확정되지 않았는지, 누가 해결하며, 어떤 증거로 완료하는지**를 기록한다. 현재 저장소와 문서에서 확인한 목록이며 현장 조사에서 새 의존성이 발견되면 추가한다.

## 2. 다시 선택할 필요가 없는 것

- 로컬 앱/DB 메인, 상시 실행 AWS 앱/DB 보조.
- PostgreSQL 동기 복제, Patroni, etcd 과반수, HAProxy, 필수 watchdog.
- AWS 두 AZ, DB별 local/aws-a/aws-b 구성. user/admin/release 분리 유지.
- AWS 전환은 자동, 로컬 복귀는 계획된 작업. 데이터 안전 조건 불충족 시 쓰기 중단.
- 회사 전체 장애의 초기 인수 기준 p95 40초/시험 최대 60초, 앱 단독 장애 p95 10초. 이것까지 채택하면 다시 기준을 선택할 필요는 없다. 다만 “모든 회사 장애를 2~5초 안에 복구”라는 목표를 충족한 설계로 바뀌는 것은 아니다.
- 기존 맥미니 앱 유지, 운영 DB는 전용 x86_64 Linux/KVM 환경. 신규 장비의 모델·가격·구매는 별도다.
- pgBackRest/PITR와 별도 백업 계정의 불변 사본. 데이터 보관 정책 적합성과 실제 복원은 별도 확인한다.

## 3. 사용자·회사가 실제로 정할 사항

| 항목 | 아직 없는 정보 | 권고와 분담 |
|---|---|---|
| 예산과 구매 한도 | 월 운영비 상한, 일회성 장비/구축 예산, 장애 시험 자원 예산 | 엔지니어가 정상/피크/복구 시험 비용 견적을 먼저 만든다. 회사는 그 금액과 상한을 결정한다. EC2 8대라는 개수만으로 금액을 승인한 것으로 보지 않는다. |
| 일정과 전환 가능 시간 | 출시 확정일, 투입 인력, 운영 점검 가능한 시간 | 출시 전에 전환 시험까지 끝내는 것을 추천한다. 이미 실거래가 있다면 리허설로 측정한 이관 시간에 근거해 점검 시간을 회사가 선택한다. |
| 운영 책임자 | 주담당/대체자 이름, 야간·주말 대응 범위, 계정 접근 책임자 | 최소 두 사람이 복귀·복원을 수행할 수 있게 한다. 실제 당직과 근무 약속은 회사가 정한다. 자동 전환이 수동 대응의 필요를 완전히 없애지는 않는다. |
| 결제·크레딧 예외의 처리 권한 | 자동 대조로 끝나지 않는 건의 담당자, 고객 안내와 환불/보상 승인 권한 | 결과 불명 건은 새 결제로 재청구하지 않고 조회·대조한다. 기존 환불 정책을 우선 적용하고 실제 승인권자는 회사가 지정한다. |
| 기존 보관·삭제 및 계정 정책 | 백업 보존 기간과 기존 회사 정책의 충돌 여부, 별도 백업 계정의 소유자 | 일별 35일/월별 12개월은 기술 제안이지 기존 회사 정책을 확인한 값이 아니다. 충돌이 없다면 그대로 채택한다. 보호된 사본은 Object Lock 모드에 따라 즉시 지울 수 없으므로 정책 적합성 확인이 먼저다. |

예산·일정·책임자를 제외한 엔지니어링 수치와 제품 설정을 사용자에게 직접 산정하도록 요구하지 않는다. 회사 정책이 이미 있으면 문서에서 먼저 확인하고, 없는 사업적 약속만 사용자 판단으로 남긴다.

## 4. 기술적으로 보완할 사항과 추천

| ID | 남은 항목과 이유 | 추천하는 처리 | 완료 증거 |
|---|---|---|---|
| T01 | **COMMIT 호출 완료와 원격 저장 확인이 같지 않을 수 있음.** 동기 대기 중 취소 요청은 PostgreSQL에서 WARNING으로 처리될 수 있고 node-postgres는 notice 이벤트로 전달한다. 기존 설계의 새 확인용 COMMIT도 같은 함정이 있다. | 보호 트랜잭션의 공통 실행기를 전용 연결에 적용한다. 동기 커밋 설정을 유지하고, COMMIT 중 WARNING·연결 종료·응답 기한 초과는 unknown으로 처리한다. notice가 설정 때문에 누락되지 않게 하고, 기한 초과 연결은 풀에 재사용하지 않는다. 이 규칙을 신규 쓰기·완료 상태조회 확인·probe에 모두 적용한다. | 복제 대기 중 pg_cancel_backend/CancelRequest, 연결 단절, 기한 초과를 재현해 HTTP 완료·결제 호출·probe 성공이 나오지 않는지 확인. 일반 SQL statement_timeout을 COMMIT 기한 보장으로 간주하지 않는다. |
| T02 | **안전한 처리의 적용 범위가 코드 경로별로 완성되지 않음.** 공통 트랜잭션 실행기를 바꿔도 직접 transaction/query/save 경로가 남을 수 있다. | 가입·로그인/권한 발급·결제/환불·크레딧·웹훅·관리 기능·배치의 쓰기/성공 응답 목록을 만들고 모두 연결한다. 자동 커밋 경로도 포함한다. 업무 원장은 보호 대상, 임시 캐시와 진단 로그는 별도 보존 등급으로 명시한다. | 기능/코드/DB/동기 확인/멱등키/장애 시험의 대응표에서 미분류 경로가 없음. |
| T03 | **부분 장애에서는 기존 메인이 권한을 유지할 수 있음.** 예: etcd 연결은 살아 있고 PostgreSQL 복제 포트만 막힘. | 회사 전체 단절은 자동 전환한다. 복제만 단절된 경우에는 안전한 쓰기 중단과 즉시 알림을 기본으로 한다. 이 경우도 무조건 자동 전환된다고 약속하지 않는다. 별도 자동 이전을 추가하려면 정상 메인의 권한 반납, 안전한 동기 후보, 재선출 차단을 포함한 프로토콜을 먼저 검증한다. | DCS만/복제만/HTTP만/단방향 차단 시험에서 실제 상태와 복구 절차 기록. 자동화 범위 밖이면 운영 복구 절차가 있음. |
| T04 | **로컬 복귀 허가와 장애 감시가 동시에 동작하는 순서.** 태그·허가·routing 상태는 여러 단계라 중간 실패와 재시도가 생김. | etcd revision 비교와 단일 운영 작업 잠금으로 복귀 명령을 직렬화한다. false가 안전 기본값이다. 허가는 scope·node·timeline 및 실행 중 복귀 작업에 묶고 일회 소비한다. bootstrap/restart/callback/허가 만료도 상태 전이로 명시한다. | 각 단계 직후 프로세스 종료·통신 차단을 넣어 재시도해도 무단 로컬 승격/라우팅 복귀가 없음. |
| T05 | **worker 프로세스가 아니라 개별 업무의 완료·재실행 경계.** lock 연결 단절과 이미 보낸 외부 호출은 별개다. | 기존 업무 claim/lease/멱등키를 재사용하고 오래된 worker의 결과 저장은 작업 소유권으로 제한한다. callback·HTTP 처리 경로도 같은 보호를 받는다. 결과 불명 결제/환불은 키를 자동 교체하지 않는다. | 실행 중 worker 종료, 오래된 응답 도착, lease 재취득, 웹훅 중복 시 이중 청구/중복 권한/이중 크레딧 없음. |
| T06 | **결제 외 주기 작업과 메모리 상태.** 카탈로그의 Interval, 운영 설정 캐시, 호출 제한 등도 여러 앱에서 실행된다. | 모든 Cron/Interval/시작 훅을 목록화해 worker 역할 또는 기존 안전한 DB claim에 연결한다. 운영 설정 캐시는 전환 시 재로딩한다. 기존 설정은 다운로드/알림용이므로 곧바로 결제 원장 오류로 단정하지 않는다. 호출 제한은 AWS 동시 앱 수를 반영한다. | 앱 3개 동시 실행/전환 상태에서 업무 중복, 설정 불일치, 외부 API 한도 초과 검사. |
| T07 | **진행 중 AI 요청·다운로드·업로드·로그인의 사용자 경험.** 서버 전환은 기존 TCP 연결이나 프로세스 메모리를 옮기지 않는다. | 이미 저장한 업무 ID로 재조회하고 안전한 요청만 재시도한다. AI/크레딧 결과 불명은 기존 operations 복구 경로에 연결한다. 정전 중 신규 installer 빌드는 중단돼도 공개된 파일 배포는 AWS/S3에서 계속되게 한다. | 데스크톱/웹의 실제 재연결 시험, 중복 차감 없음, 기존 공개 파일 다운로드 가능. |
| T08 | **모니터 배치와 알림 전달.** 기존 모니터 문서는 회사 DB/백업 맥미니 실행을 전제로 한다. 회사 정전 때 그 모니터도 사라진다. | 회사 밖의 감시와 감시 자체 중단 경보를 둔다. 기존 HTTP 모니터를 재사용하고 CloudWatch 로그/경보로 수집한다. 관리형 외부 canary는 별도 독립 검사로 사용한다. 자동 전환은 Patroni/HAProxy가 담당한다. | 회사 전체 차단, 감시 프로세스 종료, 알림 자격증명 오류 시 각 경보가 실제 담당 채널까지 도착함. |
| T09 | **계정·TLS·키 갱신과 접근 권한의 상세 설정.** 제품 이름 선택만으로 권한 경계는 완성되지 않음. | 앱/복제/백업/배포/운영자 권한을 분리한다. AWS 앱은 인스턴스 역할을 사용한다. 내부 DB/제어 통신 인증, 인증서 갱신, 로컬 secret 배포와 키 교체를 명세한다. 회사 회선 없이 관리할 경로를 유지한다. | 만료·교체·권한 오류 시험, 회사망 없는 상태의 운영자 접속, Git/로그에 비밀값 없음. |
| T10 | **백업 실행 주체와 동시 실행 잠금, 복구 명령, 암호화 키 복구.** 보관 정책과 restore-index 원칙은 있으나 실행 단위가 남음. | DB별 backup/expire/index 작업을 직렬화하고 작업 중단 후 재시작을 정의한다. 별도 계정의 객체 버전·KMS·WAL을 함께 복구한다. Object Lock의 모드와 우회 권한을 명시한다. | 원본 repo에서 expire/delete marker가 생긴 후에도 불변 인덱스로 빈 환경에 복원. 키 접근과 업무 대조까지 성공. |
| T11 | **최초 전환과 업그레이드·롤백의 실제 소요 시간.** 세 DB와 ARM/Alpine→Linux 환경 변경이 포함됨. | 데이터 사본으로 이관을 리허설하고 모든 writer를 멈추는 목록을 만든다. migration은 단일 실행 주체로 수행한다. 신규 쓰기 이후에는 옛 DB로 단순 롤백하지 않는다. PG/Patroni/etcd의 순차 업그레이드 절차도 둔다. | dump/restore·데이터 검증·WAL 동기화·도메인 전환·역이관/앱 롤백 시간 기록. |
| T12 | **인프라 자원 고정값.** 8대와 2vCPU/8GiB 등의 값은 기준안이지 용량 검증 결과가 아님. 앱과 etcd의 동거도 조건부다. | 서울 리전에서 정확한 인스턴스/AMI/패키지 버전을 선택하고 부하 시험으로 확정한다. 앱 부하·배포가 etcd 갱신에 영향을 주면 제어 노드를 분리한다. DB 커넥션·WAL/slot 상한·볼륨 증가 절차를 정한다. | 한 AWS 앱이 전체 목표 부하를 처리하며 제어면 기한을 지킴. 장애·백업·복귀가 겹친 부하에서도 동일. |
| T13 | **COMMIT와 probe에 독립적인 시간 상한이 없음.** 일반 SQL timeout으로 동기 COMMIT 대기가 끝난다고 가정할 수 없다. 1초마다 새 probe를 시작하면 연결이 누적될 수 있다. | COMMIT의 앱 측 deadline은 초기 5초로 제안하며 초과 시 unknown·연결 폐기로 처리한다. 각 검사 프로세스의 DB별 probe는 동시에 1개만 실행하고 전용 연결 수도 제한한다. 결과 신선도 2초와 실행 기한은 별도로 둔다. 미종료 서버 세션의 정리까지 포함한다. | 복제 대기가 길어져도 probe/연결이 무한 증가하지 않음. timeout 뒤 같은 연결 재사용 없음. |
| T14 | **점검 중 이미 시작한 외부 요청이 새 DB 쓰기를 만들 수 있음.** HTTP 입구 가드와 기존 DB 세션 drain만으로 충분하지 않다. | 모든 DB 변경 트랜잭션·외부 효과 시작 경계에 업무 가드를 적용한다. 완료 상태조회 확인, 기동 seed/import도 포함한다. 점검 중 도착한 결제사 응답은 기존 업무 ID로 대조하며 임의 실패 처리하지 않는다. | drain 완료 후 오래 걸린 외부 응답이 도착해도 허가 없는 새 업무 변경이 시작되지 않음. |
| T15 | **worker session lock의 해제 기한과 복귀 경쟁.** 반쯤 끊긴 TCP가 lock을 남기거나 다른 AWS worker가 다시 취득할 수 있다. | 전용 연결의 heartbeat 1초·응답 기한 2초·전용 역할 idle_session_timeout 5초를 시작값으로 한다. 그 연결에서 장기 업무를 실행하지 않는다. 계획 복귀에서는 AWS의 lock 경쟁을 중지하고 local 취득 확인 후 대기 경쟁을 재개한다. | worker만 멈추거나 연결이 반쯤 끊겨도 인계가 한정된 시간에 이뤄짐. 계획된 로컬 인계의 대상이 바뀌지 않음. |
| T16 | **빈 클러스터 최초 bootstrap은 switchover와 다름.** 초기에는 기존 메인이 없고 nofailover=true 및 복제본 부재가 초기화를 막을 수 있다. | 업무 진입을 닫고 local만 초기화할 수 있게 함 → 빈 local 클러스터 생성 → AWS 두 복제본 가입 → 동기 조건 확인 → 기존 데이터 논리 restore → 검증 → 업무 개방 순으로 정한다. 초기 허가와 재승격 허가는 구분하고, 이후 DCS/데이터 누락 시 자동 새 클러스터 생성은 금지한다. | 완전히 빈 환경에서 최초 이관이 끝남. 재시작 중 DCS/데이터가 누락돼도 새 빈 운영 DB를 서비스하지 않음. |

T01은 단순히 코드를 아직 작성하지 않았다는 뜻이 아니라, 이전 설계의 성공 판정 조건에 보완이 필요한 사항이다. T03 역시 자동 전환이 되는 장애와 쓰기 중단으로 대응하는 장애를 구분해야 한다. T13~16은 이전 설계에 부족했던 시간 제한·점검·작업 인계·초기화 계약이다. 나머지도 사용자의 기술 선택을 기다릴 일이 아니라 엔지니어가 구체화하고 검증할 책임이다.

백업 실행 위치는 회사 장애와 무관한 AWS 작업자로 정하고, DB별 단일 작업 권한을 유지한다. 월별 백업 실패 시 경보 후 성공할 때까지 재시도하고, 누락된 월을 성공한 것으로 표시하지 않는다. WAL 지연은 마지막 업로드 시각만이 아니라 아직 보관되지 않은 WAL의 나이와 복원 가능한 연속 구간으로 판단한다. 회사 etcd가 사라진 동안에는 남은 AWS etcd 두 노드가 모두 필요하므로 해당 제어 호스트의 계획된 재부팅/정비를 피한다.

## 6. 검증 전에는 확정할 수 없는 결과

1. 정전/WAN 장애에서 p95 40초·시험 최대 60초를 실제 충족하는지. `ttl=20`이 전체 복구 시간을 뜻하지 않으며 장애 발생 시점에 따라 잔여 lease 대기가 다르다.
2. 정상 앱 HTTP의 AWS→회사 경로와 동기 WAL 복제가 로그인/회원가입/결제/AI 요청의 체감 지연에 미치는 영향. COMMIT p95 150ms·p99 500ms는 제안 기준이며 측정값이 아니다.
3. 성공 응답을 외부에서 기록한 모든 업무 ID가 복구 후 보존되고, 내용도 일치하는지. T01의 취소 경고와 T02의 우회 경로를 포함해야 한다.
4. 네트워크 단절·Patroni 정지·재시작·반복 단절 중 이전 메인이 다시 성공 응답/업무 효과를 만들지 않는지.
5. 결제사에는 성공했으나 로컬이 결과를 못 받은 거래를 같은 ID로 확정하고 중복 청구·환불·크레딧 효과 없이 처리하는지.
6. 한 AWS 앱에서 피크 전체 부하를 처리하고, 백업·replica 재생성 중에도 etcd/DB의 기한을 지키는지.
7. 불변 백업과 보관된 키만으로 세 DB 및 파일을 복구하고 업무 불일치를 대조하는 데 걸리는 실제 시간. 백업 복원 시간은 정상 AWS 승격 시간과 다르다.
8. 장애 후 자동화가 안전하게 정지한 경우 운영 담당자가 제공된 정보와 도구로 복구할 수 있는지.
9. 정상·피크·복구 시험 각각의 비용과 팀의 운영 부담. 고정비와 변동비, 작업 시간을 별도 평가한다.

위는 선택지가 남았다는 의미가 아니라 결과를 측정해야 한다는 의미다. 반복 시험의 관측 최대값을 무조건적인 SLA로 바꾸지 않는다.

## 7. 이미 채택한 선택에 포함된 운영상 결과

- 로컬과 AWS의 연결이 없고 AWS에서도 안전한 새 메인을 준비할 수 없으면 쓰기를 중단한다. 데이터를 보존하면서 모든 통신 단절에서 계속 쓰는 것을 약속하지 않는다.
- AWS DB 복제본 하나가 이미 고장 난 상태에서 회사까지 꺼지면, 남은 단독 DB는 새 쓰기를 확정하지 못할 수 있다. 정상 회사 장애 복구 목표의 전제는 AWS의 필요한 복제본과 제어면이 준비돼 있다는 것이다. 이 상태를 경보와 정기 점검으로 확인한다.
- API가 준비됐다는 것과 모든 과거 미확정 결제·AI 작업이 이미 끝났다는 것은 다르다. 신규 정상 요청의 재개와 과거 거래의 대조 완료를 따로 측정한다.
- 기준안은 user/admin/release 중 하나라도 준비되지 않으면 API 전체를 준비되지 않은 상태로 둔다. 기능별 부분 운영은 현재 기준안에 포함하지 않았다.
- 기존 HTTP/TCP 연결의 무중단 이동이나 실행 중 프로세스 메모리 이전을 제공하지 않는다. 클라이언트의 재조회·재시도 동작이 필요하다.
- 공개 입구·DB 복제·백업에 AWS를 계속 사용하므로 “AWS 보조이니 거의 비용이 없다”는 전제가 성립하지 않는다. EC2 8대는 선택한 배치의 수이지 모든 가능한 설계의 최소 대수는 아니다.
