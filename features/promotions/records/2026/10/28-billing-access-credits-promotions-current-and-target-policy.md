## 1. 확인 범위와 상태 표시

- 코드: 준비한 6개 작업 저장소의 실제 소스, 테스트, Git 상태. API는 최신 dev `b2aead8e99270f6a71384668b38b3fa095ddbf6f` + 추가 크레딧 승인 검사 관련 미커밋 6파일.
- 실제 상품 설정: 개발 서버와 현재 로컬 API의 공개 상품 응답을 직접 조회했다. 무료체험·재시도·DB 단가는 **로컬 관리자 DB를 읽기 전용 거래로 조회**했다. 회원 정보나 결제 데이터는 조회·변경하지 않았다.
- 운영 API는 공개 상품 조회가 HTTP 502로 실패했다. 운영 DB 값이나 운영 배포 revision을 개발·로컬 값과 동일하다고 쓰지 않는다.
- 이 현황 조사에서는 제품 소스·DB·서버를 수정하지 않았다. 마지막 제품 수정의 검증 결과는 API 4,845개 통과·69 skip, 빌드 통과이며 별도 기록을 따른다.
- 아래 ‘기존 구현’은 코드에 이미 존재한다는 뜻이다. ‘작업 브랜치 구현’은 이번 세션의 미커밋 변경이며 원격 dev/현재 실행 서버에 반영됐다는 뜻이 아니다. ‘기반만 있음’과 ‘기술 실험’은 사용 가능한 제품 기능과 구분한다.

## 2. 현재 이용권과 실제 상품

### 2.1 개념

| 구분 | 현재 역할 |
|---|---|
| 등급 | Basic·Pro·Business. 내부에는 무료체험용 `trial`도 있으나 유료 판매 등급이 아니다. |
| 판매 상품 | 같은 등급의 월간·연간 등 결제 주기와 금액. 등급과 결제 주기는 별개다. |
| 구독 | 회원이 동의한 상품·금액·주기와 다음 결제·실패·해지·변경 예약 상태. |
| 이용권 | 어떤 등급을 언제부터 언제까지 적용하는지. 유료 구독, 관리자 지급, 프로모션 지급의 출처를 기록한다. |
| 크레딧 지급분 | 지급량·남은 양·지급일·만료일·출처를 각각 보존한다. 여러 지급분을 합쳐 사용 가능한 총량을 표시한다. |
| 결제 주문 | 실제 청구액·결제 결과·구매 당시 상품 조건과 혜택 반영 상태를 보존한다. |
| 프로모션 등록 | 어느 회원이 어느 캠페인의 코드를 사용했으며 무엇을 지급받았는지 연결한다. |

현재 주 이용권은 회원당 한 개만 열려 있도록 관리한다. 주 이용권의 출처는 `subscription`, `admin_plan`, `promotion`이다. 무료체험은 같은 이용권 지급 테이블의 별도 기간제 이용권으로 생성되지 않고, 가입 1회 지급과 연결된 참여 정보로 관리한다.

### 2.2 현재 개발·로컬 상품값

두 환경의 아래 가격·수량은 직접 조회 결과가 같다. **연간 금액은 한 번에 결제하는 전체 금액**이며 크레딧은 매월 지급한다.

| 등급 | 매월 크레딧 | 월간 금액 | 연간 총액 |
|---|---:|---:|---:|
| Basic | 400 | 5,900원 | 58,800원 |
| Pro | 1,000 | 10,900원 | 82,800원 |
| Business | 4,000 | 29,900원 | 234,000원 |

| 추가 상품 | 지급 크레딧 | 금액 | 결제 성공 후 유효기간 |
|---|---:|---:|---:|
| 추가 크레딧 400 | 400 | 5,900원 | 30일 |
| 추가 크레딧 1,000 | 1,000 | 10,900원 | 30일 |
| 추가 크레딧 4,000 | 4,000 | 29,900원 | 30일 |

같은 추가 상품은 요금제에 따라 금액이나 수량을 바꾸지 않는다. 400개·1,000개·4,000개 상품 사이의 단가는 다를 수 있다. 같은 상품을 Basic 회원과 Pro 회원에게 다른 가격으로 파는 구조가 아니라는 뜻이다.

### 2.3 현재 무료체험

로컬 정책의 실제 값은 **가입 1회 400크레딧, 가입 시점부터 30일, 활성화됨**이다. 지급이 지연되어도 만료 기준을 나중 지급 시점으로 밀지 않는다. 반복·동시 호출도 한 번만 지급한다. 현재 관리자 화면에서 초기 크레딧·활성 여부는 편집하지만 30일 값은 편집 가능한 입력으로 노출하지 않는다.

현재 공통 이용 상태 조회는 주 이용권 → 사용 가능한 무료체험 → 없음 순서다. 무료체험 조회는 그 400 지급분의 잔액·만료에 연결돼 있다. 따라서 유효한 주 이용권이 없고 400이 소진/만료되면 공통 조회의 trial이 사라질 수 있다. 한편 크레딧 대시보드의 무료체험 혜택 진행 표시는 잔액 0이어도 만료 전까지 남기는 별도 처리가 있다. **기간이나 잔액과 무관하게 항상 존재하는 기본 상태는 아직 구현되지 않았다.**

## 3. 현재 크레딧 정책

### 3.1 출처와 만료

| 출처 | 지급·만료·이용권과의 관계 |
|---|---|
| 가입 무료체험 | 최초 1회 지급. 가입일 기준 유효기간. 유료 이용권 구매/종료가 이를 재지급하거나 연장하지 않는다. |
| 정기 구독 | 매월 지급하고 해당 월별 혜택 기간 종료 시 만료. 연간 구독도 매월 지급·만료하며 연말까지 누적되지 않는다. |
| 추가 구매 | 결제 주문에 저장한 유효일수로 결제 성공 시점부터 계산. 현재 판매 상품은 모두 30일. 구매 당시 이용권에 붙이지 않으므로 구독 종료나 변경 후에도 원래 만료일까지 사용 가능하다. |
| 프로모션 | 캠페인에서 정한 월 지급분과 각 지급분의 유효일수를 적용. 캠페인 종료·코드 중지·이용권 정상 종료 자체로 유효한 잔여분을 회수하지 않는다. |
| 관리자 이용권 | 관리자 지급 이용권의 월별 크레딧과 해당 월별 혜택 기간을 따른다. |
| 관리자 직접 크레딧 지급 | 해당 지급분에 기록한 수량·유효기간을 따른다. 별도 운영 지급 기록으로 남긴다. |

- 총잔액을 합쳐 표시해도 지급분별 출처·남은 양·만료일·결제/등록 연결은 지우지 않는다.
- 차감 순서는 **먼저 지급된 유효 크레딧부터**(`granted_at`, 동일 시 `id`)이다. 만료가 빠른 순서로 이번에 바꾸지 않는다.
- 유효한 지급분은 잔액이 있고 지급 시각이 도래했으며 만료되지 않았고 회수/환불 잠금 상태가 아니어야 한다.
- 현재 실제 차감은 이용권이 없어도 유효한 크레딧을 사용할 수 있다. 새 플러그인 제한이 연결되기 전이므로 현재 잔액 조건을 새 등급별 실행 제한과 동일시하지 않는다.
- 작업 차감은 실행 시작에 기록하고, 실패/정산에 따른 크레딧 반환은 원래 차감했던 지급분에 되돌린다. 이미 만료·회수된 지급분을 새 유효 크레딧으로 부활시키지 않는다.
- 구독 업그레이드 결제가 미확정인 동안 기존 정기 지급분을 일시 보류하는 기존 보호 처리가 있다. 추가 구매·무료체험·프로모션 등 다른 출처 전체를 같은 이유로 막지는 않는다.

### 3.2 추가 구매 자격

활성 유료 구독의 실제 이용 기간 또는 현재 활성 프로모션 이용권이 있어야 새로 구매할 수 있다. 해지 예약 상태라도 이미 결제한 기간 안이면 구매할 수 있다. 기본/무료체험만 있거나 관리자 지급 이용권만 있는 상태는 자격이 아니다.

추가 구매분을 **사용**하는 조건은 새로 **구매**하는 조건과 다르다. 이용권이 종료돼도 이미 산 유효 크레딧을 사용할 수 있다.

이번 세션에서 주문 생성 때와 **신규 승인 시작 직전** 같은 자격 검사를 공유하도록 보완했다. 자격이 없으면 승인 요청 전에 거절하고 기존 결제 결과 화면에서 이유를 안내한다. 이미 결제됐거나 승인 진행/복구 중인 주문은 기존 멱등 처리로 다룬다. 이 보완은 작업 브랜치에만 있다.

### 3.3 작업별 차감

크레딧 출처에 따라 같은 작업의 차감량을 달리하지 않는다. 구독 크레딧·추가 구매분·무료체험·프로모션 모두 같은 작업 단위를 사용한다.

과금 목록의 한 행은 ‘플러그인’이 아니라 **과금 작업**이다. 한 플러그인이 여러 작업을 가질 수 있다. 현재 코드에는 16개 과금 작업/14개 사용자 플러그인 ID가 있다. DB 단가는 관리자 수정값을 사용하며 기존 값을 seeder가 덮지 않는다. 다만 하이라이트 3종은 코드의 길이 구간표를 사용하고 관리자 DB의 `credit_cost`를 사용하지 않는다.

- 대사/안무/인물 하이라이트: 입력 영상 5분 미만 40, 5분 이상~20분 미만 80, 20분 이상~60분 미만 160, 60분 이상 200.
- 스토리보드: 요청 개수 × 단가. 완료 증거를 확인한 정산 경로가 별도로 있다.
- 베리에이션: 생성 영상 수 × 단가.
- 생성형 AI 숏폼 그림: 요청 그림 수 × 단가, 결과 수량 정산 경로가 있다.
- 나머지 작업은 해당 작업 단가와 계약을 따른다. 회사가 기존 원가 기준으로 정한 단가 체계를 이번 기능에서 재설계하지 않는다.

로컬 DB의 실제 행과 소스 기본값의 차이는 부록 A를 따른다. 실행 단가를 단순히 DB 숫자 하나로 오해하지 않도록 계산 단위까지 구분한다.

## 4. 현재 결제·구독 정책

### 4.1 첫 구독과 갱신

- 로그인 회원이 활성 판매 상품을 선택하고 상품·가격·결제 주기·크레딧 조건에 동의한다. 주문과 구독에 당시 조건을 저장한다.
- 첫 결제가 성공하고 혜택 반영이 완료돼야 유료 이용권과 첫 월 크레딧을 지급한다. 카드 등록 중·결제 대기·첫 결제 실패는 유료 혜택 지급 완료가 아니다.
- 첫 유료 계약은 결제 성공을 서버에 반영한 시각에 시작한다. 이후 갱신은 기존 계약 종료일을 기준으로 이어진다. 늦은 갱신 재시도 성공을 새 가입처럼 처리하지 않는다.
- 월간은 매월, 연간은 연간 전체 금액을 결제한다. 크레딧 지급 주기는 둘 다 월별이다.
- 월 기념일은 한국 달력 기준이며 해당 날짜가 없는 달에는 말일로 조정한다. 결제 기준일과 크레딧 혜택 기준일을 보존한다.
- 일반 갱신은 기존 구독 계약에 저장한 금액·조건을 사용한다. 관리자가 상품 가격을 수정했다고 이미 시작한 구독의 청구액을 다음 달 자동으로 현재 카탈로그 값으로 바꾸지 않는다.

### 4.2 실패·재시도·유예

로컬 실제 관리자 설정은 **유예 3일, 최초 실패 D+1·D+2 자동 재시도**다. 설정은 변경 가능하며 이미 시작한 실패 주기는 당시 설정을 보존한다.

| 상황 | 현재 처리 |
|---|---|
| 첫 결제 실패 | 구독은 pending. 같은 관리자 재시도 일정을 사용하지만, 아직 시작하지 않은 유료 이용권과 크레딧을 지급하거나 갱신 유예를 주지 않는다. 명확한 실패 상태에서는 수동 재시도도 가능하다. |
| 갱신 결제 실패 | past_due로 전환하고 유예 및 재시도 일정을 시작한다. 재시도마다 유예 기간을 새로 늘리지 않는다. |
| 결제 결과 불명확 | 기존 주문을 조회·대조해 확정한다. 모르는 상태를 확정 실패로 보고 새 결제를 무조건 시작하지 않는다. |
| 갱신 유예 종료 | 미확정 결제 처리와 기존 복구 조건을 확인한 뒤 유료 이용권을 종료하고 stopped로 전환한다. |
| 첫 결제의 자동 재시도 소진 | 자동 retryAt은 없어지며 수동 재시도 경로가 남는다. 확인한 코드에 첫 결제용 별도 유예 종료/자동 중단 시한은 없다. 새 정책으로 추가하지 않는다. |

관리자는 유예 1~30일, 최대 5개 재시도일을 설정할 수 있다. 재시도일은 증가 순서이고 각각 유예일수보다 작아야 한다. 첫 결제와 갱신에 같은 재시도 설정을 적용하는 기능은 이미 있다.

### 4.3 요금제 변경

- 상위 등급 등 허용된 즉시 변경: 현재 상태·결제 수단·미확정 주문·환불 진행 여부와 상품 조건을 확인하고 추가 결제한다.
- 하위 등급 변경: 현재 결제 기간 종료 후 적용하도록 예약한다. 연간 구독은 해당 연간 계약 종료 시점이다.
- 연간→월간은 등급과 관계없이 금지한다. 월간→연간은 같은 등급·상위 등급이면 즉시 변경하고, 하위 등급이면 현재 계약 종료 시점으로 예약한다.
- 즉시 변경은 5분 유효 견적과 원래 계약/사용량을 재확인한다. 추가 금액이 100원 미만이면 예약 변경으로 처리하는 기존 규칙이 있다.

즉시 변경 금액은 다음과 같다. 과거 상품 전체 가격 P, 새 상품 전체 가격 T, 남은 기간 비율에 따른 잔여 가치 A, 사용하지 않은 계약 크레딧 비율에 따른 잔여 가치 B에 대해 **청구액 = T − min(A, B)**이다. 각 잔여 가치는 원 단위로 내림한다. 사용량은 작업 차감에서 작업 반환을 반영한 순사용량이다. 기간 잔여 가치 A는 `floor(P × 남은 계약 시간 / 전체 계약 시간)`이며, 크레딧 잔여 가치 B는 `floor(P × (C−U) / C)`다. C는 기존 월 지급량 × 기존 결제 주기 개월 수이고, U는 기존 계약 기간에 지급된 정기 크레딧의 순사용량이다.

즉시 변경 결제가 성공하면 **새 상품의 전체 계약 기간을 그 시각부터 시작**하고, 기존 정기 지급분의 잔여분을 정리한 뒤 새 상품의 첫 월 전체 크레딧을 지급한다. 추가 구매·가입 혜택 등 무관한 지급분은 새 정기 지급분으로 변환하지 않는다.

### 4.4 해지·결제수단

- 일반 해지는 다음 자동 결제를 중단하는 처리다. 이미 결제한 기간까지 이용하며 원화 환불을 자동으로 수행하지 않는다.
- 해지 예약 상태에서 재개하는 기존 경로가 있다. 기간과 유효한 등록 결제수단 조건을 검사한다.
- 카드 등록·변경, 마스킹된 카드 정보 확인, 이전 키 정리·실패 복구가 구현돼 있다. 전체 카드번호나 평문 결제 키를 회원 화면에 저장하지 않는다.
- 갱신 실패 상태에서 결제수단을 변경하려면 실패한 갱신 상품명·금액과 변경 후 재결제에 명시적으로 동의해야 하며, 변경 완료 후 갱신 재시도를 수행한다. 첫 결제 실패 상태의 결제수단 변경은 그 자체로 즉시 재결제하지 않는다.
- 신규 카드 등록 전 abandoned checkout은 30분 정리 대상이다. 카드 등록이 완료된 첫 결제 예약까지 30분 후 자동 취소된다는 의미는 아니다.

### 4.5 현재 환불

일반 해지와 환불은 별개다. 환불은 관리자 권한으로 조건을 조회·생성·실행하며, 현재 생성 가능한 일반 환불 정책은 다음과 같다.

| 대상 | 현재 조건과 처리 |
|---|---|
| 월간·연간 정기 구독 | 현재 계약에 지급된 정기 크레딧의 **순사용량이 0**이어야 한다. 사용한 정기 크레딧이 있으면 일반 환불 불가. 연간의 사용한 달을 빼고 비례 환불하는 정책은 현재 생성 경로에 없다. |
| 미사용 정기 크레딧의 만료 | 만료 자체를 사용으로 세지 않으므로, 과거 월 지급분이 미사용으로 만료된 사실만으로 환불을 막지 않는다. 실제 생성에는 구독 상태와 결제/공급자 조건도 필요하다. |
| 추가 크레딧 | 해당 구매분이 미사용·활성·미만료이며 전체 잔량이 최초 지급량과 같을 때 전액 환불. 이용권과 무관한 다른 크레딧이나 구독을 함께 회수하지 않는다. |
| 부분 금액 입력 | 일반 환불 생성에서는 임의 부분 환불을 허용하지 않는다. 연간도 동일하다. 내부에 부분 취소 관련 자료형이 있다고 현재 상품 정책이 부분 환불이라는 뜻은 아니다. |
| 즉시 변경 후 현재 계약 | 현재 계약을 시작한 업그레이드 차액 결제를 환불 대상으로 삼는다. 앞선 이미 교체된 계약의 원결제를 같이 돌려주는 구조가 아니다. |
| 혜택 회수 시점 | 환불 진행 중 대상 지급분을 잠그고, 모든 원화 환불 항목 완료 후 대상 지급분을 회수하고 유료 이용권을 종료한다. 돈 환불 완료와 내부 반영 실패를 별도 상태로 관리해 재시도한다. |

환불 건을 생성하면 다음 자동 결제를 중단하고 기존 요금제 변경 예약을 지운다. 이 처리는 모든 원화 환불이 완료되기 전에 적용한다.

‘사용량’은 작업 차감에서 작업 크레딧 반환을 뺀 순사용량이다. 만료·운영 회수는 작업 사용량으로 세지 않는다. 현재 환불 evaluator에는 ‘결제 후 N일’이나 연간 사용 개월 수 비례 계산이 없다. 실제 생성은 active/past_due/cancel_at_period_end 등 허용 구독 상태와 결제 조건을 함께 검사한다.

기존 테스트·도메인에 남아 있는 사용한 연간 월을 유지하는 `benefit_period_end` 처리는 현재 일반 환불 자격/생성 경로가 만들어 내지 않는다. 이를 현재 정책으로 다시 제시하지 않는다.

## 5. 현재 프로모션·레퍼럴

### 5.1 캠페인과 등록

- 캠페인 아래 복수 코드를 발급한다. 캠페인이 이용권 등급·이용 개월 수·크레딧 유효일수·등록 기간·코드별 상한·과거 이력 제한을 공유한다. 추천인은 코드별 선택값이다.
- 현재 혜택은 **이용권 지급형만** 지원한다. Basic/Pro/Business 이용권과 해당 등급의 월별 크레딧을 지급한다. 일회 크레딧만 주는 종류는 없다.
- 코드는 대문자·숫자·밑줄·하이픈 5~20자이며 대문자로 정규화한다. 전체 코드에서 고유하다.
- 캠페인과 코드의 상태는 독립이다. 둘 다 활성이고 등록 기간 안이어야 한다. 캠페인 비활성화는 코드 저장 상태를 일괄 중지시키지 않는다. 신규 참여 가능 여부를 막는다.
- 코드가 없거나 종료일이 지난 캠페인은 활성화할 수 없다. 종료 캠페인은 스케줄러가 비활성화하며 등록 시에도 기간을 검사한다.
- 상한은 **코드별 누적 성공 건수**다. 캠페인에서 2건을 설정하면 A·B 코드가 각각 2건 가능하다. 회수해도 상한이나 참여 이력을 되돌리지 않는다.
- 회원당 같은 캠페인에서 코드 한 개만 등록할 수 있다. 같은 코드 재등록·다른 코드 등록 모두 막으며 회수 후에도 재등록하지 못한다.
- 다른 캠페인의 과거 참여 이력과 무료체험 이력 자체로 등록을 막지 않는다.
- 과거 이력 제한 선택지는 유료 이용권 결제·사용 이력과 관리자 지급 이용권 이력이다. 추가 구매만 했다는 이력은 유료 구독 이력으로 보지 않는다. 실제 캠페인 적용은 운영자가 선택한다.
- 현재/시작 예정 주 이용권 또는 첫 결제 진행·예약 중 구독이 있으면 새 프로모션 이용권을 겹쳐 지급하지 않는다. 무료체험만 있는 경우는 등록 가능하다.
- 코드 확인 때 등록 가능 여부·혜택·거절 이유를 보여주고 실제 등록 시 거래 안에서 다시 검사한다. 회원·캠페인 중복과 코드별 상한은 잠금 및 DB 고유 제약으로 보호한다.

### 5.2 혜택과 운영 변경

- 등록 즉시 이용권과 첫 월 크레딧을 지급하고 이후 월별 크레딧을 지급한다.
- 캠페인 종료·코드 중지·프로모션 이용권의 정상 종료는 유효한 지급 크레딧을 자동 회수하지 않는다.
- 등록 혜택 회수는 사유를 남기고 그 이용권을 종료하며 해당 등록의 미사용 프로모션 크레딧을 회수한다. 사용 내역과 별도 구매/지급분은 유지한다. 기존 관리자 지급 외 별도 복구 기능은 없다.
- 캠페인은 등록 이력이 전혀 없을 때 삭제 가능하다. 회수 이력도 이력이므로 삭제하지 않는다. 개별 코드만 삭제하는 별도 endpoint/UI는 현재 없다.
- 등록 후 캠페인 이름·종료일 연장·상한 조정은 가능하지만, 시작일·등급·이용 개월 수·크레딧 유효일수·이력 제한은 고정한다. 상한은 어느 코드의 누적 성공 건수보다 낮출 수 없다.
- 개별 코드의 문자열·추천인은 그 코드의 등록 이력이 없을 때만 수정한다. 캠페인/코드 상태 변경·등록 회수·수정·삭제 등은 운영 기록을 남긴다.

### 5.3 프로모션 종료 후 유료 예약

- 프로모션 이용권 사용 중 종료일에 첫 유료 결제를 시도하도록 예약할 수 있다. 현재 등급 상품 또는 기존 요금제 선택 화면에서 다른 상품을 고른다.
- 카드 등록이 끝나야 완료된 예약이다. 미완료 카드 등록을 예약 완료로 표시하지 않는다. 예약 상태/취소는 회원 대시보드에 있다.
- 동의한 날짜 전에는 청구하지 않고 성공 후에 유료 혜택을 지급한다. 첫 실패 재시도는 기존 관리자 설정을 사용하고 첫 유료 혜택에 갱신 유예를 주지 않는다.
- 회원이 결제 전 예약을 취소해도 현재 프로모션 혜택은 유지한다.
- 관리자가 프로모션 혜택을 회수해도 별도로 동의한 첫 결제일을 당기거나 예약을 자동 취소하지 않는다. 회수와 예약 유지 사실을 알린다.

### 5.4 현재 성과 연결과 정산

- 성과는 등록 ID에 연결된 주문/구독을 사용한다. 가장 최근 코드나 첫 코드를 임의 추측하지 않는다.
- 활성 프로모션 이용권에서 신청한 첫 유료 예약과 당시 추가 크레딧 구매에 등록 ID를 붙인다.
- 그 ID로 시작한 유료 구독의 갱신·즉시 변경은 같은 연결을 유지한다. **연결된 동일 구독이 1년 이상 계속돼도 별도 귀속 만료 조건은 없다.**
- 훗날 독립적으로 새로 시작한 구독은 과거 코드에 자동 연결하지 않는다.
- 이미 유료 구독 상태에서 별도로 산 추가 크레딧은 과거 프로모션 구독 ID를 추정해 붙이지 않는다. 현재 topup의 귀속은 주문 생성 당시 활성 프로모션 이용권 경로에만 있다.
- 성과 표의 한 행은 회원의 코드 등록 1건이다. 코드·회원·등록일 필터가 있고, 선택한 등록과 연결된 이후 결제·사용을 계속 포함한다.
- 첫 결제·갱신·즉시 변경·추가 구매의 금액/환불액, 순결제액과 유료 전환을 구분한다. 순결제액은 결제액에서 누적 환불액을 뺀다.
- 사용량은 해당 등록 ID의 프로모션 지급분과 연결 주문/구독의 정기·추가 구매 지급분을 각각 집계한다. 가입 기본 400, 관리자 지급, 무관한 구매분 등 회원의 전체 사용량을 이 코드의 성과로 합산하지 않는다.
- 현재 전환 건수는 첫 결제 성공을 기준으로 하므로 나중에 전액 환불돼도 전환 이력은 남고 금액/순액에 환불이 반영된다.
- XLSX 내보내기를 제공한다. 화면 회원 표시는 이메일을 보강하지만 현재 XLSX 회원 식별자는 ID다.
- 인플루언서 지급액 자동 계산·송금·정산은 구현 범위가 아니다. 회사가 조회/내보내기 자료로 정산하는 기존 범위를 유지한다.

## 6. 현재 플러그인/관리자 기능

- 개발 서버 카탈로그의 Basic/Pro/Business는 모두 `all`이며 14개 등록 플러그인을 반환한다. 요금제별 실행 차등은 현재 적용되지 않는다.
- 허용 목록 저장 테이블, all/allowlist 모드, 목록 교체 API, 관리자 API client는 있다. 그러나 /plans 화면에 선택 UI가 없고 신규 등급은 all로 만든다. **저장 기반만 있는 상태**다.
- `allowsPlugin` 메서드는 있지만 제품 실행 경로에서 호출하지 않는다. 작업 견적/시작은 현재 과금 작업과 잔액을 검사한다.
- Desktop 작업 생성/예약/재시작의 검사 연결점은 있으나 현재 LicensePolicyService는 항상 허용한다. 라우트 guard는 설치 여부를 검사한다.
- 스토어는 로컬 Python manifest·Nest executor·가상 워크플로와 Angular 정적 메타데이터를 결합한다. 과금 정책 목록과 공통 상품용 카탈로그로 동기화돼 있지 않다.
- 카테고리 이름/소속/기본 순서는 TypeScript의 정적 배열이다. 관리자 CRUD/순서/배정 메뉴는 없다.
- 현재 코드 분류는 하이라이트 추출 3, 영상 자동제작 6, 영상 편집·변형 2, 영상 구성 3의 총 14개다.
- 스토어는 분류 내부 지정 순서를, 사이드바는 일반 분류 내부 설치 순서를 적용한다. 즐겨찾기는 회원 개인 순서를 사용한다.

## 7. 이번 대화에서 정한 변경 방향

### 7.1 지속 기본 상태와 플러그인 허용

- 유료 요금제 3등급과 기본 상태를 합쳐 4가지 이용 상태로 표현한다. 무료체험/기본 상태의 최종 표시명은 미정이다.
- 유효한 주 이용권이 없으면 기본 상태가 항상 존재한다. 가입 400 소진/만료가 기본 상태 자체를 없애지 않는다.
- 가입 크레딧은 최초 1회 지급 혜택이다. 기본 복귀마다 다시 주거나 무기한화하지 않는다.
- 기본·Basic·Pro·Business의 허용 플러그인은 회사가 각각 지정한다. 기본 목록을 Basic과 강제로 같게 만들지 않는다. 회원이 임의 N개를 고르는 구조가 아니다.
- 유효한 주 이용권이 있으면 그 등급, 실제로 종료되면 기본 허용 목록을 사용한다. 해지 신청과 결제 실패 유예의 기존 기간 규칙을 바꾸지 않는다.
- 사용할 수 있는 플러그인과 충분한 크레딧은 별도로 검사한다. 금액을 지불해 받은 크레딧이 남아 있어도 이전 Pro/Business 권한을 유지하는 것은 아니다.
- 같은 작업의 차감량은 크레딧 출처로 나누지 않는다. 신규 추가 구매 가격도 같은 상품이면 요금제별 동일하고, 자격은 활성 유료/프로모션 이용권에만 준다. 30일과 기존 차감 순서는 유지한다.

### 7.2 가입 코드와 크레딧 전용 혜택

- 가입 필수 동의 화면에 선택 코드 입력을 추가한다.
- 유효한 크레딧형 코드를 등록하면 예를 들어 가입 400 + 프로모션 200을 출처별로 지급받는다. 200은 예시다.
- 이 코드는 이용권을 주지 않으므로 그 사실만으로 Basic/Pro/Business가 되지 않는다. 기본 플러그인 목록을 적용한다.
- 기존 이용권 지급형 프로모션을 없애겠다는 지시는 없다. 기존 기능은 유지하고 크레딧 전용 혜택을 추가하는 전제로 범위를 정리한다.
- 캠페인·참여·크레딧 연결은 재사용하지만, 현재 이용권 필수 캠페인/조회/회수/예약 전제를 분리해야 한다.

### 7.3 공통 카탈로그와 운영 화면

- 플러그인 관리에서 공통 플러그인 목록과 카테고리 CRUD, 카테고리 순서, 소속과 스토어 내부 순서를 관리한다.
- 요금제 허용 선택과 과금 작업 연결, 앱 스토어가 동일한 플러그인 ID/목록을 사용한다. 과금 작업과 플러그인을 1:1로 억지로 합치지 않는다. 무료 기능도 카탈로그에 포함 가능해야 한다.
- 관리자 /plans에 기본·유료 등급별 허용 목록 선택 UI를 추가한다.
- 카테고리 이름/순서/소속은 공통 정보를 소비하지만 **사이드바 분류 내부 설치 순서와 즐겨찾기 개인 순서는 그대로 유지**한다. 스토어의 분류 내부 순서는 관리자 설정을 사용한다.
- 개발 등록 목록을 빌드/배포 절차에서 동기화하고, 새 플러그인은 설정 대기 → 관리자 설정 → 공개로 이어가는 방향이다. 재동기화는 운영 설정을 덮지 않는다. 새 구현이 발견됐다는 이유만으로 자동 공개/사용 허용하지 않는다.
- 실행 요청을 처리하는 서버에서도 현재 공개 상태/허용 등급을 확인한다. 과금 없는 플러그인도 권한 검사가 필요하다.

## 9. 다른 팀에 확인할 정책과 운영값

### 9.1 새 유형 때문에 실제로 필요한 정책 확인

| 항목 | 확인할 내용 | 이유/현재 상태 |
|---|---|---|
| 크레딧형 가입 코드의 유료 전환 성과 | 어떤 첫 결제를 해당 코드의 성과로 인정할지, 등록/가입 후 인정 기간을 둘지, 여러 크레딧형 등록이 공존하면 중복 귀속을 어떻게 막을지 | **새 유형의 결정 필요.** 현재 귀속 출발점인 활성 프로모션 이용권이 존재하지 않는다. 기존 이용권형의 예약/후속 갱신 규칙을 다시 결정하자는 뜻은 아니다. |
| 가입용 코드의 사용 경로/대상 | 크레딧형 코드를 가입할 때만 쓸지, 가입 후에도 기존 코드 등록 화면에서 쓸지. 가입 화면에서 기존 이용권형 코드도 받을지 | 이번 요구는 가입 시 크레딧 지급 예시까지다. 이 범위가 등록 자격·가입 화면의 혜택 표시와 성과 기준에 영향을 준다. 기술적으로 임의 확대하지 않는다. |
| 잘못 입력한 선택 코드의 가입 흐름 | 코드를 수정/비운 뒤 계속하도록 할지, 명시적으로 혜택 없이 가입을 선택할 수 있게 할지 | 기획 UX 확인 항목이다. 추천은 오류를 안내하고 수정 또는 코드 없이 계속할 선택을 주며, 보너스가 사라진 채 자동 가입시키지 않는 방식이다. 아직 확정된 요구로 취급하지 않는다. |

크레딧형 성과의 논의 가능한 예시는 ‘가입 코드 기록은 신규 유입 출처로 보존하고, 가입 후 회사가 정한 기간 안의 첫 구독 결제만 직접 전환으로 인정’하는 것이다. **제안일 뿐 선택한 규칙이나 확정된 기간이 아니다.** 크레딧형도 일반 캠페인 혜택 종류로 지원하되, 여러 등록이 공존할 수 있는 경로에서는 어느 등록의 첫 전환으로 인정할지 규칙이 필요하다. 첫 결제를 연결한 뒤 동일 구독의 갱신·즉시 변경·환불 연결은 기존 정책을 유지하며, 이를 다시 결정 대상으로 올리지 않는다. 단지 잔액이 어느 출처에서 차감됐는지만으로 구매 원인을 확정하지 않는다.

### 9.2 회사가 채워야 할 설정값 — 기능 개발을 막는 미정 정책과 구분

- 기본/Basic/Pro/Business의 실제 허용 플러그인 목록. 같거나 다르게 지정할 수 있다. 상위 목록을 코드에서 임의 상속시키지 않는다.
- 가격이나 지급량을 바꾼다면 새 월간·연간 금액, 월 크레딧과 할인 표시값. **변경 지시가 없으면 현재 값 유지**이며, 저장할 구조를 만들기 위해 새 숫자를 먼저 받아야 하는 것은 아니다.
- 가입 보너스 캠페인의 실제 크레딧 수량과 지급분 유효기간. 200은 예시다. 캠페인 운영 설정으로 받을 값이다.
- 기본 상태의 최종 표시명. 내부 코드·DB 키 설계는 개발에서 결정할 기술 사항이다.
- 실제 코드 문자열·시작/종료일·상한·추천인 등 캠페인 실행값은 기존 관리자 입력 사항이다. 기능 설계 전에 정답을 요구하지 않는다.

### 9.3 다시 정책 결정 대상으로 올리지 않을 항목

- 연간 구독의 월별 지급/만료, 기존 변경 계산·적용 시점, 기존 환불·해지·재시도·유예.
- 유효 추가 크레딧의 30일과 구매 자격, 동일 추가 상품의 요금제 공통 가격, 기존 FIFO.
- 가입 크레딧 최초 1회, 같은 캠페인 1회, 다른 캠페인 이력/무료체험 이력 제외, 코드별 상한.
- 기존 이용권형 프로모션 회수 범위·재등록 금지·예약 유지·성과·XLSX 및 회사의 외부 정산.
- API/DB 계약, 재사용 컴포넌트, 소스 등록 artifact, 배포 인증, 캐시/동기화 구현은 개발 설계 사항이다. 이를 전략실이 정해야 할 상품 정책으로 넘기지 않는다.

## 10. 실제로 바뀔 구현 구성

1. Web API: 지속 기본 상태 조회, 공통 카탈로그와 공개/분류 데이터, 등급별 허용 저장의 완성, 실행 검사, 크레딧형 캠페인과 가입 보너스/참여/회수/조회/성과 연결.
2. 회원 웹: 가입 선택 코드와 혜택/오류 안내, 새 기본 상태 표시, 크레딧형 참여 내역, 기존 결제/예약 화면과의 연결.
3. 관리자 웹: 플러그인 관리·분류/순서/공개와 /plans의 기본·등급별 허용 목록, 캠페인 혜택 종류 및 크레딧형 입력/내역/성과 표시.
4. Desktop Angular: 공통 목록/분류 소비, 현재 허용 정보로 스토어/진입/실행 표시, 기존 설치·즐겨찾기 순서 보존.
5. Desktop NestJS/Electron: 실제 구현과 공통 공개 목록 대조, 실행 생성/예약/재시작의 허용 검사, 등록 artifact 생성/배포 동기화 연결. 기능 구현 파일을 관리자 등록만으로 설치 앱에 새로 만들어 주는 구조는 아니다.

세부 DB 계약과 실제 담당 저장소는 최종 설계에서 확정한다. 이 목록은 현재 승인된 요구에 필요한 구현 구성으로, 해당 전체 구현이 이미 끝났다는 뜻이 아니다.

## 11. 확인된 정합성/환경 주의점 — 새 회사 정책 질문이 아님

1. **환불 미리보기와 생성의 상태 조건 차이:** 사용량/금액 evaluator는 구독 상태를 직접 제한하지 않지만 실제 생성은 허용 상태를 제한한다. 종료 구독에서 미리보기는 가능처럼 보이고 생성은 거절될 수 있다. 기존 정책에 맞춰 화면/검사 일치 여부를 보완할 코드 점검 항목이다.
2. **오래된 문서·테스트의 다른 시점 정책:** 8월 설계의 무료체험 없음 또는 현재 일반 생성 경로가 쓰지 않는 연간 부분 환불 처리 등을 현행 정책으로 되살리지 않는다.
3. **코드와 현재 로컬 실행본 차이:** 개발 공개 카탈로그는 플러그인 14개, 로컬 실행 API는 13개(생성형 AI 숏폼 없음)다. 로컬 과금 DB도 13행이고 현재 소스 정의 16개 중 생성형 AI 3개 작업이 없다. 상품 가격은 같더라도 실행 중인 로컬 기능이 준비한 최신 코드와 같다고 볼 수 없다. 이번 조사에서 서버 재시작·자동 seeding을 하지 않았다.
4. **새 혜택 종류의 기존 이용권 전제:** 현재 회원 참여 내역은 이용권과 INNER JOIN하고 회수도 이용권 존재를 요구한다. 크레딧형 지급만 추가하고 이 경로를 그대로 두면 내역/회수가 맞지 않는다. 새 종류 구현에 포함할 기술 작업이다.
5. 가격 우회 관점에서 같은 추가 상품의 공통 가격은 등급 변경을 통한 구매 가격 차익을 만들지 않는다. 할인된 정기 크레딧은 정해진 월 기간 안에서 사용하고 만료하며 새 추가 구매분으로 변환하지 않는다. 실제 새 가격표의 상품 간 비교는 회사가 바꿀 값으로 검토하되, 이 때문에 기존 과금 작업 단가를 새 정책으로 다시 정하지 않는다.
