# 가입 프로모션 크레딧·요금제별 플러그인 접근 — 현재 구조 조사

2026-10-28 KST. 상태: **새 브랜치 준비·소스 조사 완료, 설계 논의 중**. 이 문서는 전체 신규 기능의 구현 승인을 받은 최종 설계가 아니다. 최초 조사에서는 제품 소스를 수정하지 않았다. 후속으로 사용자가 요청한 추가 크레딧 승인 전 자격 검사만 보완했다. [현재 정책 구분·보완·검증](28-topup-confirmation-access-and-existing-policy-check.md).

## 사용자가 전달한 변경

- 가입 필수 동의 화면에서 프로모션 코드를 선택 입력한다.
- 유효한 코드라면 기본 무료체험 400에 프로모션 출처의 추가 크레딧(예: 200)을 더해 총 600 상태로 서비스를 시작한다. 200은 예시이며 캠페인 지급값이다.
- 요금제마다 허용 플러그인 종류를 다르게 한다. 추가 확인 답변: **회사가 요금제별 사용 가능한 플러그인을 지정한다.** 회원이 N개를 직접 고르는 방식이 아니다.
- 관리자 /plans의 설정 UI와 /operation-policies·앱 스토어의 플러그인 목록 출처를 확인하고, 플러그인 관리 메뉴 필요성과 역할을 검토한다.

## 확인된 현재 구조

### 크레딧 정책 목록

관리자 `OperationPoliciesApiService.listPolicies()`는 `GET /admin/operation-policies`를 호출한다. 서버 `OperationPolicySeeder`가 `OPERATION_DEFINITIONS`를 관리자 DB `operation_policies`에 추가하며 기존 행을 덮지 않는다. 목록 응답은 현재 정의에 있는 operationKey로 필터링된다.

이 표의 한 행은 플러그인이 아니라 **과금 작업 하나**다. `shortform_explainer` 플러그인에는 `.script`, `.visuals`, `.video` 세 과금 작업이 있다. 현재 Web API의 `REGISTERED_PLUGIN_KEYS`도 이 작업 정의에서 pluginKey를 뽑아 만든다. 과금 작업이 없는 기능은 이 방식으로 목록에 잡히지 않는다.

주요 소스: API `src/modules/operations/{domain/operation-definitions.ts,application/operation-policy-seeder.ts,application/operations.service.ts,infrastructure/typeorm-operations.repository.ts}`.

### 요금제 허용 목록

Web API에 `entitlementMode=all/allowlist`, `plan_plugin_entitlements`, `PUT /admin/catalog/tiers/:id/plugins`가 이미 존재한다. 관리자 API client에도 replaceTierPlugins가 있다. 현재 /plans 화면은 플러그인 설정을 숨기며, 새 등급을 만들 때 all로 저장한다. 일반 등급 수정 patch는 entitlementMode 자체를 바꾸지 않는다.

`EffectiveAccessService.allowsPlugin`은 등록된 pluginKey와 해당 목록을 판단하지만 현재 production 호출자가 없다. OperationsService의 quote/start도 실제로는 크레딧을 확인하며 이 판정을 호출하지 않는다. 따라서 저장 UI를 추가하는 것만으로 실제 실행이 제한되지는 않는다.

주요 소스: API catalog controller/service/repository, access/application/effective-access.service.ts; admin plans.component.ts:288 및 plans.component.html:64.

### 앱 스토어

Angular 스토어는 로컬 Nest `GET /plugins` 응답을 받는다. Nest는 실제 Python manifest·Nest executor·정적 virtual workflow 카탈로그를 합친다. 패키징 앱은 Electron이 resources 안의 manifest를 읽는다. Angular는 다시 빌드에 등록된 14개 사용자 기능 목록으로 필터링하고 표시 이름·순서를 덮는다. Web API의 상품용 플러그인 카탈로그를 받는 구조가 아니다.

현재 원격 /access/current의 allowedPluginKeys는 계정 정보로 전달되지만 스토어·설치·시작 판정에는 연결되어 있지 않다. 데스크톱 LicensePolicyService.canStartPluginJob는 현재 항상 allowed:true를 반환한다.

사용자 기능 ID와 실행 보조 모듈 ID를 구분해야 한다. 예를 들어 shortform_director는 storyboard 표시 별칭을 쓰며, clipper_video_render와 tts_supertonic은 여러 기능이 공유하는 내부 모듈이다. 관리자에서 이 내부 모듈을 독립 판매 플러그인처럼 체크하게 만들면 안 된다.

주요 소스: desktop Angular core/plugins/plugin-status.service.ts, core/navigation/app-navigation-metadata.ts; Nest modules/plugins/domain/plugin-catalog.ts, workflows/application/workflow-executor-registry.service.ts, core/auth/license-policy.service.ts; Electron main/plugin/plugin-manager.ts.

### 가입·추가 크레딧

기존 프로모션 등록은 항상 Basic/Pro/Business 이용권을 만들고 그 등급의 크레딧을 지급한다. 추가 200만 지급하려면 이용권 없는 크레딧 혜택 유형을 지원해야 한다. 캠페인 설정, 지급·이력·회수·조회가 accessGrantId를 필수로 가정하는 부분을 조정한다. 기존 크레딧 원장과 프로모션 등록 ID는 재사용할 수 있다.

가입은 사용자 DB에서 티켓 소비·회원 생성·필수 동의·무료체험 지급 대기 작업을 함께 저장하고 실제 크레딧은 관리자 DB의 후속 처리로 지급한다. 가입 후 보너스 API를 단순히 한 번 호출하면 이탈/재시도 때 누락이 생길 수 있다. 기존 지급 대기·중복 방지 구조를 확장하는 방향을 검토한다.

**현재 실제 차감은 이용권과 독립적이다.** CreditGrantsService의 summary/consume은 유효한 모든 출처를 합산/차감하며, source=promotion/accessGrantId=null인 크레딧도 자체 만료까지 사용할 수 있다. 무료체험 400 소진 때문에 프로모션 200의 차감이 막히는 현행 규칙은 없다. EffectiveAccess.spendableCreditSources=['free_trial']만 읽고 반대로 결론내리면 안 된다. 해당 필드는 현재 실제 차감에 사용되지 않는다.

다만 새 플러그인 제한을 적용할 때는 무료체험 잔액 0만을 이유로 남은 프로모션/추가 구매 크레딧의 사용 경로까지 막지 않도록, 무료 회원의 기능 허용 정책과 크레딧 잔액을 분리해야 한다. 무료체험을 Basic/Pro/Business와 같은 상품 등급이라고 표현하지 않는다.

## 논의용 제안 — 아직 확정 아님

1. Web API에 사용자에게 제공하는 플러그인의 공통 카탈로그를 둔다. 요금제 허용 목록, 과금 작업의 소속, 앱 스토어의 상품 정보가 같은 pluginKey를 참조한다. 로컬 앱은 실행 구현·설치 상태·지원 여부를 제공한다.
2. /plans의 기존 ‘요금제 등급’ 수정 UI에 ‘사용 가능한 플러그인’ 체크 목록과 선택 수를 추가한다. 목록 표에는 ‘N개 사용 가능’을 보여준다. 월간/연간 상품은 그 등급 설정을 공유한다.
3. 별도 ‘플러그인 관리’ 메뉴는 목록의 명칭·설명·분류·표시 순서·스토어 노출 및 연결된 과금 항목/요금제 확인에 쓴다. 등급별 허용 체크는 /plans에 둔다. 임의 ID를 입력해 실행 코드가 없는 플러그인을 생성하는 기능은 불필요하다.
4. 빠른 대안은 메뉴 없이 /plans 설정만 추가하는 것이지만, 현재 여러 곳에 있는 상품용 목록의 관리 문제는 남는다. 플러그인 운영 정보까지 공통화할 목적이면 위 별도 메뉴가 더 자연스럽다.
5. 가입 보너스는 ‘크레딧만 지급’ 혜택 유형으로 표현한다. 이용권형을 함께 유지할지/앞으로 신규 캠페인을 어떻게 제한할지는 확정 전이다.

미확정: 무료 회원의 허용 플러그인 목록, 코드 오류/상한 도달 시 가입 UX, 보너스 만료 정책, 이용권 없는 등록의 후속 유료 전환 귀속. 구체적 Basic/Pro/Business별 플러그인 선택값을 임의로 정하지 않았다. 새 공통 카탈로그의 저장/배포 상세도 최종 설계에서 결정한다.

## 추가 논의 — 플러그인 카테고리와 표시 순서의 관리자 관리

사용자가 관리자 ‘플러그인 관리’에서 카테고리 생성/이름 수정/삭제/순서 변경, 플러그인의 카테고리 배정/이동 및 카테고리 내부 순서 변경까지 가능한지 문의했다. 구현 승인은 아직 받지 않은 논의 단계다.

확인된 현행:

- Desktop Angular `src/core/navigation/app-navigation-metadata.ts:98-129`에 NavGroupId 타입과 NAV_GROUPS TypeScript 배열로 카테고리·순서·소속 플러그인을 하드코딩한다. 외부 JSON이나 서버 설정을 읽는 구조가 아니다.
- 배열의 카테고리 순서, 각 members의 플러그인 순서가 기본 표시 순서다. PLUGIN_FEATURE_ORDER도 이 배열에서 파생한다.
- 스토어 `src/shell/store/store-catalog.ts:22-35`와 사이드바 `src/shared/layout/nav/nav-groups.ts:19-34`가 같은 정의를 사용한다.
- 다만 실제 사이드바 `arrangeNavGroups(:41-70)`는 즐겨찾기를 별도 최상단에 두고 일반 분류 내부를 로컬 설치 순서로 다시 정렬한다. 스토어의 카탈로그 순서와 실제 사이드바 순서가 항상 동일하다고 설명하면 틀리다.
- 최신 dev의 ‘영상 구성’ 정의는 스토리보드/영상 랭킹/상품 큐레이션 3개다. 사이드바는 설치된 기능만 표시한다. 사용자가 본 화면의 2개 원인을 실제 화면 없이 단정하지 않는다.
- 관리자에 이 카테고리 CRUD API/화면은 없다. 단 관리자 소식의 연결 화면 선택 `app-news-targets.ts:19-46`에도 별도로 복사한 분류 정보가 있다. 공통화 시 이 소비자도 고려한다.

추천 방향(제안):

- 공통 카탈로그에 카테고리 ID/이름/순서와 플러그인의 소속/내부 순서를 둔다. 사용자 기능 플러그인 하나는 한 카테고리에 배정하는 현재 모델을 유지한다.
- ‘플러그인 관리’에서 ‘플러그인 목록’과 ‘분류·순서 관리’를 탭으로 나눈다. 분류·순서 화면은 왼쪽 카테고리 목록, 오른쪽 선택한 카테고리의 플러그인 목록으로 구성한다.
- 카테고리와 내부 플러그인은 드래그 또는 순서 이동 버튼으로 조정하고, 카테고리 간 이동은 대상 선택/드래그를 제공한다. 전체 변경을 한 번의 저장으로 반영한다.
- 카테고리에 플러그인이 남으면 다른 분류로 옮긴 뒤 삭제한다. 분류 삭제로 플러그인 자체를 삭제하지 않는다.
- 최초 제안은 스토어와 사이드바 모두 관리자 순서 적용이었으나, 아래 후속 사용자 지시로 변경됐다. 사이드바 카테고리 안의 플러그인은 기존 설치 순서, 즐겨찾기도 기존 개인 순서를 유지한다. 관리자 지정 플러그인 순서는 스토어 내부 순서에 적용한다.
- 앱은 공통 카탈로그 응답을 함께 사용한다. 마지막 정상 응답을 보관하여 통신 실패 시 빈 메뉴가 되지 않도록 한다.
- 카테고리 배치와 요금제별 실행 허용은 별개 설정으로 관리한다. 분류를 이동해도 pluginKey가 동일하므로 해당 플러그인을 허용한 요금제 연결을 유지한다.

## 후속 확인 — 사이드바 순서 유지·신규 플러그인 공개 전 설정

사용자 지시:

- 즐겨찾기 순서는 기존대로 유지한다.
- 사이드바의 각 카테고리 안 플러그인 표시 순서도 설치 순서를 유지한다.
- ‘일반 카테고리’와 ‘내부 순서’를 구체적인 화면 대상으로 설명한다.
- 새 플러그인 개발 시 현재 분산 등록 작업을 확인하고, 관리자 자동 감지 및 분류/요금제 설정 후에만 스토어에 공개되는 구조가 가능한지 검토한다.

용어와 적용 대상:

- 카테고리 = ‘하이라이트 추출’, ‘영상 자동제작’ 등 이름이 붙은 묶음.
- 카테고리 순서 = 이 묶음들의 위아래 순서. 관리자 설정을 사이드바와 스토어가 공유하는 제안.
- 카테고리 내부 플러그인 순서 = 같은 묶음 안의 개별 기능 순서. 스토어는 관리자 지정 순서, 사이드바는 기존 회원 설치 순서 유지.
- 즐겨찾기는 기존 개인 순서 유지. 분류 소속을 바꾸면 두 화면 모두 새 분류를 사용하되 위 순서 규칙을 각각 적용한다.

현재 개발자 작업의 주요 연결 지점:

- Angular 사용자 화면 및 `src/app/app.routes.ts` 라우트, `app.config.ts`의 providePipelineFeature 등록.
- Angular `core/navigation/app-navigation-metadata.ts`의 기능 메타데이터/기능 타입/카테고리 members. 현재 스토어는 이 알려진 기능 목록으로 필터링한다.
- Nest 가상 워크플로는 `modules/plugins/domain/plugin-catalog.ts`; Python 구현은 실제 manifest와 executor 연결. 구현 종류에 따라 필요한 등록이 다르다.
- 과금 작업이 있으면 Web API `operations/domain/operation-definitions.ts` 및 실제 차감/정산 호출을 연결한다. 무료 기능은 과금 작업을 억지로 만들 필요가 없다.
- 현재 코드에는 이 개발 등록 목록을 관리자 상품용 카탈로그에 자동 등록하는 경로가 없다. 저장소의 CI/빌드에 이미 있는 기능이라고 주장하지 않는다.

추천 흐름(구현 전 제안):

1. 개발자가 플러그인 ID와 기술 등록 정보를 선언하고 기능을 개발한다. 카테고리·상업적 공개·요금제 선택을 앱의 정적 분류 배열에 중복 등록하지 않도록 분리한다.
2. 개발/빌드/배포 절차의 명시적인 카탈로그 동기화 단계에서 등록 목록을 Web API로 전달한다. 신뢰할 수 있는 개발 도구/배포 경로를 사용하며 일반 회원 앱의 임의 보고를 공개 근거로 쓰지 않는다.
3. 신규 ID는 관리자에 ‘설정 대기’로 자동 생성/표시한다. 기존 ID를 다시 동기화해도 운영자가 정한 분류/순서/공개/허용 대상을 덮지 않는다. 자동 감지와 자동 공개를 분리한다.
4. 운영자가 카테고리/표시 정보, 허용 요금제 또는 무료회원 대상, 필요한 경우 과금 작업 연결을 확인하고 공개한다. 필수 설정이 없는 플러그인은 스토어에 노출하지 않는다.
5. 실제 실행 경로에서도 공통 공개 상태와 회원 사용 허용 여부를 검사한다. 스토어에서 숨기는 것만으로 실행 차단을 대신하지 않는다. 과금 작업 없는 플러그인도 검사 대상이다.

현재는 자동 동기화 방식·시점 및 카탈로그 저장 계약을 최종 확정하거나 구현하지 않았다. 사용자에게는 자동 감지 후 관리자 공개라는 한 흐름을 우선 추천하며, 수동으로 ID를 다시 입력하는 일을 필수 절차로 만들 필요는 없다.

## 추가 확정 — 무료체험의 독립된 플러그인 허용 목록

사용자 추가 지시: trial(무료체험 상태)에서 사용할 수 있는 플러그인 목록도 독립적으로 설정한다. Basic 목록과 같게 지정할 수도 있고 다르게 지정할 수도 있어야 한다.

- 관리 대상은 ‘무료체험 상태의 허용 플러그인’과 Basic/Pro/Business 각 요금제의 허용 플러그인이다. 무료체험을 유료 상품 등급에 포함하거나 Basic 설정을 강제로 상속시키지 않는다.
- 회사가 공통 플러그인 카탈로그에서 각각의 목록을 선택한다. 동일한 선택이 가능하더라도 설정은 독립적이다.
- 관리자 /plans의 기존 ‘무료 체험 정책’ 영역에서 무료체험 허용 목록을 편집하고, ‘요금제 등급’에서는 각 유료 등급의 목록을 편집하는 방향이다. 같은 선택 UI와 검증을 재사용한다.
- 가입 시 프로모션 보너스 크레딧만 받는 경우 사용 가능한 플러그인은 무료체험에 허용된 목록이다. 크레딧 출처가 promotion이라는 이유로 별도 Basic/Pro/Business 이용권을 부여하지 않는다.
- 플러그인 사용 허용과 유효 크레딧 잔액은 따로 검사한다. 무료체험 크레딧 소진만으로 유효한 프로모션 크레딧을 무효화하지 않는다. 기존 이용권/크레딧 자체 유효기간 원칙은 보존한다.
- 무료체험 종료 후 유효 크레딧만 남는 상태의 허용 목록 및 기존 유료 이용권 만료 후 접근 규칙은 새 권한 검사 연결 시 시점 정책을 명확히 해야 한다. 이 문서에서 임의로 무료체험 기간을 늘리는 정책을 확정하지 않는다.

설계 논의 계속 중이며 제품 코드 변경은 없다.

## 자동 동기화 기술 실험 완료

사용자 요청으로 실제 앱 소스 추출→HTTP 전송→격리 PostgreSQL 저장 및 관리자 공개 분리를 실험했다. 11개 검사 통과. 실제 사용자 플러그인 14개를 추출했고 소스 fixture의 신규 등록 1개를 추가 감지했다. 제품 API/배포 연동은 아직 구현하지 않았다. [실험 코드·증거·범위](28-plugin-catalog-sync-proof.md). 크레딧 소진과 무료체험 기간 종료의 구분도 해당 기록에 명시했다.

## 후속 제안 — 유료 이용권이 없을 때 항상 존재하는 기본 이용 상태

사용자 설명: 가입 후 일정 기간의 무료체험이 끝나 ‘이용권 없음’이 되는 모델 대신, 유료 이용권이 없으면 언제나 기본 상태가 존재해야 한다. 유료 이용권을 구매하면 해당 이용권 상태가 되고, 사용 기간이 끝나면 기본 상태로 돌아오며, 이후 재구매하면 다시 해당 유료 이용권을 적용한다. 무료체험/trial이라는 명칭은 미정이다. **기획팀/전략팀과 상의 전의 사용자 제안이며 회사 정책으로 최종 확정된 것은 아니다.**

현재 코드 확인:

- migration ApplyLaunchCreditAccessPolicies의 초기 정책은 400크레딧/30일이다. 이 답변에서 운영 DB의 실제 값을 직접 조회한 것은 아니다.
- FreeTrialProvisioner는 expiresAt=가입일+policy.validityDays로 무료체험 크레딧을 만들고, 별도의 무료체험 이용권 종료일은 저장하지 않는다. 참여 정보는 지급 크레딧 ID를 참조한다.
- findUsableByUserId는 해당 크레딧이 active·잔량>0·미만료인지 검사한다. 따라서 가입 30일 경과뿐 아니라 그 이전 전액 소진도 무료체험 권한 응답을 없앤다.
- EffectiveAccessService는 다른 활성 이용권을 먼저 찾고, 없으면 위 무료체험 조회를 사용하며, 둘 다 없으면 null이다. 고객 대시보드는 null을 ‘이용권 없음’으로 표시한다.
- 실제 크레딧 차감은 별도 유효 잔액을 검사하므로, 이 권한 응답 null과 현재 작업 차감 가능 여부를 동일시하면 안 된다.

사용자 제안에 맞는 논의용 구조:

- ‘기본 이용 상태’(가칭)는 기간 만료나 가입 크레딧 잔액과 무관하게 존재한다.
- 적용 중인 유료·프로모션·관리자 지급 이용권 등이 있으면 그 이용권의 플러그인 허용 목록을 우선하고, 유효한 주 이용권이 없으면 기본 허용 목록으로 돌아온다.
- 기본 허용 목록은 Basic/Pro/Business와 독립적으로 관리한다. 이 기본 상태가 기존 무료체험 권한 역할을 대체하는 방향이다.
- 가입 400은 1회 지급 크레딧 혜택으로 분리한다. 현재 30일 유효기간을 유지할지 변경할지는 별도 정책이며, 기본 상태가 계속된다는 이유로 400을 무기한화하거나 기본 복귀마다 재지급하지 않는다.
- 코드로 받은 크레딧·추가 구매 크레딧은 각 지급분의 유효기간을 따른다. 주 이용권 종료 후 기본 상태에서 유효 잔액을 사용할 때에는 기본 허용 플러그인 범위를 적용하는 제안이다. 남은 크레딧이 이전 Pro/Business 권한 자체를 연장하는 의미는 아니다.
- 구독 해지/자동결제 중단 요청 시 즉시 기본으로 전환하지 않고, 기존 결제·유예 정책에 따라 실제 주 이용권의 이용 가능 기간이 끝난 뒤 복귀한다.
- 관리자 /plans는 ‘기본 이용 정책’(플러그인 허용 목록)과 ‘가입 크레딧 혜택’(초기 지급량/크레딧 유효일수)을 구분해 편집하는 구성이 자연스럽다. 이 구체적 UI/명칭은 제안 단계다.

이 방향을 채택하면 기존에 미정으로 적었던 ‘이용권 종료 후 유효 크레딧만 남은 회원에게 적용할 플러그인 목록’은 **기본 이용 정책**으로 설명할 수 있다. 제품 구현은 아직 변경하지 않았다.


## 후속 사용자 확인과 별도 승인 검사 보완

유료 요금제 3등급과 기본 포함 4가지 이용 상태, 추가 크레딧 상품 공통 가격, 신규 구매는 활성 유료·프로모션 이용권에만 허용하는 조건을 확인했다. 명시되지 않은 기존 결제·환불·월별 지급/만료·차감·일회 지급 정책은 변경하지 않는다. 기존 구현 4개와 신규 플러그인 제한 구현 항목을 구분하고, 사용자 요청으로 추가 크레딧의 신규 결제 승인 전 구매 자격을 재검사하도록 보완했다. [정책 확인·제품 변경·4,845개 검사 기록](28-topup-confirmation-access-and-existing-policy-check.md).


## 전체 정책·구현 상태 현황 추가

사용자 요청으로 코드·기존 테스트·개발/로컬 공개 상품·로컬 읽기 전용 정책 조회를 대조했다. [전체 현황/변경 방향/구현 여부/회사 확인 항목](28-billing-access-credits-promotions-current-and-target-policy.md)을 따른다. 기존 결제 정책을 다시 미정으로 올리지 않고, 크레딧형 신규 유입 코드의 유료 전환 연결 조건 등 실제 새 정책만 구분했다. 이번 현황 조사에서 제품 소스와 DB는 변경하지 않았다.
