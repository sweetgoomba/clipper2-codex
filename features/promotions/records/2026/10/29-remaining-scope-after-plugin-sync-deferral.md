## 1. 이번 요청과 작업 분리

- 관리자와 앱 스토어의 플러그인 목록 동기화는 **W18 후속 작업**으로 명시한다. 기존 TODO 링크뿐 아니라 WORKBOARD 작업 목록의 실제 행과 작업카드를 만든다.
- **남은 W19:** 가입 선택 코드, 크레딧 전용 혜택, 지속 기본 이용 상태, 관리자 등급별 허용 설정, 서버/앱 실행 허용 검사, 회원 웹 요금제 카드의 허용 플러그인 표시.
- 신규 필수 요구: **`/#price`와 `/pricing`의 허용 기능은 관리자 저장값을 읽는다. 프런트엔드에 Basic용 배열·Pro용 배열·Business용 배열을 별도로 하드코딩하지 않는다.**
- 공통 플러그인 카탈로그 CRUD, 카테고리·순서 운영, 개발 등록 자동 감지/릴리스 동기화, 전체 긴급 중지 운영은 앞서 W18 관련 후속으로 정리한 범위를 유지한다. 이를 W19의 필수 선행으로 다시 포함하지 않는다. 등급별 권한 검사 자체는 W19에 남는다.
- 기존 결제·구독 변경·환불·월별 크레딧 지급/만료·FIFO는 변경 지시가 없는 한 유지한다.

## 3. 새 요구인 회원 웹 요금제 표시

### 현재 사실

- 랜딩 `/#price`는 PricingSectionComponent를 거쳐 공통 `PlanCardComponent`를 쓴다. `/pricing`도 같은 카드를 쓴다.
- 두 화면은 이미 `CatalogApiService.listTiers()` → 공개 `GET /catalog`로 등급·상품을 받는다.
- 서버 `CatalogTierView`와 회원 웹 `CatalogTier`에는 `entitlementMode`와 `pluginKeys`가 이미 있다. `all`이면 서버가 현재 등록 ID 전체로 확장하고, `allowlist`는 DB 목록으로 만든다.
- 카드 HTML의 ‘모든 요금제에서 같은 기능 사용’과 `/pricing` 하단의 동일 기능 안내는 새 정책과 충돌한다. 관련 기존 테스트도 그 고정 문구를 기대한다.
- 표시명은 공개 DTO에 없다. 사용하지 않는 `plugin-label.ts`는 4개만 매핑하고 일부는 현재 ID가 아니므로 그대로 연결하면 충분하지 않다. 과금 작업 표시명도 플러그인의 고객용 이름과 같지 않다.

### 적용할 설계 방향

`관리자 /plans 저장 → 기존 등급/허용 DB → 기존 공개 /catalog → 공통 PlanCardComponent → /#price와 /pricing`

1. **허용 조합의 정본은 기존 DB**다. 고객 웹에서 상위 등급의 목록을 임의 합치거나 등급별 배열을 만들어 대체하지 않는다.
2. 현재 알려진 사용자 기능 ID의 고객용 표시정보를 최소 보강하고 기존 공개·관리자 응답에서 재사용하는 방향을 검토한다. 이것은 전체 카탈로그 관리/자동 감지/앱 스토어 동기화 도입과 구분한다.
3. ID→이름은 한 곳에서 관리할 기술 표시정보이며, ‘누가 어느 요금제에서 사용 가능한가’는 관리자 DB 데이터다. 화면마다 새 ID/이름 사본을 만들지 않는다.
4. 공통 카드 한 곳에서 허용 목록을 렌더링한다. 월간/연간은 같은 tier의 목록을 공유한다. 실제 금액·월 지급량·결제주기 동작은 유지한다.
5. 고정 문구 두 곳을 교체하고 긴 목록·빈 목록·로딩/오류·모바일·카드 높이와 랜딩 앵커 위치를 검증한다. 최종 긴 목록 UI의 접기·펼치기 같은 구체적 디자인은 아직 정하지 않았다.
6. 관리자 저장 뒤 **새 catalog 조회**에 반영되는 경로를 보장한다. 열린 화면을 실시간 push로 즉시 바꾸는 별도 시스템은 이번 요구로 추가하지 않는다.
7. 기본 상태의 이름 미정이나 앱 스토어 목록 동기화 보류를 유료 3개 카드 연동의 차단 사유로 삼지 않는다. 기본 상태를 네 번째 판매 카드로 추가하는 요구도 없다.

### 가격 화면 검증 기준

- 서버가 서로 다른 허용 목록을 주면 두 URL의 같은 등급 카드에 같은 목록이 나온다.
- 관리자 저장 후 다시 조회하면 두 화면과 실제 허용 판정이 같은 결과를 쓴다.
- 월/연 토글로 기능 목록이 다른 등급의 목록으로 바뀌거나 고정 배열로 대체되지 않는다.
- ‘모든 요금제 동일 기능’ 문구가 남지 않고 ID 원문이나 잘못된 과금 작업 이름이 고객용 기능명으로 노출되지 않는다.
- 카드/부모 컴포넌트·표시 로직을 복제하지 않는다.

## 4. 관리자 허용 목록과 저장 일관성

### 현재 사실과 위험

기존 DB·API는 있지만 `/plans`의 TierDraft/폼에는 허용 목록이 없고 신규 등급 생성은 `all`로 고정한다. 기존 `replaceTierPlugins()`도 운영 UI 호출처가 없다.

현재 mode PATCH와 keys PUT은 각각 자기 등급 하나를 잠그는 별도 트랜잭션이다. 아래는 소스로 확인한 **새 UI 연결 시의 위험**이며 이번에 실제 DB 동시성 시험을 실행한 결과는 아니다.

- `all → allowlist`를 먼저 저장하면 목록은 비어 있고, 다음 목록 저장이 실패하면 빈 권한이 남는다.
- 목록부터 저장하면 `all` 상태에서는 목록이 버려진다. 순서만 바꿔 해결되지 않는다.
- 기존 서비스에는 등록 ID 검사나 Basic⊆Pro⊆Business 검사가 없다.
- 각 등급만 잠그고 다른 등급을 일반 조회해 포함 관계를 검사하면 동시 수정으로 관계가 깨질 수 있다. 예: Basic에 B 추가와 Pro에서 B 제거가 서로 이전 값만 보고 통과.

### 구현 전 보완 방향

- 기존 테이블을 재사용하고 **mode+keys를 한 번에 저장하는 트랜잭션 경로**를 만든다.
- 변경 대상과 관련 유료 등급을 일정한 순서로 잠그고 변경 후 전체 포함 관계를 검사한다. 기존 교체 API도 같은 검증 경로를 사용한다.
- 등록된 ID, 중복, 빈 목록/전체 허용을 명확히 처리한다. 과거 `all`을 임의의 미정 회사 목록으로 바꾸지 않는다.
- UI의 자동 체크 전파 또는 관계 오류 안내는 한 방식으로 설계하되 저장 데이터와 실행 판정이 어긋나지 않게 한다.
- 권한 저장 도입을 이유로 기존 구독의 금액·크레딧 계약 스냅샷이나 변경 과금 규칙을 수정하지 않는다.

## 5. 지속 기본 상태와 실제 실행 허용

### 현재 사실

`EffectiveAccessService.resolve`는 주 이용권을 먼저 보고, 없으면 가입 크레딧이 활성·잔액 양수·미만료인 무료체험만 반환한다. 나머지는 null이다. 현재 기본 상태는 지속되지 않는다.

`spendableCreditSources`는 조회 응답에 있지만 실제 quote/start/consume의 소비 제한으로 쓰지 않는다. 실제 소비는 유효 지급분 전체를 기존 FIFO로 처리한다. trial 응답의 `['free_trial']`를 그대로 소비 필터로 강제하면 유효한 프로모션·추가 구매분 사용을 막아 기존 정책을 바꿀 수 있다.

`allowsPlugin`은 실행 경로에서 호출하지 않으며 Desktop LicensePolicyService는 항상 허용한다. 앱에는 현재 허용 목록을 받는 응답 경로가 있지만 스토어/진입/실행에 연결되지 않는다. 설치 guard는 설치 여부만 검사한다.

### 보완 방향

1. 주 이용권이 없으면 기본 허용 정책을 조회 결과로 반환한다. 사용자당 하나인 주 이용권 테이블에 무기한 active 행을 새로 만들어 프로모션/유료 지급을 막지 않는다.
2. 가입 지급과 기본 이용 상태를 분리한다. 조회 자체가 grant 생성·400 재지급·과거 지급분 만료 연장을 해서는 안 된다.
3. 외부 표시명이 ‘이용권 없음’이어도 내부 기본 정책은 적용할 수 있다. 내부 ID/타입은 기술 결정이며 `Free` 확정으로 간주하지 않는다. 이름/source 계약을 바꾸면 Web API·양쪽 웹·Desktop의 enum/null 소비자를 함께 수정한다.
4. 기존 주 이용권의 실제 종료·유예 정책을 그대로 따르고 그 이후 기본으로 복귀한다. 해지 버튼을 눌렀다고 즉시 기본으로 내리지 않는다.
5. **현재 등급의 플러그인 허용**과 **기존 유효 크레딧 충분 여부**를 따로 검사한다. 기본에서 예전에 산 유효 topup을 쓸 수 있지만 과거 Pro 전용 기능은 쓸 수 없다.
6. Web API quote/신규 start와 Desktop 작업 생성·예약·재시작·실제 대기 실행, 직접 진입 경로를 점검한다. 거절 전에 차감하지 않고, 이미 차감된 대기 작업을 거절하면 기존 반환/정산을 보존한다. 기존 성공 작업의 멱등 조회·완료 정산·반환 복구를 새 시작 거절과 혼동하지 않는다.
7. 스토어 목록의 기술 수집·카테고리는 기존 것을 유지한 채 현재 허용 데이터만 적용할 수 있다. 노출 여부는 이사님 확인에 맞추고 사이드바의 설치·즐겨찾기 순서를 바꾸지 않는다. 전역 긴급 중지·공개 운영은 W18과 구분한다.
8. 무료 기능이 추가되어도 권한 검사는 필요하다. 다만 지금 존재하지 않는 기능을 억지로 추가하거나 전체 자동 목록 시스템을 이를 위해 선행 구현하지 않는다.

## 6. 크레딧 전용 프로모션과 가입 코드

### 6.1 현재 이용권 전제와 변경 경계

현재 캠페인은 tier·1~12개월·월 지급량을 필수로 갖고 등록마다 이용권과 첫 월 크레딧을 만든다. 참여 current/history는 이용권 INNER JOIN이고 회수는 accessGrantId가 없으면 실패한다. 따라서 `source=promotion`으로 크레딧만 넣는 것만으로 새 기능이 완성되지 않는다.

보완 방향:

- 기존 이용권형은 유지하고 **혜택 종류**를 분리한다. 종류별 필드·DTO·DB 제약·혜택 스냅샷을 정한다. 구체적 필드명은 최종 계약에서 결정한다.
- 크레딧형은 한 번의 수량·자체 유효기간으로 지급하고 주 이용권·월 지급 일정을 생성하지 않는다. 수량 200을 코드에 박지 않는다.
- 관리자 추가/수정/내역, 회원 확인 모달/참여 이력/크레딧 표시, 회수·운영 기록·성과·XLSX를 종류에 맞게 수정한다. 크레딧형 행을 Basic 이용권이나 1개월로 잘못 표시하지 않는다.
- 종류별 회수는 해당 등록의 미사용분만 대상으로 한다. 과거 사용과 별도 지급분은 보존하며, 기존 이용권형 회수는 이용권+해당 미사용 크레딧을 함께 처리하는 규칙을 유지한다.
- 같은 캠페인 1회, 코드별 상한, 회수 이력 보존, 원장·등록 ID 연결과 잠금 장치를 재사용한다. 다른 캠페인의 과거 참여와 무료체험 이력은 새 제한으로 되살리지 않는다.
- 주 이용권 중복 검사는 이용권을 새로 주는 조건과 구분한다. 크레딧형의 가입 후 사용 대상·기존 이용권과의 공존 범위를 회사가 정한 적 없이 자동 허용/금지로 바꾸지 않는다.

### 6.2 가입의 실제 DB 경계

현재 가입 complete에는 티켓·만 14세·약관/개인정보 버전만 있다. `promotionCode`는 허용 DTO가 아니며 기존 프로모션 API는 회원 JWT가 필요하므로 가입 전 그대로 호출할 수 없다.

가입 동의 화면은 신규뿐 아니라 기존 계정의 재동의에도 사용된다. 사용자 저장 결과의 `created`로 신규를 구분해야 하며 재동의마다 가입 보너스를 주면 안 된다.

현재 사용자 DB 거래에는 티켓 사용·회원·필수동의·무료체험 지급 대기 작업을 함께 저장한다. 실제 무료체험 지급은 관리자 DB에서 별도 거래로 수행한다. job은 재처리되고 grant/ledger는 사용자별 잠금·멱등키로 중복을 막는다. **두 DB를 한 트랜잭션이라고 표현하거나 사용자 DB manager를 관리자 저장소에 넘기면 안 된다.** 현재 job에는 프로모션 코드/혜택 payload도 없다.

가입 보너스는 다음을 함께 설계해야 한다.

1. 가입용 코드 확인·complete 계약과 필수 동의와 분리된 선택 입력, 코드 정규화와 실패 안내.
2. 사용자 DB에 신청 의도를 내구성 있게 저장하고 관리자 DB 지급을 재시도해도 참여·grant·ledger를 한 번만 만드는 구조.
3. preview는 상한을 예약하지 않는다는 점과 실제 등록 시 상태/기간/마지막 자리 경쟁 재검사. “로그인 후 예시 600”을 충족하려면 최종 참여 확보·지급 완료/처리 중/거절 상태를 명확히 구분한다. 단순 후속 API 호출이나 무조건 성공 가정은 부족하다.
4. 가입 후 세션 발급/클라이언트 복귀 실패, 관리자 DB 일시 장애, 지급 성공 후 job 완료기록 실패를 각각 재처리해도 누락·중복이 없는지 검증.
5. 잘못된 코드·상한 소진·중지 등으로 혜택을 못 줄 때 수정 또는 코드 없이 계속할 명시적 선택을 제공하는 제안을 검토한다. 최종 UX는 미확정이며 보너스 없이 조용히 성공 처리하지 않는다.

기존 가입 1회 지급의 정책 수량·활성 설정·가입일 기준 만료·처리시점 동작은 그대로 재사용한다. 이 조사에서 이를 새 회사 결정 대상으로 올리지 않는다.

### 6.3 성과 귀속

프로모션 크레딧의 지급/순사용/회수와 내보내기는 등록 ID 기반을 재사용할 수 있다. 유료 전환 연결은 현재 활성 프로모션 이용권에서 출발하므로 크레딧형의 후속 첫 결제까지 자동 연결되지는 않는다.

새 확인 대상은 크레딧형 첫 결제의 인정 조건·기간과 여러 등록이 공존할 때 중복 귀속 방지 기준이다. 임의로 최근 코드를 선택하지 않는다. 첫 결제를 연결한 뒤 같은 구독의 갱신·즉시 변경·환불 연결은 기존 정책을 유지한다. 자동 지급액 계산/송금은 추가하지 않는다.

## 7. 보존할 결제와 크레딧 원칙

- 정기 크레딧의 월별 지급·만료, 연간 결제의 월별 지급, 구독 변경 금액/적용·해지·환불·재시도·유예는 기존 규칙이다.
- 같은 작업의 비용은 크레딧 출처로 다르게 하지 않는다. 유효 지급분의 FIFO·만료·회수/환불 잠금도 유지한다.
- topup은 동일 상품의 공통 가격과 현재 30일을 유지하고 구매 당시 등급 권한을 저장해 연장하지 않는다.
- **기본 상태가 존재한다는 사실 또는 `promotion` 크레딧 잔액만으로 topup 신규 구매 자격을 주지 않는다.** 활성 유료 구독 또는 이용권형 프로모션만 대상이다. 관리자 지급 이용권만으로도 자격을 넓히지 않는다.
- 작업 브랜치의 topup 신규 승인 직전 자격 검사 6파일은 이미 작성된 보완이다. pending/paid/결과 미확정 복구까지 새 구매 검사로 차단하지 않는 기존 경계를 보존한다.
- 이용권형 프로모션의 유료 예약·회수 후 예약 유지·코드별 상한·동일 캠페인 1회·XLSX는 기존 기반이다. 크레딧형에 없는 이용권 종료일을 억지로 만들어 예약시키지 않는다.

## 8. 상태표와 저장소별 영향

| 남은 항목 | 지금 상태 | 필요한 범위 |
|---|---|---|
| 요금제 카드의 DB 허용 목록 | ID 전달은 있음. 고정 문구가 남음 | 공통 카드·안내·전체 표시명 보강 |
| 관리자 허용 선택 | API/테이블만 있음 | 기존 `/plans` 편집과 원자 저장·상위 포함 검증 |
| 지속 기본 상태 | 미구현 | 잔액/만료와 독립한 조회 fallback·응답/표시 소비자 |
| 서버/앱 실제 권한 검사 | 미구현 | 현재 허용 데이터로 실행 거절·비용/복구 일관성 |
| 크레딧 전용 캠페인 | 미구현 | 혜택 종류·DB/조회/회수/UI/원장 연결 |
| 가입 선택 코드 | 미구현 | 가입 전 계약·내구 신청/지급·신규 여부·오류/완료 표시 |
| 크레딧형 첫 유료 전환 | 기준 미정 | 회사의 귀속 조건 확정 후 연결. 추측 집계 금지 |
| topup 승인 전 재검사 | API 작업 브랜치 구현 | 6파일 미커밋·미푸시, 이후 실제 통합/배포는 별도 |
| 앱 목록 공통화/자동 동기화 | W18 후속 | W19 선행으로 넣지 않음 |

저장소 영향:

- Web API: 기존 catalog/access/auth/promotions/operations와 가입 후속 작업 계약·검증.
- 회원 웹: 가입, 공통 요금제 카드 두 경로, 기본 상태/참여 내역/오류 표시.
- 관리자 웹: 기존 `/plans` 허용 설정, 크레딧형 캠페인 입력/내역, 회원의 실제 상태 표시.
- Desktop Nest: 현재 access 응답 소비와 실행 허용 연결, 대기/재시작/정산 경계.
- Desktop Angular: 허용 상태 표시와 진입/실행 UX, 기본 상태 계약 소비. 카테고리·설치/즐겨찾기 순서 유지.
- Electron: 현재 직접 수정이 필수라는 근거는 없다. IPC/계약 확인 결과 필요할 때만 범위를 늘린다. 전체 자동 배포 연결은 W18이다.

## 9. 미확정 사항의 분류

### 회사·기획 확인

1. 기본 상태를 ‘이용권 없음’으로 둘지 별도 명칭을 쓸지. 별도 명칭은 필요할 때만 받는다.
2. 기본·유료의 실제 허용 플러그인 목록과 기본에 대한 상위 포함 범위. 유료 세 등급의 상위 포함 자체는 전략실 답변이 있으므로 재질문하지 않는다.
3. 크레딧형의 가입 후 등록 대상과 가입 화면의 이용권형 코드 수용 범위. 새 혜택 수량·유효기간은 관리자 운영 입력값으로 구분한다.
4. invalid/상한 소진 코드의 가입 UX와 처리 중 변경/거절 시 명시적 안내.
5. 크레딧형 첫 유료 결제 귀속 조건·기간·복수 등록 중 선택.
6. 앱 스토어의 요금제 미제공 노출 UX에 대한 이사님 답변. 회원 웹의 요금제별 기능 표시는 이미 사용자 요구다.

### 개발에서 해결할 것

mode+keys 원자성, 유료 세 등급의 동시 수정 잠금, 기존 catalog 표시정보 보강, 두 DB의 내구 신청/멱등 처리, 공통 상태/권한 검사 재사용, 마이그레이션·계약·통합 검증은 구현 설계다. 전략실에 기술 구현 결정을 넘기지 않는다. 이 항목들이 모두 완료되거나 이미 검증됐다고 쓰지 않는다.

기존 가격·연간 월 지급·FIFO·무료체험 최초 1회·환불·재시도 등을 다시 정책 결정 목록에 넣지 않는다. 새 가격/지급량 변경 지시가 없으면 기존값을 유지한다.

## 10. 제안 구현 순서와 완료 검증

아래는 경계와 의존성을 확인한 순서 제안이다. 이번에 제품 구현은 하지 않았다.

1. 허용 데이터 저장/조회 계약, 최소 표시정보, 기본 상태와 혜택 종류의 API/DB 계약을 정한다. 실제 운영 숫자·행사 문자열을 기다리며 구조 설계를 막지 않는다.
2. 관리자 설정과 서버의 원자 저장·상위 포함 검증을 연결하고 두 회원 웹 경로를 같은 카드로 반영한다.
3. 지속 기본 상태와 실제 플러그인 실행 허용을 함께 연결한다. UI 설정만 출시하고 서버는 항상 허용하는 상태를 기능 완료로 하지 않는다.
4. 크레딧형 캠페인의 등록·조회·회수·화면·원장과 기존 이용권형 회귀를 구현한다.
5. 가입 선택 코드와 두 DB 지급 복구를 연결하고 코드/지급/복귀 실패 시 상태와 안내를 검증한다.
6. 확정된 새 귀속 기준을 성과/내보내기에 적용하고 기존 결제·프로모션 흐름과 함께 통합 검증한다.

검증 체크리스트:

- [ ] API 허용 집합 = 관리자 재조회 = 두 가격 화면 기능 목록 = 해당 등급 실제 실행 허용.
- [ ] mode+keys 전체 성공/실패와 동시 등급 수정 후에도 Basic⊆Pro⊆Business.
- [ ] 기본은 신규/가입 크레딧 소진·만료/각 주 이용권 종료 후 모두 존재, 400 재지급·기존 기록 변경 없음.
- [ ] 유효 topup은 기본에서도 허용 플러그인에 사용 가능하되 신규 구매 불가. 크레딧형 보너스만으로 topup 허용 안 됨.
- [ ] 권한 거절된 새 작업에 차감 없음. 대기 중 권한 변화·재시작과 이미 차감된 작업의 반환/멱등 복구 정상.
- [ ] 티켓 재사용·동일 Google 동시 가입·기존회원 재동의·세션 실패 재진입에서 가입/보너스 중복 없음.
- [ ] user DB 신청 저장 후 admin 지급 실패, admin 지급 커밋 후 user job 완료기록 실패를 각각 재처리해 등록·grant·ledger가 한 번만 생성. admin 지급 커밋 전 job을 completed로 만들지 않음.
- [ ] 동일 코드 마지막 자리 경쟁·다른 코드의 같은 캠페인 중복·preview 후 변경 처리.
- [ ] 크레딧형은 이용권/월 지급 없음, 참여 이력에서 사라지지 않고 올바른 수량/유효기간·회수 상태 표시.
- [ ] 기존 이용권형 월 지급·유료 예약·회수·성과·XLSX, 기존 결제/환불/추가구매 정책 회귀 없음.

## 11. 이번 확인 방법과 증거
