# 캠페인 생성 전 확인 · 쉬운 문구 · 수정 가능 범위

**후속 정책 정정:** [종료일 단축 허용과 확인창 열 배경](02-campaign-deadline-and-summary-colors.md). 아래 수정 규칙도 최신 정책으로 갱신했다.

2026-11-02 KST. 사용자 요청에 따라 전용 `feat/signup-credit-promotion-free-20261102`의 관리자만 수정했다. API 정책/DB 스키마/크레딧 지급/회원 앱은 변경하지 않았다. 커밋·푸시·병합 없음.

## 생성 흐름

유효한 설정 입력→저장→기존 `ConfirmDialogService` 공통 Material 확인창→‘확인 후 생성’에서만 생성 요청을 보낸다. 확인창에는 캠페인 이름, 시작/종료일(미정 포함), 혜택 종류와 수량 또는 등급/기간, 크레딧 사용기한, 참여 대상, 추가 조건, 코드별 등록 인원 제한, 생성 후 비활성 상태를 표시한다. 생성은 기존대로 비활성이고 상세에서 코드를 발급한 뒤 활성화한다.

‘돌아가서 수정’/확인 취소는 작성 값을 보존하며 요청을 보내지 않는다. 확인 중 busy로 중복 제출을 막는다. 실제 요청은 확인에 쓴 정상화된 입력값을 사용한다. 수정 저장은 기존 흐름을 유지한다.

경고와 수정 패널 안내는 ‘회원이 코드를 등록한 이후에는’으로 구체화했다. 잠금 오류는 ‘이미 코드를 등록한 회원이 있어 시작일·지급 혜택·참여 대상·추가 조건을 변경할 수 없습니다.’로 바꾸었다.

## 후속 문구·배치

- ‘코드별 성공 등록 상한’→‘코드별 등록 인원 제한’, ‘최대 건수’→‘최대 등록 인원’. 한 회원의 같은 캠페인 중복 등록을 금지하므로 코드 등록 수와 인원은 같은 집계다. 제한값과 각 코드 등록 수를 ‘명’으로 표시한다. 캠페인/코드 개수의 ‘건’은 그대로 둔다.
- 최대 등록 인원 입력란은 체크 항목 오른쪽 대신 아래에 전체 폭으로 표시하고 ‘명’을 붙인다. 목록/상세/마감 안내의 관련 용어도 통일했다.
- 공통 확인창에 optional `factsLayout: 'columns'`를 추가해 이 생성 확인창에서만 고정된 두 열/라벨·값 모두 왼쪽 정렬을 사용한다. 다른 페이지의 기존 기본 좌우 정렬·공통 모달 스타일은 유지한다. 별도 확인창 컴포넌트나 직접 색상을 추가하지 않았다.

## 현재 API 기준 수정 규칙

성공적으로 코드를 등록한 회원이 아직 없으면 모든 캠페인 설정을 수정할 수 있다(입력 유효성 검사/상품 활성 여부 등 기존 검사는 적용).

코드 등록 이력이 하나라도 있으면 다음과 같다. 회수된 이력도 보존되고 누적 등록 수를 줄이지 않으므로 잠금이 해제되지 않는다.

| 항목 | 수정 여부 | 조건 |
| --- | --- | --- |
| 캠페인 이름 | 가능 | 이름 유효성 검사 |
| 종료일 | 가능 | 시작일 이후의 날짜로 단축/연장, 날짜↔미정 모두 허용. 기존 지급 혜택에는 영향 없음 |
| 코드별 등록 인원 제한 | 가능 | 제한 해제/증가 가능. 감소 시 어느 코드의 기존 등록 인원보다도 작아질 수 없음. 캠페인 합계가 아닌 각 코드별 검사 |
| 시작일 | 불가 | 기존 참여 당시 기간 보존 |
| 혜택 종류 | 불가 | 크레딧형↔이용권형 변경 불가 |
| 지급 크레딧/자체 유효기간 | 불가 | 크레딧형 조건 보존 |
| 지급 이용권 등급/이용 개월 | 불가 | 이용권형 조건 보존. 월 지급량은 생성 당시 등급 스냅샷 |
| 참여 대상 | 불가 | 신규/기존/모두 설정 보존 |
| 추가 조건 | 불가 | 활성 이용권/과거 유료 이력 조건 보존 |
| 활성·비활성 | 별도 조작 가능 | 신규 등록만 통제. 기존 지급 유지. 종료일 경과/코드 미발급 등 기존 활성화 검사 적용 |
| 캠페인 삭제 | 불가 | 성공 등록 이력 보존. 이력이 없을 때만 연결 코드와 함께 삭제 가능 |

등록 이력이 있는 캠페인의 종료일을 미정으로 바꾸더라도 비활성이 자동 활성으로 바뀌지 않는다. 기존 [양방향 수정 검증](02-open-ended-campaign-edit-regression-check.md) 원칙을 유지한다. 이번에는 잠금 자체를 풀지 않았다.

근거: API `PromotionsService.updateCampaign`의 redeemedCount/시작·종료/혜택·대상·조건 비교와 코드별 cap 검사, `deleteCampaign`, TypeORM의 누적 등록 및 회수 처리. 관리자 HTML의 기존 disabled/min 조건도 유지했다.

## 검증과 반영

- 생성 전 확인/취소/중복 차단/요청 snapshot/크레딧형과 이용권형 요약/잠금 오류를4개 RED로 먼저 재현했다.
- 후속 인원 입력 위치와 공통2열 정렬을2개 추가 시험으로 검증했다. 기존 생성 시험은 확인 Promise를 기다리도록 조정했다.
- 최종 관리자 전체2,717개 통과. 별도 API 수정 정책35개 통과. build/check:colors(직접 색상0)/git diff --check 통과.
- 최초 생성 GREEN에서 옛 subtitle 기대문구1개가 남아 있었고, 후속 단위 전환 GREEN/첫 전체에서 ‘2건/2건’의 옛 기대값1개가 남아 있었다. 테스트 기대 문구만 새 요청에 맞춘 뒤 최종 전체를 다시 실행해 통과했다. 새 정책으로 오인할 제품 수정은 하지 않았다.
- 브라우저 실제4242에서 기존 공통 Material 확인창, 이름/혜택/대상/상한/미정 종료일, 라벨·값 text-align=left/display=grid,10행 값의 동일 x=680.92px를 확인했다. 체크 항목 bottom688.35px, 최대 인원 field top704.34px로 입력란이 아래임을 확인했다.
- 실제 공통 취소 버튼으로 패널 복귀와 작성한 이름/날짜/수량/상한의 보존을 확인했다. 첫 자동화 경로에서 창 전환 중 뒤쪽 컨트롤을 건드려 재확인을 진행했으며, 최종 접근성 버튼 동작으로 취소 완료를 확인했다. 이를 제품 결함으로 단정해 공통 동작을 임의 수정하지 않았다.
- 실제 사용자가 만든 캠페인/회원 등록 기록을 변경하지 않았다. 확인용 캠페인은 생성하지 않았고 임시 브라우저 탭만 닫았다.
- 전용 관리자4242는 서버 중단 없이 최신 빌드 사본으로 갱신했다. 로컬 사본만 API4340으로 치환했다. API4340/클라이언트4241/전용DB15438/앱과 다른 작업 서버·DB는 유지했다.
- 로그: `/tmp/campaign-confirmation-red.log`, `campaign-confirmation-layout-red.log`, `campaign-confirmation-all-green.log`, `campaign-confirmation-build-final.log`, `campaign-confirmation-api-edit-policy.log`. 기존880.45kB 관리자 번들 예산 경고는 남아 있다.
