# AI 부스 출시를 위한 가입 프로모션 크레딧과 Free 범위

현재 구현/검증 상태: [11/02 완료 기록](02-ai-booth-signup-free-implementation-and-verification.md). 아래 ‘구현 전’ 표시는 범위 승인·브랜치 준비 당시의 기록이다.

기준일: **2026-11-02 KST**. 사용자가 기존 범위를 수정했다. AI 부스에서 홈페이지로 유입된 신규 회원이 가입할 때 코드를 입력하고, 가입 혜택과 이벤트 크레딧을 모두 받은 상태로 서비스를 시작하는 것이 최우선이다. 레퍼럴 결제 성과·정산용 내보내기는 후속으로 미룬다.

이 기록은 10월 29일 문서와 작업카드의 상충하는 범위를 대체한다. 범위 기록·브랜치 보존·목업 확인을 완료한 것이며, 아래 제품 코드 삭제·신규 가입 흐름 구현을 완료했다는 뜻은 아니다.

## 1. 출시 목표와 남길 기능

1. 가입 필수동의 화면에 선택 프로모션 코드 입력란을 제공한다. 실제 신규 가입에만 적용하며 기존 회원 로그인·재동의·가입 후 입력으로 가입 전용 혜택을 지급하지 않는다.
2. 코드가 실제 등록 가능한지 서버에서 검사하고, 회원에게 기존 최초 가입 크레딧과 별도의 `promotion` 출처 크레딧을 지급한다. 현재 400과 예시 200이면 처음 사용 가능 잔액은 600이다. 수량을 코드에 고정하지 않는다.
3. 두 지급분은 각각 출처·수량·유효기간·사용 기록을 가진다. 잔액 표시는 현재 유효한 지급분의 합계다. 지급 전부터 600이라고 표시하거나 지급 실패를 숨기고 로그인 성공으로 처리하지 않는다.
4. 관리자에서 어떤 회원이 어떤 코드를 언제 등록했는지, 특정 코드의 참여 회원이 누구인지 조회한다. 회원 식별은 이메일 등 기존 회원 표시를 재사용한다.
5. 기존 캠페인/코드 관리, 기간·활성 상태, 코드별 상한, 등록 기록과 중복 지급 방지 중 출시 흐름에 필요한 공통 부분을 재사용한다. 회원당 같은 캠페인 1회, 캠페인 공통값을 각 코드에 따로 적용하는 상한 원칙을 보존한다.

가입 이벤트의 대외 명칭은 미정이다. 내부 프로모션 이름을 임의로 회원에게 노출하거나 새로운 이벤트 명칭을 확정하지 않는다.

## 2. 제거할 기능과 보존 방식

사용자 요청으로 다음 기능을 현재 출시 코드에서 제거하는 범위로 바꾼다.

- 프로모션 이용권 종료 후 유료 이용 예약과 그 전용 화면·모달·진입 경로.
- 프로모션의 후속 결제 귀속·유료 전환 인정·갱신 매출 등 레퍼럴 성과 측정.
- 프로모션 성과 요약 카드·성과 조회 탭과 성과 전용 API/집계/백그라운드 처리.
- 프로모션 성과 XLSX와 관련 내보내기 경로. CSV로 대체하거나 숨은 API로 남기지 않는다.
- 가입 크레딧형에 대한 후속 결제 인정 기간·최초/최근 코드 귀속 등 정책 결정 항목.

기존 구현은 **Git 보존 브랜치**로 남기고, 현재 코드 안의 대량 주석·상시 꺼진 기능 플래그·화면에서만 숨긴 실행 코드로 보존하지 않는다. 정기결제·일반 구독의 다음 결제·재시도·환불·크레딧 원장 기능 전체를 지우라는 지시로 넓히지 않는다.

관리자의 참여 회원 조회와 상한 운영에 필요한 등록 건수는 성과 지표와 구분한다. 결제 성과를 제거해도 크레딧 지급의 원본 기록·사용/차감 원장·멱등키를 제거하지 않는다. 운영 DB 데이터 삭제·기존 회원의 이용권/크레딧 강제 회수는 이번 지시에 포함되지 않는다.

기존 이용권형의 종료 후 예약을 유지하겠다는 이전 답변은 철회됐다. 기존 이용권 발급 기능 자체의 유지 여부와 관계없이 그 예약 및 성과 측정은 이번 출시 범위에서 제거 대상이다.

## 3. Free 상태와 가입 혜택

- 이용 상태는 Free / Basic / Pro / Business로 다룬다. 유료 판매 등급은 Basic·Pro·Business 3개다.
- 활성 주 이용권이 없으면 Free를 적용한다. 가입 크레딧이 0이 되거나 만료되어도 Free가 사라져 ‘이용권 없음’으로 떨어지지 않는다.
- 유료·프로모션 등의 활성 주 이용권이 있으면 그 이용권을 적용하고, 종료 후 다른 활성 이용권이 없으면 Free로 복귀한다. 기존 해지·유예·만료 규칙을 바꾸지 않는다.
- Free는 지속 상태이며, 가입 혜택 크레딧은 가입 시 최초 1회 지급하는 별도 혜택이다. 기존 관리자 수량 설정을 사용하고 매월·Free 복귀 시 재지급하지 않는다.
- 요금제 카드에는 반드시 **‘가입 시 1회 N크레딧’**과 **‘가입 크레딧 유효기간: 가입일부터 D일’**을 구분해 표시한다. N과 D는 실제 가입 혜택 설정을 읽는다. Free 자체는 계속 유지되고, D일은 최초 가입 혜택 크레딧의 사용 기한임을 명확히 한다. ‘매월 N크레딧’이나 Free 상태의 종료일처럼 표시하지 않는다.
- 과거 무료체험 크레딧의 지급·사용·만료·중복 지급 방지 기록을 보존한다. 새 명칭 도입을 과거 지급 기록 삭제나 만료 연장의 이유로 삼지 않는다.

## 4. 계속 포함되는 요금제와 플러그인 작업

앞선 목록의 3·4·5·6번은 취소되지 않았다.

- 지속 Free 조회와 모든 소비자의 이용 상태 표시.
- 관리자 요금제별 허용 플러그인 설정 및 Basic ⊆ Pro ⊆ Business 저장 검증. Free 목록은 별도 정책이다.
- 앱에서 미제공 플러그인의 탐색·설치·화면 진입·작업 준비를 허용하고, 제한 대상 실제 실행에서 현재 이용 상태와 크레딧을 검사한다. 중간 유료 작업을 무료로 바꾸지 않는다.
- `/#price`와 `/pricing`의 공통 요금제 카드가 관리자/API 데이터를 읽도록 한다. 허용 목록을 화면별 등급 배열로 하드코딩하지 않는다.
- 기존 결제·월별 지급·만료·FIFO·환불·추가 구매 자격은 변경 지시가 없는 한 유지한다. 유효 추가 구매 크레딧의 사용 가능 여부와 신규 구매 자격을 구분한다.

플러그인 등록 자동 감지·관리자/앱 스토어 목록 동기화·분류/순서·전역 중지 운영은 계속 W18 후속이다.

## 5. 요금제 목업 제안 F

사용자가 선택한 목업은 [Claude Design 제안 F](https://claude.ai/artifact/Vir1fujgQnWxy2bWMGRTrD#artboard-f26af133c213)다. 브라우저에서 해당 아트보드의 선택 상태와 전체 화면 미리보기를 실제로 확인했다. 제목은 ‘제안 F — 모든 카드에 같은 플러그인 목록 ✓·✕, 충전은 구분선 아래 (아래 충전 = E-1)’이다. 내부 렌더링 파일명은 `MainF.dc.html`이다.

적용할 시각적 구성:

- Free를 맨 왼쪽에 둔 4개 카드와 월간/연간 선택.
- 모든 카드에 같은 플러그인 목록과 같은 행 순서를 표시하고 포함/미포함을 체크·X로 비교.
- 플러그인 목록 아래 구분선 뒤에 추가 크레딧 구매 가능 여부를 별도 표시.
- Pro·Business 상단 강조 띠와 카드 간 비교가 가능한 배치.
- 카드 아래 별도 추가 크레딧 상품 안내 영역.

목업의 **150크레딧·14일 체험·유료 가격/지급량·최대 할인율·추가 크레딧 상품·플러그인별 체크값은 확정 정책이 아니다.**

실제 적용 기준:

- Free 문구는 ‘가입 시 1회 N크레딧’으로 바꾸고, 별도 안내로 ‘가입 크레딧 유효기간: 가입일부터 D일’을 표시한다. N/D는 실제 설정을 읽는다. 목업의 ‘14일 체험’은 Free 이용 기간이 아니라 최초 가입 혜택 크레딧의 유효기간으로 명확하게 바꾼다.
- 가격·주기·할인·지급량·추가 크레딧 상품과 유효기간은 API 데이터를 사용한다. 목업 예시 숫자로 기존 정책을 덮어쓰지 않는다.
- 플러그인 행과 고객용 이름은 공통 표시정보, 체크·X는 관리자 저장 허용 목록에서 만든다. 목업의 기능 묶음과 실제 플러그인 ID가 정확히 대응하는지 확인한다.
- Free는 결제 없이 적용되는 상태다. 0원 자동결제 상품이나 유료 구독 계약을 만들지 않는다.
- `/#price`·`/pricing`은 기존 공통 카드 재사용을 유지한다. 목업 HTML 런타임·스크립트를 제품에 그대로 삽입하지 않고 Angular 컴포넌트와 기존 스타일 체계로 구현한다.

HTML 추가 첨부 없이 목업 열람은 가능했다. 로그인 안내가 일부 표시됐지만 제안 F 본문·비교 목록·렌더링 소스를 확인할 수 있었으므로 전체 접근 불가라고 안내하지 않는다.

## 7. 출시 완료 검증 기준

- 신규 가입 + 코드 없음: 최초 가입 혜택만 정확히 한 번 지급.
- 신규 가입 + 유효 코드: 최초 가입 혜택과 프로모션 지급 기록 각각 1건, 첫 로그인 잔액은 두 유효 지급분 합계.
- 기존 회원 로그인/재동의/가입 완료 뒤 입력: 가입 전용 혜택 지급 불가.
- 코드 형식·미존재·기간·중지·상한 오류와 마지막 자리 동시 가입: 정확한 안내, 잘못된 혜택 표시·초과 지급 없음.
- 가입 재시도·응답 유실·세션 발급 실패·두 DB 중 한쪽 장애 후 복구: 가입 혜택·프로모션 참여·원장 중복이나 누락 없음. 단순 로그인 후 일회성 후속 호출만으로 처리하지 않음.
- 관리자에서 회원→입력 코드, 코드→참여 회원 양방향 조회가 일치.
- 현재 프로모션 코드에 유료 이용 예약·레퍼럴 성과 API/탭·내보내기 진입이 남지 않음. 일반 결제 기능 회귀 없음.
- Free는 잔액 소진·만료 뒤에도 유지, 가입 혜택 재지급 없음, 카드 문구는 가입 시 최초 1회.
- Free/유료 허용 목록·공통 가격 카드·서버 실제 실행 검사가 일치. 미허용 작업 거절 전에 크레딧 차감 없음.
- 제안 F를 사용한 두 요금제 화면에서 관리자 변경값·월/연 토글·모바일·긴 목록·로딩/실패를 확인.

## 8. Google 인증과 가입 코드 입력의 순서

원격 dev의 현재 구현 순서는 `Google 인증 → 우리 API 콜백 → /signup/consent → POST /auth/signup/complete → 클리퍼 세션/앱 복귀`다. GoogleStrategy는 신규 회원을 생성하지 않고 Google 프로필과 기존 회원 여부만 반환한다. 콜백은 신규/재동의 대상에게 15분짜리 서명된 가입 대기표를 발급하고 동의 화면으로 보낸다. 기존 회원의 일반 로그인은 이 동의 단계 없이 끝날 수 있다.

선택 코드 입력란은 **Google에서 돌아온 뒤의 클리퍼 동의 화면**에 추가한다. 따라서 프로모션 코드를 Google 왕복 전에 받아 OAuth state에 싣거나 Google에 보내 보존할 필요가 없다. `SignupCompleteDto`에 선택 코드를 추가해 같은 요청의 가입 대기표와 함께 우리 서버로 보낸다. 서버는 대기표의 Google 계정과 실제 신규 생성 결과를 확인한 뒤 해당 회원의 가입 지급 의도를 보존한다.

현재 `signup-ticket.ts`는 대기표를 URL fragment에서 읽고 주소에서 지운 뒤 같은 탭 sessionStorage에 보관한다. 새로고침으로 대기표가 바로 없어지지는 않는다. 프로모션 코드 필드는 아직 없으므로, **현재 코드 입력이 보존·지급된다고 말하지 않는다.** 구현에서는 제출 실패 시 입력 유지, 새 대기표/다른 계정과 임시 입력 분리, 완료·취소·만료 시 정리를 검증한다.

기존 동의 화면은 기존 회원의 재동의에도 쓰인다. UI의 신규 표시만 믿지 않고 서버의 실제 `created` 결과/최초 가입 의도로 가입 전용 혜택을 제한한다. 앱에서 시작한 신규 가입도 같은 웹 동의 화면을 거쳐 마지막에 원래 앱으로 복귀하는 경로를 유지한다.

현재 경로 확인 근거: API `google.strategy.ts`, `auth.controller.ts`, `signup-ticket.service.ts`, `signup.service.ts`, `typeorm-signup-completion.repository.ts`; 회원 웹 `signup-consent.component.ts`, `signup-ticket.ts`. 해당 API 소스와 관련 테스트 9파일은 작업 폴더와 이번 fetch의 원격 dev에서 바이트 단위로 같음을 확인했다.

[구현 순서와 검증 계획](02-ai-booth-signup-free-implementation-plan.md).

현재 경로 회귀 검증: API 작업 폴더에서 `npm test -- --runInBand --runTestsByPath src/modules/auth/presentation/signup-flow.spec.ts src/modules/auth/application/signup-ticket.service.spec.ts src/modules/auth/application/signup.service.spec.ts src/modules/auth/infrastructure/typeorm-signup-completion.repository.spec.ts`를 실행해 **4 suites / 34 tests 통과**를 확인했다. 해당 파일은 fetch한 origin/dev와 같다. Google 응답은 테스트 대역이며 실제 Google 로그인이나 신규 프로모션 지급 완료를 검증한 결과가 아니다.
