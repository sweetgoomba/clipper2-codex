### 3.2 갱신과 재시도 사이에 취소를 알게 된 이유

11-07의 운영 구버전 dc04f1e…에는 외부 취소 감지·청구 차단이 없었다. 11-08의 교체 후 별도 취소 점검 작업이 과거 취소를 발견했다. 갱신 실패 자체가 외부 취소 조회를 촉발했다고 결론 내린 것이 아니다.

당시 일반 갱신과 갱신 재시도는 공통 청구 준비 단계에서 DB에 이미 확인된 외부 취소 기록을 검사했다. 매 갱신 직전에 토스에 직접 조회하는 기능을 이번 세션에서 새로 요구하거나 구현한 것은 아니다.

### 3.3 후처리 오류

결제 주문 failed, 구독 past_due, 유예 이용권 active는 서로 다른 상태다. past_due는 갱신 대금이 미납되어 재시도와 유예 종료를 관리하는 구독 상태이며, 단순히 결제 한 번 실패했다는 표현보다 구체적이다.

기존 후처리는 구독을 past_due로 둔 중간 UPDATE에서 next_retry_index를 NULL로 만들었다. DB의 subscriptions_recovery_state_check는 past_due의 재시도 번호를 요구해 SQLSTATE 23514로 거절했다. 트랜잭션이 롤백되어 이용권·크레딧 정리도 완료되지 않았다.

최종 수정은 종료 전까지 재시도 번호를 유지하고, 종료 상태로 전환하는 UPDATE에서 관련 재시도 정보를 함께 정리한다. 결제·실패 이력을 삭제하는 변경이 아니다. 과거 데이터 혼재만의 문제가 아니므로 런칭 전 DB 초기화와 별개로 필요했다.

당시 후처리 작업은 반복 실패 1건으로 확인됐으며 한 조회 시점의 시도 횟수는 1,668회였다. 다른 수동 확인 필요 건 전체를 같은 오류로 취급하지 않았다. 오래된 retry_at을 현재로 옮기거나 외부 취소 차단을 풀어 추가 청구하는 운영 복구는 하지 않았다.

## 4. 외부 취소와 웹훅 결정 및 라이브 검증

### 4.1 최종 처리 구조

- 모든 과거 paid 주문을 반복 순회하던 scanNext()와 그 순회 실행 경로를 제거했다.
- 토스 웹훅 수신·저장·재처리, 발견된 취소 건 후처리 재시도, 주문 한 건의 관리자 재확인은 유지했다.
- 정상 환불은 클리퍼 어드민에서 진행하고, 예외적인 외부 취소는 웹훅으로 받아 처리한다.
- 웹훅 수신 성공과 내부 후처리 완료를 별도 상태로 다룬다. HTTP 200은 저장 성공을 뜻하며 이용권 정리 완료와 같지 않다.
- 결제 상태 변경 알림을 받은 뒤 토스에서 해당 결제를 다시 조회해 주문·금액·통화·결제 유형·취소 거래를 검증한다.

중복 방지는 inbox의 dedupe_key 고유성, FOR UPDATE SKIP LOCKED와 작업 점유, 후처리 claim token, 회수 원장 고유 키와 트랜잭션 잠금으로 유지한다. 전체 순회 제거는 이러한 동시 처리 보호를 없애는 변경이 아니다.

최초 감지 출처는 당시 아직 가동 중이던 scan이었다. 웹훅 수신과 처리, 후처리 성공은 확인했지만 이 한 건으로 전체 순회 없이 웹훅만이 후처리를 시작했다는 운영 E2E까지 확정하지 않았다. 순회 제거본 반영 후 그 경로를 다시 시험하는 항목이 남았다.

### 4.4 실패 대응의 범위

서버에 도착하기 전 또는 저장 전 실패는 Clipper 관리자에 행이 없을 수 있어 토스 전송 기록을 확인한다. 받은 웹훅 처리 실패와 취소 후처리 실패는 서로 다른 관리자 상태로 표시한다.

당시 토스 문서 조사에서는 같은 등록 URL로 최대 7회 재전송 후 최종 실패 이메일 안내를 확인했고, 각 실패마다 이메일을 보낸다고 단정하지 않았다. 실제 수신 이메일 주소·관리 위치는 확인하지 못했다. 이 기록은 당시 조사 결과이며 현재 정책·수신 설정을 새로 검증한 운영 문서가 아니다.

후처리 재시도·운영 확인 기록은 유지하지만, 미수신 알림을 Clipper가 모두 알아내는 전용 화면이나 웹훅 장기 실패 운영자 자동 알림을 이번 세션에서 완성한 것은 아니다.

일반 주문 재확인은 requested, succeeded, failed 이벤트를 저장한다. 실패도 인증 운영자와 안전 오류 코드가 남고 공통 이력 그리드에서 한글로 표시된다. succeeded는 재확인 실행이 끝났다는 뜻이며 미확정 결제가 승인·지급 완료됐다는 뜻으로 바꾸지 않는다.

오래된 CS 메모를 최근 자동 실행자로 표시하지 않도록 실행 종류와 실제 시각을 비교한다. 이미 해결된 조회 실패는 검증 성공 시 해결 시각을 저장해 미해결 목록에서 제외한다. 정상 paid+succeeded도 웹훅 후처리 완료 필터에 포함하며 웹훅 전달 처리 필터는 독립적으로 유지한다.

## 6. 마이페이지 A안과 구독 정책

### 6.1 확정 UI

기존 구조를 유지하는 A안을 채택했다. 종료 카드에서 당초 이용 예정 종료일을 빼고 실제 구독 종료 일시·사유, 환불 금액·완료 여부, 크레딧 회수·만료 결과와 다음 자동결제 중단을 표시한다. 종료된 구독의 원래 예정일을 실제 종료일로 재사용하지 않는다.

확정 문구는 구독이 종료되었습니다 / 현재 Free 요금제를 이용 중입니다 / 구독 해지다. 실제, 사용자 요청으로 같은 불필요한 표현과 현재 구독이 있는 듯한 설명을 정리했다. 정상 이용 안내는 현재 ○○ 요금제를 이용 중입니다로, 기간은 이용 기간 종료일로 정리했다. 환불 내역 보기 동선은 기존 결제내역 화면으로 연결한다.

종료된 이용권과 환불 기록의 연결은 이번 회원·구독·계약 기간에 해당하는 사실을 표시하기 위한 것이다. 나중에 환불했다는 이유로 과거 자연 만료를 환불 종료로 바꾸지 않는다. 금전 환불 완료와 아직 진행 중인 이용권·크레딧 후처리도 구분한다.

초기 21개 목업은 실제 코드와 대조해 임의 상태를 제거·통합했다. 결제창만 열었다가 나간 미완료 신청을 계속 대기 카드로 보여주지 않는다. 내부 코드에 존재하는 모든 상태를 별도 사용자 카드로 무조건 노출하지 않는다. 비교용 B·C안이나 초기 목업 번호를 최종 요구사항으로 사용하지 않는다.

### 6.3 유예 중 해지와 정상 해지

유예 이용 중 사용자가 구독 종료를 확인하면 재시도를 중단하고 유예 이용권을 즉시 회수한다. 해당 만료 구독 기간의 크레딧을 정리하고 무료 이용 상태로 돌린다. 가입 크레딧·다른 추가 크레딧을 함께 회수하지 않는다.

정상 active 구독은 다음 자동결제만 취소하며 이미 결제한 이용 기간은 유지한다. 다른 팀원이 확정·구현한 정상 자동 결제 취소 모달은 기존 코드에 있었고 이번에는 유지했다. 유예 종료 확인창만 구분했다.

cancel 요청은 retain_paid_period와 end_grace 의도를 현재 잠긴 상태와 대조한다. 오래된 해지창이 새 첫 결제 예약을 취소하지 못하도록 예약 취소 분기에도 검사한다. 불일치하면 SUBSCRIPTION_CANCELLATION_MODE_CHANGED로 변경 없이 거절한다. mode 없는 정상 예약 취소 흐름은 유지한다.

처리의 원자성·롤백·멱등성과 진행 중 청구·카드 변경·환불·외부 취소 차단을 유지했다. accountMutationVersion으로 focus·재시도·플랜 변경·해지·카드 변경 전후의 늦은 조회와 오류가 최신 화면을 덮지 못하도록 했다.

### 6.4 메일 세션과 합친 결과

환불 신청과 플랜 변경 차단의 원래 구현은 [별도 세션 기록](2026-11-10-refund-plan-change-guard.md)을 따른다. 이번 통합에서는 메일 쪽 pendingRefundRequestId와 환불 검토 중 플랜 변경 차단·오류 안내를 lifecycle 표시와 결합했다. 응답에서 ID를 생략하면 기존 값을 보존하고 명시적 null이면 해제하는 updateSubscription 규칙을 유지했다. lifecycleReader 의존성 자리 뒤에 mailEvents를 붙여 생성자 인자 충돌을 해결했다. 지급 완료와 갱신 첫·최종 실패의 트랜잭션 내 메일 이벤트 등록을 보존했다.

### 8.3 메일 통합 후 추가 검증

메일 변경과 합친 뒤에는 실제 DB 교착 테스트 1개가 간헐 실패했다. 테스트가 PostgreSQL이 항상 탈퇴 쪽을 중단한다고 가정한 것이 원인이었다. 어느 쪽이 중단되어도 가능한 상황이므로, 탈퇴 쪽이 중단되면 ConflictException과 전체 상태 보존을, 카드 변경 쪽이 40P01로 중단되면 rollback 후 정상 탈퇴·종료·fence를 확인하도록 보완했다. 즉시 rejection handler를 연결하고 production 잠금 동작은 변경하지 않았다. 기존 단위 테스트의 40P01 변환 검증도 유지했다.

독립 검증에서 실패한 사실과 초기 PG 실패 로그를 보존했고, 최종 13개 DB 묶음 268개가 통과한 결과를 별도로 기록했다. 단순 재실행 성공만으로 실패를 숨기지 않았다. 충돌 해결 코드와 보완 테스트를 추가 읽기 전용 리뷰로 확인했다.
