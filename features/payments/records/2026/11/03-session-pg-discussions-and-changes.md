# 이번 세션의 PG・결제 논의와 변경 범위

> **후속 상태:** [11/03 최종 dev 통합](../../../../plugin-catalog/records/2026/11/03-store-plan-badges-dev-merge.md)으로 W19의 추가 크레딧 승인 보완을 포함한6개 제품 저장소는 커밋·푸시·원격 dev 반영됐다. 아래 미커밋 문구는 이 결제 요약 작성 당시의 상태다. 100원 업그레이드 문제는 계속 이번 범위에서 제외한다.

2026-11-03 KST 정리. 이 문서는 프로모션과 섞여 진행된 결제 관련 작업만 분리한 인계다. 아래 ‘확인’은 연결한 당시 소스·시험·공식 문서 조사 기록에 근거하며, 이번 문서 정리에서 실결제를 실행하거나 외부 정책을 새로 조회한 것은 아니다.

**다른 세션 담당:** 토스 카드 최소 결제금액 100원 때문에 업그레이드 즉시 적용 대신 다음 결제일로 예약되는 문제는 사용자 지시로 이번 세션의 구현·TODO·검증 범위에서 제외한다. 해결 방식을 여기서 정하거나 관련 코드를 수정하지 않는다. 다른 세션의 브랜치·완료 상태는 확인하지 않았으므로 완료로 표시하지 않는다.

## 1. 실제 수정한 결제 코드

### 추가 크레딧 승인 직전 구매 자격 재검사

이용권이 있을 때 추가 크레딧 주문을 만들고 결제창을 열어 둔 뒤, 이용권이 종료·회수된 상태에서 결제하는 경로를 보완했다.

- 주문 생성과 아직 승인 시작 전인 주문의 승인 직전에 같은 `requirePurchaseAccess` 판정을 사용한다.
- 활성 유료 구독 또는 활성 프로모션 이용권이 있어야 신규 추가 크레딧을 구매한다. 지속 Free·크레딧만 보유한 상태·관리자 지급 이용권만 있는 상태는 신규 구매 자격이 아니다.
- 자격을 잃었으면 토스 승인 호출 전에 거절하고 회원에게 이유를 안내한다.
- 이미 승인됐거나 승인 진행·확인 중인 주문은 기존 멱등·결과 확인·복구 경로를 유지한다. 이를 신규 구매처럼 중간에 차단하지 않는다.
- 추가 크레딧의 사용 자격과 구매 자격은 별개다. 정상 구매분은 이용권이 종료돼도 자신의 만료일까지 사용할 수 있고, 실행 가능한 플러그인은 사용 시점의 등급을 따른다.

원래 10/28 브랜치의 API 6파일 보완이며, 현재 W19 작업 브랜치에도 보존했다. 당시 관련82개/전체4,845개 테스트와 빌드가 통과했다. [원인·코드·정책 대조·검증](../../../../promotions/records/2026/10/28-topup-confirmation-access-and-existing-policy-check.md).

### 이전 결제·크레딧 감사 수정

현재 W19 이전에도 별도 감사에서 A01–A17과 추가 복구 경계2건을 수정했다. 환불 철회/갱신 경합, 승인 결과가 미확정인 업그레이드 복구, 기존 정기 크레딧 정리, 가용 잔액 판정, 월별 지급일, 현재 이용권 표시 등을 포함한다. 이 수정들은 **2026-10-26 원격 dev 병합·푸시 완료**이며 미해결17건으로 재등록하지 않는다.

## 2. 조사·설명한 내용: 새 결제 정책 구현과 구분

| 주제 | 확인한 내용 | 이번 처리 |
| --- | --- | --- |
| 구독 업그레이드 차액의 MID | 기존 구독의 billingKey와 billing 키 세트로 `/v1/billing/{billingKey}` 호출 | 기존 코드와 공식 안내를 조사. MID 선택 변경 없음 |
| 추가 크레딧의 MID | 별도 ONE_TIME 키 세트와 `/v1/payments/confirm` 사용 | 기존 경로 확인. 구독 차액을 이 경로로 옮기지 않음 |
| 정기결제일 외 추가 청구 | 토스 공개 안내는 가맹점이 금액·호출 시점을 관리하는 빌링을 설명함 | 현재 설계와의 부합 여부를 검토. 해당 MID 특약/서면 승인 확보와는 구분 |
| 다른 서비스의 업그레이드 | Notion·GitHub·Stripe·Paddle의 즉시 정산/등록 수단 청구 공식 사례 | 사례 조사. 이들이 토스 MID를 사용한다는 의미 아님 |
| 회원의 직접 변경 | 회원이 동의 후 상품 변경·구독 취소·카드 변경 가능 | 관리자 승인 절차가 필요한 구조가 아님을 확인 |
| 업그레이드 다음 정기결제 금액 | 새로 선택한 상품의 계약 가격 | 과거 Basic 결제액에 이전 차액을 계속 더하는 방식 아님 |
| 즉시 변경의 기간 | 결제 성공 시점부터 새 상품의 전체 이용 기간과 결제 기준일 시작 | 기존 동작 확인. 모든 서비스의 보편 정책이라고 일반화하지 않음 |
| 토스 문의 | 비정기일에 기존 빌링키로 동의받은 차액을 청구해도 되는지 묻는 문구 작성 | 메시지 발송·토스 회신·개별 계약 승인 완료 아님 |

공식 출처와 코드 대조는 [빌링 MID 조사 기록](../../../../promotions/records/2026/11/02-upgrade-charge-billing-mid-official-evidence.md)에 모았다. 공개 안내에 부합한다는 판단과 클리퍼 MID의 계약상 확정은 구분한다.

## 3. 유지한 요금제 변경 원칙

아래는 일반 정책이며, 위에서 다른 세션으로 제외한 최소 청구액 분기와 섞어 해결 완료로 표현하지 않는다.

| 변경 | 적용 원칙 |
| --- | --- |
| 월간 → 월간 | 상향 즉시 / 하향 다음 결제일부터 |
| 월간 → 연간 | 동일 등급·상향 즉시 / 하향 다음 결제일부터 |
| 연간 → 월간 | 동일·상향·하향 모두 불가 |
| 연간 → 연간 | 상향 즉시 / 하향 다음 결제일부터 |

동일 등급·동일 주기로 그대로 바꾸는 요청은 변경 없음이다. 이번 프로모션/Free 요구로 위 변경 유형 정책을 다시 설계하지 않았다.

즉시 변경 추가 청구액은 새 상품 전체 가격에서 기존 계약의 인정 잔여 가치를 공제한다. 기존 코드는 남은 기간 기준과 미사용 계약 크레딧 기준으로 각각 잔여 가치를 계산하고, **더 작은 잔여 가치**를 공제한다(같은 뜻으로 두 계산의 추가 청구액 중 큰 금액을 선택). 단순한 월 가격 차이 또는 현재 월 잔액만의 계산은 아니다. 상세 근거는 `subscription-plan-change-policy.ts`와 이전 정책 점검 기록을 따른다.

결제 성공 후에는 이전 구독 이용권의 정기 지급분을 정리하고 새 상품의 첫 월 크레딧 전체를 지급한다. 새 월 지급분의 만료는 새 월별 이용 기간이다. 연간 계약도 매월 지급·매월 만료하는 기존 원칙을 유지한다. 별도로 추가 구매한 크레딧과 가입 혜택 등 다른 출처 지급분은 자신의 수량·원래 만료일을 유지한다.

## 4. 추가 크레딧 가격·기간·권한 논의

- 같은 추가 크레딧 상품의 가격을 이용권 등급별로 달리하지 않는 방향을 정리했다. 정기 이용권에 포함된 크레딧의 단위 가격과 별개의 항목이다.
- 개발·로컬의 실제 상품은 10/28 확인 당시 `validityDays=30`이었다. 1년으로 단정했던 설명은 정정했다. 운영 응답은 당시502여서 운영 상품도30일이라고 확정하지 않았다.
- 주문에 상품의 수량·가격·유효일수를 보존하고 승인 성공 시점부터 만료일을 계산한다. 이용권 변경으로 추가 구매분의 기간이 초기화되거나 Pro 권한이 따라붙지 않는다.
- 예: Pro 중 구매한 추가 크레딧이 남아 있는 채로 Free로 돌아가면, 만료 전 잔액은 Free에서 허용한 플러그인에 사용할 수 있다. Pro 전용 기능 이용 자격까지 연장되지는 않는다.
- 가격 우회·권한 우회를 피하려는 취지와 전략실 확인 문구를 작성했다. 문의문 작성 자체를 상대 팀의 확정 답변으로 취급하지 않는다.

## 5. 현재 한계와 인계

실제 토스망의 신규 승인·자동 청구·환불을 이 문서 정리에서 검증하지 않았다. 테스트의 PostgreSQL을 ‘PG’로 줄여 쓴 옛 기록은 결제사 실결제 검증과 구분한다.

현재 W19 변경은 로컬 미커밋이며 공유 dev/운영 배포 완료가 아니다. 추가 크레딧 승인 보완을 별도 분리 커밋할지 여부는 추후 실제 통합 요청에서 판단한다. **100원 최소 청구 문제는 다른 세션 담당이므로 이 문서 때문에 병행 구현·새 TODO·새 시험을 시작하지 않는다.**
