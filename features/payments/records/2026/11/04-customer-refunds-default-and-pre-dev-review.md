# 고객 환불 신청 기본 제공과 dev 반영 전 독립 검증

2026-11-04 KST. 사용자가 `CUSTOMER_REFUNDS_ENABLED` 자체를 없애고 고객 신청과 관리자 승인 환불을 기본 흐름으로 제공하도록 요청했다. 이후 dev 반영 전에 다른 검증 세션의 독립 검토를 필수로 추가하도록 요청했고, 실제 푸시 전에 적용했다.

## 기본 환불 흐름

**고객의 결제별 조건 확인 → 환불 신청 → 관리자 승인 대기 → 관리자의 재검증·승인 → 토스 취소·내부 정리**로 동작한다. 신청 접수만으로 토스 취소나 내부 환불 건을 만들지 않는다.

- API 두 고객 컨트롤러의 ConfigService 의존성과 플래그 검사, 비활성 오류를 제거했다. 환경 설정이 없거나 이전 설정이 false여도 기능을 차단하지 않는다.
- 이전 조회 응답의 `requestsEnabled`도 API·OpenAPI·클라이언트 타입에서 제거했다. 새 활성화 플래그로 대체하지 않았다.
- 인증, 회원 소유권, 환불 가능 조건, 요청 제한, 중복 방지 키, 안내 버전, 관리자 권한과 승인 시 재검증은 유지했다.
- 클라이언트 목 API는 실제 화면이 사용할 결제 UUID와 기본 조회·승인 대기 접수·상세·중복 요청·신청 취소 흐름을 제공한다. 고객의 직접 결제취소 경로는 제공하지 않는다.
- 관리자 소스와 DB 스키마는 이번 변경 대상이 아니다.

## dev 반영 전 필수 절차

이 PG 작업에서 이후 dev 반영은 다음 순서를 따른다.

1. 사용자 요구와 변경 범위를 명시하고, 반영할 정확한 커밋 또는 소스 tree의 테스트·빌드를 완료한다.
2. 구현을 맡지 않은 별도 컨텍스트의 검증 세션 또는 에이전트에 대상 SHA·변경 내용·검증 근거를 전달한다. Astra를 사용하지 않는 사용자 선택을 유지한다.
3. 검증 결과를 이 세션으로 받아 확인한다. P0/P1/P2 발견 사항은 수정하고 해당 수정 범위를 재검토받는다. 전체 테스트는 실제 변경이나 실패가 생겼을 때 다시 실행한다.
4. 최종 검증 대상과 실제 푸시할 tree가 같은지 확인하고, 최신 원격 dev를 다시 가져와 충돌·기준 변경 여부를 확인한다. 코드가 바뀌면 영향을 받는 검증을 갱신한다.
5. 검증 통과를 기록한 뒤에만 dev에 푸시하고 원격 SHA를 확인한다. 검증을 받은 로컬 커밋이 있다는 사실을 원격 반영 완료로 표현하지 않는다.

이번 변경은 최초 독립 검토에 이어 사용자가 추가한 별도의 dev 반영 전 검토도 수행했다. 두 번째 검증은 커밋 자체를 읽고 Spec PASS / Quality PASS, P0/P1/P2 없음으로 판정했다. [검토 원문](04-customer-refunds-default-independent-review.md)과 [푸시 전 판정·원격 확인 증거](04-customer-refunds-default-evidence.json)를 보존했다.

## 최신 원격 기준과 로컬 실행

수정 시작 시 API `197af45`, Client `aabcf3d`가 최신 원격 dev와 같았고 그 위에 이번 변경을 작성했다. 푸시 후 두 작업 폴더는 새 원격 dev와 일치한다. 관리자·앱 Angular·Nest도 조회 당시 최신이었다.

Electron 작업 폴더는 원격보다2커밋, Python은3커밋 뒤였다. 이 앱 저장소들을 이번 웹 수정의 최신성으로 확대해 설명하지 않으며, 작업 폴더나 실행 중 앱을 변경하지 않았다.

기존에 보존했던 API3311도 이번 확인 시 이미 종료돼 있었다. 새 API 실행 빌드는 준비했고 최대365일 검증과 플래그 없는 코드가 생성됐음을 확인했다. 전용 시작 스크립트에서는 해당 export 한 줄만 제거했다. API3311·웹4203/4204를 새로 시작하지 않았으며, 공유 DB·키·다른 실행 환경은 변경하지 않았다.

운영 배포와 실제 토스 전체 연동 검증은 이 결과에 포함하지 않는다. 기존의 미검증 항목은 [통합 인계](04-two-session-pgops-summary.md)를 따른다.
