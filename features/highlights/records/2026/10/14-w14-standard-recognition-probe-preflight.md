# W14 — SeetaFace6 일반형 비교 실행 전 준비

2026-10-14. 사용자의 “진행해 다음”에 따라 다음 얼굴 인식 후보의 공식 자료, 파일, 전처리, 비교 범위를 조사했다. 이 문서는 실행 전 준비 기록이다. 새 모델은 아직 내려받거나 실행하지 않았고 제품 코드도 수정하지 않았다. 처음 정한 “새 모델 다운로드는 별도 범위” 조건에 따라 제한된 비교 실험의 범위를 구체화했다.

## 1. 현재 결정

- 제품은 YuNet + SFace를 사용한다. AuraFace는 비교 후보로 유지한다.
- 방금 비교한 SeetaFace6 **Light**는 이번 도입 경로에서 채택하지 않는다. [실제 시험 결과](14-w14-seeta-light-comparison-result.md)
- 다음 비교 후보로 **SeetaFace6 일반형 `face_recognizer` (ResNet-50)**을 제안한다. Light와 구조, 가중치, 입력 크기, 출력 차원이 다르다.
- 일반형이 Clipper 영상에서 더 정확하다는 결과는 아직 없다. 공식 상업 이용 안내가 있고, 현재 쓰는 ONNX Runtime으로 비교할 경로가 있다는 점이 후보 선정 이유다.
- 얼굴 매칭 품질 개선은 여전히 미완료다. 지금 사용자에게 얼굴 정답을 다시 입력하거나 결과를 내보내 달라고 요청할 필요는 없다.

## 2. 이번에 비교한 선택지

| 선택지 | 검토 이유 | 현재 제약 | 판단 |
|---|---|---|---|
| SeetaFace6 일반형 ResNet-50 | 공식 상업 이용 안내, Light와 다른 1,024차원 특징, 기존 ONNX Runtime 활용 가능성 | 모델 파일 약 102.5 MB. 실제 CPU 실행, 원본과 변환본의 일치, 작은 무대 얼굴 성능은 미확인 | 제한 비교 1순위 |
| PETALface (WACV 2025) | 저해상도 얼굴과 참조 사진·영상 사이의 품질 차이를 다룬 연구 | 선택 가중치 약 861 MB. 품질 평가 모델과 LoRA가 필요하며, 현재 구조에서의 ONNX·CPU 배포 및 상업 재배포 조건이 미확인 | 현재 시험에서 보류 |
| GhostFaceNetV1 | 가벼운 구조와 제공자의 IJB 계열 평가 | 코드의 MIT 표시만으로 해당 H5 가중치, 학습 자료, 제3자 ONNX의 사용 조건을 확정할 수 없음 | 보류 유지 |
| dlib / Taguchi | 작성자의 공개 배포 경로 | 대상 운영체제용 wheel, 네이티브 빌드, 정렬 전환 부담이 있으며 새 성능 근거가 없음 | 예비 후보 유지 |

PETALface 논문의 “0.48%”는 학습 중 조정하는 파라미터의 비율이다. 배포 파일이 작다는 뜻은 아니다. 공식 Hugging Face 파일 목록에서 선택 가중치의 크기 861,129,401바이트를 확인했다. 기반 가중치와 학습 자료의 권한 관계는 확인되지 않았다. WebFace 공식 링크도 이번 조회에서 응답하지 않았다. 이를 상업 재배포 허용이나 금지의 확정 근거로 쓰지 않는다.

## 3. Light와 일반형의 차이

| 항목 | 시험한 Light | 비교를 제안한 일반형 |
|---|---|---|
| 구조 | MobileFaceNet | ResNet-50 |
| 원본 파일 | `face_recognizer_light.csta` | `face_recognizer.csta` |
| ONNX 파일 크기 | 4,714,634바이트 | 102,530,399바이트 (Git 메타데이터) |
| 얼굴 정렬 | ArcFace 방식, 112 × 112 | Seeta single 방식, 256 × 256 |
| 모델 입력 | BGR 112 × 112, float32 값을 255로 나눔 | BGR 256 × 256 정렬 후 중앙 248 × 248, float32. 외부에서 255로 나누지 않음 |
| 출력 처리 | 512차원, L2 정규화 | 1,024차원, 제곱근 1회 후 L2 정규화 |

일반형 원본의 메타데이터에는 정렬 항목이 생략돼 있다. 공식 C++ 코드의 기본 single 방식과 변환 프로젝트의 Normal 설정을 대조했다. 실제 가중치를 확보하면 파일 내부 명세와 그래프를 다시 확인해야 한다. 기존 Light나 SFace의 112 × 112 정렬 이미지를 확대해 쓰지 않는다. 원본 프레임과 같은 YuNet 특징점 5개에서 새로 정렬한다. 입력 크기가 커져도 원본에 없는 얼굴 정보가 복구되지는 않는다.

후처리에도 차이가 있다. 공식 C++ 코드는 출력에 `sqrt(x)`를 적용하고, 제3자 C# 코드는 `sqrt(max(0, x))`를 적용한다. 시험 시 실제 출력에 음수나 유효하지 않은 값이 있는지 확인하고 두 방식의 결과를 대조한다. 처리 오류를 정상적인 미매칭으로 기록하지 않는다.

변환 저장소의 고정 revision은 `3cefcf6896a2e7268add82ea89f720271a825157`, 공식 인식 코드 revision은 `55506482e72bb14b3bb0df7a91249dceebb3ebaf`다. 공식 `FaceAlignment.cpp`에서 single 방식의 특징점 5개 기준 위치를 확인했다. 변환 파일의 실제 연산자와 원래 TenniS 런타임의 픽셀 단위 일치는 아직 검증하지 않았다.

## 5. 비교 방법과 통과 기준

입력은 기존 참조 사진 23장, 개발 자료 135행, 안무 관측 353행, 추가 영상 34행으로 고정한다. 안무 관측은 유효 얼굴 309개와 기존 연결 실패 44개로 구분한다. 총 545행 중 새 정렬 전에 사용할 수 있는 입력은 최대 501개다. Light에서 정렬에 실패한 개발 자료 2개도 원인을 보존하고, 일반형의 새 정렬 결과를 따로 확인한다.

메인 인물의 위치, 몸 경로, 구간, 얼굴 상자, YuNet 특징점 5개, 참조 사진은 동일하게 사용한다. 일반형이 요구하는 인식 가중치와 입력·출력 처리만 바꾼다. SFace와 AuraFace의 저장된 결과는 비교 기준으로 유지한다.

1. 승인된 파일을 취득하고 원본 연결, 라이선스, 크기, SHA-256을 확인한다.
2. 실제 모델 그래프와 전후처리를 확인한다. 정렬 검증용 입력을 점검한 후 원본·모델·설정·픽셀·실행 코드의 해시와 OS·장치를 기록한다.
3. 고정된 임의 입력과 참조 사진 1장으로 CSTA와 ONNX의 수치를 비교한다. 이는 원래 TenniS 런타임의 독립 검증은 아니다.
4. 참조 사진과 개발 자료만 먼저 추론한다. 얼굴 특징의 평균을 쓰는 한 가지 방식으로 개발 자료에서 기준을 정하고 평가 전에 고정한다.
5. 안무와 추가 영상을 평가한다. 얼굴마다 후보 점수, 거부 이유, 처리 실패, 멤버별 정답 손실과 회복을 기록한다. 같은 안무 대상 35개와 몸 경로 37개의 판정은 별도로 계산한다.
6. 계산을 독립적으로 검산하고 원본·메인 위치·얼굴을 비교 화면에서 확인한다. 최종 구간이 보류됐더라도 몸 경로 안에서 발생한 오분류를 기록한다.

다음 검증으로 넘어갈 최소 조건은 두 집합, 즉 식별 가능한 안무 얼굴 28개와 추가 영상 얼굴 19개에서 모두 SFace 이상의 정답 수를 얻고, 적어도 한 집합에서 정답을 늘리면서 오분류를 늘리지 않는 것이다. 사용자 확인 지점인 105.105초의 SFace 정답도 유지해야 한다. 이미 확인된 메인 인물·몸 경로의 모순을 늘리거나 등록 외 인물 얼굴 5개에 잘못 이름을 붙여서도 안 된다. AuraFace와의 차이, 기존 정답의 개별 손실도 모두 보고한다. 정답을 알 수 없는 얼굴 5개의 보류는 정답 처리로 세지 않는다. 25.759초 다니엘과 61.6616초 혜인은 필수 점검 사례다.

이 조건을 충족해도 곧바로 제품 모델을 바꾸지 않는다. 안무 얼굴 34개는 개발 자료와 같은 프레임이며 추가 영상도 이미 사용한 회귀 자료다. 이후에는 새 촬영 자료의 독립 평가와 macOS Apple Silicon·Windows x64 패키징 검증이 필요하다. 평가 결과를 보고 기준값을 다시 맞추지 않는다.

## 6. 실행 상한과 이번에 실제로 한 일

제안한 실행 환경은 기존 Python 3.11·ONNX Runtime 1.24.4 CPU 평가용 가상환경이다. 배치 크기 1, 내부 스레드 2개를 사용한다. 사전 수치 대조를 포함해 총 추론 호출은 **600회**, 실행 감독 시간은 **20분**, 최대 메모리는 **4 GiB**로 제한한다. 새 패키지 설치, 제품 수정, 유료 API, Build5는 범위에 포함하지 않는다. 다른 가중치의 추론이나 몸·자세·얼굴 검출·구간 계산 변경도 포함하지 않는다.

이번에 실제로 수행한 일은 다음과 같다.

- 새로 읽은 웹 문서와 메타데이터 9개(공식 ZIP의 HEAD 응답 포함), 기존에 고정한 소스 9개 등 총 18개의 해시를 확인했다.
- 기존 원본, 정답, 참조 사진, 비교 결과 등 관련 입력 88개의 해시가 일치함을 확인했다. Light 전용 정렬 이미지는 일반형의 입력으로 재사용하지 않는다.
- 모델 가중치 다운로드와 추론, 패키지 설치, 제품 및 공통 모듈·W13 코드 수정은 각각 0건이다.
- WebFace 문서 조회 실패도 그대로 기록했다. 조회 실패를 사용 허용의 근거로 해석하지 않는다.

준비 산출물은 `/Users/jina/project/adlight/.worktrees/shared-reference-face-matching-20261013/evaluation-output/candidate-comparison-20261014/recognition-next-v2/`의 `probe-proposal.json`과 `sources/manifest.json`에 있다. 이 파일은 실행 승인이나 성능 결과를 뜻하지 않는다. **남은 입력은 위 신규 파일과 제한된 비교 범위에 대한 승인 한 건이다. 얼굴 정답을 다시 작성하거나 내보낼 필요는 없다.**

## 7. 공통 모듈과 W13 인계

시험 코드는 기존 격리 평가 영역에 둘 예정이다. 현재까지 공개 API를 바꿔야 할 근거는 확인되지 않았다. 일반형의 새 1,024차원 얼굴 특징은 모델 SHA-256, 정렬 방식, 전처리, 제곱근 후처리, 출력 정규화, 거리 계산 방식, 실행 엔진 버전별로 구분한다. 참조 사진 23장도 이 새 경로에서 특징을 다시 만든다. Light, AuraFace, SFace의 저장된 특징과 캐시, 판정 기준은 섞지 않는다.

W14는 공통 API, 검증용 입력, 격리 평가를 맡는다. W13은 메인 인물, 몸 경로, 구간, 멤버 연결, 크롭, 안무 제품용 연결 코드를 맡는다. 유효한 후보가 나오면 공통 계약 확인 → 기존 소비자 호환성 검증 → 선택 가상환경과 모델 준비 → macOS Apple Silicon·Windows x64 패키징 → 합의한 순서의 병합으로 진행한다. 이번 지원 대상에 Mac Intel은 포함되지 않는다. 다른 채팅으로 메시지를 보내거나 새 세션을 만들지 않았고, 커밋·푸시·병합도 하지 않았다.
