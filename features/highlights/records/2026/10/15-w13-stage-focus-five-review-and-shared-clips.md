# W13 — 72번 추가 5곳 사용자 확인과 다중 인물 장면

## 사용자가 확인한 것

- 72번 노트북의 다음 검토 1·2번(189.256–192.192초, 55.389–56.573초)은 오른쪽 결과가 맞다. 이는 그 두 구간에 대한 사용자 평가이며 모든 프레임·정확한 클립 경계의 정답은 아니다.
- 3번(15.816초): 화면에 보이는 세 명 가운데 **중앙 인물**이 주요 인물로 보이는데, 빨간 상자는 왼쪽 인물을 선택했다. 사용자 판정은 오선택이다.
- 4번(43.911초): 빨간 상자가 실제 주요 인물을 선택했다. 자동 점검이 찾은 ‘가장 큰 얼굴과 선택 몸 상자 불일치’가 이 장면에서는 오류를 뜻하지 않는다.
- 5번(149.883초): 세 명 가운데 한 명만 고르는 것이 적절하지 않다. 사용자는 셋 모두를 이 장면의 하이라이트 대상으로 보고, 각 인물의 결과 목록에 같은 장면이 들어가길 원한다. **이 시각은 요구 예시이며 정확한 시작·끝은 아직 정해지지 않았다.** ‘군무라서 아무에게도 배정하지 않음’과 구분한다.

## 저장 관측과 원인

- 3번에서는 기존 65B가 15.749초부터 임시 몸 추적 52(왼쪽)를 단독으로 골랐다. 72번은 15.816초의 기존 `uncertain` 틈을 바로 앞의 52번으로 이어 메웠다. 중앙 몸 추적 56도 저장 관측에 있다. 따라서 **3번 오류의 첫 선택은 72번의 새 몸 후보 전에 발생**했고, 72번은 그 오류를 연장했다.
- 이 시각의 중앙 얼굴은 가장 크게 검출됐지만, 72번의 ‘큰 얼굴’ 입력 조건(화면 너비의 12%, 전체 면적의 2.5%, 다음 얼굴 면적의 2.5배)을 충족하지 않아 선택기로 전달되지 않았다. 문턱을 단순히 낮추는 것은 4번에서 맞는 몸을 바꿀 위험이 있다. 4번의 가장 큰 얼굴도 선택된 몸 밖에 있지만 사용자 선택은 맞다고 확인했다.
- 5번의 72번 후보는 가장 큰 몸 상자(임시 추적 419)를 `visual_body` 근거로 단독 선택한다. 저장 자세에는 몸 상자 세 개(임시 추적 413·418·419)가 있다. 현재 후보 역할/구간은 `single`에 추적 ID 하나만 담아, 같은 장면을 세 인물에게 배정할 수 없다. 이 세 추적 번호가 영상 전체에서 같은 멤버를 안정적으로 가리키는지는 이 확인으로 입증되지 않는다.
- 3·4·5번은 얼굴 **위치**를 참고한 진단이다. 얼굴 **이름 인식·매칭**의 정답이나 W14 모델 성능 평가는 아니다.

## 현재 제품 계약과 설계 방향

- Python export는 `main` 클립마다 `person_id` 하나, `group` 클립에는 인물 ID 없이 저장한다. Nest의 `ProjectClipItem.personId`와 클립 이동 기록도 한 명만 표현한다. 상세의 인물별 `clipIds`, 인물 ZIP, 숏폼 입력 검증은 그 단일 소유값을 기준으로 한다. **지금 앱에서는 한 장면을 세 인물 목록에 자동으로 공유 배정할 수 없다.** 기존 클립 이동은 소유자를 바꾸는 기능이며 복사 배정이 아니다.
- 역할 판단과 결과 배정을 분리한다. 역할은 `single` / `joint` / `group` / `uncertain`으로 남기고, 별도 `eligible_persons[]` 또는 인물별 클립 참조를 둔다. 5번처럼 한 사람을 독점 메인으로 고르기 어려워도 세 사람이 각각 하이라이트에 들어갈 수 있어야 한다. 하나의 원본 시간 구간과 하나의 물리적 클립을 여러 인물 목록에서 참조하는 방향을 먼저 설계한다. 각 사람별 crop이 다르면 렌더만 인물별로 분기한다.
- 평가 전용 다음 비교는 3번의 잘못된 52번 연장을 끊는 조건과 4번의 맞는 137번 유지 여부를 **동시에** 확인해야 한다. 5번은 세 몸 후보를 가진 공유 장면으로 표시하되, 단일 시각을 임의로 전체 클립 경계나 세 멤버 이름 정답으로 확대하지 않는다. W14가 제공할 얼굴 ID와의 결합은 별도 계약 검증 뒤에 한다.
- 제품 계약 변경은 Python metadata, Nest 상세/ZIP/숏폼, Angular의 인물 목록과 이동/되돌리기에 영향을 준다. 현 단계에서는 이 요구를 설계·회귀 항목으로 고정하고 제품 적용 여부와 범위를 별도 검토한다. 기존 정답 7구간·이번 1·2·4번을 잃지 않는 것이 회귀 기준이다.

새 모델 추론, 얼굴 이름 매칭, 새 클립 생성, 제품 코드 수정은 이 기록에서 하지 않았다.

## 제품 연결 가능성 점검

- W13 격리 Python 브랜치는 `feature/w13-dance-metadata-eval-20261001`이다. 72 역할 재생은 `desktop/clipper_python/tools/w13_stage_focus72.py`와 저장 평가 JSON에서만 실행된다. 제품 `plugins/dance_highlight/dance_highlight/services/pipeline.py`에는 72 역할 결정이나 RTM/YOLO 결합 호출이 없다. 이 파일의 현재 미커밋 변경은 평가 adapter와 W14 얼굴 통합 작업이 섞여 있으므로 덮어쓰거나 그대로 릴리스 브랜치에 옮기면 안 된다.
- 72의 기존 기록은 평가 전용 테스트 11개와 저장 결과 검증이다. 제품 파이프라인의 최종 MP4, Nest 인물별 목록, ZIP, 숏폼에서 새 규칙을 통과했다는 근거는 없다. 여기에 사용자 확인 오선택 3번과 다중 배정 미지원 5번도 남아 있어 **72 전체를 오늘 제품 기본값으로 채택할 근거가 없다.**
- 오늘 범위를 줄인다면 이미 구현된 단일 클립의 수동 이동·숨김·되돌리기로 잘못된 결과를 검토해 수정하는 기존 경로를 사용할 수 있다. 이는 3번의 자동 선택이나 5번의 세 인물 자동 공유를 해결한 것으로 보고하면 안 된다. 다중 공유는 Python 결과 계약부터 Nest/Angular 목록·ZIP·숏폼까지 새 인터페이스와 검증이 필요하다.
