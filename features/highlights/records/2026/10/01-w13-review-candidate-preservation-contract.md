# W13 탈락 장면 보존의 첫 제품 범위 — 검토용 설계안

2026-10-01. 사용자가 추천 순서의 첫 범위를 선택해 **격리 worktree에 읽기 전용 구현을 작성·검증**했다. 아직 기존 앱에 병합·배포하거나 실제 공연 영상을 새로 분석하지 않았다. 이 문서는 앞선 [전체 설계](09/30-w13-investigation-evaluation-design.md)의 첫 보존 단계를 실제 앱 결과에 맞춰 좁힌다. 사용자 목표는 메인/멤버 판정이 불확실해도 공연 장면을 조용히 버리지 않고, 원본에서 다시 보고 여러 인물 배정까지 검토할 수 있게 하는 것이다. 첫 단계의 성공은 **탈락 이유와 원본 시간이 보이는 것**이며, 메인 정확도 향상·새 MP4 생성·공동 메인 자동 결정은 아니다.

쉽게 말하면, 지금 앱은 판정에서 탈락한 장면을 결과 화면에서 찾기 어렵다. 첫 변경을 적용하면 결과 화면의 원본 타임라인에 **`확인 필요: 20.49~30.03초 (그룹과 겹침)`**, **`확인 필요: 30.03~34.83초 (그룹과 겹침)`** 같은 항목을 보여준다. 항목을 누르면 보관된 원본의 그 시점으로 이동한다. 기존 20개의 main/group MP4는 그대로 사용하고, 확인 필요 항목은 아직 MP4나 특정 멤버 카드가 아니다. 첫 화면에서는 장면 경계·멤버를 편집하지 않는다. 이렇게 원본을 찾고 이유를 이해할 수 있는지 확인한 뒤 편집/복수 배정과 새 clip 생성을 별도 단계로 정한다.

## 같은 원본에서 확인한 규모

이미 완료된 Dev 앱의 `dance_meta_v1` SHA-256 `274eddd3f4a7777987d29a34517abf39c4af344c65155efc6209e5ea03110450`과 9/29 그룹 필터 로그를 읽기 전용으로 대조했다. [원본·기존 결과 목록](01-w13-existing-app-input-inventory.json)과 [정적 비교](01-w13-first-comparison-scope.md)에 경로와 근거가 있다.

| 원본 공연 창 6.0~112.5초 | 기존 완료 결과 | 탈락 후보 2개를 `확인 필요`로 남긴 정적 가정 |
|---|---:|---:|
| 기존 main/group **MP4가 덮는 시간** | 102.229초 | **102.229초 그대로** |
| clip은 없으나 원본으로 찾아가 검토할 수 있는 시간 | 0초 | **4.271초 추가** |
| clip 또는 검토 후보 중 하나 이상이 덮는 시간 | 102.229/106.5초 | **106.5/106.5초** |

로그의 그룹 중첩 탈락 main 후보는 `20.487~30.030`초와 `30.030~34.835`초, 합계 **14.348초**다. 이 가운데 그룹 MP4 `23.357~33.433`초와 중복되는 약 **10.077초**는 기존에도 영상 clip이 있지만 사람별 검토가 안 보인다. 나머지 **4.271초**는 어떤 clip에도 없다. 표의 오른쪽 수치는 두 후보의 원본 시간만 검토 목록에 더한 **정적 합집합 계산**이다. 새로운 사람 판정, 실제 화면 구현, 사용자가 검토 완료한 결과 또는 MP4 생성 결과가 아니다. 얼굴 표본 탈락 1건은 현행 meta에 시점이 없어 이 숫자에 포함하지 않았다.

## 첫 범위의 입력·출력

현행 분석에서 `_filter_group_like_main_segments()`가 `group_overlap`으로 버린 **smoothed main 구간**과, 얼굴 표본을 얻지 못해 clip 생성 전에 버린 **main 구간**을 검토 후보로 보존한다. 현재 [평가 adapter](01-w13-evaluation-adapter.md)에는 `group_filtered_main`, `dropped_main`, `kept_main`을 구분한 관측이 있지만 제품 `dance_meta_v1`에는 탈락 구간이 없다. 분석 단계의 이 구분을 제품 결과의 선택적 sidecar `json/dance_review_candidates.json`으로 전달한다. 기존 `lists.main/group` 및 이미 생성한 MP4 계약은 그대로 둔다.

Sidecar의 한 항목은 최소한 다음 값이 필요하다.

| 값 | 이유와 규칙 |
|---|---|
| `analysisRevision`, `candidateId`, `sourceSha256` | ID는 **해당 분석 revision 안에서** 안정적이다. 재분석 후 같은 사람/장면이라는 추정으로 예전 수정을 자동 재적용하지 않는다. |
| `sourceStartMs`, `sourceEndMs`, `timeProvenance`, `legacyBoundsSec` | 원본 기준 검토/기존 export 경계 `[start,end)`를 밀리초로 표시한다. 현재 `Segment.end`는 다음 관측 시각인 경우와 마지막 관측 시각인 경우가 섞여 있으므로, 이것을 **마지막 포즈 프레임까지 포함한 정확한 끝**이나 원본 PTS로 표시하지 않는다. 원래 float 경계를 별도 보존하고 변환 규칙을 버전으로 기록한다. |
| `reason` | `group_overlap` / `insufficient_track_samples` / 더 구체적인 실제 실패 사유. 없는 세부 원인을 만들어 기록하지 않는다. |
| `autoMainTrackId`, `autoPersonId`, `candidateBBoxRef` | 현재 구현은 track ID만 기록하고 인물 ID와 bbox 참조는 `null`로 둔다. track ID는 분석 revision 안에서만 의미가 있고 틀릴 수 있다. 다른 사람의 crop track은 이 값에서 자동 생성되지 않는다. |
| `overlappingOutputClipIds`, `reviewState` | 그룹 clip과 시간상 공존 가능. 기본 `reviewState=needs_review`; clip이 없는 후보도 `videoPath`를 꾸며 넣지 않는다. |

Python이 분석 직후 이 정보를 원본 결과와 별도 파일로 원자적으로 기록하는 경로를 우선 설계한다. 완료된 프로젝트에서 Nest는 **선택적** sidecar를 읽어 `reviewScenes`처럼 `clips`와 다른 결과 항목으로 제공한다. 예전 sidecar가 없는 프로젝트는 현재 결과와 동일하게 연다. Angular의 첫 화면은 원본 타임라인 위에 기존 clip과 검토 후보를 별도 줄로 놓고 이유·시작/끝·원본 재생 위치를 보여주는 **읽기 전용 검토**다. `확인 필요`가 인물 카드나 완성 MP4인 것처럼 표시하지 않는다. 원본 파일의 hash가 연결되고 실제 파일이 있어야 재생하며, 없으면 후보 메타데이터와 원본 재연결 안내를 표시한다.

첫 sidecar의 `sourceStartMs/sourceEndMs`는 **기존 export에 전달되는 `seg.start/end`와 같은 잘림 경계**를 기록한다. 따라서 위 4.271초 가시성도 그 경계 기준이다. `observationTimesMs`는 해당 구간에 남은 pose 표본 시각이며, smoothing 전 구간의 종료 방식은 복원할 수 없어 `endBoundaryProvenance=mixed_after_smoothing`으로 표시한다. 이 시각은 원본 PTS나 마지막 프레임 보증이 아니다. 후속 trim/export 또는 crop track에 쓰기 전에 원본 PTS와 실제 인코딩된 첫·끝 프레임을 대조해 경계 변환을 고정한다. 현행 `build_raw_main_segments()`의 혼합 end 의미와 `RenderService.extract_clip()`의 `-ss/-to` 경로를 확인한 결과다.

이 첫 범위에서는 보류 후보를 멤버에게 자동 배정하지 않는다. 20.487~34.835초의 긴 후보 둘은 원본에서 여러 사람의 순서를 가로지르므로, 후보 한 건을 한 인물에게 그대로 붙이면 오배정할 수 있다. 배정/분할/경계 수정·복수 선택·undo는 다음 edit revision 범위다. 기존 개별 clip 이동·숨김·되돌리기·숏폼 생성은 재구현하지 않는다. 안무 trim은 현행에서 거절되므로 읽기 전용 검토를 trim 기능으로 소개하지 않는다.

## revision과 실패 처리의 경계

- 첫 읽기 전용 구현의 `analysisRevision`은 실행마다 새 UUID이고 `sourceSha256`을 별도로 기록한다. weight/config/code 지문과 결정적 캐시 키는 **아직 구현하지 않았다**. 검토 항목에 대한 사용자의 추후 수정은 이 자동 판정에 덮어쓰지 않고 **별도 `editRevision`**으로 기록해야 한다.
- 재분석하면 새 revision과 새 후보 ID를 만들고, 예전 override는 자동 적용하지 않는다. source hash와 시간/track 대응을 보여준 뒤 충돌 없이 옮길 수 있는지 검토해야 한다. 원본 hash가 다르면 자동 연결하지 않는다.
- 첫 읽기 전용 단계에는 batch 적용이 없으므로 현재 JSON 저장소의 CAS/원자성 문제를 해결했다고 주장하지 않는다. 이후 복수 선택 → 목적 인물 선택 → 일괄 적용/되돌리기를 채택할 때 expected `editRevision` 검사, 단일 원자 저장, 대상별 undo 충돌 검사가 필요하다.
- 현재 구현은 sidecar 생성·원자 교체 실패를 무시하지 않고 `dance_meta` 완료 기록 전에 예외로 중단한다. 이미 생성한 MP4는 남을 수 있다. 재시도 멱등성과 같은 revision 재사용은 **아직 구현하지 않았다**.
- 검토 화면이 원본을 참조하는 동안 원본을 삭제하면 안 된다. 현행 사용자 선택 영상은 남아 있지만 일반 프로젝트의 원본 보존 기간·저장 비용은 별도 정책 결정이 필요하다. 이번 첫 범위는 원본이 있는 프로젝트에서만 실제 재생을 검증한다.

## 적용 전에 확인할 검증 기준

1. 동일 입력의 분석 관측에서 `group_overlap` 2건이 각각 원본 시간·사유를 가진 별도 review 항목으로 보이고, 기존 main/group MP4 수와 바이트가 바뀌지 않는다. 얼굴 표본 탈락은 시점과 실제 `drop_reason`이 있을 때만 별도 항목으로 보인다.
2. 원본 공연 창의 **MP4 coverage는 그대로**, MP4+review 후보 가시성은 정적 계산의 102.229→106.5초에 맞는지 확인한다. review 시간은 MP4 coverage나 메인 정확도 점수에 더하지 않는다.
3. sidecar 없는 오래된 프로젝트·원본 누락·source hash 불일치·불완전한 sidecar에서 기존 결과가 안전하게 열리는지 검사한다. hash 불일치 후보는 원본 재생/자동 배정하지 않는다.
4. `candidateId` 중복, 구간 역전·범위 이탈, 그룹 clip 중복 표시, 재시도/취소와 partial 파일, 분석 revision 변경 시 stale 후보 재사용을 검사한다.
5. 시간축에서 원본 seek와 선택 후보 시작/끝을 비교한다. 현재 저장 float 시각은 프레임 기준 근사이므로 ffmpeg 재인코딩 경계 정확도까지 검증한 것으로 쓰지 않는다.

**현재 구현 상태:** Python sidecar → Nest 선택적 읽기 계약 → Angular의 `생성된 클립`/`확인 필요` 두 줄 타임라인을 새 격리 worktree에 구현했다. 유효한 원본은 SHA-256으로 확인하며, 다른 로컬 경로로 바뀌었거나 없는 경우에는 재생 링크를 만들지 않는다. `/sources/stream`은 다운로드 캐시 또는 현재 프로세스의 허용 목록에 든 로컬 파일만 재생할 수 있으므로, 앱 재시작 후 캐시 밖의 로컬 원본은 hash가 맞아도 플레이어가 실패할 수 있다. 화면은 재생 오류 시 후보 정보와 안내를 유지한다. 긴 원본의 상세 화면에서 SHA를 다시 읽는 지연도 아직 측정하지 않았다. W14 공통 얼굴 경로는 수정하지 않았다. source-relative **인물별 crop track**, 복수 배정, export 전 review-ready job은 각각 후속 범위다. 자세한 구현·검증은 [구현 기록](01-w13-review-scenes-implementation.md)에 남긴다.
