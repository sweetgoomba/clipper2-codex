# MPS 시작 실패 수정과 통합 앱 재검증

2026-11-04 KST. 공통 GPU 담당 세션이 MPS 시작 실패를 재현·수정해 원격 dev에 반영했다. 이 세션은 원본 dev 저장소에서 앱을 다시 빌드하고 기존 세 YouTube 영상을 실행했다. **세 영상 모두 YOLO MPS 추론을 완료했고, CPU 재분석은 없었다. 합계는 53분 29.4초에서 49분 12.5초로 약 8.0% 줄었다.** 얼굴 처리와 메인 판정은 여전히 큰 병목이다.

이 결과는 **Mac의 안무 하이라이트** 실측이다. 인물·대사 하이라이트나 Windows 전체 앱의 실측 결과가 아니다. 모든 단계가 GPU로 실행된 것도 아니다.

## 원인과 수정

실제 원본 프레임 재현에서 302,892,000바이트(약 289MiB)를 예약하려 했으나, host free 258,195,456바이트(약 246MiB)만 반영한 메모리 검사가 HTTP409 `memory_admission_deferred`를 반환했다. MPS 추론은 0회였다. GPU 연산을 시작하기 전 자원 검사에서 거절된 경우로, macOS가 회수할 수 있는 캐시를 반영하지 못했다.

과거 세 실행은 정확한 최초 거절 응답이 소실돼, 과거의 모든 실패가 같은 원인이었다고 소급 확정하지 않는다.

담당 세션은 macOS VM 통계와 메모리 압력을 함께 읽고, 회수 가능한 캐시 일부를 보수적으로 반영하도록 고쳤다. 안전 여유, 위험하거나 알 수 없는 상태의 거절, 누적 예약, 동시 사용 보호와 Windows의 기존 제한은 유지했다. 거절 사유·HTTP 상태·안전한 판단 수치를 자식 프로세스에서 부모와 CPU 재분석 최종 진단까지 보존한다. 품질 판정 정책을 바꾸거나 자원 검사를 우회한 수정은 아니다.

수정 후 같은 PoseEngine으로 실제 MPS 추론 24회가 성공했다. 모델의 `mps:0`, GPU 메모리 약 48MB 할당, CPU/MPS 각각 5명 검출, 대응 박스 최소 IoU 0.9999993을 확인했다. 이 짧은 실험은 FP32이며 전체 영상의 품질 동등성을 인증하지 않는다. 실제 앱은 기존 MPS FP16 경로를 사용했다.

원본 desktop 네 저장소를 fast-forward했다. 추적하는 소스 변경은 0이며, 최신 Nest/Angular/Electron의 다른 팀 변경도 보존했다. Python `9a9a940`의 안무 품질 수정이 조상이다. 해당 커밋 대비 Dance/Person/Dialog/FaceCore/SDK 소스 차이는 0이며, 고비용 SAM/mask/joint 호출은 OFF다. 공통 런타임 수정은 GPU 담당 세션이 맡았다.

원본 Electron에서 Node24.19로 `npm run build:app:mac:arm64:local-api` 빌드가 성공했다. 기본 `dist-app/mac-arm64/Clipper Studio (dev).app`을 정상 실행했다. 패키지 Python 소스 160개와 Electron 실행 JS 164개가 소스/빌드 출력과 일치한다. 실제 설치 venv의 수정 공통 파일 4개와 각 영상의 실행 모듈 50개도 일치한다. 판정 지도 복구와 기존 품질 변경이 포함됐다.

세 URL, 동일한 1080p 영상 바이트, 멤버 선택과 대표 이미지 바이트(MMN/ANT31장·NEON40장)를 대조했다. 새 프로젝트로 40크레딧씩 정상 UI에서 실행하고 기존 자동 결과와 교정본은 보존했다. 양쪽 모두 같은 YouTube 소스 캐시를 사용했으므로 신규 다운로드 속도 시험은 아니다.

시간은 **큐 대기를 제외한 `startedAt→finishedAt`**이다. 전후 각 1회이며 측정 중 추가 모델, 대량 테스트, 빌드는 실행하지 않았다. 사용자의 다른 앱은 중단하지 않았다. 시스템 변동이 포함된 관측값으로, 반복 실험의 평균이나 인과적 속도 효과로 일반화하지 않는다.

세 영상 모두 `attempt=0`, `requested_device=mps`, `selected_backend=torch_mps`, 성공한 호출>0, `cpu_reanalysis=false`, fallback 없음으로 완료했다. 실제 MPS 호출 완료, 해당 장치로 실행하는 코드, 같은 PoseEngine의 장치·메모리 할당 계측을 대조했다. NativeRecord의 `provider_only/profile_verified=false`를 정식 ONNX 인증으로 올리지는 않았다.

**YOLO의 GPU 사용을 확인한 것이다.** AuraFace는 `CPUExecutionProvider`, YuNet은 `opencv_cpu`다. CPU 전후처리와 기존의 가벼운 기하 연속성 처리는 남아 있고, 고비용 몸 재검증은 OFF다.

YOLO와 구간 구성에서 감소가 관측됐지만, **메인 판정·얼굴 처리가 여전히 가장 큰 CPU 병목**이다. 얼굴 처리 시간은 오히려 늘어난 경우도 있다. 누적 얼굴 인식 시간은 MMN283.46→336.42초, ANT476.07→647.65초였고, 실행 횟수 차이는 작았다. OpenCV CPU 병렬 설정도 전후 GCD10으로 같았다.

이 한 번의 순차 실험만으로 CPU 시간 변동을 GPU 또는 FP16의 인과 효과라고 단정하지 않는다. 이름 붙인 단계 외 I/O, 진단, 출력 구성, 시작·정리 시간도 전체 경과에 들어가므로 단계 합계를 전체 경과와 혼동하지 않는다.

기존 검토 구간 14개 중 2개에서 전후 라벨 차이가 관측됐다. 두 곳 모두 ANT다. 유지된 구간도 이미 정답이라고 단정할 수 없으며, 숫자 감소를 정확도 개선으로 세지 않는다. [전체 타임라인·14구간 비교](04-mps-revalidation-evidence/actual-comparison.json)에 정확한 차이가 있다.

- MMN의 단체50.2502–50.8341초→허윤진50.8341–52.4524초와 홍은채97.7978–104.0206초는 유지됐다. 실제 새 앱 지도에서 50.577초 단체, 102.943초 홍은채와 얼굴 박스를 확인했다. ANT64초의 검증된 김채원 suffix와171초 미확인 경계, NEON78초 시리·150초와183초 단체도 유지됐다.
- **확인된 회귀:** ANT9.9098–10.276933초는 사용자가 김채원 메인으로 확인했지만 새 MPS 결과는 미확인이다. 기존8.975633–17.150467초 연속 김채원 구간 사이에0.367133초 미확인이 생겼다.
- MMN에서 사쿠라였던 세 짧은 구간, 합계0.6006초가 미확인으로 바뀌었다:52.4524–52.6526,53.119733–53.420133,57.791067–57.891067초. 이 장면들의 최종 정답은 새로 확정하지 않았다.52.577초 앱 화면은5명 전신 원경이며 이를 이전 이름/새 미확인 중 어느 쪽의 정답 증명으로 삼지 않았다.
- ANT4.57–6.14초 홍은채 등 기존 미해결 구간은 여전히 충분히 복원되지 않는다. 극히 짧은 이름 조각이나 미확인·단체의 숫자 감소만으로 복원 성공을 보고하지 않는다.

공통 담당 세션의 추가 읽기 검토는 모델·테스트·파일 변경 없이 끝났다. CPU FP32와 실제 MPS FP16이 달랐다. 같은 포즈 샘플·메인 후보 ID여도1픽셀 ROI, 얼굴 선택, 주변 이름 근거의 변화가 후속 장면·이름 결과로 전파될 수 있음을 확인했다. FP16 단독 영향과 MPS 자체 수치 차이, 판정 민감도는 아직 분리하지 못했다. [읽기 검토 원문](04-mps-revalidation-evidence/owner-readonly-quality-review.json). 전체 품질 동등성은 입증하지 않았다.

## 후속 작업과 사용자 우선순위

담당 세션의 더 최근 실제 사용자 지시는 “기존 품질과 완전히 같지 않아도 돼. 지금 가장 중요한건 실행 시간을 단축시키는거라고”다. 따라서 작은 분류 차이만으로 정밀도 수정·전체3영상 추가 재실행을 완료 조건으로 붙이지 않는다. 차이는 보존해 큰 병목 개선에 함께 넘긴다. 이름·병합을 강제하지 않고 고비용 몸 추적 OFF와 인물 분류 정책 보존을 유지한다. [직접 지시와 조정 근거](04-mps-revalidation-evidence/latest-user-priority.json).

남은 CPU 병목, 얼굴 GPU 선택 조건 미충족, Mac·Windows 실측과 원본8개 최신 dev 빌드는 기존 **「하이라이트 GPU·ONNX 전환 및 Windows 시험 도구 감사」** 세션이 새 사용자 지시에 따라 진행 중이다. 이 세션은 최종3영상 근거를 전달했고, 빌드·모델 시험을 중복 실행하지 않는다.

**MPS 시작 실패 수정과 이 앱의3영상 실측은 완료했다. 서비스 수준의 속도 개선과 전체 품질 문제가 해결된 것은 아니다.**
