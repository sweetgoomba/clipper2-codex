# 플러그인 목록 동기화 권고 설계와 검증 반영

기준일: 2026-11-18 KST. 상태: 독립 검증 2회와 재검증의 필수 보완을 반영한 설계 제안 v3. 사용자 구현 승인 전이다. 제품 코드·DB·빌드·배포 변경은 포함하지 않는다.

추천은 **기존 Angular 사용자 기능 등록에서 빌드별 목록을 생성하고, 기존 릴리스 성공 보고로 서버에 보관한 뒤 관리자 운영 설정과 결합하는 방식**이다. 개발 등록을 운영자가 다시 입력하지 않고, 새 빌드가 운영자의 요금제·분류·공개·중지 결정을 덮지 않도록 한다.

이 권고는 [최초안](18-catalog-sync-initial-design.md)과 [새 세션의 독립 검증 원문](18-catalog-sync-independent-review.md)을 비교해 정했다. 원격 9개 저장소의 SHA는 최초안의 표를 기준으로 하며 검증 세션도 동일함을 확인했다. 기존 [W18 논의](../10/29-admin-store-sync-discussion-and-deferral.md), [W18 작업카드](../../../../../handoff/tasks/plugin-catalog-sync.md)의 범위를 재개하는 설계이고 구현 착수는 아니다.

## 1 현재 구조와 목표

현재 사용자 플러그인 14개의 ID 집합은 Angular 등록·Web API 표시 목록·과금 정의의 소속 ID 사이에서 일치한다. 이 일치는 자동 동기화 결과가 아니며 각 소스에서 따로 관리한다. 과금 작업은 사용자 플러그인과 일대일 관계가 아니다. Python manifest에는 공유 TTS·렌더 등 실행 단위도 있으므로 전체 사용자 카탈로그와 동일하게 취급하지 않는다.

W19가 구현한 Free 기본 상태, `/plans`의 일괄 허용 설정, 하위 자동 포함 ON/OFF, 웹 가격 카드, 앱 배지·업그레이드·실행 제한을 재사용한다. W18 때문에 이 기능을 다시 만들거나 과거의 상위 등급 무조건 포함 정책으로 되돌리지 않는다.

목표는 다음과 같다.

- 개발된 사용자 기능을 안정적인 pluginKey로 발견하여 어드민에 표시한다.
- 운영자가 공개 전에 이름·분류·순서·요금제와 필요한 과금 연결을 확인한다.
- 앱 스토어·사이드바 분류·웹 가격 카드·관리자 선택 목록이 같은 운영 카탈로그를 사용한다.
- 앱에 구현되지 않은 기능은 서버 등록만으로 실행되지 않는다.
- 전체 중지는 요금제 설정·설치 이력·즐겨찾기·기존 결과를 보존한다.

앱 업데이트 없이 새 실행 코드를 내려받기, 모든 repo의 계약을 공유 패키지로 통합하기, Python manifest 중복 전면 제거, 모바일 기능 설명 계약 통합은 이번 범위에 넣지 않는다. 현재 기능 코드의 배포 단위는 앱 설치 파일이다.

## 2 대안과 최종 선택

| 방식 | 판단 |
|---|---|
| 관리자에서 pluginKey 수동 입력 | 등록 누락·오타·중복 관리와 지원 앱 판정이 남아 기본 경로로 선택하지 않음 |
| Nest에 새 사용자 기능 JSON을 만들어 Angular에도 공급 | 가능한 방식이나 이미 존재하는 Angular 등록을 옮기는 비용과 형제 저장소 의존성이 생겨 최초안을 교체함 |
| 기존 Angular 사용자 기능 등록에서 빌드 목록 생성 | 실제 스토어의 사용자 기능 범위를 재사용하고 새 사람이 관리할 목록을 늘리지 않으므로 선택함 |
| 각 회원 PC의 보고로 공통 목록 생성 | 개발판·구버전·임의 보고를 운영 정본에 섞으므로 선택하지 않음 |

목록 파일은 빌드 산출물이며 사람이 별도로 편집하는 정본이 아니다. Angular의 순수 메타데이터 export에서 생성한다. 화면·라우트 코드, 실제 Nest 처리기, Python 모델 manifest, Web API의 과금 코드는 각 실행 영역에 남으며 빌드 검사에서 ID와 연결을 대조한다. 정규식으로 소스를 훑는 도구를 제품 정본으로 삼지 않는다.

`APP_NAVIGATION_METADATA`의 사용자 기능과 실제 `providePipelineFeature`·라우트 등록을 확인하고, `NAV_GROUPS`의 초기 분류·순서를 목록에 싣는다. 필요하면 이 기존 등록에서 순수 데이터 부분만 분리한다. 동일한 사용자 ID를 Nest에 또 적는 새 목록은 만들지 않는다. 가상 workflow 목록에 이름이 있다는 이유만으로 실제 기능이 구현됐다고 판정하지 않는다.

## 3 정보의 소유권

| 정보 | 소유권과 규칙 |
|---|---|
| pluginKey와 실제 화면·실행 연결 | 개발 코드. 이름 변경과 무관한 안정 ID이며 폐기 ID를 다른 기능에 재사용하지 않음 |
| 특정 빌드가 포함한 사용자 기능과 개발 기본값 | 그 빌드의 불변 목록. 다른 빌드·플랫폼 목록이 덮지 않음 |
| 운영 이름·설명·카테고리·스토어 순서 | 관리자 DB. 처음 설정할 때 빌드 기본값으로 채우고 이후 운영자가 소유함 |
| 공개·전체 실행 중지 | 관리자 DB. 빌드·등록·재전송이 자동 변경하지 않음 |
| Free와 요금제별 허용·상속 ON/OFF | 기존 관리자 DB와 W19 편집기. 복제 사본을 만들지 않음 |
| 과금 작업·단가 | 기존 Operations. 한 사용자 기능에 여러 작업이 가능하며 무료 기능은 작업 0개도 가능함 |
| 설치 상태·카테고리 내부 설치 순서·즐겨찾기 | 회원 PC. 서버 갱신으로 초기화하지 않음 |

운영 이름은 어드민 플러그인 선택, 요금제 카드, 앱 스토어 및 사이드바의 해당 기능 표시에 함께 적용한다. 기능 화면 전체의 설명·입력 UI를 원격으로 편집하는 CMS까지 넓히지 않는다. 서버가 내려준 문자열로 route·handler를 실행하지 않고 로컬의 pluginKey 연결을 사용한다.

카테고리 이름·순서·플러그인 소속은 서버에서 관리한다. 스토어의 내부 순서는 관리자 설정을 따르고 사이드바의 내부 순서는 기존 회원 설치 순서를 따른다. 즐겨찾기는 기존 개인 순서를 유지한다. 카테고리 삭제는 소속 항목을 이동한 뒤 허용한다.

## 4 서버 저장을 단순하게 유지하는 방법

### Release DB

성공한 artifact에 연결되는 불변 사용자 기능 목록을 저장한다. 정규화된 목록 JSON과 hash, schemaVersion, sourceSnapshotId, build/job 식별자, 환경 프로필, platform·arch를 보관한다. installer artifact hash와 연결하되 패키지 안에 나중에 생성될 artifact DB ID를 미리 넣으려 하지 않는다. 패키지에는 패키징 전에 존재하는 build/job 식별자와 목록 hash를 넣고, 서버가 이를 성공 artifact에 연결한다.

설치 앱의 지원 근거로 사용할 **해당 서버 최종 배포 채널의 최초 공개 사실**도 artifact에 남긴다. `firstPublishedAt`과 공개 채널을 target 변경과 같은 release DB 트랜잭션에 저장하며 이후 target 롤백으로 지우지 않는다. 현재 변경 가능한 target이나 트랜잭션 밖 감사 이벤트만으로 과거 공개 여부를 판정하지 않는다. 단순 업로드·테스트용 임시 채널 공개와 실제 회원 배포를 구분한다.

### Admin DB

운영자가 저장한 플러그인별 이름·설명·categoryId·storeOrder·공개 상태·실행 상태와 카테고리·변경 이력을 보관한다. 기존 요금제 허용 테이블과 설정 revision을 재사용한다. 첫 범위에서 빌드 목록 전체를 admin DB에 다시 복제하지 않는다.

### 관리자 조회

Web API가 release 저장소의 성공 목록에서 발견한 사용자 ID와 admin 저장소의 설정을 애플리케이션 계층에서 결합한다. DB 간 FK·JOIN은 만들지 않는다. 설정 행이 없는 신규 ID는 **설정 대기·미공개·실행 중지**로 보여준다. 운영자가 발견된 항목을 선택해 저장할 때 운영 설정 행을 만든다. ID 재입력은 없다.

이 구조에서는 성공 보고와 admin 등록을 연속으로 쓰는 이중 쓰기가 없어 별도의 `catalogSync=pending/failed` 상태와 복구 작업을 첫 범위에 만들 필요가 없다. DB를 읽지 못한 경우 빈 목록으로 성공 처리하거나 이전 설정을 삭제하지 않고 조회 실패로 처리한다.

동시에 새 목록·요금제가 추가되는 동안 `/plans`를 저장하면 기존 revision에 더해 등록 ID 집합의 변경도 감지해야 한다. 동일한 카탈로그 스냅샷을 관리자 입력 검증·상위 포함 검사·`all` 확장·회원 가격 표시·실행 허용에 전달한다. 현재 전역 `REGISTERED_PLUGIN_KEYS`를 한 소비처에서만 바꾸지 않는다.

## 5 성공 보고와 공개의 연결

기존 runner 흐름에 다음을 추가한다.

1. 동결된 정확한 source snapshot에서 목록을 생성하고, 사용자 route·실제 처리 경로·플랫폼·필요 과금 키 연결을 검사한다.
2. 앱 패키지에 목록을 포함하고, 패키징된 목록의 hash와 보고할 목록의 hash가 일치하는지 확인한다.
3. 기존 설치 파일 검증·업로드 후 성공 보고에 목록과 hash를 포함한다.
4. Web API는 job에 저장된 snapshot·환경 프로필·platform·arch를 기준으로 요청을 검증하고 **artifact 성공 기록과 목록을 같은 release DB 트랜잭션에 저장**한다.

성공 보고 전체가 재전송에 안전해야 한다. 같은 job·attempt의 정규화된 artifact 메타데이터와 파일 hash·목록 hash가 기존 성공 기록과 같으면 기존 결과를 반환한다. 다르면 충돌로 거절한다. 늦은 실패 보고는 기존 성공을 되돌리지 않는다. 목록 재전송은 배포 target 공개를 다시 호출하지 않으므로 rollback 슬롯도 바꾸지 않는다.

W18 관리 대상 새 빌드 job은 유효한 목록 없는 성공 보고를 거절한다. 기존 artifact를 나중에 임의의 소스 목록과 연결하지 않는다. 기존 CI 인증은 공유 runner 토큰이다. 이 설계는 job별 암호학적 신원 증명을 이미 제공한다고 가정하지 않으며, 기존 신뢰 경계 안에서 서버의 job 정보와 제출 범위를 대조한다. 등록 권한에는 운영 이름·요금제·공개·긴급 중지 변경 권한이 없다.

빌드 성공·목록 검사는 어드민에 발견할 근거이고, 실제 기능의 QA 완료와 회원 공개 승인은 별개다. 현재 코드의 `ready`도 QA 대기 상태다. 운영 공개는 기존 릴리스 QA와 플랫폼별 target 공개 이후 별도 관리자 동작으로 한다. 개발 환경 보고를 운영 카탈로그에 넣지 않는다.

## 6 상태와 공개 조건

공개 상태는 `draft / published / retired`, 실행 상태는 `enabled / paused`로 구분한다. 새 ID는 draft·paused다.

| 상태 | 사용자에게 보이는 동작 |
|---|---|
| 새 draft | 스토어에 노출하지 않으며 신규 실행을 허용하지 않음 |
| published + enabled | 지원 앱에서 탐색·설치·준비 가능. 실제 실행은 요금제와 필요한 크레딧 검사 |
| published + paused | 스토어·기존 진입점에 일시 중지 안내. 새 제작 실행을 막고 결과 조회·제거는 허용 |
| 공개 취소로 draft 또는 retired | 스토어에서 숨기고 신규 실행도 막음. 설치·즐겨찾기·결과 데이터 보존 |

공개 취소도 신규 실행에 영향을 준다는 점을 관리자 확인창에 설명한다. 전체 중지는 목록을 지우지 않고 즉시 새 실행을 막기 위한 조작이다. **중지 해제는 execution만 enabled로 변경하며 현재 공개 상태와 요금제 설정은 변경하지 않는다.** 중지 중 공개를 취소했다면 중지를 해제해도 미공개 상태가 유지되어 새 실행은 계속 차단된다. 공개나 재배포가 paused를 자동으로 enabled로 만들지 않는다. 최초 공개에서만 공개와 사용 시작을 운영자가 함께 명시할 수 있다.

공개 조건은 필수 운영 표시값·분류·요금제 설정 확인, 실제 대상 서버의 필요한 과금 정의/정책 준비, 해당 환경에서 실제 공개한 지원 artifact의 존재다. 앱 snapshot의 Web API 소스에 정의가 있다는 것만으로 서버가 준비됐다고 판정하지 않는다. 반대로 서버에 신규 과금 코드를 먼저 배포할 때 카탈로그가 없다고 서버 전체 시작을 막지 않는다. 아직 미등록인 기능의 공개·실행만 차단한다.

`all`은 현재의 동적 전체 허용 의미를 유지한다. 신규 draft·paused는 `all`이어도 실행 불가다. 공개·활성화 시 `all`인 등급에는 새 기능도 포함된다는 사실을 보여주고, 운영자가 기존 `/plans`에서 원하는 허용 범위를 저장하게 한다. 신규 ID는 모든 요금제에 자동 미허용이라고 약속하지 않는다. 모든 신규 기능을 명시 승인만 허용하도록 바꾸는 것은 `all`을 allowlist로 전환하는 별도 정책 결정이다.

등록된 ID의 전체 집합과 공개 목록은 다르다. 미공개·중지·폐기 항목도 기존 설정·과금 이력의 ID로 남는다. 새 빌드에서 항목이 빠졌다는 이유로 전역 삭제하지 않는다.

## 7 설치된 앱과 배포 target의 구분

현재 target은 지금 내려받거나 업데이트할 설치 파일을 정한다. 이미 설치된 앱의 지원 여부는 그 앱의 불변 목록과 실제 공개 이력으로 판단한다. 처음부터 현재 target 하나만을 모든 앱의 지원 기준으로 사용하지 않는다.

Windows와 Mac의 비동시 공개를 허용하는 방향을 추천한다. 공개된 플랫폼에서만 기능을 제공하고 어드민에는 플랫폼별 준비 상태를 보여준다. 웹 요금제의 공통 기능 목록에도 플랫폼 제한을 표시하여 지원하지 않는 플랫폼에서 쓸 수 있다고 약속하지 않는다. 앱 카드는 자신의 빌드가 지원하는 것만 활성 기능으로 표시한다.

target 롤백은 기본적으로 신규 배포 파일만 되돌린다. 이미 설치한 새 빌드를 자동 지원 철회하거나 앱을 강제 다운그레이드하지 않는다. 최초 범위의 지원 기준은 실제 공개 이력이 있는 W18 대응 빌드이며, 긴급하게 문제 기능을 막을 때는 전체 중지를 사용한다. 빌드별 선택적 지원 철회와 구체적인 장기 지원 기간은 후속 버전 정책으로 분리한다. 옛 개발판마다 별도 adapter는 만들지 않는다.

공식 앱은 실행 요청에 build/job 식별자·platform·arch·목록 hash를 전달하도록 계약을 확장한다. 이 값은 서버에서 등록한 지원 빌드를 찾는 호환성 정보이며 클라이언트 무결성을 증명하는 수단은 아니다. 정책을 모르는 옛 앱이나 변조된 클라이언트의 순수 로컬 동작을 원격에서 완전 차단한다고 주장하지 않는다.

## 8 실행 중지와 과금 복구

신규 실제 실행의 기준은 **사용자 기능 pluginKey**다. 화면과 기능별 Nest 서비스가 신뢰할 수 있는 코드 경로에서 originPluginKey를 정하고, 공유 렌더·큐·재시도까지 전달한다. 회원이 임의로 보낸 key나 로그용 flowName을 권한 정본으로 쓰지 않는다. `clipper_video_render` 같은 worker 이름으로 사용자 기능의 중지를 판단하지 않는다.

신규 제작 요청은 공개/전체 중지·지원 앱 확인 뒤 기존 요금제·크레딧 확인 및 과금으로 이어진다. 실제 처리 직전에도 운영 중지·지원 정책을 확인한다. 공통 큐의 실제 dispatch와 큐를 거치지 않는 직접 실행 경계, 기존 묶음 과금 run을 재사용하는 새 단계 실행까지 포함한다. `LicensePolicyService`를 일괄 차단으로 바꾸어 탐색·설치·준비를 막지 않는다.

이미 과금해 큐에 들어간 작업은 당시의 요금제·차감 승인을 유지한다. dispatch에서 잔액이나 변경된 요금제를 다시 적용하거나 재차 차감하지 않는다. dispatch에서는 새로 도입한 공개/전체 중지·지원 앱 정책을 확인한다. 실행을 중지하게 된 작업은 기존 기능별 취소·수량 정산·terminal outbox를 통해 한 번만 정산한다. 미실행 작업은 기존 규칙에 맞게 반환하고, 부분 완료가 있는 수량형 작업에 일괄 전액 환불을 적용하지 않는다.

중지의 기본 범위는 아직 실제 시작하지 않은 작업과 새 사용자 실행이다. 실제 시작한 하나의 workflow와 그 안에서 이미 계획한 자동 하위 단계는 완료시키는 방향을 추천한다. 사용자가 별도 버튼으로 후속 단계·재시도를 시작하면 같은 과금 묶음을 사용하더라도 새 실행 경계이므로 다시 검사한다. Web API의 run 상태가 running이거나 Python 프로세스가 살아 있다는 이유만으로 이미 실제 실행 중이라고 판단하지 않는다.

기존 과금 요청의 재전송·run 조회·응답 유실 복구는 원래 run을 반환하는 현재 규칙을 유지한다. 그 응답은 새 실행 허가가 아니다. 성공/실패 보고·정산·환불·복구는 전체 중지로 막지 않는다. 실행 허용 검사와 금전 복구를 별도 경로로 둔다.

서버 연결 실패 시에는 캐시된 카탈로그로 탐색·설치 상태·기존 결과·편집 준비를 유지한다. 새 관리 대상 제작 실행은 무료 기능도 온라인 허용 확인 후 시작하도록 제안한다. 연결이 안 되면 보류·재시도·취소를 제공하며 임의로 실행하거나 무조건 환불하지 않는다. 이는 원격 중지를 일관되게 적용하기 위한 제안이고, 오프라인 신규 제작까지 보장하는 정책은 아니다.

목록 표시는 앱 시작·스토어 진입·포커스 복귀 등에 갱신하고 실제 새 실행은 현재 정책으로 확인한다. 최초 범위에 실시간 푸시를 추가하지 않는다. 허용 판정 직후의 중지는 이미 승인된 실행을 즉시 강제 종료하는 기능이 아니므로 관리자에도 이 범위를 표시한다.

## 9 개발부터 회원 공개까지

`auto_subtitle`은 설명용 ID이며 실제로 추가하지 않는다.

1. **개발:** 기존 사용자 기능 등록에 ID·기본 이름·화면 연결을 추가하고 실제 Angular/Nest/Python 처리를 만든다. 필요한 모델을 연결한다. 유료 작업이 있으면 기존 Web API Operations에 연결한다.
2. **서버 준비:** 신규 API·과금 코드와 필요한 DB 변경을 개발 환경에서 검증하고 대상 서버에 준비한다. 서버 배포만으로 회원 공개되지 않는다.
3. **목록 생성과 앱 검사:** 기존 릴리스 source snapshot을 동결한다. 그 정확한 소스에서 사용자 목록을 생성하고 등록·실제 처리 경로·플랫폼·과금 소속을 검사한다. 개발 환경의 발견도 검증된 개발 빌드의 같은 보고 경로를 사용한다. 파일을 저장하는 순간 원격 서버가 감시하는 방식은 아니다.
4. **패키징과 등록:** 같은 목록을 앱에 포함해 빌드·검증·업로드한다. 기존 runner 성공 보고가 artifact와 목록을 함께 저장한다. 실패·dry-run/local_verified 산출물은 운영 공개 근거가 되지 않는다.
5. **어드민 발견:** 신규 ID가 설정 대기로 나타난다. 운영자는 목록에서 선택하며 ID·기술 연결을 다시 입력하지 않는다.
6. **운영 설정:** 이름·설명·카테고리·스토어 순서를 저장한다. 기존 `/plans`에서 Free·각 요금제 허용과 하위 포함 정책을 확인하고, 기존 과금 정책 화면에서 연결·단가를 확인한다. 설정이 덜 되면 공개 버튼이 필요한 항목을 설명한다.
7. **앱 릴리스 공개:** 기존 QA를 거친 플랫폼별 설치 파일을 릴리스 관리에서 배포 target에 공개한다. 이때도 신규 플러그인은 자동 공개되지 않는다.
8. **플러그인 공개:** 지원 플랫폼과 허용 요금제, `all` 영향, 현재 중지 상태를 확인하고 플러그인을 공개·활성화한다. 미지원 플랫폼은 준비 중으로 명시한다.
9. **회원 사용:** 앱이 자기 빌드의 기능 목록과 서버 운영 카탈로그를 결합한다. 회원은 탐색·설치·준비 후, 실제 실행 시 정책과 요금제·크레딧 검사를 거친다.
10. **이후 운영:** 이름·분류·순서·요금제·공개·중지는 어드민에서 변경한다. 화면·처리 코드나 모델의 실질 변경은 기존처럼 새 앱 릴리스로 배포한다.

## 10 최초안과 독립 검증의 차이 및 최종 판단

| 주제 | 최초 생각 | 독립 검증의 지적 | 최종 판단 |
|---|---|---|---|
| 사용자 등록 정본 | Nest에 새 공통 JSON 추가 | 이미 Angular에 사용자 기능 등록이 있고 새 저장소 의존성을 늘림 | 기존 Angular 등록에서 목록을 생성하는 방식으로 교체 |
| 서버 등록 | release 성공 후 admin DB에 기술 목록 upsert·복구 상태 | 이중 DB 쓰기 없이 조회 시 결합하면 충분함 | release에 불변 목록, admin에 운영 설정만 보관 |
| 재시도 | 같은 목록 hash의 재처리 | 현재 성공 보고 자체는 재전송을 거절함 | 성공 보고 전체의 동일 요청 재처리를 정의하고 artifact·목록을 함께 저장 |
| 지원 앱 | 현재 배포 target과 지원 목록 연결 | 롤백·플랫폼 선공개 때 이미 설치한 앱을 오판함 | 배포 target과 설치 빌드의 공개 이력을 구분 |
| 전체 중지 | 플러그인 ID로 공통 실행 경로 검사 | 공유 worker ID와 사용자 ID가 다르고 직접 실행·묶음 재사용도 있음 | originPluginKey와 실제 실행 경계를 명시, 과금 복구와 분리 |
| 큐와 과금 | 최신 정책 재검사 범위가 모호함 | 기존 요금제·잔액을 재검사하면 이미 결제된 작업 정책이 바뀜 | 기존 차감 승인 보존, 운영 중지·지원 여부만 추가 검사 |
| 신규 허용 | 신규 ID 자동 허용 없음 | 기존 all의 동적 의미와 충돌함 | all 유지, 미공개·중지로 차단하고 공개 시 영향 확인 |
| 운영 표시값 | 개발 기본값과 필드별 override를 별도 모델링 | 최초 범위에는 운영 저장값만으로 충분함 | 첫 설정에 기본값을 채우고 이후 운영자가 소유, 자동 덮어쓰기 없음 |

검토자의 위 지적은 관련 원격 코드를 직접 대조한 뒤 채택했다. 공유 worker 경로는 Nest `video-render.service.ts:12`, 직접 묶음 재사용은 `shortform/application/explainer-visuals.ts:425`, 과금 복구 순서는 Web API `operations.service.ts:252`와 Nest `billable-job-attempt.coordinator.ts:197`에서 확인했다. 성공 보고 재전송과 target 동작은 release repository의 현재 트랜잭션을 대조했다.

같은 새 세션에 수정안 v2를 재검증받았다. 검토자는 큰 구조는 적합하며 두 항목의 보완이 필요하다고 판단했다. 이에 (1) 최초 최종 채널 공개 사실을 target 변경과 같은 release 트랜잭션에 보관하는 규칙, (2) 중지 해제는 현재 공개 상태를 되살리지 않고 execution만 바꾼다는 규칙을 v3에 반영했다. 재검증의 조건을 문서에서 해소했으며 구현 검증을 수행했다는 뜻은 아니다.

등록·운영 분리, 무료 플러그인과 과금 작업 분리, 운영 상태·개인 순서 보존, 일반 회원 PC를 운영 정본으로 삼지 않는다는 큰 방향은 유지한다. 신규 공유 패키지·별도 메시지 버스·독립 플러그인 업데이트는 추가하지 않는다.

## 11 이전 순서와 인수 기준

서버·어드민 카탈로그 준비 → 현재 14개 ID·운영 표시·분류와 현재 제공 동작을 초기 상태로 설정 → 기존 허용·상속 ON/OFF·과금 이력 보존 → W18 대응 앱을 빌드·공개해 목록 확인 → 앱이 서버 카탈로그 소비 → 전체 제어를 적용할 지원 앱 기준을 운영한다.

현재 DB에는 플러그인별 공개 상태가 없으므로 없는 값을 복사한다고 하지 않는다. 지금 제공되는 14개 기능을 그대로 제공하도록 초기 운영 상태를 명시한다. 새 ID의 draft·paused 기본값을 기존 14개에 적용하여 기존 기능을 일괄 숨기지 않는다. 기존 `REGISTERED_PLUGIN_KEYS` 소비처는 같은 ID 스냅샷 기반으로 모두 전환한 뒤 과금 목록에서의 유도를 제거한다.

| 인수 시나리오 | 설계가 요구하는 결과 |
|---|---|
| 기존 14개 이전 | ID·현재 제공 동작·요금제·상속 설정·개인 순서·결과 보존 |
| 무료 기능과 다중 과금 기능 | 가짜 과금 없이 등록, 사용자 카드와 과금 작업 개념 구분 |
| 신규 항목 설정 전 접근 | 미공개·중지이며 회원 신규 실행 불가 |
| 동일 성공 보고 재전송 | 같은 결과 반환, artifact·목록 중복 없음 |
| 같은 job의 다른 hash | 충돌하며 기존 성공 불변 |
| 과거 목록 역순 수신 | 전역 ID·운영명·요금제·중지 상태를 덮거나 삭제하지 않음 |
| Windows만 공개·Mac 실패 | Windows 제공, Mac 제공을 추정하지 않음 |
| 배포 target 롤백 | 신규 배포 파일만 변경, 이미 설치된 지원과 운영값은 자동 철회하지 않음 |
| 큐 대기 중 전체 중지 | 실제 처리기 미호출, 재차 차감 없음, 필요한 기존 정산 한 번만 수행 |
| 과금 응답 유실 후 중지 | 과금 조회·복구 가능, 복구 응답을 새 실행 허가로 쓰지 않음 |
| 공유 렌더·직접 실행·묶음 단계 | 원래 사용자 기능으로 실행 정책을 적용 |
| 서버 실패 | 탐색·기존 결과 보존, 신규 실행은 보류, 복구 때 이중 실행·환불 없음 |

이 표는 구현 후 필요한 검증 기준이다. 이번 정리에서 빌드·테스트·장애 주입을 수행했다는 뜻이 아니다.

## 12 제안으로 정한 제품 동작

Windows/Mac 비동시 공개 허용, target 롤백과 설치 앱 지원 분리, 기존 all 의미 유지, 공개 취소 시 새 실행 차단, 이미 실제 시작한 workflow 완료 허용, 신규 제작은 무료도 온라인 정책 확인을 이번 권고안의 기본값으로 정했다. 이는 사용자가 이미 승인한 정책으로 기록하지 않는다. 기존 결제·단가·크레딧 유효기간·과금 복구 원칙은 변경하지 않는다.

최종 설계는 이 저장소와 현재 W18 범위에 맞는 권고안이다. 구현 승인 후 실제 계약·migration·화면·검증 계획을 작성할 단계이며, 이 문서만으로 코드·DB·배포 변경을 시작하지 않는다.
