# 플러그인 목록 동기화 최초 설계안

작성일: 2026-11-18 KST. 상태: 독립 검증용 초안. 구현 승인·구현 계획이 아니며 제품 코드·DB·빌드·배포를 변경하지 않는다. 이 파일은 검증 전 판단을 보존한다. 최종안은 검증 후 별도 기록한다.

## 2 비교한 방식과 최초 선택

| 방식 | 이점 | 비용과 한계 | 최초 판단 |
|---|---|---|---|
| 어드민에서 ID부터 수동 입력 | 시작 구현이 작음 | 개발 등록과 운영 등록이 계속 중복되며 누락·오타·지원 앱 판별이 남음 | 장애 복구용으로도 검증된 목록 파일을 가져오게 하고 임의 ID 수기는 피함 |
| Git의 사용자 기능 선언을 빌드가 목록 파일로 생성하여 서버에 반영 | 코드와 등록 증거를 연결하고 운영 설정을 분리하기 쉬움 | 생성·검증과 기존 릴리스 보고 확장이 필요 | 추천 |
| 각 회원 PC가 자기 플러그인을 서버에 보고해 공통 목록 생성 | 로컬 설치 실상 파악 가능 | 구버전·개발판·조작된 PC가 운영 정본을 바꾸거나 잘못 공개할 수 있음 | 공통 등록 경로로 사용하지 않음 |

추천은 두 번째다. 다만 지속 감시·새 메시지 버스·독립 플러그인 다운로드·신규 공유 패키지 저장소는 첫 범위에 넣지 않는다. 새 코드 추가 자체는 기존처럼 앱 설치 파일 배포가 필요하다.

## 3 등록의 정본과 정보 소유권

사용자 플러그인과 Python 실행 단위는 다르다. 사용자 기능은 14개이고 Python 기능·공유 TTS/렌더 worker의 수는 다르다. Python manifest 하나를 전체 사용자 카탈로그 정본으로 삼을 수 없다.

최초 제안은 Nest 저장소의 framework 무관 JSON `user-plugin-definitions.json`을 사용자 기능 ID·기본 이름·기본 설명·기본 분류·기술 연결 키의 정본으로 삼는 것이다. 실제 파일 위치는 검증에서 비교한다. 기존 Nest `PLUGIN_CATALOG` 전체를 전송하지 않는다. Angular 빌드는 이 파일에서 필요한 정적 기본값을 생성해 사용하고, 실제 route/component와 실행 handler는 각 코드의 명시적 ID 등록을 유지한다. JSON에서 실행 코드를 만들거나 서버 문자열을 실행하지 않는다.

| 데이터 | 소유자 | 동기화 규칙 |
|---|---|---|
| 안정적 pluginKey, 기술 연결, 지원 플랫폼 | 개발 소스·해당 빌드 | 동일 ID 재사용 금지. 연결 변경은 다른 빌드 기록으로 남김 |
| 개발 기본 이름·설명·분류 | 개발 선언 | 재전송은 기본값만 갱신. 운영 override가 있으면 표시값은 유지 |
| 회원에게 표시하는 이름·설명·분류·순서 | 관리자 DB | 운영값이 있으면 우선. 빌드가 덮지 않음 |
| 공개, 전체 실행 중지 | 관리자 DB | 동기화나 재빌드가 자동 해제하지 않음 |
| Free 및 요금제별 허용 | 기존 관리자 DB 설정 | W19 편집기와 데이터를 재사용. 독립 사본을 만들지 않음 |
| 과금 작업·단가 | 기존 Operations | pluginKey로 연결. 플러그인 하나에 작업 여러 개, 무료 플러그인에 가짜 작업 없음 |
| 설치 여부, 설치 순서, 즐겨찾기 | 회원 PC | 운영 목록 갱신으로 삭제·초기화하지 않음 |

Web API의 등록 키는 과금 정의에서 유도하지 않고 운영 카탈로그를 읽도록 전환한다. 과금 정의의 pluginKey가 카탈로그에 존재하는지는 검사한다. API 서버가 런타임에 형제 Angular/Nest 저장소 파일을 읽게 만들지 않는다.

빌드 검사: 중복·누락 ID, 사용자 route·실행기 연결, 선언된 과금 작업의 존재·소속, runtime kind, 플랫폼 지원, worker를 사용자 기능으로 오분류한 경우를 검사한다. 실제 처리 코드는 사람이 개발하고 필요한 코드 연결은 여전히 작성한다. JSON 한 줄로 기능이 완성된다는 뜻이 아니다.

## 4 서버 상태와 데이터 경계

최소 논리 구조는 관리자 DB의 플러그인과 카테고리, release DB의 불변 빌드 목록이다. 기존 `plan_plugin_entitlements`와 `catalog_plugin_settings`를 재사용한다. DB 간 FK나 JOIN은 추가하지 않는다.

- 관리자 플러그인: pluginKey, 개발 기본값, 운영 override, categoryId·storeOrder, publication(draft/published/retired), execution(enabled/paused), 설정 revision·변경 이력.
- 카테고리: 안정적인 ID·운영명·순서. 삭제는 소속 이동 뒤 허용한다. 사이드바는 카테고리와 소속을 따르지만 내부 설치 순서와 즐겨찾기 개인 순서는 유지한다.
- 빌드 목록: sourceSnapshotId·buildId·artifactId·platform·arch·환경 프로필·schemaVersion·정규화 hash·그 빌드의 사용자 기능/기술 연결. 릴리스 버전 문자열만 식별자로 사용하지 않는다. 같은 버전 재빌드·서로 다른 플랫폼이 가능하다.

모든 목록 수신은 upsert로 처리한다. 같은 빌드 키+같은 hash는 재시도 성공이고 같은 키+다른 hash는 충돌이다. 과거 목록이나 일부 플랫폼 목록에서 ID가 빠져도 공통 플러그인을 삭제하지 않는다. 폐기는 관리자 조작과 이력을 남기는 tombstone으로 한다.

미공개와 실행 중지는 독립 상태다. 처음 발견한 신규 ID는 미공개·중지·미설정으로 만들고 요금제 기본 허용도 자동 추가하지 않는다. 기존 `all` 모드가 새 미공개 플러그인의 공개/실행을 우회하지 못하게 한다. 미공개→공개 때 분류·필수 표시값·허용 요금제·필요 과금 연결·실제 배포 가능 빌드를 확인한다. 재공개가 긴급 중지를 자동 해제하지 않는다.

## 5 목록 수신과 공개의 순서

최초안은 성공한 빌드의 기존 runner report를 확장해 목록 또는 목록 hash·검증된 파일 위치를 함께 받는 것이다. 앱 번들에도 같은 목록을 포함하고 설치 파일에 포함된 목록과 업로드한 목록의 hash를 검사한다. 운영 서버가 개발자 PC나 임의 URL을 수집하지 않는다. 기존 runner identity를 재사용하되 요청된 job·snapshot·profile·플랫폼 범위에서만 기술 목록을 등록할 수 있게 한다. 등록 자격에 공개·요금제 편집 권한은 없다.

두 이정표를 구분한다. (1) 빌드 성공·설치 파일 업로드는 어드민 설정 대기를 만들 수 있다. (2) 배포 target의 실제 공개는 회원 공개 가능 조건이다. 실패 빌드·local_verified·다른 환경 프로필의 목록은 회원 공개 근거가 아니다. 개발 서버와 운영 서버는 기존 desktopProfile·API 대상·배포 권한으로 분리한다.

release DB 성공 저장과 admin DB 등록은 하나의 트랜잭션이 아니다. 성공 보고 후 admin 등록이 실패하면 빌드 결과를 없애거나 다시 빌드하지 않고 catalogSync=pending/failed와 원인을 표시하고 동일 목록을 재처리한다. 공개 준비 조건은 등록 성공을 요구한다. 공개 시점에는 release 저장소에서 업로드·배포 target을 확인하고, 실행 판단도 마지막 확인된 지원 배포 목록과 관리자 정책을 사용한다. 중간 실패가 있어도 자동 공개보다 비공개가 우선이다. 구체적인 원자성·재처리 단위는 독립 검증에서 집중 검토한다.

## 6 새 플러그인 전체 흐름

예: `auto_subtitle`은 설명용 새 사용자 기능이다. 실제로 추가하지 않는다.

1. 개발자가 안정적인 ID로 사용자 선언·Angular 화면/route·Nest 실행 연결·필요 Python 처리와 모델을 개발한다. 크레딧이 있으면 Web API의 실제 과금 작업을 같은 ID로 연결한다.
2. 개발 빌드에서 선언과 실제 등록의 일치를 검사하고 목록 파일을 만든다. 신규 항목은 개발 어드민에 미공개로 나타난다. 개발 서버에 필요한 API·과금 코드가 먼저 준비돼 있어야 한다.
3. 기존 source snapshot에서 대상 플랫폼 앱을 빌드·검증·업로드한다. 같은 소스에서 생성·번들된 목록을 기존 성공 보고에 붙인다.
4. 해당 환경 어드민의 플러그인 관리에 신규 ID가 설정 대기로 나타난다. ID를 운영자가 다시 타이핑하지 않는다. 개발 환경 설정을 운영으로 무조건 복사하지 않는다.
5. 운영자가 이름·설명·카테고리·스토어 순서를 확인하고 기존 `/plans`에서 허용 요금제를 지정한다. 과금 작업 연결·단가도 기존 화면에서 확인한다. 신규 항목이 설정 미완료이면 공개를 거절하고 필요한 항목을 보여준다.
6. 릴리스 관리에서 검증된 설치 파일을 배포 target에 공개한다. 플러그인 공개는 별도 운영 동작이다. 빌드를 공개해도 플러그인이 자동 공개되지는 않는다. 플랫폼마다 준비 상태를 표시한다.
7. 운영자가 플러그인을 공개·사용 가능으로 설정한다. 앱은 자신이 실제 구현한 ID와 서버의 공개 카탈로그를 ID로 결합한다. 새 코드를 포함하지 않은 앱은 해당 기능을 실행할 수 없고, 지원하지 않는 항목을 실행 가능한 카드로 만들지 않는다.
8. 회원은 플러그인 탐색·설치·작업 준비를 한다. 현재 요금제에 미허용이면 기존 배지·업그레이드 흐름을 따른다. 실제 실행 직전에 전체 실행 중지→해당 앱 지원→요금제 허용→크레딧/필수 자산을 확인한다. 서버도 과금 시작 전에 같은 정책을 검사한다.
9. 이후 이름·분류·순서·공개·중지는 어드민에서 변경한다. 기능의 화면·처리 코드를 바꿨다면 앱을 새로 배포한다.

## 7 앱 조회와 실행 및 중지

표시 가능 = 로컬 실제 사용자 기능 ∩ 서버 공개 목록 ∩ 해당 설치 빌드의 검증된 지원 목록. 개발용 로컬 실행은 개발 서버의 검증 경로를 사용하고 운영 등록·공개 권한을 얻지 않는다. 서버 목록은 카테고리·이름 등 표시 데이터만 바꾼다. route·실행 handler는 로컬 연결을 사용한다.

실행 가능 = 지원되는 공개 플러그인 + 전체 활성 + 현재 요금제 허용 + 필요한 크레딧·모델·자원. 무료 플러그인도 앞의 정책을 확인하되 과금 작업은 만들지 않는다. UI guard만으로 완료 처리하지 않고 Nest 실행 진입점·직접 요청·큐 실제 dispatch와 Web API 작업 시작을 확인한다. 전역 상태로 TTS/렌더 worker 프로세스 전체를 죽이지 않는다.

운영 중지 기본 제안: 이미 실행을 승인받아 처리 중인 작업은 끝내고 새 실제 실행을 막는다. 큐 대기는 실제 dispatch 전에 최신 정책을 재검사한다. 중지된 작업은 실행하지 않고 사용자에게 알린다. 이미 차감한 큐 작업을 취소할 때 기존 실패/반환 경로로 한 번만 복원한다. 과금 성공/실패 보고·정산·환불·재시도 복구는 공개/중지 검사로 막지 않는다. 요청 재전송과 새로운 실제 작업 시작도 구분해야 한다.

서버 연결이 끊기면 캐시된 목록으로 탐색·설치 상태·기존 결과 조회를 유지하고 신규 관리 대상 실행은 보류한다. 새 서버 정책 조회가 실패했다고 미등록 기능을 허용하지 않는다. 목록은 시작·스토어 진입·포커스 복귀 시 갱신하고 실행 직전 정책은 실시간 확인한다. 첫 범위에는 강제 푸시를 넣지 않는다. 승인 직후 중지와 실제 CPU 작업 시작 사이의 경합은 있으므로 즉시 강제 종료를 보장하지 않는다. 기본 온라인 실행 정책의 UX 영향은 사용자에게 제안으로 명시한다.

과거 정책 확인 기능이 없는 설치 앱의 무료 로컬 실행을 서버에서 즉시 멈출 수는 없다. W18 지원 앱을 기준 버전으로 도입하고 서버가 제어할 수 있는 신규 유료 요청에는 최소 지원 정책을 적용한다. 출시 전 오래된 개발판별 예외 어댑터를 만들지 않는다.

## 8 기존 데이터 전환과 검증 기준

현재 14개 ID·이름·카테고리·공개 상태를 대조해 초기 카탈로그로 등록한다. 기존 허용 목록·전역 상속 설정·설치 이력·즐겨찾기는 그대로 보존한다. 신규 등록의 미공개 기본값을 기존 14개에 무작정 적용하지 않는다. 과금 이력의 ID와 과거 표시 스냅샷도 유지한다.

서버·어드민이 카탈로그를 준비한 뒤 앱을 전환한다. 서버가 없는 상태의 신규 앱이 모든 기능을 보여주고 실행하는 fallback은 운영에서 허용하지 않는다. 배포 target 롤백은 해당 빌드 지원 목록을 바꾸며 운영 이름·요금제 설정은 되돌리지 않는다. 설치한 앱은 자동으로 구버전이 되지 않으므로 롤백 시 새 설치 지원과 이미 설치된 지원을 어떻게 나눌지 검증 대상이다.

설계 검증 기준: 기존 14개 보존, 무료 기능 등록, 복수 과금 작업 연결, 신규 설정 전 미공개, 동기화 재시도/동시 전송/역순 전송/플랫폼 차이, 운영 override 보존, 등록 권한과 공개 권한 분리, 실패 빌드 공개 차단, 분류 삭제 전 이동, 개인 순서 보존, 구형 앱 미지원 차단, 큐 중지와 중복 환불 방지, 성공 응답 유실 뒤 복구, 두 DB 사이 실패와 재처리, 서버 연결 실패 처리.

## 9 검증에서 판단할 핵심

등록 정본을 Nest의 작은 JSON으로 새로 만드는 것이 최선인지, 현 Angular 등록을 추출하는 편이 더 작은지, 별도 manifest 중복을 늘리는지 비교한다. 성공 빌드 등록과 공개 target을 연결할 때 새로운 이중 DB 불일치와 release 결합 비용이 과한지도 비판한다. 최소 지원 빌드/플랫폼 정보의 범위, 실행 중지의 실제 강제 가능 범위, 신뢰하는 runner의 한계, 현재 요금제/과금 구현을 훼손하지 않는 전환을 검토한다. 절대적인 최선이라는 표현 대신 이 저장소 제약에서 가장 단순하고 검증 가능한 방법을 선택한다.
