# 플러그인 목록과 관리자 및 앱 스토어 동기화 논의와 후속 이관

기록일: **2026-10-29 KST**. 상태: **이번 세션 구현 제외, 후속 TODO**.

사용자 최종 지시: “플러그인 목록 웹 관리자페이지랑 앱의 스토어 목록이랑 동기화하는 작업은 이 세션에서는 하지 않을게. 너무 복잡해질 것 같아.” 관련 논의를 보존하고 별도 작업으로 다시 검토한다. 아래 개발·배포 구조는 검토한 제안이며 승인된 구현 명세가 아니다.

## 1. 이번에 정한 범위

- 공통 플러그인 목록, 웹 관리자와 앱 스토어의 목록 동기화, 빌드·배포 등록 목록 전송을 이번 세션에서 구현하지 않는다.
- 관리자 플러그인 관리·분류·공개·긴급 비활성화 등 연결된 논의도 이 기록과 후속 TODO에 모은다. 목록 동기화에 필요하다는 이유로 이 기능들을 자동 착수하지 않는다.
- 기존 가입 코드 보너스·지속 기본 상태·요금제별 사용 제한 논의 자체를 취소한 지시는 아니다. 다른 기능의 진행 중 이번 동기화 과제를 필수 선행 작업으로 임의 편입하지 않는다. 필요한 최소 목록 활용 범위는 해당 작업에서 따로 설계한다.
- 이번 요청은 문서화다. 제품 코드·DB·빌드·서버·배포에 변경을 가하지 않는다. 커밋·푸시 지시는 별도로 받지 않았다.

## 2. 논의가 시작된 이유와 현행 구조

회사가 요금제별로 사용할 수 있는 플러그인을 지정하려면 관리자 요금제 설정에 선택할 목록이 필요하다. 사용자는 그 목록, 앱 스토어, 과금 작업이 서로 다른 이름·목록을 갖는 문제를 지적했다. 무료 플러그인도 관리해야 하므로 과금 작업 목록을 전체 플러그인 목록으로 사용할 수는 없다.

10월 28~29일 소스 조사 기준:

| 대상 | 현재 목록과 동작 |
|---|---|
| 관리자 `/operation-policies` | Web API의 과금 작업 정의와 DB 단가를 사용한다. 한 행은 과금 작업이다. 한 플러그인에 여러 작업이 있을 수 있고, 과금하지 않는 기능은 이 목록만으로 수집되지 않는다. |
| Web API의 요금제 플러그인 허용 목록 | `all/allowlist`, 저장 테이블, 목록 교체 API와 `allowsPlugin` 기반은 있다. 관리자 선택 UI와 실제 실행 검사에 연결돼 있지 않다. 등록 plugin ID도 현재는 과금 정의에서 파생한다. |
| Desktop 앱 스토어 | 로컬 Nest의 `GET /plugins`를 받는다. Python manifest·Nest 실행기·정적 가상 워크플로를 합친 결과를 Angular의 사용자 기능 등록 목록으로 다시 제한한다. Web API의 공통 운영 카탈로그를 소비하지 않는다. |
| 카테고리 | Angular TypeScript의 `NAV_GROUPS`에 이름·소속·순서가 있다. 외부 JSON이나 관리자 DB로 운영하는 분류가 아니다. 관리자 소식의 연결 화면 선택에도 별도 분류 사본이 있다. |
| 스토어 순서 | 앱에 정의된 카테고리 순서와 카테고리 내부 순서를 따른다. |
| 실제 사이드바 순서 | 설치된 기능을 보여주며 일반 카테고리 내부는 회원 설치 순서, 즐겨찾기는 회원 개인 순서를 따른다. |
| 실행 허용 검사 | Desktop `LicensePolicyService`는 현재 항상 허용한다. Web API 작업 시작도 새 등급별 허용·전체 중지 검사를 적용하지 않는다. |
| 앱 배포 | Angular 빌드 → Desktop Nest 번들 → Electron 컴파일 → 설치 파일 생성. Python 소스도 앱 리소스에 포함한다. 모델 다운로드·설치 상태 전환은 있으나 관리자 등록만으로 새 화면·실행 코드가 생기지는 않는다. |

조사한 최신 앱 소스의 사용자 기능은 14개이며 분류는 하이라이트 추출 3, 영상 자동제작 6, 영상 편집·변형 2, 영상 구성 3이다. 내부 TTS·영상 렌더 등 공유 모듈은 독립 사용자 플러그인과 구분한다. 10월 28일 실제 실행 로컬 API가 13개였던 환경 차이는 별도 현황 증거를 따른다. 여기서 현재 운영 배포의 개수를 다시 확정하지 않는다.

## 3. 용어

- **사용자 플러그인:** 스토어·사이드바에서 회원에게 제공하는 기능.
- **plugin ID/key:** 화면, 실행, 과금, 허용 설정을 연결하는 안정적인 식별자. 표시 이름 변경과 별개다.
- **과금 작업:** 크레딧을 차감·정산하는 작업. 플러그인과 1:1 관계가 아니다. 무료 기능에 가짜 과금 작업을 만들 필요가 없다.
- **실행기:** 해당 플러그인의 요청을 실제 처리 코드에 연결하는 앱 내부 코드. 예를 들어 인물 하이라이트 요청을 Python 분석 코드로 전달한다. 공통 실행기를 재사용할 수 있으므로 모든 플러그인마다 새 클래스를 만드는 요구가 아니다.
- **기술 등록/manifest:** 개발 코드가 구현한 기능과 실행 연결·지원 정보를 설명한다. 현재 Python manifest와 Angular 등록 등이 분산돼 있다.
- **운영 카탈로그:** 관리자에게 보이는 이름·분류·순서·공개·전체 활성 상태 등을 관리할 서버 데이터의 제안 명칭.
- **동기화 artifact:** 특정 앱 릴리스에 포함된 사용자 기능 목록을 기계적으로 만든 전송 파일. 제품 기능 코드나 공개 승인 자체가 아니다.

## 4. 사용자 요구와 외부 답변의 상태

### 4.1 유지할 사용자 요구

- 회사가 기본 상태와 Basic·Pro·Business에서 사용 가능한 플러그인을 정한다. 회원이 임의 N개를 선택하지 않는다.
- 기본 상태의 목록과 Basic 목록은 같을 수도 다를 수도 있어야 한다. 기본 상태를 유료 판매 상품으로 세지 않는다.
- 카테고리 생성·수정·삭제·순서 변경, 플러그인의 분류 배정·이동과 스토어 내부 순서 관리를 검토한다.
- 사이드바 카테고리 내부 설치 순서와 즐겨찾기 개인 순서는 기존대로 유지한다. 관리자 지정 플러그인 순서를 사이드바 내부 순서까지 덮어쓰지 않는다.
- 새 플러그인은 관리자에게 발견·등록돼 필요한 분류·요금제 설정을 한 뒤 회원에게 공개하는 흐름을 검토한다.
- 긴급 상황에는 요금제별 제공 설정을 지우지 않고 해당 플러그인의 사용을 전체적으로 중지할 관리자 토글이 필요하다는 요구가 추가됐다.
- 목록 동기화의 실제 구현은 이번 세션에서 제외한다.

### 4.2 전략실 답변

사용자가 전달한 답변의 요지:

1. **요금제상 이용 불가 플러그인 노출:** 숨기면 상위 플랜의 이점을 알기 어려우므로, 스토어에 표시하되 “현재 요금제에서 이용할 수 없음”으로 안내하는 편이 적합하다는 의견이다. 다만 UI/UX 판단을 위해 이사님 추가 확인이 필요하다고 답했다.
2. **상위 플랜 포함 관계:** 현 기준으로 상위 플랜이 하위 플랜의 기능을 모두 제공한다. 하위 플랜에서 제공하지만 상위 플랜에서는 제공하지 않는 형태는 고려하지 않는다.

따라서 유료 등급은 **Basic ⊆ Pro ⊆ Business**가 최신 정책 방향이다. 과거의 “유료 등급을 완전히 독립적으로 정해 상위에서 하위 기능을 제외할 수도 있다”는 설명을 최신 결정으로 사용하지 않는다. 저장/API/UI는 이 포함 관계를 지켜야 하지만, 자동 체크 전파와 오류 안내 중 구체적인 편집 UX는 아직 정하지 않았다.

기본 무료 상태에도 같은 포함 관계를 적용하는지까지 전략실 답변이 명시한 것은 아니다. 기존 기본 상태의 별도 목록 요구를 보존하고 후속 설계에서 적용 범위를 확인한다.

### 4.3 이사님 확인 상태

이사님께 물을 문구를 작성했다:

> 이사님, 요금제별로 사용 가능한 플러그인을 다르게 제공하는 것과 관련해 질문드립니다. 현재 요금제에서 사용할 수 없는 플러그인도 스토어에 표시하되, ‘현재 요금제에서는 이용할 수 없음’으로 안내해도 괜찮을까요?

이사님 답변은 아직 이 대화에 전달되지 않았다. 실제 메시지를 보냈다고 기록하지 않는다. **노출 후 이용 불가 안내는 전략실 선호안이며 최종 UI 확정은 아니다.**

## 5. 검토한 공통 목록과 관리자 역할

| 정보 | 제안한 소유 주체 | 재동기화 시 지킬 점 |
|---|---|---|
| ID·실행 코드·화면·실행 연결·지원 정보 | 개발 소스와 릴리스 | 운영자가 임의 ID/실행 코드를 생성하는 화면으로 대체하지 않는다. |
| 표시 이름·설명·카테고리·카테고리/스토어 순서 | 서버의 관리자 설정 | 개발 기본값을 다시 보냈다고 운영자 편집값을 덮지 않는다. |
| 공개·전체 활성 상태 | 서버의 관리자 설정 | 새 항목 자동 발견과 자동 공개를 분리한다. 긴급 중지가 배포로 풀리지 않는다. |
| 등급별 사용 허용 | 서버의 요금제 설정 | 유료 상위 포함 규칙을 보존한다. 전체 중지 때도 허용 목록은 지우지 않는다. |
| 설치 여부·설치 순서·즐겨찾기 | 회원 앱 | 서버 분류 변경·전체 중지가 개인 설치 이력을 초기화하지 않는다. |
| 과금 작업·단가 | 기존 Web API 과금 정책 | 같은 plugin ID로 소속만 연결한다. 과금 작업을 플러그인 카탈로그와 같은 행으로 합치지 않는다. |

관리자 메뉴 제안:

- **플러그인 관리:** 표시 정보, 공개/전체 활성, 소속 분류, 연결된 과금 작업·허용 요금제 확인.
- **분류·순서 관리:** 카테고리 CRUD, 카테고리 순서, 배정/이동, 스토어 내부 순서.
- **`/plans`:** 기존 등급 설정 안에 허용 플러그인 선택을 추가하고 월간/연간 상품이 같은 등급 설정을 공유한다. 동일 허용 데이터를 다른 메뉴에서 독립 사본으로 편집하지 않는다.

카테고리 삭제 전에 소속 플러그인을 다른 분류로 옮기도록 하는 안, 좌측 카테고리·우측 플러그인 UI, 드래그/이동 버튼과 한 번의 저장 등은 제안 단계다. 새 메뉴명·상태 명칭·배치가 확정되거나 구현된 것은 아니다.

## 6. 개발부터 회원 사용까지 검토한 절차

이 절의 자동화는 제품 미구현·미승인 제안이다. 현재 배포 명령에 이미 연결돼 있다고 해석하지 않는다.

1. **개발:** 안정적인 plugin ID로 화면·처리 코드·실행 연결을 추가한다. 과금이 있으면 서버 작업을 연결한다. 모델·실행 환경도 준비한다.
2. **검사·목록 생성:** 앱에 선언된 사용자 기능을 읽어 앱 버전/소스 revision/hash/기능 목록을 생성한다. 중복 ID, 메타데이터 누락, 화면/실행/과금 연결을 검사하는 방향이다. 기존 실험은 이 검사의 전체를 구현한 것이 아니다.
3. **서버 준비:** 신규 API·과금 정의가 필요하면 서버가 먼저 지원하도록 배포한다. 기존 서버 기능만 쓰면 해당 제품 코드 변경은 없을 수 있다.
4. **패키징과 동기화:** 성공한 대상 릴리스의 목록을 해당 개발/운영 서버로 명시적으로 전송한다. 개발자가 파일을 수정한 순간 원격 서버가 감시·수집하는 방식은 아니다. 운영 동기화는 일반 회원 앱의 임의 보고를 근거로 삼지 않는다.
5. **신규 설정 대기:** 새 ID는 관리자에게 미공개·미설정으로 나타난다. 같은 목록의 재전송은 중복을 만들지 않고 관리자 설정을 보존한다. 전송 자격에 공개 권한을 주지 않는다.
6. **관리자 설정:** 분류·표시 정보·요금제 허용·필요한 과금 설정을 확인한다. 필수 설정 없이 자동 공개하지 않는다.
7. **앱 배포와 공개:** 실제 릴리스의 설치 파일/업데이트를 배포하고 준비된 기능을 공개한다. 서버에 등록했다고 그 코드가 없는 앱에서 실행되지는 않는다.
8. **앱 조회와 실행:** 앱이 실제 지원하는 목록과 서버 운영 정보를 결합하고 현재 회원 허용 여부를 적용한다. 필요한 설치/모델과 크레딧을 검사한 뒤 실행한다.

순서 중 동기화/릴리스 업로드/관리자 공개의 정확한 결합 지점과 실패 시 재실행 절차는 최종 설계에 남는다. 실패한 빌드가 공개 가능한 기능이 되어서는 안 되고, 개발 환경 업로드가 운영 설정을 바꿔서는 안 된다.

### 동기화 방식 대안

- **수동 등록:** 개발자가 관리자에서 ID·지원 정보를 직접 추가. 초기 구현은 작지만 기술 정보 중복 입력·누락·오타의 부담이 있다.
- **릴리스 목록 전송:** 빌드/배포 도구가 등록 정보를 추출해 서버로 전송. 중복 입력을 줄이지만 수집 정본·인증·버전과 배포 연결 구현이 필요하다.

기존 추천은 두 번째였지만 **사용자가 선택·승인한 최종 방식은 아니다**. 이 복잡성을 이유로 이번에 이관했다. “자동 감지”가 유일한 가능한 방식이라는 전제로 다시 시작하지 않는다.

릴리스별 지원 목록을 구분하고 이전 목록 전송이 새 항목을 전역 삭제하지 않도록 하는 점도 논의했다. 다만 출시 전 옛 개발판을 위해 임의의 호환 adapter/예외 계층을 추가하자는 요구는 아니다. 정식 출시 후 지원 버전 정책은 기존 별도 TODO와 함께 검토한다.

## 7. 노출과 실행 허용의 구분

| 상황 | 논의한 표시와 실행 | 확정 상태 |
|---|---|---|
| 현재 요금제에서 미제공 | 스토어에 보여주되 이용 불가 안내, 실행 차단 | 전략실 선호안. 노출 UX는 이사님 확인 전 |
| 관리자 전체 비활성화 | 전체 회원의 새 실행 차단. 스토어/진입점 숨김 또는 중지 안내 검토 | 전체 토글 요구 있음. 구체적 표시 UX 미확정 |
| 신규 미공개·설정 대기 | 회원에게 아직 제공하지 않음 | 제안한 공개 흐름, 전체 제품 미구현 |
| 앱이 해당 기능을 구현하지 않음 | 목록 등록만으로 기능 생성 불가. 지원하지 않는 기능을 실행시키지 않음 | 기술적 제약. 구버전 표시 UX는 설계 전 |

따라서 “내 요금제에서 못 쓰는 플러그인도 보임”과 “전체 긴급 중지한 플러그인은 숨김”을 같은 정책으로 합치면 안 된다.

## 8. 긴급 전체 비활성화 논의

사용자 요구의 핵심: 요금제별 제공 설정은 보존하고, 관리자가 토글로 전체 사용을 중지·재개한다. 예를 들어 Pro·Business 허용 설정이 있는 플러그인을 전체 중지했다가 다시 켜도 원래 Pro·Business 설정을 다시 입력하지 않는다.

제안한 동작:

- 비활성화는 새 실행을 거절하고 스토어·사이드바·즐겨찾기의 실행 진입점을 숨기거나 중지 표시한다.
- 이미 열린 화면, 직접 URL, 작업 생성·예약·재시작과 대기열의 실제 실행도 빠짐없이 검토한다. 화면에서 숨기는 것만으로 실행을 막았다고 하지 않는다.
- 설치 파일·모델·즐겨찾기 개인 설정·기존 프로젝트와 결과물은 보존한다.
- 과금 유무와 관계없이 실행 허용을 검사한다. 거절된 신규 작업에 먼저 크레딧을 차감하지 않는다.
- 이미 차감된 대기 작업을 취소하면 기존 실패/크레딧 반환 절차로 정리한다. 실행 차단 때문에 결제·정산·크레딧 반환 복구까지 막으면 안 된다.
- 여러 사용자 기능이 공유하는 TTS·렌더 프로세스 전체를 한 사용자 플러그인의 중지와 혼동하지 않는다.

**아직 정하지 않은 운영 세부:** 이미 실행 중인 작업까지 강제 종료할지, 중지 화면 안내와 문구, 설정 캐시/전파 주기, 서버 연결 실패 시 새 실행 처리. 기존 추천은 진행 중 작업은 완료시키고 새 실행을 막는 것이었지만 확정 정책으로 취급하지 않는다.

최초에는 앱이 원격 정책을 읽고 실행 전에 확인하도록 업데이트해야 한다. 이 기능이 반영된 뒤에는 중지·재개 때마다 앱을 재배포하지 않는 것이 목표다. 오프라인 앱의 화면을 서버가 즉시 바꾸는 것은 불가능하며, 실행 직전 서버 확인을 강제하려면 연결 실패 처리도 정의해야 한다. 엄격한 즉시 차단과 오프라인 실행을 동시에 무조건 보장한다고 쓰지 않는다.

## 9. 기술 실험의 결과와 한계

기존 일회성 로컬 실험은 실제 앱 등록 14개를 추출하고 HTTP로 임시 서버에 전송해 격리 PostgreSQL에 저장했다. 기록된 검사 결과는 11개 통과다. 신규 소스 fixture를 넣었을 때 1개 추가 감지, 반복/동시 전송 중복 방지, 운영 설정 보존, 설정 전 비공개, 동기화 자격과 공개 자격 분리를 확인했다.

**제품에 적용하지 않은 부분:** 실제 Nest 제품 endpoint, 관리자 JWT/배포 인증, DB migration, 실제 릴리스 자동화, 앱 스토어 소비, 전체/등급별 실행 제한, 앱 패키징·배포.

이번 문서화에서 실험·테스트를 재실행하지 않았다. 11개 통과는 당시 별도 실험 기록이며 제품 전체 기능 검증이나 구현 완료가 아니다. 실험의 임시 토큰·설정은 운영 인증 설계가 아니다. 14개 목록의 특정 revision과 source fixture의 15번째 등록을 구분한다.

## 10. 재개할 때 결정할 것

1. 수동 등록과 릴리스 목록 동기화 중 어떤 방식으로 시작할지, 기술 등록 정보의 정본을 어디에 둘지.
2. 목록과 관리자 운영값의 데이터 계약, 개발/운영 환경 구분, 전송 권한·공개 권한, 릴리스 성공/업로드와 동기화 시점.
3. 공개·전체 활성·요금제 허용의 상태 모델과 각 표시 대상.
4. 이사님 노출 UX 답변. 공개됐지만 현재 요금제에서 못 쓰는 기능의 설치/진입/안내 범위.
5. 전략실의 유료 상위 포함 정책을 UI/API에서 보장하는 방법과 기본 무료 상태의 포함 관계 범위.
6. 실제 기본·Basic·Pro·Business 허용 목록은 회사 운영 입력값으로 받는다. 개발자가 임의 지정하지 않는다.
7. 긴급 중지의 진행 중/대기 작업 처리, 과금 복구, 오프라인·캐시·갱신 시점.
8. 카테고리 삭제/배정/순서 UX, 기존 정적 분류에서의 전환, 공통 목록의 다른 소비자(관리자 소식 연결 화면 포함).

## 11. 구현 상태와 재개 원칙

| 항목 | 이 세션에서 확인한 상태 |
|---|---|
| 회사가 허용 플러그인 지정 | 사용자 요구. 실제 값 미입력 |
| 유료 상위 플랜이 하위 기능 포함 | 전략실 현 정책 방향 확인 |
| 요금제 미제공 기능의 노출 | 전략실 의견 있음. 이사님 확인 전 |
| 등급별 저장/API 기반 | 기존 코드 일부 있음. 사용자 기능 완료 아님 |
| 관리자 플러그인/분류 메뉴 | 제품 미구현 |
| 공통 카탈로그 제품 API/DB/앱 연결 | 제품 미구현 |
| 전체 긴급 중지 | 요구·제안 단계, 제품 미구현 |
| 자동 목록 추출/HTTP/DB 실험 | 별도 기술 실험만 완료 |
| 빌드·배포 동기화 | 제품 미구현 |
| 이번 요청 | 기록·후속 TODO·인덱스 반영 |

사용자가 후속 작업을 시작하겠다고 할 때 이 기록을 먼저 읽고 필요한 저장소의 현재 원격 dev·미커밋 상태부터 다시 확인한다. 과거 브랜치가 지금도 최신이라고 간주하지 않는다. 최소 범위의 설계를 정한 뒤 구현하며, 실험 코드를 그대로 운영에 연결하지 않는다. 이 기록이나 체크리스트 자체를 구현 승인으로 해석하지 않는다.
