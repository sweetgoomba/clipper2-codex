## User Product Language Decision

User rejected `workflow` as a user-facing product concept.

Confirmed product model:

- Users should understand only two core concepts:
  - `플러그인`
  - `프로젝트`
- A plugin is a Store item that users install, open, and use.
- A project is what users start creating inside a plugin.
- The queue unit users see is always a project.
- The archive/library/project page should show completed projects.
- `workflow`, `job`, `runtime`, `worker`, and `pipeline` should not be exposed
  as user-facing concepts.

Important correction:

- `shortform_prompt`, `shortform_url`, and `shortform_paste` are each separate
  user-visible plugins.
- They are not just input modes inside one shortform plugin.
- They may share internal shortform project/render implementation.

## Developer Terminology Decision

Use these concepts for new docs and future implementation planning:

| Term | Meaning |
| --- | --- |
| `Plugin` | User-visible Store feature unit |
| `Project` | User-created work item; queue/archive unit |
| `ProjectRun` | Internal execution record for processing/rendering a project |
| `RuntimeProgress` | Raw worker/provider progress event |
| `ProjectProgress` | User-facing normalized progress state |
| `ProgressStep` | User-visible analysis step message when appropriate |
| `RuntimeWorker` | Hidden Python/render/ffmpeg process or executor |

Avoid using `task` as a new product/doc term because it collides with
user-visible progress stages.

## Progress Message Decision

- Highlight analysis can show detailed user-facing progress steps.
  - Example: `문장 위치를 영상과 맞추고 있습니다`.
- Shortform/ffmpeg render should not expose technical render messages like:
  - `Staging render assets`
  - `Rendering clip 1/5`
  - `Concatenating rendered clips`
  - `Mixing render audio`
- Render UI should show simplified messages:
  - `영상 생성 중`
  - `영상 생성 완료`
  - `영상 생성 실패`
  - `영상 생성 취소됨`

## Target Direction

Move from current `/jobs`-first behavior toward Project-first behavior:

```text
Current:
Job created -> queue run -> completed -> Project created/promoted

Target:
Project created -> ProjectRun created -> queue run -> same Project updated
```

Keep existing `/jobs`, `VideoRenderJob`, and Python runtime `/jobs` as
compatibility/internal execution layers until the Project-first model is
implemented safely.

## Shortform Legacy Parity Scope

The user clarified that the current shortform production UI in
`work/clipper1-input-workflow-split` is not acceptable. The branch itself should
not be thrown away because it contains required changes:

- `shortform_url`, `shortform_paste`, and `shortform_prompt` remain separate
  user-visible plugins.
- Recent `workspace` -> `project` terminology cleanup remains.
- Existing Clipper2 plugin/project pre-render structure remains where possible.

The new Phase 1 target is strict legacy parity:

- The Clipper2 shortform production editor must match the legacy
  `adlight_angular` Clipper shortform screen exactly in UI, styling, and
  pre-render behavior.
- "Close enough" is not accepted; differences are bugs unless explicitly
  approved by the user.
- Internal code may differ from legacy, but user-visible UI/behavior must match.
- The legacy `D2XDataService` should not be copied as the core state model.
  Clipper2 should use its own state/service boundaries and adapt to the legacy
  UI contract.
