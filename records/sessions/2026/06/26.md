## App Version / Release Policy Notes

관련 문서:

```text
.codex/design/APP_VERSION_MANAGEMENT_APPROACHES_2026-06-23.md
```

확정된 큰 방향:

- 앱 버전 관리는 `/versions` 방식으로 확정한다.
- macOS/Windows는 독립 버전 스트림으로 나누지 않는다.
- user-facing product version은 하나다. 예: `2.5.0`.
- Windows-only fix여도 다음 공통 patch version으로 올린다. 예: `2.5.1`.
- OS별 빌드/서명/공증/검증/다운로드/자동 업데이트 상태는 `release_artifacts`와 target pointer에서 분리 관리한다.
- `/versions2`는 독립 버전 스트림 정책으로 채택하지 않고, OS별 artifact 상태를 강하게 보여주는 UI 감각만 `/versions`에 흡수한다.

브랜치/채널 방향:

```text
dev branch
  -> alpha
  -> 개발팀 내부 확인용 build

stage or release/<version> branch
  -> rc
  -> 출시 직전 QA/스테이징 검수용 build

production/release tag
  -> stable 후보
  -> 필수 artifact 검증과 수동 publish 승인 후 stable
```

`beta`는 현재 필수 채널이 아니다. 외부 베타 프로그램이 필요해지면 추가한다.

버전 표기 방향:

```text
productVersion: 2.5.0
channel: alpha | beta | rc | stable
displayVersion: 2.5.0-alpha.12 | 2.5.0-rc.1 | 2.5.0
buildNumber: release coordinator가 부여하는 전역 단조 증가 build 번호
artifactVersion: 실제 Electron packaging/OS metadata에 들어가는 버전 문자열
```

DB 모델 변경:

- `release_versions`는 `2.5.1` 같은 제품 버전 단위다.
- `release_versions`에 `build_number`를 직접 두지 않는다.
- `release_builds`를 별도로 두고 `build_number`, `display_version`, `artifact_version`, build source snapshot, build status를 저장한다.
- `release_artifacts`는 OS/arch 설치 파일 단위이고 `release_build_id`를 참조한다.
- `release_artifact_attempts`는 같은 artifact job을 재시도한 이력을 저장한다.
- stable로 publish되는 macOS/Windows artifact는 같은 `release_build` 아래에 묶이고 같은 build number를 공유한다.
- `build_number`는 제품 버전마다 1부터 다시 시작하지 않는다.

Release coordinator 배치:

- 본체는 `web/clipper_web_api`의 release module에 둔다.
- `clipper_web_api`가 release DB, build job 상태, publish/pull/rollback, download/update target의 SoT다.
- `web/clipper_web_admin`은 operator UI다.
- `web/clipper_infra`는 runner 설치/운영, S3 prefix, signing/notarization secret, runbook/compose를 담당한다.
- `desktop/clipper_electron`은 packaging script와 release metadata 주입을 담당한다.

코드 배포와 앱 릴리즈:

- web repo의 `prod` deploy는 실제 prod container/page/API를 바꾸는 운영 배포다.
- desktop repo의 `prod` branch에 코드가 있다고 해서 사용자가 바로 app update를 받는 것은 아니다.
- desktop stable release는 build/sign/notarize/upload/QA/manual promote 후 `release_download_targets`와
  `release_update_targets`가 바뀔 때 사용자에게 반영된다.
- 성공 artifact는 S3에 올라갈 수 있지만, target pointer에 연결되기 전까지 사용자에게 배포된 것이 아니다.
- 실패/QA 탈락 build도 DB에 남긴다. artifact가 생성되어 upload된 경우 retention policy로 일정 기간 보관한다.

Desktop branch/tag 정책:

- 기본 환경 브랜치는 `dev`, `stage`, `prod`를 유지한다.
- `release/<version>`은 필요할 때만 만드는 desktop 안정화 브랜치다. 환경 브랜치가 아니라 특정 버전 RC/QA 작업대다.
- QA가 며칠 이상 걸리거나 다음 기능 개발이 stage에 병행되면 desktop 4개 repo에 `release/2.5.0` 같은 브랜치를 만든다.
- stable release마다 desktop 4개 repo 모두에 annotated tag, 예: `v2.5.0`, 를 찍는 방식을 기본으로 한다.
- tag는 git 이름표이고, source snapshot은 release DB에 남는 multi-repo commit/tag 조합 기록이다. 둘 다 필요하다.
- 같은 commit에 `v2.5.0`, `v2.5.1`처럼 여러 tag가 붙을 수 있다.

SemVer 기준:

- `MAJOR`: 프로젝트/템플릿/플러그인 호환성 파괴, 큰 로컬 데이터 migration, 런타임 호환 정책 변경.
- `MINOR`: 기존 호환성을 유지하는 사용자 기능 추가, 새 플러그인, 새 workflow, 관리자 기능 추가.
- `PATCH`: 버그 수정, 설치/서명/공증 수정, 보안 patch, OS-only hotfix, 기능 의미 변화가 없는 수정.

릴리즈 상태 용어:

```text
stable      현재 일반 사용자에게 배포 중인 정식 버전
superseded  정상적으로 더 새 stable에 의해 대체된 과거 버전
pulled      한때 배포됐지만 문제로 배포 대상에서 내려진 버전
```

롤백 정책:

- 신규 다운로드/업데이트 target rollback과 이미 설치된 앱 downgrade는 다른 문제로 본다.
- 일반 정책은 설치된 앱을 낮은 버전으로 내리지 않는다.
- 문제 버전이 발견되면 해당 release를 `pulled`로 표시하고 신규 다운로드 target을 마지막 정상 artifact로 임시 변경한다.
- 이미 문제 버전을 설치한 사용자는 `2.4.3 -> 2.4.1`로 내리는 대신 `2.4.4` 같은 더 높은 patch release로 복구한다.
- `2.4.4`가 준비되면 다운로드 페이지와 auto update target 모두 `2.4.4`로 바꾼다.

플랫폼별 auto update 예외:

- 공통 product version은 유지한다.
- 다만 auto update target은 platform/arch artifact 단위로 제어할 수 있게 둔다.
- Windows-only fix로 `2.4.2`를 만들었고 macOS artifact가 no-op이면, macOS `2.4.1` 사용자에게 `2.4.2` update 알림을 숨기는 예외를 둘 수 있다.
- 이 예외는 macOS 쪽 코드/데이터/보안/호환성 변화가 없을 때만 허용한다.
