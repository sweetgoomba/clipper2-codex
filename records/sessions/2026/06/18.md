## Shortform TTS Duration Truncation Follow-Up

사용자 QA:

- 새로 만든 shortform의 마지막 대사 `큰 환경 보호가 가능해요! 함께 실천해요.` 중
  TTS가 `큰 환경 보호가 가능해요!`까지만 재생됐다.

원인:

- 최신 job `shortform_render_1781743028087`의 payload에는 마지막 subtitle text와
  `tts_url`이 온전하게 들어 있었다.
- 실제 TTS 파일
  `tts.shortform_project_1781743003682.clip.7.line.clip.7.1.1781743024154.mp3`은
  ffprobe 기준 `2.760s`였지만, `shortform/projects.json`과 render payload에는
  `durationMs=1981` / `duration=1.981`로 저장돼 있었다.
- 저장된 `1981ms`는 `estimatedTtsDurationMs()` fallback 공식과 정확히 일치했다.
  즉 packaged/backend 환경에서 ffprobe duration 측정이 실패했고, 짧은 추정 duration이
  저장됐다.
- Python render worker는 subtitle duration을 믿고 TTS segment에
  `atrim=0:1.981`을 적용하므로 뒤 문장이 잘렸다.

구현:

- `clipper_nestjs`
  - `NaverClovaShortformTtsProvider`가 ffprobe를 사용할 수 없을 때도 TTS 응답 buffer에서
    WAV/MP3 duration을 직접 계산하도록 fallback parser를 추가했다.
  - 기존 프로젝트처럼 이미 짧은 duration이 저장된 경우도 다시 렌더하면 고쳐지도록,
    render job 준비 시 local TTS 파일의 실제 duration을 읽어 in-memory render project의
    narration line duration, clip duration, media slots를 보정한다.
  - 저장 project 구조는 바꾸지 않고 render manifest/payload 생성에 쓰는 project copy만
    보정한다.

검증:

```text

- node --test test/shortform-tts-provider.test.js
  1 pass
- node --test test/shortform-project-generation-assets.test.js --test-name-pattern "shortform render manifest stretches"
  6 pass
- node --test test/shortform-tts-provider.test.js test/shortform-project-generation-assets.test.js test/shortform-project-api.test.js
  17 pass
- Actual latest MP3 parser check:
  audioDurationMsFromBuffer(...clip.7.line.1.mp3) = 2784ms

  outputDurationSec: 29.76
```

## App FFmpeg/FFprobe Env Contract

사용자 정정:

- `/opt/homebrew/bin/ffprobe` 같은 개발자 로컬 설치본은 앱 런타임 기준이 아니다.
- packaged 앱은 `userData/bin`에 설치한 앱 전용 ffmpeg/ffprobe를 전체 런타임에서
  사용해야 한다.
- 표준 env는 `FFMPEG_BIN`, `FFPROBE_BIN`으로 통일하고, `IMAGEIO_*`,
  `CLIPPER_FFMPEG_BIN`, `CLIPPER_YTDLP_FFMPEG_LOCATION` 같은 별도 이름은 직접 사용하지
  않는 방향으로 정리한다.

앱 전용 설치 경로:

```text
macOS: ~/Library/Application Support/Clipper2/bin/ffmpeg
macOS: ~/Library/Application Support/Clipper2/bin/ffprobe
```

구현 커밋:

```text
clipper_electron: d461dfd Pass app ffmpeg tools to runtimes
clipper_nestjs:  b4739c6 Use app ffmpeg env in NestJS
clipper_python:  c2e54c7 Use standard ffmpeg env in plugins
```

구현 내용:

- `clipper_electron`
  - packaged NestJS startup preflight에서 `ensureFfmpeg()`를 호출한다.
  - `getFfmpegPaths()`의 앱 전용 경로를 NestJS process env에
    `FFMPEG_BIN`, `FFPROBE_BIN`으로 주입한다.
  - NestJS process `PATH` 앞에도 앱 전용 `userData/bin`을 추가한다.
  - Python plugin process도 `FFMPEG_BIN`, `FFPROBE_BIN`을 받도록 바꾸고
    `IMAGEIO_FFMPEG_EXE`, `IMAGEIO_FFPROBE_EXE` 주입은 제거했다.
- `clipper_nestjs`
  - TTS duration probe는 `FFPROBE_BIN`을 사용한다.
  - `simple_ffmpeg_transform`은 `FFMPEG_BIN`만 표준으로 사용하고
    `CLIPPER_FFMPEG_BIN` fallback을 제거했다.
  - source ingest/yt-dlp 병합은 `FFMPEG_BIN`에서 dirname을 계산해
    `--ffmpeg-location`으로 넘긴다. `CLIPPER_YTDLP_FFMPEG_LOCATION` 직접 config는 제거했다.
- `clipper_python`
  - `clipper1_video_render`, `dance_highlight`, `dialog_highlight`,
    Template Builder frame extraction script의 직접 ffmpeg/ffprobe lookup을
    `FFMPEG_BIN`, `FFPROBE_BIN`으로 바꿨다.

## URL Shortform Clip Generation 500 Follow-Up

사용자 QA:

- packaged app에서 URL 숏폼 제작 페이지에
  `https://blog.naver.com/fall38/224294202770` 입력 후 `클립 생성하기`를 눌렀을 때
  Angular가
  `Http failure response for http://127.0.0.1:61940/v1/projects/shortform/projects/shortform_project_1781746600126/clips: 500 Internal Server Error`
  를 표시했다.

확인:

- 같은 running NestJS endpoint를 직접 재호출했다.
- 재호출은 201 Created로 성공했고, `shortform_project_1781746600126`은 `ready`,
  clips 8개, Naver Blog parsed text/source images, TTS artifact가 모두 저장됐다.
- 저장된 TTS duration은 실제 ffprobe 기반 값으로 보이며, 이전처럼 fallback 공식에
  고정된 패턴은 아니었다.
- 앱 데이터 디렉터리에는 첫 500의 stack trace가 남아 있지 않았다.

추정 원인:

- URL 파싱/저장 로직은 같은 입력으로 성공했다.
- 첫 500은 OpenAI script generation, Naver Clova TTS, 네트워크 fetch 같은 외부 provider
  transient failure가 plain `Error`로 올라와 NestJS에서 generic 500이 된 케이스로 본다.

구현 커밋:

```text
clipper_nestjs: 095e61d Map shortform clip provider errors
```

구현:

- `ShortformProjectService.generateClips()` catch에서 이미 의도된 NestJS
  `HttpException`은 그대로 유지한다.
- provider/network plain `Error`는 `ServiceUnavailableException`으로 감싸서 500 대신
  503으로 응답하고 원인 메시지를 보존한다.
- 회귀 테스트를 추가했다.

검증:
