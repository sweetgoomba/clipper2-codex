## 이 세션이 시작된 이유와 목표

하이라이트 분석 시간이 길어 안무·인물·대사에 GPU 가속과 ONNX 모델·실행기 전환을 조사했다. 11월 4일 4차 내부 QA에서는 가속 경로가 들어간 개발판을 설치해 시험했고, 인물·대사 등에서 실패가 발생했다. 기존 두 세션의 실험과 당시 수정이 현재 코드, 실제 설치본, 운영판에 각각 어디까지 반영됐는지 불명확했다.

목표는 두 가지였다.

1. **안정성과 속도를 함께 검증한다.** 최신 원격 `dev`를 출발점으로 CPU 기준과 사내 GPU 후보를 같은 영상으로 비교한다. 실제 GPU 추론, CPU 복구, 결과 품질, 취소·복구·과금까지 확인하고, Windows·Mac의 사내 장비와 빠진 환경으로 넓힌다.
2. **실패를 고칠 수 있을 만큼 근거를 남긴다.** 개발 어드민의 설치형 앱 에러·크레딧 통계·진단을 검토하고, 개별 실행의 시간과 실패 단계를 추적한다. 제품 어드민 UI는 목업을 먼저 검토하고 사용자 승인 후 적용한다. 운영 가속 활성화와 배포는 실기기 근거를 갖춘 뒤 별도로 판단한다.

**현재 위치.** 문제를 재현하고 원인을 좁히는 단계를 지나, R3 오프라인 CPU판에서 2·3·8번 인물 분석의 기준값을 확보했다. 다음은 **같은 R3의 오프라인 GPU 비교**와 **격리된 로컬 API·DB·어드민을 통한 실제 앱 통합 검증**이다. 개발 서버 이전과 별개로 이 두 시험을 시작할 수 있다.

## 어드민과 데이터 수집

- **설치형 앱 에러**는 신고 단위다. 수동 신고와 동의한 자동 상세 신고가 들어온다. 기본 사용 진단(Tier 1)은 원칙적으로 켜져 있으며 변경할 수 있다. 자동 상세 로그(Tier 2)는 별도 동의가 기본 OFF이고 로그인·네트워크와 종료/전송 조건을 탄다. 즉시 전송 전체를 보장하지 않는다. 앱이 먼저 로컬에 기록한 뒤 조건에 맞춰 전송하는 방식으로 설계한다.
- **현재 화면에서 `에러 n회`**는 신고에 붙은 ERROR·FATAL 로그 수, **`소요`**는 첨부 로그의 첫 시각부터 마지막 시각까지의 범위다. **통계 → 플러그인** 시간은 서버의 크레딧 작업 생성부터 정산까지, **진단 개요**는 세션 집계 기반이다. 계정 필터와 수집 동의 상태의 영향을 받을 수 있다. 앱·개별 실행 원장이 성능 실측과 정산 대조의 근거다.
- 기존 자동 표기의 `prod / stable`과 수동 표기의 `packaged`는 실제 개발판·운영판을 정확히 가르지 못할 수 있다. 앱 버전은 수집된다. 같은 앱 버전의 **설치 빌드 번호와 실제 채널**은 앱 패키지 → 수동·자동 수집 → 웹 API 저장 → 어드민 표시를 연결할 과제다. 기존 신고의 누락값은 확인된 근거 범위로 표시한다.
- **목업 결정.** 신고 상세의 기존 기본 정보 다음, ‘진단에서 에러 그룹 보기’ 위에 **실행 진단**을 둔다. 시간 표기는 `소요 1h 1m 6.22s`처럼 짧게 한다. 에러 횟수·OS 원문 표기는 유지하고 툴팁은 생략한다. `처리 방식`을 사용한다. 기능·실행 번호·결과·단계·시간·빌드는 공통이며, GPU·드라이버·메모리 등은 해당되는 기능에 표시한다. 정보를 펼친 상태로 보여주고 서버 주소·수신 서버·중복 상태 설명은 뺐다. 개별 **실행 기록**은 앱 전체의 탭으로 하고 플러그인으로 필터링한다. **개요**에는 집계를 둔다. 처리 순서와 인과는 작업·시도 ID와 구조화된 이벤트를 코드로 연결한다. 정해진 문구에 LLM은 필요 없다.

### 1. R3 인물 오프라인 GPU 시험판과 PC 2·3·8 비교

**대기 없이 진행할 첫 작업이다.** 첫 개발 API용 GPU 시험판은 R3보다 앞선 코드와 원격 API를 사용한다. 다음 시험은 오프라인 CPU판과 같은 R3 분석·저장·로그 경로를 사용하고, 사내 전용으로 가속 런타임과 자동 선택을 연결한다. 이 시점에는 오프라인 GPU 설치본과 결과가 없다.

- 기존 모델·정밀도·런타임을 먼저 고정한다. 첫 비교에서 native CUDA, ONNX 변환, 얼굴 provider 교체를 동시에 바꾸지 않는다. 이전 Windows 휠/드라이버 자료를 확인하고 1050 Ti와 1660 Ti 지원 범위 및 런타임 버전을 검사한다. 모델과 실행기별로 GPU 사용 근거를 보존한다.
- 입력 영상 SHA-256, 해상도·코덱·설정, 모델·런타임 버전, OS 빌드·GPU·드라이버·가용 RAM/VRAM·캐시 상태를 기록한다. R3 CPU와 GPU를 각 PC에서 같은 조건으로 비교한다. 우선 한 번 완주한 뒤 순서를 바꿔 정상 조건의 CPU/GPU 최소 3쌍으로 반복 변동폭과 중앙값을 본다.
- `요청 모드 → 선택 정책·거절 이유 → 실제 실행한 단계·기기/provider → 오류·종료 코드 → CPU 시도 → 최종 결과`를 같은 실행 ID로 남긴다. **GPU 완료, GPU 진입 전 CPU 선택, GPU 일부 실행 후 CPU 복구 완료, 최종 실패**를 나눠 센다. CUDA 사용 가능 여부만으로 GPU 사용을 판정하지 않는다. PyTorch 장치 및 실제 추론 근거, ONNX는 해당 후보를 시험할 때 provider와 노드 배치·프로파일 근거를 확인한다.
- 전체, 화면 분석, 음성, 썸네일, 저장 시간 및 결과를 비교한다. 품질은 사람 수·클립 수 외에 선택 구간·경계·전사·중요 누락을 대조한다. 2·8은 저메모리와 지원 경계를 확인하고, 3은 정상 GPU 완주와 CPU 복구를 먼저 검증한다. CPU 복구를 재현하는 시험은 정상 속도 표본에서 제외한다.

| 로컬 어드민 | Angular 로컬 설정의 `useMocks: false`로 같은 웹 API를 바라보도록 해 실제 운영자 권한과 데이터 저장을 검증한다. 현재 설치형 앱 에러·진단·크레딧 원장으로 먼저 시험한다. 목업의 화면 적용은 승인 이후 작업이다. |
| 오류와 사용 기록 | 일반 앱의 수동 신고는 데스크톱 Nest `/v1/error-reports/desktop`의 경로를, 자동 상세는 웹 API `/ingest/desktop-error-reports`와 동의 조건을 검증한다. Tier 1은 `/ingest/desktop-telemetry`, 어드민 오류 조회는 `/admin/desktop-error-reports`다. 기존 DB·API 계약을 사용한다. 성공한 개별 실행이나 복구 기록이 현재 계약에서 보이지 않으면, 추적 가능한 구조화된 실행 기록을 별도로 수집·저장하는 범위를 설계한다. |
| 파일로 재현·공유 | 각 사례의 앱 빌드·설치 채널·작업 ID·시도 ID·신고 ID·과금 run ID, 단계별 시간, JSONL·요약, 정산 대조 결과를 묶는다. 팀에 공유할 번들에는 테스트 데이터와 필요한 로그만 담고 토큰·키·개인정보·소스 영상·전사 원문을 넣지 않는다. |

**통과 조건.** 일반 앱으로 로컬 로그인 → 잔액/견적 → 인물 작업 시작 → 저장 → 정산을 한 건 통과한다. 2·3번 이전 실패가 발생했던 일반 앱과 비슷한 경로 길이에서 결과 확정을 확인한다. 그다음 깨진 영상 또는 제어한 실패, GPU→CPU 복구, 취소, 작업 중 강제 종료와 재기동을 각각 확인한다. 실패 로그의 원인·단계가 로컬 어드민에 도착해야 하고, 작업과 크레딧 차감·반환이 한 번씩 연결돼야 한다. 수동 신고와 자동 상세는 별도 시나리오로 확인한다. 8번처럼 배너를 못 본 경우 로그 보기 경로 및 배너가 사라지는 조건도 확인한다. 성공·복구 성공·최종 실패·취소·종료 미확인을 구별하고, 시작과 종료 기록이 각각 남는지 본다.

공식 개발 서버 복구 후에는 실제 개발 채널의 설치·업데이트·서버 설정과 로컬 결과를 한 차례 대조한다. 로컬에서 끝낸 GPU·DB·정산·오류 진단 검증은 그때까지 보류할 이유가 없다.

### 3. 제품 적용과 대상 확대

1. **어드민 개선 확정.** 현재 단계에서 필요한 수집 계약과 화면을 검토한다. 승인된 화면을 제품 코드에 반영하고 앱 채널·빌드 번호·개별 실행·재시도 데이터가 도착하는지 로컬에서 실제 조회한다.
2. **세 하이라이트 재시험.** 인물 외 안무·대사의 R3 진단판 실기기 시험이 남았다. 이전 3·8번 긴 대사 실패와 RTX 3060의 `d99952ed` 재현, 2·3번 일반 경로 저장, 시작 타임아웃·정상 취소·큐·내보내기 등을 대표 기기에서 확인한다. 11월 18일 첫 CPU판의 안무·대사 완주는 해당 판에만 해당한다.
3. **Windows와 Mac 확대.** 사내 약 20대의 Windows 및 사용 가능한 Mac에서 짧은 기본 완주, 대표 기기에서 긴 영상·신규 설치·기존 업데이트·복구를 수행한다. 같은 장비는 반복 신뢰도에 도움이 된다. 빠진 조합은 직원/협력사 기기, 대여·실기기 랩, NVIDIA GPU VM 등으로 채운다. 일반 VM은 CPU·권한·업데이트에 적합하고, iGPU·듀얼 GPU·OEM 드라이버는 실제 노트북 실측을 우선한다. PC방은 관리형 Windows·RTX 표본으로 활용할 수 있다.
4. **Windows를 OS 이름 하나로 묶지 않는다.** 에디션·빌드·누적 업데이트·x64/ARM64·드라이버/WDDM·DirectX를 기록한다. NVIDIA 구형·RTX, AMD, Intel iGPU·Arc, 듀얼 GPU, Mac 칩·macOS와 통합 메모리를 나눈다. CPU의 세대·명령어 지원·코어·스레드, RAM/VRAM·페이지 파일, 디스크, 절전·발열·동시 부하, 설치 상태·VC++·Python/DLL, 백신·권한·긴/한글/동기화 경로, 코덱·VFR·길이·음성·얼굴 밀도까지 결과에 영향을 줄 수 있다.
5. **운영 반영은 별도 판단.** 소수 동의 QA 또는 사전 배포 채널에서 검증한 플러그인·OS·장치·처리 방식만 제한 활성화하고, 오류 시 다음 작업을 CPU로 돌릴 수 있도록 한다. 비정상 종료·정산·결과 품질과 반복 단축이 확인된 조합부터 적용 여부를 결정한다. 기존 조사에서 VS Code의 Insiders 및 설치 점검, Electron의 릴리스 채널, Chrome의 제한 실험, OBS의 공개 베타 사례를 참고했다.
