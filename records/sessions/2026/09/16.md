## 후속: 과금 복구 설계 후보의 저장 경계 정정

- 앞서 job/attempt-operation 연결의 "디스크 영속 저장"을 설명 없이 해결책으로 확정한 표현을 정정했다. 뜻은 원격 서버 DB에 사용자 프로젝트·미디어·전체 job을 저장하는 것이 아니라, 우선 사용자 PC의 기존 로컬 job 저장소에 operation ID·attempt ID·미전송 종결 상태 같은 최소 metadata를 남기는 후보안이었다.
- 서버에는 이미 금융 원장인 operation run이 있으므로, 추가 검토 대상은 중복차감을 막는 idempotency key와 콘텐츠를 포함하지 않는 불투명한 job/attempt 참조다. 아래 후속 결정에서 최소 연결 metadata의 사용자 PC 로컬 보존 원칙은 승인됐고, 정확한 schema·보존기간·서버 참조 범위는 아직 확정 설계가 아니다.
- 자동 reconciliation도 모든 `interrupted` job을 곧바로 실패·환급하는 안이 아니다. 완성 산출물이나 명시적 실패·취소처럼 판정 가능한 경우만 자동 종결하고, 앱 종료 시점과 외부 작업 결과가 모호한 경우는 기존 Admin 수동 recovery에 남긴다.
- 아래 후속 결정에서 기능별 terminal 종결의 공통 finalizer는 필수 방향으로 확정됐다. 네트워크 실패한 종결 보고를 로컬에 보류하는 `pending billing sync`(outbox)는 필요성에 동의했지만 낮은 우선순위 TODO이며, 둘 다 아직 구현·병합 승인된 범위는 아니다.
- 문서 표현만 정정했다. 코드·branch·worktree·DB·서버는 변경하지 않았고 병합·cherry-pick·commit·push·배포도 없다.

## 후속: Shortform 준비 구간과 과금 복구 방향 확정

- 최신 `origin/dev`를 다시 추적해 Shortform의 두 구간을 분리했다. 첫 `클립 생성하기`에서 LLM 대본·미디어·줄별 TTS를 실제 생성한다. 마지막 `숏폼 생성하기` 뒤 비동기 `render_prepare_pending` 구간은 기존 TTS 경로/길이 확인, 원격 선택 미디어 로컬화, asset·manifest·`clipper_payload` 조립, 예약 job 활성화를 수행한다. 다만 공용 `ClipperStudioAssetPreparer`가 이때 클립 전체 대사의 별도 fallback TTS를 다시 합성(또는 seed/silent fallback)하는 사실도 확인했다. manifest 자막은 기존 줄별 TTS ID를 우선 사용하므로 이 중복/legacy fallback의 필요성을 통합 설계에서 재검토한다.
- Nest가 operation start·출력 폴더·reserved job·프로젝트 상태 저장까지 성공하면 HTTP가 먼저 돌아가 Angular가 보관함으로 이동한다. 그 뒤 준비 실패는 보관함의 reserved job을 failed로 접지만 실제 렌더 실행 큐에는 들어가지 않은 실패다. 그 이전의 preflight·operation start·mkdir·reserve·프로젝트 저장 실패는 응답 실패라 기존 화면에 남는다.
- 사용자는 job/attempt-operation 최소 연결정보를 사용자 PC의 기존 로컬 데이터 영역에 영속 보존할 수 있고 그렇게 하는 방향에 동의했다. 원격 DB에 프로젝트/미디어를 올리는 결정이 아니다. 정확한 schema·보존기간·병합 범위는 별도 승인 대상이다.
- 사용자는 기능별로 흩어진 terminal 과금 종결을 공통 finalizer로 반드시 통합하라고 결정했다. `pending billing sync` outbox도 필요성은 인정했지만 우선순위가 높지 않은 후속 TODO로 보존한다.
- 향후 reconciliation은 사용자가 직접 삭제한 terminal 프로젝트/job을 실패로 오인하거나 재환급하면 안 된다. 삭제 가능한 콘텐츠와 과금 연결 metadata/tombstone을 분리하고, user-deleted·기존 terminal 상태·billing-finalized 여부를 구분하는 요구를 기록했다.
- 설명·문서만 갱신했다. 코드·branch·worktree·DB·서버는 변경하지 않았고 병합·cherry-pick·commit·push·배포도 없다.

## 후속: legacy 제거 범위·Shortform preflight·waiting 이력 정정

- `legacy*`라는 이름 자체는 정리 대상이 아니다. fallback TTS/seed TTS/참조 0 `prepareClipTts()`와 누락 media placeholder는 완전성 검사를 먼저 넣고 제거할 대상이다. 현재 BGM 파일과 `legacy-bgm.*` identity는 그대로 유지하며 이름만 바꾸는 migration을 만들지 않는다. layout/logo seed도 이름 때문에 template migration 대상으로 삼지 않고, 실제 기능 필요성을 확인한 뒤 유지 또는 producer·consumer 동시 제거를 결정한다.
- 최초 `클립 생성하기`는 TTS 합성 throw 시 완료되지 않지만, 최종 `숏폼 생성하기`에는 모든 TTS ID·파일/media를 확인하는 동기 preflight가 없다. 대사 수정은 기존 TTS ID를 먼저 지우므로 재합성 실패 시 누락 상태가 남고, ID 누락은 fallback으로 숨겨진다. 파일 누락은 보관함 이동 뒤 비동기 준비 실패, 손상 파일은 실행 단계 실패까지 갈 수 있다.
- `waiting` 중복은 `6e98b153`(2026-06-17)이 오래 걸리는 준비를 비동기로 보내 job을 즉시 노출하면서 기존 상태를 재사용해 생겼다. 현재 보조 flag/queue membership으로 보완하지만 retry·billing·recovery가 숨은 상태 조합에 의존하는 위험이 있어 별도 phase 영속화를 검토한다.
- URL/paste/prompt는 이미 한 workflow를 공유한다. 세 Strategy 클래스를 지금 추가하는 것은 과한 추상화가 될 수 있어 필수 범위에서 제외하고, 공통 billing attempt/finalizer/retry를 우선한다. 설명·문서만 갱신했으며 코드·branch·DB·서버·병합·커밋·push·배포 변경은 없다.

## 후속: job enum 직접 확장·Shortform preflight 수용 기준 확정

- 사용자는 `waiting + phase` 과도기안 대신 status enum을 `preparing | queued | starting | running | completed | failed | cancelled`로 바로 확장하기로 결정했다. `render_prepare_pending` 등은 v2 store migration에서만 옛 상태 판정에 쓰고 신규 정본에서는 제거하는 설계를 기록했다.

- Shortform preflight는 TTS ID 누락, 파일 누락, 손상, 대사 수정 뒤 재합성 실패, 새/빈 줄, media/slot 누락, preflight 뒤 I/O 실패를 각각 처리·검증해야 한다. 편집 저장→서버 preflight→성공 시에만 과금 확인→Nest start 전 authoritative recheck→job/보관함 이동 순서로 고정했다.

## 후속: restart reconciliation·호환 필드 설명 정정

- 자동 재개에 로그인 토큰을 job 파일로 추가 저장해야 한다는 앞선 표현은 부정확했다. 기존 로그인 세션 복원 뒤 현재 토큰을 전달받아 재개할 수 있다. 실제 쟁점은 사용자 확인 없는 유료 작업 재개와 동일 billing attempt의 안전한 연속성이다.
- 앱 종료 뒤 디스크 `queued`만 남고 in-memory queue가 사라진 상태를 방치하면 영원히 실행되지 않는 ghost job이 된다. startup reconciliation은 인증 후 동일 attempt로 재구성하거나, interruption 실패·환급 뒤 명시적 재시도로 종결해야 한다.
- `render_prepare_pending`은 신규 snapshot/runtime에서 제거하고 v1→v2 전용 migrator 입력에서만 읽는다. serializer가 옛 필드를 출력하지 않는 테스트와, 통제된 개발 데이터 전환 후 migration reader까지 제거할 수 있는 기준을 설계 문서에 추가했다. 문서 외 코드·branch·DB·서버·병합·커밋·push·배포 변경은 없다.
