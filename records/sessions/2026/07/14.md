# 2026-07-14 YouTube 인증·다운로드 안정화 및 패키지 QA

## 작업 범위와 안전 경계

- 작업 브랜치: 코드 repo는 `feature/youtube-auth-diagnostics`, `.codex`는 `main`.
- 실제 cookie/env/JWT key/provider secret 내용은 기록하지 않았다.
- `clipper_docs`에는 문서를 추가하지 않았다.
- 사용자의 마무리 요청에 따라 관련 코드와 문서는 저장소별로 나눠 commit했다. push/deploy/DB 초기화/runner 재시작은 수행하지 않았다.

## 구현 요약

- YouTube 로그인 필요와 채널 멤버십 entitlement 필요를 분리했다.
- 제품 UI는 Clipper Studio 계정과 영상용 YouTube 계정이 서로 다를 수 있음을 명시하고, 로그인 액션을 `영상용 YouTube 계정 선택`으로 안내한다.
- 개발자용 YouTube 디버그 페이지는 계정 변경 전후 인증 상태와 결과를 보존하며, 개발용으로 실제 계정 이메일을 표시한다. 계정 이메일은 제품 로그에 넣지 않는다.
- 실제 하이라이트 소스 경로는 익명 metadata를 먼저 확인하고 인증이 필요한 경우 관리 쿠키 파일로 재시도한다.
- 공개 영상 download의 `media_access_forbidden`은 기존 1080p 이하 포맷 선택식을 유지한 채 새 미디어 주소를 얻도록 1초/3초 후 최대 2회 재시도한다.
- yt-dlp `unknown` 실패 로그에 안전한 provider 오류 요약과 16자리 오류 지문을 추가했다. URL, 이메일, 로컬 경로, cookie, Authorization, PO Token, visitor data, token/signature 값은 제거한다.
- 동일 멤버십 영상에서 YouTube가 간헐적으로 반환한 `Video unavailable. This video is not available`을 확인했다. 이 일반 `UNPLAYABLE` 계열이 metadata 단계에서 나오면 1초 뒤 같은 인증 전략으로 1회만 재확인한다. 일반 문구를 멤버십으로 직접 매핑하지 않고 두 번째 실제 응답으로 최종 사유를 결정한다.
- Dialog Highlight의 web_api 413 원인은 NestJS가 LLM 단계별로 필요하지 않은 대형 분석 배열을 중복 전송하고 web_api가 기본 JSON body limit를 사용한 것이었다. 실제 실패 payload는 약 172KB였고 필요한 입력으로 투영한 결과 약 13KB가 됐다. web_api JSON limit는 1MB로 명시했다.
- 디버그 로그에는 YouTube metadata/download/auth/cache/retry 과정과 Dialog Highlight web_api 요청의 단계·크기·소요 시간·상태를 구조화해 기록한다.
- packaged runtime은 시스템 Python을 탐색하지 않고 uv 관리 Python 3.11을 명시적으로 준비한다. base venv와 플러그인별 `uv sync` 모두 `--python 3.11 --managed-python`을 사용한다.
- Python 3.9 또는 실행 불가능한 base venv는 앱 소유 `clipper_venv`만 비우고 3.11로 재생성한다. Python 3.11이 정상이고 yt-dlp/EJS만 빠진 경우에는 venv를 보존하고 패키지 설치만 재시도한다.
- 필수 runtime 준비가 끝나기 전에는 앱에 진입하지 않는다. 제품 요구사항에 맞지 않던 `로컬 파일로 계속` 버튼과 local-only 분기는 제거하고 `다시 시도`/`앱 종료`만 남겼다.

## macOS packaged 수동 QA 결과

### 멤버십 영상과 계정 전환

- 멤버십 미보유 계정의 관리 쿠키로는 `members_only` 실패가 표시됐다.
- 멤버십 보유 계정으로 영상용 로그인을 변경한 뒤 같은 영상 metadata가 성공했다.
- 디버그 페이지는 이전/현재 인증 상태를 분리해 결과와 실제 관리 쿠키 계정을 표시했다.
- 전체 초기화 후 실제 하이라이트 입력에서도 멤버십 전용 안내와 `영상용 YouTube 계정 선택` 액션이 표시됐다.

### 일반 UNPLAYABLE 변동

- 같은 멤버십 영상이 두 번은 `members_only`, 세 번째는 다음 provider 원문으로 실패했다.
  - `Video unavailable. This video is not available`
- 이 실패는 runtime/cookie/cache 변경이 아니라 YouTube player 응답 이유의 간헐적 변동으로 확정했다.
- 안전 로그에 `providerErrorSummary`와 `providerErrorFingerprint`가 기대대로 남았다.
- 일반 UNPLAYABLE 1회 내부 재확인 구현 후에는 수동으로 같은 응답을 다시 재현하지 못했다. 다음 실제 발생 시 아래 trace를 확인한다.
  - `youtube.metadata.failed` (`unknown`)
  - `youtube.metadata.retry_scheduled` (`delayMs: 1000`)
  - `youtube.metadata.started` (`attempt: 2`)
  - 두 번째 실제 결과에 따른 성공 또는 구체적 실패

### 공개 영상 download 403

## 외부 Chrome 쿠키 경로 확인

- YouTube 디버그 페이지의 명시적 `browser: chrome` 진단은 `yt-dlp --cookies-from-browser chrome`을 실행한다.
- 실제 packaged 하이라이트 경로에서 Electron은 NestJS에 관리 쿠키 파일 경로를 명시적으로 전달한다.
- 실행 중 진단은 `cookiesFromBrowser=미설정`, `autoBrowserCookies=꺼짐`이었다. 따라서 현재 제품 기본 동작은 외부 Chrome 쿠키를 사용하지 않는다.
- NestJS에는 `CLIPPER_YTDLP_COOKIES_FROM_BROWSER`와 `CLIPPER_YTDLP_AUTO_BROWSER_COOKIES`로 외부 브라우저 fallback을 선택적으로 켤 수 있는 기반 코드가 있다. 현재 제품 UI나 packaged 기본 설정은 아니므로 외부 Chrome 쿠키 성공 QA는 해당 기능을 실제 채택할 때 수행한다.

## 신규 설치 Python/yt-dlp/EJS 수동 QA 절차

### 발견된 신규 설치 회귀와 수정

- 새 `test1` macOS 사용자에서 기존 `uv venv --no-project --allow-existing`가 Command Line Tools의 Python 3.9.6을 선택했다.
- yt-dlp/EJS는 Python 3.10 이상을 요구해 `uv pip install`이 dependency resolution 단계에서 실패했고, 같은 3.9 venv를 재사용하므로 `다시 시도`도 계속 실패했다.
- 원인은 2026-07-01 base/plugin venv 분리 때 base가 Python 프로젝트의 `requires-python == 3.11.*`를 더 이상 읽지 않게 됐지만 Python 버전을 명시하지 않은 것이다.
- 수정된 빌드는 uv 관리 Python 3.11을 먼저 설치하고 잘못된 base venv를 자동 재생성한다.

### 실제 `test1` packaged 재검증 결과

- 수정 빌드 최초 실행에서 앱 소유 base venv의 Python 3.9.6을 감지했다.
- 앱 내장 uv가 CPython 3.11.14 macOS ARM64 런타임을 내려받고 기존 base venv를 3.11.14로 재생성했다.
- 같은 base venv에 yt-dlp 2026.7.4와 yt-dlp-ejs 0.8.0을 설치한 뒤 `youtube.runtime.check.ready`가 기록됐고 메인 창과 NestJS가 정상 실행됐다.
- 같은 userData의 두 번째 실행에서는 약 222ms 만에 Python 3.11.14, yt-dlp 2026.07.04, EJS 0.8.0을 재확인하고 바로 준비 상태가 됐다. Python 다운로드, base venv 재생성, yt-dlp/EJS 재설치는 없었다.
- 두 번째 실행에서 처음 필요해진 `clipper_video_render` 플러그인 venv는 관리 CPython 3.11.14로 생성됐고 관련 패키지 26개가 정상 설치됐다.
- uv가 사용자 실행 파일 디렉터리가 shell `PATH`에 없다고 경고했지만 앱은 base/plugin venv 실행 파일을 절대 경로로 사용하므로 동작에는 영향을 주지 않았다.
- 이번 packaged 검증은 수정 전 빌드가 만든 Python 3.9 부분 설치를 수정 빌드가 복구하는 경로다. 완전히 비어 있는 clean userData에서 수정 빌드를 처음 실행하는 정확한 분기는 별도 packaged QA로 남긴다. 해당 분기가 사용하는 관리 Python 설치·venv 생성 명령 자체는 임시 clean HOME 실제 실행과 자동 테스트로 검증했다.

### 권장 격리 방법

프로젝트·로그인·쿠키 손실을 피하기 위해 별도 macOS 사용자 계정에서 검증하는 방법을 우선한다. 기존 사용자에서 해야 한다면 앱을 완전히 종료한 후 아래 디렉터리를 삭제하지 말고 별도 이름으로 이동해 백업한다.

```text
~/Library/Application Support/Clipper Studio
~/Library/Logs/Clipper Studio
```

검증이 끝나면 테스트 중 생성된 새 디렉터리를 별도 보관하거나 제거한 뒤 기존 백업을 원래 이름으로 복원한다. 앱이 실행 중인 상태에서 userData를 이동하거나 복원하지 않는다.

### 사전 조건

- 새로 빌드한 packaged macOS 앱 사용
- 인터넷 연결 유지
- 앱을 처음 실행하기 전 해당 테스트 사용자의 `Clipper Studio` userData가 없는 상태
- 설치 중 앱을 강제 종료하지 않음

### 최초 실행 검증

1. 앱을 실행하고 메인 창이 열릴 때까지 기다린다. 최초 실행은 내장 `uv`가 관리 Python과 base venv를 준비하므로 평소보다 오래 걸릴 수 있다.
2. 앱이 오류 모달 없이 진입하는지 확인한다.
3. 개발자 모드의 디버그 로그에서 다음 이벤트 순서를 확인한다.
   - `youtube.runtime.check.started`
   - 신규 Python 준비라면 `youtube.runtime.python.install.started`/`succeeded`
   - 기존 잘못된 venv 복구라면 `youtube.runtime.python.repair.started`/`succeeded`
   - yt-dlp/EJS 준비가 필요했다면 `youtube.runtime.repair.started`
   - `youtube.runtime.repair.succeeded`
   - `youtube.runtime.check.ready`
4. YouTube 인증 디버그 페이지의 runtime에서 다음을 확인한다.
   - yt-dlp: 사용 가능 + 버전 표시
   - JavaScript: 사용 가능, Electron 사용 표시
   - EJS: `ready` + 버전 표시
5. 다음 파일이 존재하는지만 확인한다. 파일 내용은 기록하지 않는다.
   - `~/Library/Application Support/Clipper Studio/clipper_venv/.clipper-ytdlp-ejs-v1`
6. 새 설치 상태에서 관리 쿠키 파일과 Electron YouTube 인증 세션이 비어 있는지 확인한다.
7. 로그인 없이 공개 YouTube 영상 metadata 확인과 실제 하이라이트 영상 불러오기를 각각 한 번 실행한다.
8. 앱을 정상 종료하고 다시 실행한다. 두 번째 실행에서 runtime 준비가 빠르게 끝나고 불필요한 `repair.started`가 반복되지 않는지 확인한다.

### 성공 기준

- 앱 메인 진입 전 Python/yt-dlp/EJS가 모두 실행 가능한 상태가 된다.
- runtime marker가 존재한다.
- 공개 YouTube 영상 metadata와 download가 로그인 없이 성공한다.
- 두 번째 실행에서 기존 준비 상태를 재사용한다.
- 실제 cookie/env/key/provider secret 내용은 로그나 보고서에 나타나지 않는다.
