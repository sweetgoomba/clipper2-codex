## Devapp Plugin Store Install State Investigation (Pre-Fix)

Status at discovery time:

- After a fresh macOS reset, Plugin Store still showed model-backed highlight plugins as `설치됨`.
- The reset removed app user data and HuggingFace model cache, so the model assets were not actually present.
- `GET http://127.0.0.1:9019/v1/plugins` returned `installState: "installed"` for `dance_highlight` and `dialog_highlight`.

Root cause:

- In devapp, Angular asks the separately running local NestJS process for `/v1/plugins`.
- That local NestJS process has no `ELECTRON_PLUGIN_HOST_URL`, so `PluginHostModule` selects `LocalPluginHost`.
- `LocalPluginHost` currently treats a discovered Python plugin manifest as installed and returns `installState: "installed"` without checking model files.
- Electron already has a stricter install-state check that treats required model files as the source of truth. That check is used by the model download IPC and packaged Electron plugin-host bridge, but not by local/devapp NestJS.

Chosen fix direction:

- Keep packaged Electron bridge behavior unchanged.
- Teach local/devapp NestJS `LocalPluginHost` to report model-backed plugin install state from the same file-presence convention used by Electron.
- Infer the Electron user data directory for local/devapp (`Clipper2`) and allow an explicit override for tests or unusual local setups.
- Unknown/no-asset plugins remain installed, matching current Electron behavior.

Verification target:

- Add a regression test showing `LocalPluginHost` reports `dance_highlight` as `not_installed` when the required model files are absent, even if a stale ready marker exists.
- Confirm the same status becomes `installed` when the expected model files are present.
- Build `desktop/clipper_nestjs` and run the focused regression test.

## Prompt Shortform Supertonic Fast-Speed TTS Clipping Fix

Correction to the previous follow-up:

- Changing the default speed only fixed newly generated projects starting too fast.
- It did not address the user-reported root issue:
  - when the user deliberately selects a faster TTS playback speed and regenerates TTS, generated audio can lose the beginning or ending of speech.

Investigation:

- Supertonic's public `TTS.synthesize(..., speed=...)` passes `speed` directly into the model call.
- Direct probes showed that higher model speed values shorten the output but keep relatively large and inconsistent leading/trailing silence.
- The risky path is model-conditioned fast synthesis, not Nest duration measurement or the renderer cutting otherwise-correct audio.

Decision:

- Do not pass the user playback speed into the Supertonic model.
- Always synthesize stable full speech with model speed `1.0`.
- Apply the requested playback speed as wav post-processing in the `tts_supertonic` plugin.
- Do this inside the plugin with existing `numpy`/`soundfile` dependencies; do not require FFmpeg or additional runtime consent for TTS regeneration.

Initial fix:

- Updated `desktop/clipper_python/plugins/tts_supertonic/tts_supertonic/synthesis.py`.
  - Added `MODEL_SYNTHESIS_SPEED = 1.0`.
  - `engine.synthesize()` now always receives `speed=1.0`.
  - Added `_apply_playback_speed()` to adjust the generated waveform according to the requested playback speed before saving.
  - Invalid/non-positive speeds normalize to `1.0`.

Follow-up correction:

- The first post-processing implementation used simple waveform resampling.
- That avoided model fast-synthesis clipping, but it also changed pitch, making `1.8x` voices sound unnaturally high.
- Replaced simple resampling with a numpy phase-vocoder time-stretch path.
  - Duration changes according to requested playback speed.
  - Pitch/fundamental frequency is preserved.
  - No FFmpeg or new runtime dependency is required.
