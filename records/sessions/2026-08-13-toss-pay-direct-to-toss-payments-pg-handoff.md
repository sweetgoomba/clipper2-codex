# 토스페이 직접 연동에서 토스페이먼츠 PG로 전환 인수인계

- 기록일: 2026-08-13 (Asia/Seoul)
- 문서 저장소/브랜치: `.codex/main`
- 현재 결정: 심사용 결제부터 토스페이먼츠 PG로 교체
- 전체 구독·크레딧 기능의 PG 전환: 후속 별도 작업
- 이번 기록 작업: 코드·환경변수·배포 상태를 변경하지 않음

## 1. 이번에 바로잡은 전제

처음 심사용 결제를 구현할 때 `https://docs-pay.toss.im`을 토스 담당자가 지정한 공식 연동 문서라고 가정했다. 그러나 이 링크는 토스 담당자가 전달한 것이 아니며, 담당자가 포함된 대화방은 `[토스x메타버즈] PG 연결`이다.

현재 개발서버에 배포된 구현은 다음 계약을 사용하므로 **토스페이 직접 연동**이다.

- API 호스트: `https://pay.toss.im`
- 일반 결제 생성: `POST /api/v2/payments`
- 빌링키 생성: `POST /api/v1/billing-key`
- 빌링키 결제: `POST /api/v1/billing-key/bill`
- 주요 식별자: `payToken`, `billingKey`, `displayId`
- 결과 처리: `resultCallback`과 토스페이 상태 조회

이번 대화에서 앞으로 사용할 결제 공급자는 **토스페이먼츠 PG**로 정정했다. 토스페이 직접 연동 구현을 실제 서비스 결제 연동의 정본으로 간주하지 않는다.

이 정정은 “기존 구현이 기술적으로 동작하지 않는다”는 뜻이 아니다. 단건 테스트 결제와 최초 빌링 결제까지 실제로 확인했지만, 계약하려는 상품과 다른 연동 방식일 가능성이 아니라 이제 **PG로 전환하기로 결정한 상태**라는 뜻이다.

### 2.2 사용자에게 보이는 동작

- `https://dev.clipperstudio.ai/pricing`에서 Clipper 로그인 없이 결제 버튼을 볼 수 있다.
- 1개월·3개월에는 정기결제와 단건결제를 표시한다.
- 1년에는 심사 요구에 따라 단건결제만 표시한다.
- 버튼을 누르면 토스페이 직접 결제창으로 이동한다.
- 결제 후 공개 결과 페이지에서 짧게 상태를 확인하고 완료 또는 실패 상태를 표시한다.
- 로컬 환경에서는 같은 버튼을 표시하되 실제 결제 시작 대신 dev에서 테스트하라는 안내를 표시한다.

### 2.3 서버에 구현된 동작

- 익명 심사용 checkout 생성 API
- 익명 주문 결과 조회와 제한된 reconcile API
- 토스페이 callback 수신과 공급자 상태 재검증
- 주문·이벤트의 `payment_orders`, `payment_events` 저장
- 공용 테스트 키의 서버 환경변수 보관
- 비밀 조회 토큰, 요청 횟수 제한, 중복·불확실 결제 결과 복구
- 정기결제 등록 후 최초 테스트 결제 1회

### 2.4 구현하지 않은 것

- 로그인 사용자와 주문 연결
- 결제 내역·영수증·구독 관리 화면
- 결제 성공 후 이용권·플러그인 권한·크레딧 지급
- 다음 회차 자동 갱신 청구
- 실제 운영 상점 키와 실결제
- 사용자 알림 이메일·SMS·알림톡

따라서 현재 개발서버 흐름은 **심사용 결제창과 테스트 결제 결과 저장**까지이며, 실제 서비스 결제 시스템은 아니다.

이 화면으로 토스 담당자에게 수정 확인을 요청했고 현재 확인 응답을 기다리는 상태다. 다만 요청한 화면이 토스페이 직접 결제창이므로, 토스페이먼츠 PG 심사 화면으로 교체한 뒤 담당자에게 다시 확인을 요청하는 것을 다음 조치로 본다.

## 3. 토스페이먼츠 PG에서 달라지는 핵심 계약

| 구분 | 현재 토스페이 직접 구현 | 전환할 토스페이먼츠 PG |
| --- | --- | --- |
| 공식 문서 | `docs-pay.toss.im` | `docs.tosspayments.com` |
| 공급자 API | `pay.toss.im/api/...` | `api.tosspayments.com/v1/...` |
| 브라우저 시작 | 서버가 받은 `checkoutPage`/`checkoutUri`로 이동 | 토스페이먼츠 결제 SDK와 클라이언트 키로 결제창 요청 |
| 단건 결제 완료 | callback 후 `payToken` 상태 검증 | `successUrl`의 `paymentKey`, `orderId`, `amount`를 서버가 승인 API로 검증·승인 |
| 정기결제 등록 | 빌링키 생성 API가 준 URL로 이동 | SDK `requestBillingAuth()` 후 `authKey`로 서버가 빌링키 발급 |
| 서버 인증 | 토스페이 API Key | 토스페이먼츠 Secret Key/MID 계약 |
| 주요 식별자 | `payToken`, `displayId`, 토스페이 `billingKey` | `paymentKey`, `orderId`, `customerKey`, 토스페이먼츠 `billingKey` |

공식 PG 기준 문서:

- 시작하기: https://docs.tosspayments.com/guides/v2/get-started
- 자동결제 개요: https://docs.tosspayments.com/guides/v2/billing
- 자동결제 결제창 연동: https://docs.tosspayments.com/guides/v2/billing/integration
- API 참고: https://docs.tosspayments.com/reference

기존 토스페이 직접 adapter의 URL과 DTO만 바꾸는 수준이 아니다. 브라우저 결제 시작 방식, 성공 리다이렉트, 서버 승인, 빌링키 발급 계약을 PG 기준으로 다시 설계해야 한다.

## 4. 다음 작업의 범위

시간과 배포 위험을 줄이기 위해 두 단계로 나눈다.

### 4.1 먼저 할 일: 개발서버 심사용 결제만 PG로 교체

각 코드 저장소의 최신 `dev`에서 새 기능 브랜치를 만든다. 기존 전체 기능 브랜치 위에서 작업하지 않는다.

포함 범위:

- 비로그인 공개 요금 페이지 유지
- 토스페이먼츠 PG 테스트 결제창으로 단건결제 연결
- 토스페이먼츠 PG 빌링 인증창으로 정기결제 등록·최초 결제 심사 흐름 연결
- 1년 상품은 단건결제만 노출
- 테스트 결제 결과 페이지 유지 또는 PG 계약에 맞게 최소 수정
- `payment_orders`, `payment_events`에는 PG 결과를 안전하게 저장
- 기존 토스페이 직접 환경변수와 callback을 PG 설정·승인 흐름으로 교체
- API·고객 웹·인프라만 필요한 범위에서 수정

이번 단계에서도 제외:

- 회원 연결
- 이용권·크레딧 지급
- 실제 구독 갱신 스케줄러
- 결제수단 관리
- 환불·해지·알림
- 전체 기능 브랜치 병합

### 4.2 나중에 할 일: 전체 구독·크레딧 기능의 PG 전환

`feat/access-credit-system-replacement`에 구현된 전체 기능은 삭제하지 않는다. 도메인 구조와 운영 안전장치를 보존하고 공급자 경계를 PG에 맞춰 교체한다.

재사용할 수 있는 부분:

- 요금제 등급, 상품, 플러그인 권한
- 사용자 access source와 구독 상태
- 출처별 크레딧 지급·차감·반환 원장
- 결제 주문·이벤트의 멱등 처리 구조
- 결제 성공 후 fulfillment와 운영 복구
- 갱신 실패 유예기간과 D+1·D+2 재시도 정책
- 관리자 정책·복구 기능
- AI 작업 차감·실패 반환과 증거 기반 복구

PG 기준으로 다시 구현하거나 재검증할 부분:

- `HttpTossPayProvider`와 토스페이 직접 DTO
- `payToken`, `displayId`, `resultCallback` 기반 흐름
- 빌링키 발급·조회·삭제·교체
- 결제수단 표시 정보 조회
- 단건 결제 승인과 정기결제 승인
- 공급자 오류코드 분류와 사용자 안내
- 토스페이 전용 환경변수·OpenAPI·테스트 fixture

최근 검증 기준:

- API: Node 22, 전체 테스트·빌드 통과
- 고객 웹: Node 22, 전체 테스트·빌드 통과
- 관리자 웹: Node 22, 전체 테스트·빌드 통과
- Nest/Angular/Electron: Node 24 기준 테스트·빌드 통과
- 인프라 compose와 배포 스크립트 정적 검증 통과

이번 PG 전환 기록을 작성하면서 위 코드 저장소의 브랜치, 프레임워크 버전, 파일 또는 커밋은 변경하지 않았다. 특히 Angular 22/Electron 업그레이드가 적용된 `clipper_angular`, `clipper_electron`과 Angular 19인 고객·관리자 웹의 버전 상태를 그대로 유지했다.

상세 검증 기록은 `2026-08-12-access-credit-release-verification.md`를 참고한다. 해당 기록은 도메인 기능 검증 근거이며, 토스페이먼츠 PG 연동 검증 근거는 아니다.

## 6. PG 심사용 구현 전에 확인할 외부 정보

코드를 시작하기 전에 다음만 토스 담당자 또는 토스페이먼츠 개발자센터에서 확인한다.

1. 계약·심사 대상이 토스페이먼츠 일반 PG 결제창과 자동결제 빌링이 맞는지
2. 심사에 사용할 테스트 Client Key, Secret Key, MID
3. 현재 상점에서 자동결제 API 또는 빌링 계약이 테스트 가능 상태인지
4. 카드사 심사자가 로그인 없이 확인해야 하는 단건·정기결제 상품과 금액
5. 심사 완료 조건이 결제창 진입인지, 테스트 승인 완료와 결과 화면까지인지
6. 현재 토스페이 직접 결제창으로 보낸 확인 요청을 PG 화면으로 교체한 뒤 다시 전달해야 하는지

## 7. 다음 세션의 권장 순서

1. 토스페이먼츠 PG 테스트 키와 심사 조건 확인
2. 최신 `dev` 기반으로 API·고객 웹·인프라에 새 브랜치 생성
3. 현재 심사용 API/UI 중 공급자 독립 부분과 교체할 부분을 파일 단위로 확정

## 8. 기존 문서의 해석 규칙

- `2026-08-10-toss-pay-review-checkout-*`: 현재 개발서버에 배포된 토스페이 직접 심사용 구현의 역사적 설계·작업 기록이다. PG 구현 계획으로 재사용하지 않는다.

- `2026-08-13-subscription-renewal-grace-retry-*`: 유예기간·재시도·미정산 복구 정책은 유지하고, 실제 결제 승인·조회 adapter만 PG 기준으로 교체한다.
