# TossPayments PG 최종 정책 변경 기준

- 작성일: 2026-09-02
- 상태: Phase 4 완료 이후 확정된 정책을 구현에 반영하기 위한 기준 문서
- 구현 기준: 7개 `toss-payments-pg-integration` worktree
- 제외 기준: 최신 `dev`는 PG 미연동의 다른 설계이므로 판단 기준으로 사용하지 않는다.

## 1. 현재 체크포인트

Phase 1~4의 구현과 당시 정책 기준 자동검증은 완료됐다. 이후 정책이 변경됐으므로 Phase 5로 바로 넘어가지 않고 기존 구현을 먼저 이 문서의 최종 정책에 맞춘다.

현재 변경이 있는 worktree:

- Web API: 크레딧 정책, 결제 스냅샷, 환불 도메인·토스 취소·복구
- Admin web: 회원 결제 정보와 환불 실행·운영 화면
- Customer web: 결제·환불·구독·크레딧 상태 표시
- Desktop Angular: 요금제별 플러그인 차단 제거와 크레딧 기반 유료 동작
- Desktop NestJS: 플러그인 이용권 차단 제거와 Web API 크레딧 연동

변경이 없는 worktree:

- Desktop Electron
- Infra

현재 staged diff는 없다. Customer의 기존 untracked `build/`와 API의 출처 미확정 `docs/api/openapi.yaml.orig`는 체크포인트 커밋에서 제외하고 수정·삭제하지 않는다.

## 2. 최종 환불 정책

### 공통 원칙

- 고객은 이메일·전화 등 외부 창구로 환불을 요청한다.
- 담당자가 환불 가능 여부와 금액을 확인한다.
- 최고 관리자만 관리자 화면에서 환불을 실행한다.
- 시스템이 토스페이먼츠 결제 취소와 이용권 종료·크레딧 회수를 함께 처리한다.
- 환불 대상 결제로 지급된 크레딧을 일부라도 사용했다면 환불할 수 없다.
- 일반 상품의 부분 환불은 제공하지 않는다.
- 무료 체험 크레딧과 별도 구매 크레딧의 사용 여부는 정기구독 환불 판단에 포함하지 않는다.
- 자동 갱신 해지는 환불이 아니며, 이미 결제한 이용기간은 만료일까지 유지한다.

### 월간 정기구독

- 해당 결제로 지급된 정기구독 크레딧을 사용하지 않은 경우에만 결제금액 전액을 환불한다.
- 환불 완료 시 이용권을 즉시 종료하고 해당 정기구독 크레딧을 회수한다.

### 연간 정기구독

- 연간 구독으로 지급된 정기구독 크레딧을 한 번도 사용하지 않은 경우에만 연간 결제금액 전액을 환불한다.
- 크레딧을 사용하지 않은 채 유효기간만 만료된 것은 사용으로 보지 않는다.
- 지급된 크레딧을 일부라도 사용했다면 남은 기간과 관계없이 환불할 수 없다.
- 남은 개월 수를 계산하는 연간 부분 환불은 제공하지 않는다.
- 환불 완료 시 이용권을 즉시 종료하고 남아 있는 해당 정기구독 크레딧을 회수한다.

### 별도 구매 크레딧

- 해당 결제로 지급된 크레딧이 유효기간 안에 전부 남아 있을 때만 결제금액 전액을 환불한다.
- 일부 사용했거나 유효기간이 끝나 소멸했다면 환불할 수 없다.
- 환불 시 해당 결제와 연결된 크레딧만 회수한다.

### 요금제 상향 차액 결제

- 회사의 공통 크레딧 미사용 조건을 적용한다.
- 환불 대상은 상향 시 실제로 발생한 차액 결제 한 건이다.
- 조건을 충족하면 해당 차액 결제금액만 전액 환불한다.
- 환불 완료 시 현재 이용권을 종료하고 상향으로 지급된 정기구독 크레딧을 회수한다.
- 상향 이전 이용권은 복원하지 않는다.
- 상향 이전 결제금액과 잔존가치는 환불하지 않는다.
- 여러 번 연속 상향했다면 현재 환불 대상인 상향 차액 결제만 판단하고 이전 상향 결제와 기본 결제를 다시 묶지 않는다.

## 3. 최종 크레딧 만료 정책

- 무료 체험 400크레딧은 회원가입 시각에 지급하고 지급 시각부터 30일 동안 유효하다.
- 별도 구매 크레딧은 결제에 따른 실제 지급 시각부터 30일 동안 유효하다.
- 한국 시간 자정이나 달력상의 구매일을 1일차로 세는 방식을 사용하지 않는다.
- 정기구독 크레딧은 구독 시작 시각을 기준으로 한 다음 월별 지급 경계까지 유효하며 다음 구독 월로 이월하지 않는다.
- 연간 구독도 크레딧을 한 번에 지급하지 않고 구독 시작 시각을 기준으로 매월 지급한다.
- 크레딧은 출처와 관계없이 실제 충전 시점이 빠른 지급 건부터 차감한다.

## 4. 최종 요금제 변경 정책

| 현재 결제기간 → 변경 결제기간 | 동일 요금제 | 상위 요금제 | 하위 요금제 |
|---|---|---|---|
| 월간 → 월간 | 변경 없음 | 즉시 적용 | 다음 결제일부터 적용 |
| 월간 → 연간 | 즉시 적용 | 즉시 적용 | 다음 결제일부터 적용 |
| 연간 → 월간 | 변경 불가 | 변경 불가 | 변경 불가 |
| 연간 → 연간 | 변경 없음 | 즉시 적용 | 다음 결제일부터 적용 |

### 즉시 변경

- 결제가 성공하면 기존 이용권과 기존 정기구독 크레딧을 종료한다.
- 변경 시각부터 새 이용기간과 결제주기를 시작한다.
- 새 요금제의 첫 월 정기구독 크레딧 전량을 지급한다.
- 무료 체험 크레딧과 별도 구매 크레딧은 유지한다.
- 결제에 실패하거나 결과가 확정되지 않으면 기존 이용권과 기존 결제주기를 유지한다.

### 다음 결제일부터 변경

- 현재 이용권과 정기구독 크레딧은 기존 만료 시각까지 유지한다.
- 다음 결제일에 변경 대상 상품의 정상 금액을 결제한다.
- 결제가 성공하면 그 시각부터 변경된 이용기간과 결제주기를 시작한다.
- 결제 실패 시 기존 정기결제 실패·재시도·유예·종료 절차를 적용하고 변경 상품을 지급하지 않는다.

### 즉시 변경 차액

- 기간 기준 잔존가치와 해당 정기구독 크레딧 기준 잔존가치를 각각 계산한다.
- 각 잔존가치로 목표 상품 가격과의 차액을 계산한다.
- 두 차액 중 더 큰 금액을 실제 차액 결제금액으로 사용한다.
- 무료 체험 크레딧과 별도 구매 크레딧은 계산에서 제외한다.
- 연간 구독의 크레딧 기준은 월 지급량이 아니라 계약 전체의 지급 예정량인 `월 지급량 × 12`와 실제 사용량을 사용한다.
- 계산 입력과 두 계산 결과, 최종 선택 금액은 결제 주문에 불변 스냅샷으로 남겨 관리자·CS가 사후 확인할 수 있어야 한다.

## 5. 현재 구현과의 확인된 충돌

| 영역 | Phase 4 현재 구현 | 변경해야 하는 최종 상태 |
|---|---|---|
| 무료 체험·추가 구매 만료 | 한국 날짜와 자정 기준 30일 계산 | 실제 지급 시각부터 30일 계산 |
| 즉시 상향 허용 범위 | 같은 결제기간의 상위 요금제만 즉시 적용 | 확정된 변경표에 따라 월간→연간 동일·상향도 즉시 적용 |
| 즉시 상향 결제금액 | 남은 기간에 비례한 요금제 가격 차이만 계산 | 기간 차액과 정기구독 크레딧 차액 중 큰 금액 적용 |
| 즉시 상향 크레딧 | 같은 구독 월 안에서 비례 계산한 차이만 추가 지급 | 기존 정기구독 크레딧 종료 후 새 요금제 첫 월 크레딧 전량 지급 |
| 즉시 상향 기간 | 기존 이용기간과 월별 혜택 경계 유지 | 변경 시각부터 이용기간·결제주기·월별 혜택 경계 재시작 |
| 연간 환불 가능 여부 | 현재 월 크레딧 사용 시 현재 월 종료 후 남은 기간 환불 허용 | 연간 구독 크레딧 사용 이력이 하나라도 있으면 환불 불가 |
| 연간 환불금액 | 관리자가 결제별 부분 환불금액 입력 | 조건 충족 시 연간 결제금액 전액만 환불 |
| 연간 환불 종료 | 즉시 종료 또는 현재 혜택 월 종료 | 전액 환불 완료 시 즉시 종료만 사용 |
| 상향 후 환불 결제 범위 | 같은 구독기간의 기본 결제와 상향 결제를 묶음 | 실제 상향 차액 결제 한 건만 환불 |
| 상향 후 환불 결과 | 묶인 결제와 현재 구독 월을 함께 정리 | 현재 이용권 종료·새 크레딧 회수, 이전 이용권과 결제는 복원하지 않음 |
| Admin 환불 입력 | 연간 결제에 임의 부분 환불금액 입력 가능 | 일반 환불은 전액만 허용하고 취소 가능 전액을 확인값으로 표시 |
| Customer 환불 표시 | 연간 부분 환불과 현재 혜택 월 종료 상태 표시 | 전액 환불과 즉시 종료 기준으로 단순화 |

## 6. 변경 시 보존할 기존 구현

- 환불 건·항목·토스 호출 시도·내부 처리 이력의 분리
- 결제 취소 결과와 내부 이용권·크레딧 처리 상태의 분리
- 환불 중복 방지, 순차 다중 결제 처리, 일부 성공 및 재처리 상태
- 응답 유실·timeout 후 토스 결제 재조회와 멱등 복구
- 토스 관리자 사이트에서 직접 취소한 결제의 수동 확인
- 환불 처리 중 크레딧 잠금과 토스 성공 후 내부 처리 재시도
- 최고 관리자 실행 권한과 일반 운영자 조회 권한 분리
- 고객 응답에서 비밀값·전체 payment key·provider 원문·관리자 메모 제외
- 실패한 작업의 내부 크레딧 복구를 금전 환불과 분리

## 7. 구현 재개 순서

1. Phase 4 완료 상태를 저장소별 로컬 체크포인트 커밋으로 보존한다.
2. 차액 계산과 변경 유형 분류를 순수 도메인 테스트로 먼저 고정한다.
3. 결제 주문에 차액 계산 스냅샷이 충분한지 확인하고 부족한 필드만 추가형 migration으로 보강한다.
4. 즉시 변경의 새 결제주기·이용권·크레딧 전환을 구현한다.
5. 시간 기준 만료와 연간 전액 환불 자격을 구현한다.
6. 상향 차액 결제 단독 환불과 이전 이용권 미복원을 구현한다.
7. Admin·Customer·OpenAPI를 새 정책에 맞춘다.
8. 저장소별 focused test 후 전체 회귀·build와 disposable DB migration을 다시 검증한다.
9. 정책 변경 반영이 완료된 뒤 기존 Phase 5 TODO와 Phase 6 출시 준비로 이동한다.

## 9. 커밋 경계

Phase 4 체크포인트는 API·Admin·Customer·Desktop Angular·Desktop NestJS의 다섯 저장소에서 각각 만든다. Electron과 Infra는 변경이 없으므로 빈 커밋을 만들지 않는다.

체크포인트 커밋 전 조건:

- 각 저장소의 `git diff --check` 통과
- Phase 4 보고서 이후 예상하지 않은 파일 변경이 없는지 확인
- Customer `build/` 제외
- API `docs/api/openapi.yaml.orig` 제외
- staged diff가 비어 있는 상태에서 저장소별 추적 대상만 명시적으로 stage
- 실제 secret, access token, billing key, 전체 payment key, raw billing data가 diff에 없는지 확인

체크포인트는 push·merge·PR·deploy를 포함하지 않는다. 새 정책 구현은 별도 후속 커밋으로 남기며 최종 통합 전에 필요하면 저장소별로 정리한다.
