- 작성일: 2026-08-31
- 상태: 사용자 승인 상세 설계
- 구현 상태: 미착수
- 기준 저장소: 7개 toss-payments-pg-integration feature worktree
- 목적: 현재 PG 구현을 완성하기 위해 필요한 환불, 정기구독, 크레딧, 관리자 운영, 재처리 구조를 정의한다.

- 전략팀이 작업 중인 약관과 법률 문구는 이 문서 범위가 아니다. 추후 전달받은 내용이 구현을 직접 변경하는 경우 별도로 반영한다.

## 2. 확정된 상품·크레딧 정책

### 2.1 기능 사용과 정기구독의 관계

Clipper는 설치형 SaaS 프로그램이며 무료 동작과 크레딧을 차감하는 유료 동작이 함께 존재한다.

- 무료 동작은 정기구독·크레딧과 무관하게 사용할 수 있다.
- 유료 동작은 사용 가능한 크레딧이 필요한 수량 이상이면 사용할 수 있다.
- 정기구독은 기능 사용 자격이 아니라 자동 결제와 정기 크레딧 지급을 관리한다.
- 베이직·프로·비즈니스 사이에 플러그인 사용 권한 차등을 두지 않는다.
- 요금제 차이는 가격과 정기 지급 크레딧 양이다.
- 요금제 또는 정기구독 상태를 유료 동작 실행 권한으로 사용하지 않는다.

### 2.2 무료 체험

- Clipper 회원가입과 동시에 무료 체험 400크레딧을 자동 지급한다.
- 별도의 eligible_from 기준 시각을 사용하지 않는다.
- 가입일을 1일차로 계산한다.
- 30일차가 끝나는 한국 시간 자정까지 사용할 수 있다.
- 31일차가 시작되는 한국 시간 자정에 남은 크레딧을 소멸시킨다.
- 유료 구독을 시작하거나 종료해도 원래 만료일은 바뀌지 않는다.
- 현재의 최초 이용권 조회 시 지연 발급 방식은 회원가입 시 자동 발급 방식으로 변경한다.
- 회원 계정 저장과 크레딧 저장이 서로 다른 DB transaction이라면 회원가입 완료 후 멱등한 무료 체험 지급 작업을 실행하고 실패 시 재시도한다.
- 첫 크레딧 조회에서 무료 체험 지급 누락을 발견하면 복구할 수 있지만, 이는 정상 발급 시점이 아니라 장애 복구 경로다.
- 복구 경로로 늦게 생성하더라도 충전일과 만료일은 실제 생성 시각이 아니라 원래 회원가입일을 기준으로 한다.

예를 들어 8월 28일 가입하면 9월 26일까지 사용할 수 있고 9월 27일 00:00 한국 시간에 소멸한다.

### 2.3 정기구독 크레딧

- 정기구독 크레딧은 매월 지급한다.
- 연간 구독도 1년치를 한 번에 주지 않고 매월 지급한다.
- 다음 구독 월로 이월하지 않는다.
- 다음 구독 월 경계에서 남은 정기구독 크레딧을 소멸시킨다.
- 월 경계는 달력의 말일이 아니라 정기구독 시작일을 기준으로 한다.
- 31일처럼 다음 달에 같은 날짜가 없으면 그달 마지막 날을 사용하고, 이후 같은 날짜가 있는 달에는 원래 기준일로 돌아간다.
- 월 경계의 달력 계산은 UTC 날짜가 아니라 한국 날짜를 기준으로 하며 DB에는 계산된 절대 시각을 저장한다.

### 2.4 추가 구매 크레딧

- 유료 정기구독 중인 사용자만 새로 구매할 수 있다.
- 다음 결제 취소를 예약했더라도 현재 유료 구독기간 안이면 구매할 수 있다.
- 구독이 종료됐거나 결제 실패로 중단된 상태에서는 구매할 수 없다.
- 구매일을 1일차로 계산해 30일차 종료까지 사용할 수 있다.
- 31일차가 시작되는 한국 시간 자정에 남은 크레딧을 소멸시킨다.
- 정기구독이 종료돼도 유효기간 안에는 사용할 수 있다.
- 다시 구독해도 만료일을 연장하거나 다시 계산하지 않는다.
- 전략팀 자료의 500크레딧은 단순 예시이며 상품 구성 변경이 아니다.

### 2.5 크레딧 사용 순서

- 무료 체험·정기구독·추가 구매·관리자 지급 등 출처와 무관하게 충전 시점이 빠른 크레딧부터 차감한다.
- 충전 시점이 같으면 지급 건 고유번호를 이용해 순서를 고정한다.
- 월별 크레딧을 사후 보정해 생성하더라도 DB 생성 시각이 아니라 원래 사용할 수 있게 된 시각을 충전 시점으로 사용한다.
- 현재의 만료일 우선 차감 방식은 변경한다.

### 2.6 유료 동작과 가격

- 무료 동작은 크레딧 확인·차감 없이 실행한다.
- 유료 동작 목록과 가격은 변경 가능한 정책 데이터로 관리한다.
- 가격 변경은 이후 시작되는 작업부터 적용한다.
- 이미 시작·완료된 작업에는 당시 실제 차감량과 사용한 크레딧 지급 건을 기록한다.
- 작업 실패 시 당시 실제 차감 내역을 기준으로 복구한다.
- 이 문서에서는 유료 동작 목록과 가격을 확정하거나 구현 조건으로 고정하지 않는다.

## 3. 환불 정책

### 3.1 고객·관리자 처리 방식

- 고객은 이메일·전화 등 외부 창구로 환불을 문의한다.
- 별도 고객용 환불 신청 화면은 만들지 않는다.
- 담당자가 환불 가능 여부와 환불금액을 판단한다.
- 관리자가 회원과 결제 건을 선택하고 결제별 환불금액과 사유를 입력한다.
- 시스템이 토스페이먼츠 결제 취소, 정기구독 종료, 크레딧 잠금·회수를 처리한다.
- 환불금액 자동 산식은 이번 범위에 포함하지 않는다.
- 문의 접수 시각과 문의 경로는 환불 건 데이터로 저장하지 않는다.
- 시스템 생성 시각과 선택적인 관리자 메모만 사용한다.

### 3.2 월간 정기구독

- 해당 월 정기구독 결제로 지급된 크레딧이 전혀 사용되지 않았으면 전액 환불할 수 있다.
- 일부라도 사용했으면 환불할 수 없다.
- 부분 환불은 허용하지 않는다.
- 무료 체험이나 추가 구매 크레딧을 사용한 사실은 월간 정기구독 환불 가능 여부에 영향을 주지 않는다.
- 요금제 상향이 있었다면 같은 구독 월의 기본 크레딧과 상향 추가 크레딧이 모두 미사용이어야 한다.
- 환불 시 기본 결제와 상향 차액 결제를 각각 전액 취소한다.
- 환불 완료 후 정기구독은 즉시 종료한다.

### 3.3 연간 정기구독

- 연간 구독의 현재 월은 연 구독 시작일을 기준으로 계산한다.
- 현재 월의 정기구독 크레딧이 전혀 사용되지 않았으면 현재 월도 환불 대상에 포함한다.
- 이 경우 현재 월 크레딧을 회수하고 정기구독을 즉시 종료한다.
- 현재 월 크레딧을 일부라도 사용했으면 해당 월 전체를 환불 대상에서 제외한다.
- 이 경우 현재 월 종료까지 남은 정기구독 크레딧을 사용할 수 있고 다음 월 시작 시 정기구독을 종료한다.
- 미래 월의 정기구독 크레딧은 지급하지 않는다.
- 관리자가 계산한 미래 기간 환불금액을 연간 결제에서 부분 취소한다.
- 환불 단가와 계산 산식은 이번 구현에서 자동화하지 않는다.

예를 들어 1월 12일 연간 구독을 시작했다면 첫 번째 월은 1월 12일에서 2월 11일, 두 번째 월은 2월 12일에서 3월 11일이다.

### 3.4 추가 구매 크레딧

- 해당 결제로 지급된 추가 크레딧이 만료되지 않고 전부 남아 있을 때만 전액 환불할 수 있다.
- 일부라도 사용했으면 환불할 수 없다.
- 실패한 작업에서 차감분이 전부 복구돼 지급량이 온전히 보전된 경우에는 새 환불 건에서 다시 확인할 수 있다.
- 부분 환불은 허용하지 않는다.
- 30일이 지나 소멸한 크레딧은 일반 정책상 환불할 수 없다.
- 환불 시 해당 결제와 연결된 크레딧 지급 건 전체를 회수한다.
- 정기구독과 다른 크레딧 지급 건에는 영향을 주지 않는다.

### 3.5 요금제 상향 차액

- 구독 전체 환불 시 같은 구독기간에 연결된 기본 결제와 상향 차액 결제를 함께 검토한다.
- 월간 구독은 기본 크레딧과 상향 추가 크레딧이 모두 미사용일 때 관련 결제를 각각 전액 취소한다.
- 연간 구독은 환불 대상 미래 기간에 해당하는 기본 연간 결제와 상향 차액 결제를 각각 부분 취소한다.
- 상향이 여러 번 있었다면 관련 상향 차액 결제가 여러 개의 환불 항목으로 들어갈 수 있다.
- 상향 차액만 환불하고 즉시 이전 요금제로 되돌리는 일반 기능은 제공하지 않는다.
- 요금제 하향은 기존의 다음 구독 월부터 변경하는 기능을 사용한다.
- 중복 청구나 회사 오류는 일반 구독 환불과 분리해 예외 처리한다.

### 3.6 실패한 작업의 크레딧 복구

- 실패한 작업의 크레딧 복구는 금전 환불이 아니다.
- 토스페이먼츠를 호출하지 않는다.
- 실제 차감한 크레딧 지급 건과 수량을 기준으로 복구한다.
- 결제 취소, 정기구독 종료, 환불 크레딧 회수와 별도의 이력으로 관리한다.

## 4. 환불 도메인 구조

### 4.1 환불 건

환불 건은 고객 문의 하나에 대한 회사의 처리 단위다.

저장 정보:

- 대상 사용자
- 연결된 정기구독
- 환불 대상 종류
- 관리자 환불 사유와 선택적 내부 메모
- 정기구독 종료 예정 시각
- 생성·실행한 관리자
- 예정 총 환불금액과 실제 총 환불금액
- 금전 환불 상태
- 정기구독·크레딧 내부 처리 상태
- 생성·수정 시각

문의 접수 시각과 문의 경로는 저장하지 않는다.

### 4.2 결제별 환불 항목

토스페이먼츠 결제 한 건마다 환불 항목 하나를 만든다.

저장 정보:

- 연결된 결제 주문
- 결제 목적: 최초 결제, 갱신, 상향 차액, 추가 크레딧
- 최초 결제금액
- 환불 직전 취소 가능 잔액
- 관리자가 입력한 환불금액
- 전액·부분 취소 구분
- 토스 부분 취소 가능 여부
- 고정된 중복 방지 키
- 실제 취소금액
- 토스 취소 거래 식별값
- 토스 취소 완료 시각
- API 취소 또는 토스 관리자 사이트 수동 취소 여부

환불 실행 후 금액은 수정하지 않는다. 추가 처리가 필요하면 새 이력을 남긴다.

모든 금액은 원 단위 정수로 저장한다. 결제별 환불 항목의 처리 상태는 대기, 처리 중, 결과 확인 필요, 실패, 완료로 구분한다. 수동 취소가 검증된 경우 완료 상태와 함께 완료 경로를 토스 API 또는 토스 관리자 사이트로 기록한다.

### 4.3 토스 요청·검증 이력

각 결제별 환불 항목에 여러 시도와 검증 이력을 연결한다.

- 최초 결제 취소 요청
- 같은 중복 방지 키를 이용한 재시도
- 결제 재조회
- timeout·네트워크 오류·5xx
- 안전한 토스 오류 코드
- 토스 관리자 사이트 수동 취소 보고
- 수동 취소 후 API 재조회
- 최종 취소 거래 식별값과 금액

비밀키, 결제 자격증명, 원문 응답 전체를 저장하지 않는다.

### 4.4 내부 처리 이력

- 정기구독 즉시 종료
- 정기구독 종료 예약
- 다음 자동 결제 중단
- 미래 월 크레딧 지급 중단
- 환불 대상 크레딧 잠금·회수
- 예약된 요금제 변경 제거
- 정기결제용 결제수단 삭제
- 실패 후 내부 처리 재시도

모든 내부 처리는 반복 실행돼도 결과가 중복되지 않도록 한다.

### 4.5 상태

금전 환불 상태:

- 대기
- 처리 중
- 일부 완료
- 전체 완료
- 확인 또는 관리자 조치 필요
- 처리 취소

내부 처리 상태:

- 실행 전
- 처리 대기
- 완료
- 재처리 필요

관리자 화면은 두 상태를 조합해 보여준다.

- 일부 환불 완료·나머지 토스 확인 필요
- 금전 환불 완료·크레딧 회수 재처리 필요
- 환불과 내부 처리 완료

### 4.6 기존 결제 상태와의 분리

- 기존 결제 주문의 결제됨·실패·만료 상태를 환불 상태로 덮어쓰지 않는다.
- 결제에는 최초 결제금액, 누적 환불금액, 현재 취소 가능 잔액, 전액·부분 환불 상태, 마지막 토스 확인 시각을 별도로 저장한다.
- 한 결제에 여러 번 부분 취소가 발생해도 원결제와 각 취소 이력을 모두 보존한다.

## 5. 토스 결제 취소 흐름

### 5.1 관리자 실행 전 조회

관리자가 환불할 결제를 선택하면 토스페이먼츠에서 최신 상태를 조회한다.

- 결제 상태
- 최초 결제금액
- 이미 취소된 금액
- 현재 취소 가능 잔액
- 부분 취소 가능 여부
- 기존 취소 거래 이력

### 5.2 환불 건 선저장

관리자가 최종 확인하면 다음 순서로 처리한다.

1. 환불 건과 결제별 환불 항목 저장
2. 결제별 중복 방지 키 저장
3. 같은 결제의 동시 환불 차단
4. DB transaction 완료
5. 토스페이먼츠 취소 호출 시작

외부 API 호출을 DB transaction 안에 넣지 않는다.

### 5.3 전체 사전 확인과 순차 실행

- 여러 결제를 취소하기 전에 모든 대상 결제를 다시 조회한다.
- 하나라도 금액·소유자·부분 취소 조건을 충족하지 않으면 돈을 취소하기 전에 중단한다.
- 모두 통과하면 결제를 한 건씩 순차 취소한다.
- 여러 토스 결제를 동시에 취소하지 않는다.

### 5.4 불확실한 결과

timeout, 네트워크 오류, 토스 5xx, 응답 유실, 성공 후 내부 저장 실패는 즉시 실패로 확정하지 않는다.

1. 새로운 취소 요청을 만들지 않는다.
2. 저장된 중복 방지 키를 유지한다.
3. 토스 결제를 다시 조회한다.
4. 취소 이력과 잔액을 확인한다.
5. 확인되지 않으면 같은 키로 재시도한다.
6. 반복 확인 후에도 모르면 관리자 조치 필요로 전환한다.

같은 중복 방지 키는 토스가 보장하는 기간 안에서 재사용한다. 보장 기간인 15일이 지난 장기 미확정 건은 토스 결제와 취소 이력을 먼저 조회하고, 실제 취소가 없다는 것이 명확할 때만 새로운 시도를 만든다.

### 5.5 일부 결제만 성공

- 성공한 환불을 새 결제로 되돌리지 않는다.
- 성공 항목과 실패·확인 필요 항목을 각각 표시한다.
- 환불 건은 일부 완료 상태를 유지한다.
- 결과를 알 수 없는 결제가 생기면 그 항목을 먼저 확인한 뒤 나머지 처리를 진행한다.

### 5.6 토스 관리자 사이트 수동 취소

- 관리자가 우리 관리자 화면에서 수동 취소 사실을 보고할 수 있다.
- 보고만으로 완료 처리하지 않는다.
- 백엔드가 토스 결제를 다시 조회한다.
- 새 취소 거래, 실제 금액, 거래 식별값, 잔액을 확인한다.
- 예정 금액과 일치하면 수동 취소 확인 완료로 기록한다.
- 금액이 다르면 예정 금액과 실제 금액 차이를 보여주고 관리자 조치 필요로 남긴다.

### 5.7 외부에서 발견된 취소

- 내부 환불 건과 연결되지 않은 토스 취소는 연결되지 않은 외부 취소로 표시한다.
- 정기구독과 크레딧을 즉시 임의 변경하지 않는다.
- 관리자가 환불 건과 연결한 뒤 내부 처리를 실행한다.

### 5.8 지속 처리

- 브라우저 요청 하나에 전체 처리를 의존하지 않는다.
- 환불 건을 먼저 저장하고 즉시 첫 처리를 시도한다.
- 오래 걸리면 백그라운드에서 재조회·재시도한다.
- 브라우저를 닫아도 처리가 유실되지 않는다.

## 6. 환불 전 잠금과 내부 처리

### 6.1 임시 잠금

환불 실행 직전 DB transaction에서 다음을 수행한다.

- 환불 대상 크레딧 지급 건 잠금
- 잠긴 크레딧을 새로운 유료 동작에서 차감하지 못하게 함
- 정기구독 갱신과 미래 월 크레딧 지급 일시 정지
- 예약된 요금제 변경 실행 일시 정지
- 기존 정기구독 상태를 복구용으로 기록

이 단계에서는 크레딧을 최종 회수하지 않는다.

### 6.2 토스 취소가 하나도 성공하지 않음

- 관리자가 환불 건을 종료할 수 있다.
- 크레딧 잠금을 해제한다.
- 정기구독 갱신·크레딧 지급·예약 변경 상태를 복구한다.
- 잠긴 사이 만료된 크레딧은 다시 활성화하지 않는다.

### 6.3 토스 취소가 하나라도 성공

- 자동 원상 복구하지 않는다.
- 환불 건을 일부 완료 또는 처리 중으로 유지한다.
- 환불 대상 크레딧 잠금을 유지한다.
- 다음 자동 결제와 미래 크레딧 지급을 중지한다.
- 나머지 취소를 재처리하거나 수동 취소 후 검증한다.

### 6.4 월간 정기구독 내부 처리

1. 현재 월 기본·상향 크레딧 미사용 확인
2. 관련 크레딧 지급 건 잠금
3. 기본 결제와 상향 차액 결제 전액 취소
4. 모든 필수 결제 취소 확인
5. 잠긴 정기구독 크레딧 전량 회수
6. 정기구독 즉시 종료
7. 다음 자동 결제와 미래 크레딧 지급 중단
8. 예약된 요금제 변경 제거
9. 정기결제용 결제수단 삭제

무료 체험과 추가 구매 크레딧은 유지한다.

### 6.5 연간 정기구독: 현재 월 미사용

1. 현재 월 기본·상향 크레딧 잠금
2. 기본 연간 결제와 상향 차액 결제에서 관리자 입력 금액 부분 취소
3. 취소 완료 후 현재 월 정기구독 크레딧 회수
4. 정기구독 즉시 종료
5. 미래 월 크레딧과 다음 자동 결제 중단
6. 예약된 요금제 변경 제거
7. 정기결제용 결제수단 삭제

### 6.6 연간 정기구독: 현재 월 사용

1. 현재 월 정기구독 크레딧은 잠그거나 회수하지 않는다.
2. 현재 구독 월 종료까지 남은 크레딧을 사용할 수 있다.
3. 기본 연간 결제와 상향 차액 결제에서 미래 기간 금액만 부분 취소한다.
4. 다음 월 경계에 정기구독이 끝나도록 예약한다.
5. 다음 월부터 크레딧을 지급하지 않는다.
6. 다음 자동 결제를 중단한다.
7. 다음 월 경계에서 현재 월의 남은 정기구독 크레딧을 소멸시킨다.
8. 해당 시점에 정기구독을 최종 종료한다.
9. 금전 환불 완료 후 정기결제용 결제수단을 삭제할 수 있다.

기존 연간 구독 종료일과 별도로 환불 적용 종료 시각을 표현해야 한다.

### 6.7 추가 구매 크레딧

1. 지급 건이 만료되지 않았고 전부 남아 있는지 확인
2. 해당 지급 건 잠금
3. 원결제금액 전액 취소
4. 취소 확인 후 해당 지급 건 전량 회수
5. 정기구독과 다른 크레딧에는 영향 없음

### 6.8 실행 중 작업

- 환불 확인 직전에 정기구독 또는 추가 구매 크레딧을 차감한 작업이 있으면 미사용 조건을 충족하지 못한다.
- 해당 작업이 나중에 실패해 크레딧이 복구되면 관리자가 새 환불 건으로 다시 확인할 수 있다.
- 환불 잠금 이후에는 새로운 작업이 잠긴 지급 건을 사용할 수 없다.
- 작업 실패 복구가 이미 회수된 지급 건에 적용돼도 해당 크레딧을 다시 사용 가능하게 만들지 않는다.

### 6.9 내부 transaction 실패

- 토스 취소가 완료된 뒤 정기구독·크레딧 변경은 하나의 DB transaction으로 처리한다.
- transaction이 실패해도 토스 취소를 다시 호출하지 않는다.
- 금전 환불 완료·내부 처리 재처리 필요 상태로 유지한다.
- 동일한 내부 처리만 반복 가능하게 재시도한다.

최종 확인창:

- 사용자
- 상품과 결제
- 결제별 원금과 환불금액
- 총 환불금액
- 정기구독 종료 시각
- 잠금·회수할 크레딧
- 유지되는 무료 체험·추가 구매 크레딧
- 다음 자동 결제 중단
- 토스 취소는 즉시 되돌릴 수 없다는 안내

### 7.4 전체 결제·환불 운영 화면

기존 결제 운영 화면에 환불 탭을 추가한다.

- 사용자·주문번호·결제 식별값 검색
- 처리 중·일부 완료·확인 필요·완료 필터
- 환불 건 상세
- 결제별 토스 취소 결과
- 재조회·재시도
- 토스 관리자 사이트 수동 취소 검증
- 내부 처리 재시도
- 회원 상세 이동

회원 상세와 전체 환불 탭은 같은 API와 처리 화면을 사용한다.

### 7.5 권한

- 일반 운영자는 결제·환불·사용량을 조회할 수 있다.
- 최고 관리자만 환불 실행, 재시도, 수동 취소 검증, 내부 처리 재시도를 할 수 있다.
- 화면뿐 아니라 API에서도 권한을 검사한다.
- 요청자와 승인자를 분리하는 2인 승인 구조는 만들지 않는다.
- 실행 관리자, 시각, 작업, 대상, 전후 상태를 감사 이력으로 남긴다.

## 8. 고객 화면

- 고객용 자동 환불 신청 기능은 만들지 않는다.
- 외부 환불 문의 연락처를 안내한다.
- 결제내역에 원결제금액, 환불금액, 미환불 잔액, 환불 상태, 완료일, 영수증을 표시한다.
- 정기구독 화면에 환불 처리 중, 즉시 종료 또는 종료 예정일, 다음 결제 중단을 표시한다.
- 무료 체험·추가 구매 크레딧이 남아 있으면 그대로 표시한다.
- 환불 때문에 잠긴 크레딧은 사용 가능 잔액에서 제외하고 환불 처리 중으로 표시한다.
- 토스 상세 오류와 내부 재처리 정보는 고객에게 노출하지 않는다.
- 무료 기능은 환불 처리 중이거나 정기구독이 종료돼도 계속 사용할 수 있다.

## 9. Migration과 데이터 안전

### 9.1 신규 migration 대상

- 환불 건
- 결제별 환불 항목
- 토스 취소 시도·검증 이력
- 내부 정기구독·크레딧 처리 이력
- 크레딧 환불 잠금 상태
- 정기구독 환불 처리 상태와 적용 종료 시각
- 결제별 누적 환불금액과 취소 가능 잔액
- 상향 전후 요금제·기간·가격·크레딧 스냅샷
- 기본 결제와 상향 차액 결제 연결
- 동시 환불 방지 제약조건과 색인
- 모든 요금제의 동일 플러그인 사용 정책
- 무료 체험 회원가입 즉시 지급·30일 만료 정책
- 추가 구매 크레딧 30일 만료 정책
- 기존 무료 체험 eligible_from 정책 무효화

### 9.2 원칙

- 기존 migration 파일과 history를 수정하지 않는다.
- 후속 migration으로 최종 정책을 만든다.
- 기존 결제·정기구독·크레딧 데이터를 삭제하지 않는 추가형 migration을 우선한다.
- 5433·5434·5435에 migration을 실행하지 않는다.
- 신규 DB와 일회용 복제 DB에서 먼저 검증한다.

### 9.3 검증

신규 DB:

- 처음부터 전체 migration 적용
- 최종 schema·초기 정책 확인
- API 시작 확인

일회용 복제 DB:

- 현재 적용 상태 복제
- 미적용 migration 전체 실행
- 데이터 변환 전후 수량 비교
- 결제·정기구독·크레딧 연결 무결성 확인
- 기존 파괴적 migration 영향 확인
