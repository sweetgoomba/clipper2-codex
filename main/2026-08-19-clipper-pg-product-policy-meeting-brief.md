# Clipper PG·요금제·구독·크레딧 정책 회의 자료

- 작성일: 2026-08-19
- 목적: Notion import 및 제품·운영·개발 정책 회의
- 기준 시점: 2026-08-19
- 문서 성격: 승인된 구조, 현재 개발 초기값, 미정 정책, 선택지를 한 문서에서 구분

> 이 문서에서 “확정”은 현재 승인된 제품·시스템 원칙을 뜻한다. “현재 구현값”은 개발을 진행하기 위해 seed 또는 운영 기본값으로 넣은 값이며, 출시 가격이나 영구 정책으로 확정됐다는 뜻이 아니다.

## 0. 맨 위 요약

### 0.1 지금까지의 핵심 결론

1. Clipper는 요금제 등급, 결제 상품, 한 개의 기본 이용 자격, 출처별 크레딧 지급 묶음을 분리한다.
2. 실제 회원용 상품은 우선 Basic과 Pro, 월간과 연간 카드 구독으로 개발 중이다.
3. 현재 개발값은 Basic 월 19,900원·400크레딧, Pro 월 39,900원·1,000크레딧이다. 연간은 약 20% 할인된 190,900원과 382,900원이며 크레딧은 연간 선지급이 아니라 매월 지급한다.
4. 위 가격·크레딧·기능 구분은 DB 카탈로그 seed로 만든 재검토 가능한 초기값이다. 공개 출시 전 원가와 고객가치 검증이 필요하다.
5. 현재 Basic과 Pro의 기능 차이는 variation 기능 하나뿐이다. 최종 Pro 가치 제안과 기능 차등은 별도 원가·상품성 분석 결과와 함께 결정해야 한다.
6. 코드에는 숏폼 생성 50, 하이라이트 50, variation 20이라는 차감값이 들어 있지만 모두 기능 흐름 검증을 위해 임의로 넣은 placeholder다. 이 숫자로 플랜 작업량·가격 적정성·top-up 가치를 계산하지 않는다.
7. 플랜 가격, 플랜별 제공 크레딧, 작업별 차감 크레딧은 별도 원가·상품성 분석 작업에서 함께 결정한다. GPT/API 호출, 입력·출력 token, 생성 모델, 영상 길이, 렌더, 저장·전송, 실패·재시도·복구 비용을 모두 반영해야 한다.
8. 추가 크레딧은 100개 5,900원, 500개 27,900원, 1,000개 49,900원, 유효기간 365일로 개발 중이다. 활성 이용 자격이 있어야 구매·사용할 수 있다.
9. 구독 크레딧은 월별 지급 후 다음 월 지급 기준일에 만료하고 이월하지 않는 것으로 개발 중이다. 경쟁 서비스에는 무이월과 1개월 이월이 모두 있어 출시 전 UX 결정이 필요하다.
10. 구독은 카드 자동결제만 지원하고, 추가 크레딧은 카드·카카오페이·네이버페이·토스페이·계좌이체·가상계좌를 지원한다.
11. 돈 환불 기능은 현재 범위에서 완전히 제외했다. 작업 실패 시 이미 차감한 서비스 내부 크레딧을 원래 지급 묶음으로 되돌리는 크레딧 반환·복구만 유지한다.
12. Task 1~10은 독립 리뷰까지 완료했다. Task 11 최초 구독 결제는 production 변경 전에 중단했으며, 현재 feature branch는 clean 상태다. 아직 전체 기능을 실행하거나 배포할 수 있는 상태는 아니다.

### 0.3 이 문서의 추천 결론

- 현재 가격과 크레딧을 결제 메커니즘 개발·테스트용 임시 카탈로그로만 유지한다. 폐쇄형 베타 판매가로도 아직 승인하지 않는다.
- 현재 가격·제공 크레딧·차감값은 결제와 원장 기능을 개발하기 위한 seed로만 둔다. 이 숫자로 판매 적정성이나 예상 작업량을 주장하지 않는다.
- 별도 원가·상품성 분석에서 작업별 P50/P95 직접비, 실패율, 재시도, 인프라, 저장·전송, 운영비를 계산한 뒤 플랜 가격·제공 크레딧·작업별 차감량을 하나의 모델로 결정한다.
- 초기에는 Basic/Pro 두 등급만 유지하되, Pro가 variation 하나 외에 어떤 명확한 시간 절감·품질·대량 처리 가치를 주는지 제품 문구와 기능표를 확정한다.
- 영구 무료 요금제는 당장 추가하지 않는다. 체험이 필요하면 별도 무료 등급보다 만료되는 promotion 또는 admin credit grant로 제한된 실험을 먼저 한다.
- 추가 크레딧 365일은 유지 후보로 적절하다. 다만 구독이 끝나면 잔액을 사용할 수 없는 정책을 결제 전에 명확히 고지해야 한다.
- 구독 크레딧 무이월은 원가 통제에는 유리하지만 박탈감이 크다. 출시 전 “무이월”과 “최대 1개월 또는 월 지급량 한도 이월”을 사용자 관점에서 최종 선택한다.
- 돈 환불 코드는 정책·약관·운영 승인이 정해질 때까지 만들지 않는다. 다만 유료 출시 전 최소 환불 접수 채널과 수동 처리 책임자는 반드시 정한다.

## 1. 상태 구분

| 표기 | 의미 |
| --- | --- |
| 확정 | 사용자 승인 설계와 현재 도메인 구조가 반드시 지키는 원칙 |
| 현재 구현값 | 개발을 막지 않기 위해 DB seed·운영 기본값으로 넣은 값. 관리자에서 변경 가능하거나 출시 전 재검토 가능 |
| 미정 | 제품·법률·운영 의사결정이 아직 필요 |
| 제외 | 이번 PG 전체 연동 feature 범위에 의도적으로 넣지 않음 |

중요한 해석:

- Basic/Pro, 가격, 크레딧, top-up 팩은 한 차례 승인되어 개발에 반영됐지만 설계 문서도 이를 “임시 초기 상품값”으로 명시한다.
- 따라서 개발 데이터로는 확정됐고, 공개 출시 정책으로는 재검토 가능하다.
- 결제·크레딧 원장·멱등성·보안 구조는 가격 숫자가 바뀌어도 다시 설계하지 않도록 분리했다.

## 2. 확정된 제품·도메인 원칙

### 2.1 상품 구조

- 요금제 등급은 사용할 수 있는 기능과 월별 기본 크레딧을 가진다.
- 결제 상품은 특정 등급을 어떤 결제 주기와 가격으로 판매하는지를 가진다.
- 같은 등급의 월간과 연간 상품은 같은 기능 권한을 공유한다.
- 가격·결제 주기·월 크레딧과 기능 권한을 분리한다.
- 가격과 월 크레딧은 구독 시작 또는 상품 변경 시 계약 snapshot으로 저장한다.
- 기존 구독자의 가격과 월 크레딧은 카탈로그를 수정해도 소급 변경하지 않는다.
- 기능 권한은 현재 등급의 최신 DB 설정을 즉시 따른다.
- 결제 주문에는 당시 상품명, 가격, 주기, 등급, 월 크레딧을 영구 snapshot으로 남긴다.

### 2.2 한 개의 기본 이용 자격

- 한 사용자에게 동시에 적용되는 기본 이용 자격은 한 개다.
- 기본 이용 자격의 출처는 유료 구독 또는 관리자 요금제 부여다.
- 관리자 계정도 별도 프리패스가 아니라 실제 표준 요금제를 부여받는다.
- 유료 구독과 관리자 요금제 부여를 동시에 활성화하지 않는다.
- 추가 구매 크레딧과 관리자 추가 크레딧은 기본 이용 자격과 별도로 공존할 수 있다.

### 2.3 로그인과 결제

- 실제 결제는 로그인 사용자만 가능하다.
- 브라우저의 가격·금액·권한 값을 신뢰하지 않고 서버 DB 카탈로그를 다시 읽는다.
- 브라우저 성공 화면만으로 구독이나 크레딧을 지급하지 않는다.
- Toss에서 결제 상태를 확인하고 DB 주문과 금액·주문번호를 대조한 뒤 한 번만 지급한다.
- 결제 성공 저장과 혜택 지급 성공을 분리한다.
- 결제는 성공했으나 지급이 실패하면 결제를 다시 하지 않고 fulfillment만 재시도한다.

### 2.4 크레딧 원칙

- 크레딧은 사용자 총 숫자 하나가 아니라 출처와 만료를 가진 지급 묶음으로 관리한다.
- 출처는 subscription, admin_plan, topup, admin_adjustment, promotion을 지원한다.
- 만료가 가까운 묶음부터 사용한다.
- 만료일이 같으면 먼저 지급된 묶음부터 사용한다.
- 만료 없음 묶음은 만료가 있는 묶음 뒤에 사용한다.
- 한 작업이 여러 묶음에서 차감될 수 있고 묶음별 내역을 기록한다.
- 작업 실패 반환은 실제 차감했던 원래 묶음으로 돌아간다.
- 원래 묶음이 이미 만료됐다면 원장과 묶음 잔액은 복구해도 사용 가능 잔액으로 되살리지 않는다.
- 어떤 출처의 크레딧이든 사용하려면 유효한 기본 이용 자격이 필요하다.

### 2.5 기존 사용자 데이터와 결과물

- 요금제 종료나 갱신 실패로 계정, 프로젝트, 작업 이력, 결과물을 삭제하지 않는다.
- 종료되는 것은 유료 기능 실행 권한과 미래 크레딧 지급이다.
- 출시 전 legacy 무통장·license 테스트 데이터는 이관하지 않는다.

## 3. 현재 개발 중인 상품값

### 3.1 구독 상품

> 아래 가격과 제공 크레딧은 현재 개발 seed를 기록한 것이다. 작업별 placeholder 차감값과 결합해 단가, 예상 작업량, margin, 상품 적정성을 판단하지 않는다.

| Basic | 월간 | 19,900원 | 400 | 매월 자동 갱신 | 현재 구현값 |
| Basic | 연간 | 190,900원 | 매월 400 | 매년 자동 갱신 | 현재 구현값 |

연간 가격 산술:

| 항목 | Basic | Pro |
| --- | ---: | ---: |
| 월간 12회 합계 | 238,800원 | 478,800원 |
| 연간 실제 결제금액 | 190,900원 | 382,900원 |
| 연간 절감액 | 47,900원 | 95,900원 |
| 할인율 | 약 20.06% | 약 20.03% |
| 월 환산 결제금액 | 약 15,908원 | 약 31,908원 |

추가 해석:

- 연간 할인표는 현재 seed의 결제 금액 관계만 보여준다.
- 포함 크레딧 1개의 가치, 작업 가능 수량, 원가율은 아직 계산하지 않는다.
- 현재 price/credit 조합은 회계상 크레딧 가치나 환불가를 뜻하지 않는다.
- 모든 소비자 표시 금액은 VAT 포함으로 개발하고 taxFreeAmount는 0원으로 요청한다.
- 3개월 상품과 고정 기간 단건 이용권은 현재 만들지 않는다.

| 기능 | Basic | Pro | 상태 |
| --- | --- | --- | --- |
| URL 기반 숏폼 생성 | 가능 | 가능 | 현재 구현값 |

현재 차등의 의미:

- variation 하나만 Pro 전용이다.
- 서버 작업 시작 시 권한을 다시 검사하므로 UI에서 버튼만 숨기는 방식이 아니다.
- 권한표는 DB와 관리자 화면에서 변경할 수 있다.
- 기존 사용자의 기능 권한은 등급 권한표 변경 즉시 바뀐다.
- 공개 가격표에서는 기능 차이와 사용량 차이를 함께 설명해야 한다.

### 3.3 현재 작업별 크레딧 차감값

- 그 결과를 바탕으로 플랜 가격, 플랜별 제공 크레딧, top-up 가격·수량, 작업별 차감 크레딧을 함께 결정한다.

현재 seed 구조:

- 팩별 단가와 할인율의 적정성은 아직 판단하지 않는다.
- top-up 수량·가격도 별도 원가·상품성 분석에서 플랜 가격·제공 크레딧·작업 차감과 함께 다시 결정한다.
- 모든 등급이 같은 팩을 같은 가격으로 산다.

- 결제 도중 구독이 끝났더라도 결제가 DONE이면 크레딧은 지급한다.
- 구독이 끝나면 잔액과 만료일은 유지하지만 사용할 수 없다.
- 유효한 이용 자격이 다시 생기면 아직 만료되지 않은 잔액을 사용할 수 있다.

## 4. 현재 개발 중인 구독 정책

### 4.1 최초 가입

1. 사용자가 서버 카탈로그의 상품 code를 선택한다.
2. 서버가 로그인, 판매 활성, 현재 이용 자격, 기존 열린 구독을 확인한다.
3. pending 구독, 결제 주문, 카드 등록 attempt를 저장한다.
4. 카드 자동결제 인증 후 빌링키를 발급하고 암호화 저장한다.
5. 같은 최초 주문과 고정 idempotency key로 첫 결제를 요청한다.
6. type=BILLING, method=카드, status=DONE, currency=KRW와 안전한 카드 정보를 모두 확인한다.
7. 결제 성공을 저장한 뒤 구독·이용 자격·첫 월 크레딧을 한 번 지급한다.

카드 등록만 성공하고 최초 결제가 실패하면:

- 이용 자격과 크레딧을 지급하지 않는다.
- 안전하게 저장한 빌링키는 명시적 재시도 또는 카드 변경에 사용할 수 있다.
- 결과가 불명확한 주문을 새 주문으로 바꿔 재청구하지 않는다.

### 4.2 연간 구독의 월별 혜택

- 연간 금액은 가입 시 한 번 결제한다.
- 크레딧은 12개월치를 한 번에 주지 않고 월별 기준일마다 400 또는 1,000을 지급한다.
- 원래 결제 승인일의 월·일 anchor를 유지한다.
- 31일과 윤년은 해당 월의 마지막 유효 날짜를 사용한다.
- 결제 주기와 혜택 지급 주기를 별도로 관리한다.

### 4.3 크레딧 만료

현재 구현 기본값:

- 구독과 관리자 요금제로 받은 월 크레딧은 다음 월별 지급 기준일 직전에 만료한다.
- 이월하지 않는다.
- 1월 31일 지급분은 2월 말에 만료하고, 다음 지급분은 2월 말 기준으로 새로 생긴다.
- 연간 구독도 같은 규칙을 12번 적용한다.

이 값은 최종 출시 정책으로 재검토가 필요하다.

### 4.4 다음 결제 취소와 철회

- 사용자는 언제든 다음 자동결제를 취소할 수 있다.
- 현재 결제기간 종료일까지 기능 권한과 예정된 월별 크레딧을 유지한다.
- 다음 결제 취소는 즉시 이용 종료나 돈 환불이 아니다.
- 기간 종료 전에는 취소를 철회하고 자동갱신을 다시 켤 수 있다.
- 철회를 위해 빌링키는 실제 기간 종료 전까지 보관한다.
- 기간이 끝나고 미정산 주문이 없으면 빌링키를 삭제한다.

### 4.5 Basic에서 Pro로 변경

현재 구현 정책:

- 같은 주기에서 즉시 변경한다. 월 Basic은 월 Pro로, 연 Basic은 연 Pro로 변경한다.
- 남은 결제기간에 대한 가격 차이를 원 단위 올림으로 계산한다.
- 계산식은 ceil(전체 기간 가격 차이 × 남은 시간 ÷ 전체 결제기간)이다.
- 공급자 최소 결제금액보다 작으면 즉시 결제하지 않고 다음 갱신 변경으로 예약한다.
- 차액 결제가 DONE인 경우에만 Pro 기능을 활성화한다.
- 현재 월 혜택 주기의 남은 비율만큼 Pro와 Basic의 월 크레딧 차이를 올림해 한 번 추가 지급한다.
- 다음 갱신부터 변경 요청 시점의 Pro 가격·주기·크레딧 snapshot을 사용한다.

### 4.6 Pro에서 Basic 및 월·연 변경

- Pro에서 Basic은 다음 갱신일부터 적용한다.
- 월간과 연간 사이 변경도 다음 갱신일부터 적용한다.
- 현재 결제기간의 기능과 크레딧을 소급 회수하지 않는다.
- 한 구독에 예약 변경은 한 개만 둔다.
- 갱신 전에 예약을 취소하거나 다른 상품으로 교체할 수 있다.
- 다음 결제 취소를 요청하면 예약 변경도 같이 취소한다.
- 예약 당시 사용자에게 표시한 대상 상품값을 snapshot하고 갱신 시 사용한다.

### 4.7 갱신 실패

현재 운영 기본값:

| 시점 | 동작 |
| --- | --- |
| D+0 | 최초 갱신 실패, past_due 시작 |
| D+1 | 자동 재시도 |
| D+2 | 두 번째 자동 재시도 |
| D+3 | 유예 종료, 성공하지 못하면 stopped |

유예 중:

- 기존 기능 권한과 아직 만료되지 않은 크레딧은 사용할 수 있다.
- 실패한 새 회차의 크레딧은 지급하지 않는다.
- 사용자의 직접 재결제는 자동 재시도 순번을 소모하지 않는다.
- 성공하면 실제 재결제일이 아니라 원래 결제 anchor를 유지한다.
- D+3에 stopped가 되어도 계정·프로젝트·결과물은 보존한다.
- 이 정책은 DB 관리자 설정에서 바꿀 수 있고 이미 past_due인 회차에는 소급하지 않는다.

## 5. 결제수단과 결제 운영 범위

### 5.1 지원 범위

| 목적 | 카드 | 카카오페이 | 네이버페이 | 토스페이 | 계좌이체 | 가상계좌 |
| --- | --- | --- | --- | --- | --- | --- |
| 월·연 구독 | 지원 | 미지원 | 미지원 | 미지원 | 미지원 | 미지원 |
| 추가 크레딧 | 지원 | 지원 | 지원 | 지원 | 지원 | 지원 |

- 구독 자동결제는 카드만 사용한다.
- 계좌 자동결제는 현재 계약과 구현 범위에서 제외한다.
- 추가 크레딧 결제수단은 Toss 주문서와 실제 MID 설정을 함께 정본으로 삼는다.
- 허용 목록 밖의 수단인데 Toss가 정상 결제를 승인한 예외는 돈만 받고 지급을 거부하지 않는다. 상품은 한 번 지급하고 운영 경고를 남긴다.

### 5.2 가상계좌

- 기본 입금기한은 발급 후 24시간이다.
- 계좌 발급은 결제 완료가 아니며 waiting_for_deposit 상태다.
- 입금 전에는 크레딧을 지급하지 않는다.
- DEPOSIT_CALLBACK과 결제 재조회로 DONE을 확인한 뒤 한 번 지급한다.
- 입금기한 만료나 입금 전 취소에는 지급하지 않는다.
- 공급자에서 늦은 DONE이 확인되면 로컬 만료 추측보다 공급자 상태를 우선한다.
- 전체 계좌번호를 저장하지 않고 정해진 형식의 마스킹 계좌만 보관·표시한다.

### 5.3 고객 결제내역

로그인 사용자는 자신의 결제만 조회한다.

- 상품명·결제 목적
- 주문번호·주문/결제 시각
- 금액·결제 상태
- 결제수단·간편결제사
- 가상계좌 입금 대기 정보
- Toss 영수증·매출전표 URL
- 결제 완료 후 상품 지급 상태

평문 빌링키, authKey, Secret Key, 전체 카드번호, 전체 계좌번호는 어떤 고객 응답에도 포함하지 않는다.

## 6. 돈 환불, 크레딧 반환, 고객지원

### 6.1 이번 범위에서 제외한 돈 환불

다음은 구현하지 않는다.

- 사용자 환불 요청 페이지

- 환불 가능 금액 산식
- 운영자 검토·super-admin 승인

이유:

- 청약철회, 디지털콘텐츠 사용 개시, 사용기간, 사용한 크레딧, 수수료, 승인 권한을 반영한 정책과 법률 검토가 먼저 필요하다.

### 6.2 계속 유지하는 크레딧 반환·복구

- AI 또는 렌더 작업이 실패하면 이미 차감한 서비스 내부 크레딧을 원래 지급 묶음으로 되돌린다.
- 이것은 사용자가 낸 돈을 돌려주는 환불이 아니다.
- 제품 문구도 “환불”이 아니라 “크레딧 반환” 또는 “크레딧 복구”를 사용한다.
- 작업 성공 여부가 불명확하면 시간 경과만으로 크레딧을 반환하지 않고 외부 작업 상태를 확인한다.

- 운영자와 최종 승인자

## 7. 관리자와 보안 정책

### 7.1 관리자 기능

- 요금제 등급, 월 크레딧, 활성 상태 관리
- 월·연 결제 상품, 가격, 주기, 판매 활성 상태 관리
- 등급별 plugin 권한 교체
- 추가 크레딧 수량, 가격, 유효기간, 활성 상태 관리
- 사용자에게 표준 요금제 부여·변경·회수
- 관리자 추가 크레딧 지급·회수
- 갱신 실패 유예·재시도 정책 관리
- 결제 주문·웹훅·fulfillment·reconciliation 조회
- 결제 성공 후 실패한 fulfillment 재처리

돈 환불 버튼은 현재 만들지 않는다.

### 7.2 보안과 장애 복구

- 일반 결제 키와 빌링 키를 분리한다.
- Client Key만 checkout session으로 브라우저에 전달한다.
- Secret Key는 API 서버에만 둔다.
- 빌링키와 짧게 필요한 authKey는 암호화한다.
- 빌링키 검색에는 HMAC fingerprint를 사용한다.
- customerKey는 이메일·전화번호·DB 순번·사용자 ID가 아닌 무작위 값이다.
- receipt token은 256비트 무작위 값이며 DB에는 SHA-256 hash만 저장한다.
- 모든 금액과 상품 데이터는 서버 snapshot을 신뢰한다.
- Toss POST idempotency key는 논리 주문마다 고정한다.
- 불명확한 결과에는 새 주문·새 키로 자동 재청구하지 않는다.
- Toss의 동일 POST 멱등 보장 기간인 최초 요청 후 15일 안에서는 같은 요청만 복구한다.
- 15일 경계 이후 결과가 불명확하면 조회·운영 reconciliation만 하고 새 자동 청구는 만들지 않는다.
- PAYMENT_STATUS_CHANGED, DEPOSIT_CALLBACK, BILLING_DELETED 웹훅을 처리한다.
- 웹훅 원문만 믿지 않고 Toss 결제 조회 및 저장 secret/fingerprint와 대조한다.

적합한 상황:

- 실제 판매나 가격 검증이 아니라 결제·구독·원장·복구 메커니즘을 테스트할 때.

필수 조건:

- 현재 숫자로 고객에게 예상 작업량이나 가격 적정성을 약속하지 않는다.
- 테스트 결제와 실제 상품 판매를 구분한다.
- 별도 원가 분석 결과가 나오기 전 공개 판매가로 승인하지 않는다.

### 안 B. 전환 친화형

- 원가 분석으로 확정한 유료 가격과 제공량을 사용.
- 일회성 promotion 체험 credit 제공.
- 구독 credit은 최대 월 지급량 1배까지 한 달 이월.
- top-up은 365일.
- Pro 기능 차이를 2~4개로 명확화.

적합한 상황:

- 신규 고객이 결제 전에 결과를 경험해야 하고 월 사용량 변동이 클 때.

위험:

- abuse와 이월 liability 관리가 필요.

### 안 C. 사용량 중심 전문가형

- 무료 없음 또는 매우 제한된 demo.
- Basic/Pro 기능은 비슷하게 유지.
- Pro는 더 낮은 credit 단가, batch, 우선 처리, 고용량을 중심으로 차등.
- 추가 대용량 top-up 또는 Business 상품 검토.

적합한 상황:

- 고객이 기능보다 반복 생산량과 처리속도에 더 높은 가치를 둘 때.

위험:

- 현재 variation 전용 권한의 의미가 약해지고 Pro를 단순 대용량 요금제로 보이게 할 수 있음.

### 권장 진행

1. 안 A로 결제 메커니즘만 제한 검증한다.
2. 별도 원가·상품성 분석 작업을 수행한다.
3. 분석 결과로 후보 가격·제공 크레딧·작업별 차감표를 만든다.
4. 그 후보로 제한된 사용자 테스트를 진행해 실제 사용 mix와 이해도를 확인한다.
5. 무료 체험 필요성, 이월 불만, Pro 기능 수요를 함께 확인한다.
6. 데이터에 따라 공개 출시 상품을 확정한다.

## 12. 가격 확정 전에 필요한 데이터

### 12.1 작업별 원가

- 모델 API 비용
- 원본 길이·출력 길이별 비용
- GPU/CPU rendering 비용
- 저장공간·전송 비용
- 성공 작업의 평균 재시도
- 실패 작업과 크레딧 반환의 실제 비용
- 운영 support 비용

### 12.2 사용자 사용량

- 사용자당 주간·월간 작업 수
- 기능별 작업 mix
- 원본 영상 길이 분포
- variation 결과물 개수 분포
- 원가 분석으로 만든 각 후보 제공량의 예상 소진 기간
- 월말 미사용 credit 비율
- top-up 구매 시점과 팩 분포

### 12.3 사업 지표

- VAT와 PG 수수료 제외 순매출
- 목표 gross margin
- 월간→연간 전환율
- Basic→Pro 전환율
- 첫 결제 전 이탈 지점
- 갱신 실패·해지·환불 비율
- 고객지원 발생률

### 12.4 가격 검증 산식 예시

- 요금제 예상 월 원가 = 기능별 평균 사용량 × 기능별 성공·실패 포함 원가
- 순매출 = VAT·PG 비용을 반영한 실제 수취액
- gross margin = (순매출 - 예상 월 원가 - 변동 운영비) ÷ 순매출
- credit 원가율 = 고객이 받은 credit이 아니라 실제 사용한 작업 mix 기준으로 계산

### 12.5 별도 원가·크레딧 산정 작업의 산출물

이 회의 문서와 PG 구현 작업에서는 숫자를 임의 확정하지 않는다. 별도 작업은 최소한 다음을 산출해야 한다.

1. 플러그인·작업별 실행 단계 목록
2. 단계별 외부 API와 모델명, 과금 단위, 단가, 환율 기준
3. 입력·출력 token, 음성 길이, 원본·출력 영상 길이, 해상도, 생성 개수별 원가 함수
4. GPU/CPU 렌더 시간, 저장공간, CDN·전송, queue, observability 비용
5. 성공·실패·timeout·재시도·복구별 기대 원가
6. P50/P90/P95 작업 원가와 최악 조건 상한
7. 기능별 고객가치와 경쟁 서비스의 고객 표시 단위
8. 목표 margin별 플랜 가격·제공 크레딧·차감 크레딧 후보표
9. 월간·연간·top-up 조합별 손익 시뮬레이션
10. 추천안과 민감도 분석, 가격 변경 시 기존 계약 처리 원칙
