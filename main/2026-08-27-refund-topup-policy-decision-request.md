# 전략팀 결정 요청서 — 환불·구독·Top-up 운영정책

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-08-27 |
| 수신 | 전략팀 |
| 목적 | TossPayments 환불 기능 설계에 필요한 사업정책 결정 |
| 상태 | 전략팀·법무·세무회계·운영CS 회신 전 미결 |
| 관련 상품 | 월간 구독, 연간 구독, Top-up credits, Trial |

## 0. 먼저 확인해 주실 사항

이 문서는 개발팀이 환불정책을 대신 정하기 위한 문서가 아니다. 현재 구현과 상품 구조를 설명하고, **전략팀이 결정해야 할 사업정책**을 구분해 회신받기 위한 문서다.

법률상 허용 범위와 의무는 법무가, 매출·세금·증빙 처리는 세무·회계가, 접수·승인·예외 대응 절차는 운영·CS가 별도로 확인해야 한다. 전략팀의 결정은 이 검토 결과에 따라 조정될 수 있다.

2026-08-20 작성된 `planning-team-requests.md`와 `legal-drafts-for-review.md`에는 당시의 잠정안과 현재 코드에 맞지 않는 전제가 포함돼 있다. 다음 항목은 더 이상 현재 전제로 사용하지 않는다.

- 제한 없는 전액 환불
- 출시 시 정기결제 미판매
- 결제 후 이용권 수동 발급
- 가격 미확정
- Trial 또는 무료 entitlement가 없다는 전제

회신이 없는 항목은 개발팀이 임의로 정하지 않는다. 특히 **“부분 환불 정책이 미정이므로 전액 환불을 기본값으로 사용”하지 않는다.** 전액 환불도 조건과 예외에 대한 승인이 필요한 정책이다.

## 1. 왜 지금 결정이 필요한가

현재 시스템에는 정기 구독 결제와 다음 갱신을 막는 구독 취소가 구현돼 있지만, 고객에게 실제 결제금을 돌려주는 전액·부분 환불 기능은 없다.

환불 시스템은 단순히 TossPayments에 취소 금액을 보내는 기능이 아니다. 다음 사항을 먼저 알아야 시스템이 일관된 결과를 계산할 수 있다.

- 어떤 구매가 환불 대상인지
- 전액 환불인지 부분 환불인지
- 환불액을 어떤 산식으로 계산하는지
- 환불 후 이용권을 언제 종료하는지
- 결제로 지급된 미사용 credits를 얼마나 회수하는지
- 구독과 별도로 구매한 Top-up credits를 어떻게 처리하는지

일반적인 환불 요청에서 고객이나 관리자가 원하는 금액을 직접 입력하게 만들 계획은 없다. 승인된 정책을 기준으로 시스템이 대상 여부와 예상 금액을 계산하고, 필요한 경우 담당자가 그 결과를 승인하는 구조를 검토 중이다. 따라서 코드 구현 전에 계산 규칙의 입력이 되는 사업정책이 필요하다.

## 2. 현재 상품·구현 상태

아래는 **현재 코드에서 확인된 상태**다. 전략팀의 최종 승인을 의미하지는 않는다.

### 2.1 구독과 가격

| 플랜 | 월 결제 | 연 결제 |
|---|---:|---:|
| Basic | 5,900원 | 58,800원 |
| Pro | 10,900원 | 82,800원 |
| Business | 29,900원 | 234,000원 |

- 월간·연간 구독 구조가 구현돼 있다.
- 연간 구독은 1년 금액을 선결제한다.
- 연간 구독의 포함 credits는 월 단위로 지급된다.
- 결제 승인 후 이용권과 credits가 자동 발급된다.
- 현재 구독 취소는 다음 갱신을 막고 이미 결제한 기간 말까지 이용하는 방식이다.
- 이 구독 취소는 이미 결제한 돈을 돌려주는 환불과 별개다.

### 2.2 Top-up credits

| credits | 가격 | 현재 코드상 유효기간 |
|---:|---:|---:|
| 400 | 5,900원 | 365일 |
| 1,000 | 10,900원 | 365일 |
| 4,000 | 29,900원 | 365일 |

현재 코드는 다음과 같이 동작한다.

- 유료 구독이 있을 때만 Top-up을 구매할 수 있다.
- 유료 구독이 끝나도 이미 구매한 Top-up이 즉시 삭제되지는 않는다.
- 다만 다시 유료 이용권이 생길 때까지 사용할 수 없다.
- 사용할 수 없는 동안에도 365일 유효기간은 계속 흐른다.
- Trial만 있는 상태에서는 Top-up을 사용할 수 없다.

이 동작은 전략팀 문구인 **“추가 크레딧 충전(유료 플랜 대상 무제한 이용 가능)”**을 개발 과정에서 구체화한 결과지만, 해당 문구만으로 아래 사항까지 승인됐다고 볼 수 없다.

- 구매할 때만 유료 플랜이면 되는지
- 사용할 때도 유료 플랜이어야 하는지
- 구독 종료 후에도 사용할 수 있는지
- “무제한”이 구매 횟수·구매 총량·사용량 중 무엇을 뜻하는지

### 2.3 Trial

현재 코드는 다음과 같이 동작한다.

- 계정당 한 번 400 credits 지급
- Trial 자체 만료일 없음
- 유료 전환 후에도 남은 Trial credits 유지
- 유료 이용권이 끝나면 남은 Trial이 다시 사용 가능
- Trial에서 사용할 수 있는 기능 범위는 제한됨

Trial 대상 계정의 기준 시각은 코드에 잠정값이 있으나 정확한 시각이 승인된 기록은 없어 운영 적용 전 별도 확정이 필요하다.

### 2.4 환불

현재 실제 결제금 환불 기능은 아직 없다.

- 다음 자동결제를 취소하는 기능: 있음
- TossPayments에 전액 취소를 요청하는 기능: 없음
- TossPayments에 부분 취소를 요청하는 기능: 없음
- 환불 대상·금액을 계산하는 기능: 없음
- 관리자 환불 심사·승인 기능: 없음
- 실패한 작업의 내부 credit 복구: 있음. 고객에게 돈을 돌려주는 환불과는 별개

## 3. 결정 원칙 제안

전략팀이 개별 고객의 환불액을 직접 계산할 필요는 없다. 다음 순서로 역할을 나누는 것을 제안한다.

1. 전략팀이 상품별 사업정책과 고객 경험을 결정한다.
2. 법무가 법정 철회·예외·중도 해지 규정과 약관 문구를 검토한다.
3. 세무·회계가 금액·증빙·매출 처리를 확인한다.
4. 운영·CS가 접수·승인·예외 처리 절차를 정한다.
5. 개발팀이 승인된 규칙을 시스템 계산식과 상태 전이로 구현한다.

기술 구조는 향후 전액·부분 환불을 모두 표현할 수 있게 설계하되, 실제 운영에서는 위 절차를 거쳐 승인된 규칙만 활성화한다.

## 4. 전략팀 결정 요청

### S1. 정기 구독 판매 구조 확인

현재 코드는 월간·연간 정기 구독을 전제로 구현돼 있다.

결정 요청:

1. 월간 정기 구독을 판매하는가?
2. 연간 정기 구독을 판매하는가?
3. 각 구독은 해지 전까지 자동 갱신되는 상품이 맞는가?
4. 고객이 갱신을 취소하면 이미 결제한 기간 말까지 이용하는 현재 방식을 유지하는가?

참고: 위 4번은 **다음 결제 취소**에 관한 질문이다. 이미 결제한 금액의 환불정책은 S3·S4에서 별도로 결정한다.

### S2. 자동 발급 방식 확인

현재 결제 승인 후 이용권과 credits가 자동 발급된다.

결정 요청:

- 현재 자동 발급 방식을 공식 운영정책으로 승인하는가?
- 결제 후 별도 수동 검토가 필요한 상품 또는 고객 유형이 있는가?

수동 발급을 선택하면 결제는 완료됐지만 이용권은 없는 대기 상태와 CS 업무가 생긴다. 별도 사유가 없다면 현재 자동 발급을 유지하는 편이 고객 경험과 운영 일관성에 맞는다.

### S3. 월간 구독의 일반 환불정책

다음 자동결제 취소와 현재 결제금 환불을 구분해 결정해야 한다.

전략팀 결정 요청:

1. 법에서 반드시 보장해야 하는 경우와 회사 귀책·중복 결제 외에, 회사가 추가로 제공할 **자발적 환불정책**이 있는가?
2. 자발적 전액 환불을 제공한다면 “미사용”을 무엇으로 판단하는가?
   - 지급된 구독 credits를 하나도 사용하지 않음
   - 유료 기능을 한 번도 실행하지 않음
   - 결과물을 생성·다운로드하지 않음
   - 위 조건을 조합한 별도 기준
3. 자발적 환불 신청 가능 기간을 며칠로 할 것인가?
4. 월간 구독에서 일부 사용 후 고객 변심으로 환불을 요청하면 회사가 추가 부분 환불을 제공할 것인가, 법정·회사 귀책 사유만 별도 검토할 것인가?
5. 환불이 완료되면 유료 이용권을 즉시 종료하는가?

필수 전제:

- 환불된 결제로 지급된 **미사용 구독 credits는 회수**한다.
- 일부 또는 전부 사용된 credits를 그대로 둔 채 결제금만 전액 돌려주는 방식을 기본정책으로 삼지 않는다.
- 이미 사용된 서비스나 이미 지나간 기간을 임의로 환불하는 산식을 만들지 않는다.
- 법정 철회·미성년자 취소·회사 귀책 등은 일반 고객 변심 정책과 별도로 법무 검토한다.

### S4. 연간 구독의 중도 해지·환불정책

연간 구독은 1년 금액을 선결제하므로, 다음 연도 갱신 취소와 현재 연간 계약의 중도 종료를 구분해야 한다.

전략팀 결정 요청:

1. 법에서 요구하는 범위 외에도 고객 변심에 따른 연간 중도 해지·부분 환불을 제공할 것인가?
2. 제공한다면 환불 대상은 **앞으로 제공하지 않을 미래 기간**으로 한정하는가?
3. 연간 할인분을 어떻게 처리하기를 원하는가?
   - 남은 미래 기간을 연 결제 단가 기준으로 비례 계산
   - 이미 이용한 기간을 월 정상가로 다시 계산한 뒤 잔액 환불
   - 다른 산식 제안
4. 월 단위 credit 지급일과 월 중간 해지 시점을 어떻게 맞출 것인가?
   - 현재 credit 기간 종료일까지 이용 후 그 다음 기간부터 환불
   - 즉시 이용권 종료 후 일할 계산
   - 다른 방식
5. 부분 환불 완료 시 이용권 종료 시점은 언제인가?

주의:

- 12개월 중 4개월을 이용했다면 단순한 미래 미제공 기간은 8개월이다. “50% 환불”이나 “남은 6개월”처럼 근거 없는 비율을 적용하지 않는다.
- 부분 환불은 이용권이 “부분적으로 활성화”된다는 뜻이 아니다. 환불정책과 별도로 access 종료 시점을 명확히 정해야 한다.
- 구체 산식은 법무·세무회계 검토를 거쳐야 한다.

### S5. Top-up 구매 자격과 “무제한”의 의미

전략팀 문서의 “추가 크레딧 충전(유료 플랜 대상 무제한 이용 가능)”을 구현 가능한 정책으로 구체화해야 한다.

결정 요청:

1. “유료 플랜 대상”은 다음 중 무엇인가?
   - 구매할 때와 사용할 때 모두 유료 구독 필요
   - 구매할 때만 유료 구독 필요
   - 유료 구독 이력이 있으면 구매·사용 가능
   - 다른 기준
2. “무제한”은 무엇을 뜻하는가?
   - 구매 횟수 제한 없음
   - 구매 가능한 누적 credits 제한 없음
   - 한 번에 구매 가능한 수량 제한 없음
   - 다른 의미
3. 내부 지원 목적으로 관리자가 부여한 무상 이용권도 “유료 플랜” 자격과 동일하게 취급하는가?
4. 결제 이상·부정 사용 방지를 위한 1회·1일·월간 구매 한도를 둘 것인가?

### S6. 구독 종료 후 Top-up 처리

Top-up은 구독과 별도 결제다. 구독 환불 또는 종료만으로 Top-up 결제까지 자동 환불하거나 Top-up credits를 자동 삭제하지 않는 것을 기본 domain 원칙으로 제안한다.

전략팀은 다음 중 원하는 고객 경험을 결정해야 한다.

#### 선택지 A — 유효기간 동안 보유하되, 유료 구독이 다시 생길 때까지 사용 중지

- 현재 코드 동작과 같음
- Top-up은 사라지지 않고 원래 유효기간은 계속 흐름
- 새 구독이 시작되면 남은 Top-up을 다시 사용
- 이용권 없는 상태에서 기능 권한 문제가 생기지 않음
- 고객은 사용할 수 없는 기간에도 유효기간이 줄어드는 점을 불리하게 느낄 수 있음

#### 선택지 B — 구독이 끝나도 유효기간 동안 계속 사용

- 고객은 이미 구매한 credits를 계속 사용할 수 있음
- 그러나 Top-up 자체에는 Basic·Pro·Business 등급과 plugin 권한이 없음
- 따라서 이용권 없이 어떤 기능을 허용할지 새로 정해야 함
  - 마지막 구독 등급의 기능 유지
  - 모든 등급에 공통인 제한 기능만 허용
  - 별도의 Top-up-only 이용권 정의
- 이 결정을 생략하면 credits는 있으나 사용할 기능이 없거나, 반대로 구독 없이 유료 구독 기능을 쓰는 모순이 생김

#### 선택지 C — 구독 종료 시 남은 Top-up을 함께 정산

- 남은 Top-up을 자동 환불하거나 별도 환불 선택권 제공
- 구독과 별도 결제를 강하게 결합하게 됨
- 일부 사용분 계산, 법적 환불 조건, provider 부분 취소, 세무·회계 처리가 복잡해짐

회신 요청:

- A/B/C 중 선호 방향
- B라면 이용권 없이 허용할 기능 범위
- C라면 자동 환불인지 고객 선택인지

### S7. Top-up 유효기간

현재 코드에는 구매일부터 365일이 설정돼 있지만 확정 정책인지 확인되지 않았다.

결정 요청:

1. 유효기간을 365일로 확정하는가?
2. S6-A처럼 구독이 없는 동안 사용을 중지한다면 유효기간도 중지하는가, 계속 흐르게 하는가?
3. 유효기간 만료 전 고객에게 알림을 제공할 것인가? 제공한다면 언제 알릴 것인가?
4. 회사 귀책으로 서비스를 장기간 사용할 수 없는 경우 유효기간 연장 정책을 둘 것인가?

기간과 고지 방식은 법무 검토가 필요하다.

### S8. Top-up 자체의 환불정책

구독 환불과 Top-up 환불은 별도로 결정해야 한다.

전략팀 결정 요청:

1. 법에서 반드시 보장해야 하는 경우 외에, 미사용 Top-up에 자발적 전액 환불을 제공하는가?
2. 제공한다면 신청 가능 기간과 “미사용” 기준은 무엇인가?
3. Top-up을 일부 사용한 경우 남은 credits에 대해 자발적 부분 환불을 제공하는가?
4. 부분 환불을 제공한다면 구매 단가에 따라 시스템이 비례 계산하는 방향을 원하는가?
5. 만료된 Top-up에 별도의 예외 환불을 제공하는가?

필수 전제:

- Top-up 환불이 완료되면 해당 결제로 지급된 미사용 Top-up credits를 회수한다.
- 일반 경로에서 고객이나 관리자가 환불액을 임의 입력하지 않는다.
- 부분 사용분의 금액과 세금 계산은 법무·세무회계 검토 후 시스템 산식으로 확정한다.

### S9. Trial과 무료 플랜의 관계

현재 구현은 지속적인 무료 플랜이 아니라 계정당 한 번 제공되는 Trial에 가깝다.

결정 요청:

1. 현재의 1회 400 credits Trial을 공식 정책으로 승인하는가?
2. Trial 자체에 만료기간을 둘 것인가?
3. 유료 전환 후 남은 Trial credits를 유지하는가?
4. 유료 이용권 종료 후 남은 Trial을 다시 사용할 수 있게 하는가?
5. Trial과 별도로 지속적인 무료 플랜을 운영할 계획이 있는가?
6. Trial 대상 계정의 기준일·시각은 언제인가?

지속 무료 플랜을 추가하면 무료 사용량, 기능 범위, abuse 방지, Top-up 구매·사용 자격을 다시 설계해야 한다.

### S10. Credit 사용 순서

한 계정에 Trial, 구독 benefit, Top-up credits가 함께 있을 수 있다. 환불 금액과 회수 대상을 정확히 계산하려면 어떤 credit을 먼저 사용하는지 확정해야 한다.

결정 요청:

- Trial, 구독 benefit, Top-up 중 소비 우선순위
- 유효기간이 빠른 credit을 항상 먼저 쓸지
- 고객이 사용할 credit 종류를 직접 선택할 수 있게 할지
- 환불 검토 중인 결제의 credits를 일시적으로 사용 중지할지

실무 제안은 고객이 직접 선택하지 않고, **만료가 빠른 credit 우선**을 기본으로 하되 환불 대상 payment와의 귀속을 추적할 수 있게 하는 방식이다. 단, 이는 아직 사업 승인되지 않은 제안이다.

### S11. 예외 환불의 사업 분류

일반 고객 변심과 다른 사유를 어떤 category로 운영할지 정해야 한다.

전략팀 결정 요청:

- 중복 결제
- 결제는 됐으나 이용권 자동 발급 실패
- 장시간 또는 반복적인 서비스 장애
- 광고·상품 설명과 실제 제공 내용 불일치
- 잘못된 가격 또는 잘못된 플랜 결제
- 계정 탈취·부정 결제 의심
- 회사가 제공하는 별도 보상

각 category에서 원하는 기본 방향을 아래 중 하나로 회신해 주기 바란다.

- 전액 환불 검토
- 부분 환불 검토
- 환불 대신 재발급·기간 연장 우선
- 법무 또는 운영 책임자 개별 검토

법적으로 반드시 처리해야 하는 사유는 회사의 일반 사업정책과 무관하게 법무 의견을 따른다. 보상성 credits 지급은 결제금 환불과 별도 처리한다.

### S12. 자동 처리와 관리자 승인 범위

시스템이 승인된 규칙으로 eligibility와 금액을 계산하더라도, 실제 Toss 취소 실행 전에 사람 승인을 거칠지 결정해야 한다.

선택지:

#### A. 모든 환불을 관리자 승인 후 실행

- 초기 정책 안정화에 유리
- 처리시간과 CS 업무 증가

#### B. 명백한 저위험 건만 자동 처리하고 나머지는 관리자 승인

- 예: 중복 결제가 기술적으로 확인된 경우, 승인된 기간 안의 완전 미사용 결제
- 고객 경험과 통제를 절충
- 자동 처리 조건을 구체적으로 승인해야 함

#### C. 승인된 일반정책에 맞는 모든 건을 자동 처리

- 가장 빠르고 CS 부담이 낮음
- 정책 오류·계정 탈취·동시 credit 사용에 대한 통제가 더 필요
- 현재 정책 확정 전 단계에는 적합하지 않음

개발팀은 **초기에는 A**, 운영 데이터와 정책 안정성이 확보된 뒤 B로 확대하는 방향을 제안한다. 이는 기술·운영 위험 관점의 제안이며 최종 결정은 전략팀과 운영·CS가 함께 내려야 한다.

### S13. 고객에게 보여줄 환불 정보 수준

결정 요청:

- 요청 전에 예상 환불 가능 여부와 금액을 보여줄 것인가?
- 계산 근거를 어느 수준까지 공개할 것인가?
- 환불 후 종료되는 이용권과 회수되는 credits를 확인받을 것인가?
- 부분 환불·거절 시 고객이 재검토를 요청할 수 있는 채널을 둘 것인가?

개발팀은 고객이 요청을 확정하기 전에 최소한 다음을 확인할 수 있게 하는 방향을 제안한다.

- 예상 환불액
- 환불 사유와 계산 기준
- 이용권 종료 시점
- 회수되는 미사용 credits
- 처리 예상시간

최종 고지 문구는 법무·운영·CS 검토가 필요하다.

## 5. 전략팀이 결정하지 않아도 되는 기술 세부사항

다음은 승인된 사업정책을 받은 뒤 개발팀이 설계할 기술 문제다.

- TossPayments 취소 API 호출 형식
- idempotency key와 중복 요청 방지
- timeout·retry·provider 상태 동기화
- webhook과 동기 API 응답의 관계
- 환불 case와 provider attempt의 DB 상태
- audit log 저장 구조
- provider 성공 후 내부 entitlement·credit 처리 실패 복구
- 부분 취소 누적액과 잔여 취소 가능액 검증

전략팀은 위 구현 방식을 고를 필요가 없다. 다만 고객 경험, 승인 권한, 자동화 범위처럼 사업 운영에 영향을 주는 결과는 S1~S13에서 결정해야 한다.

## 6. 다른 담당자에게 별도 확인할 항목

### 6.1 법무

- 월간·연간 구독과 Top-up의 디지털콘텐츠·용역·계속거래 해당 여부

- 일부 credit 사용 시 환불 제한 가능 범위

- Top-up 유효기간·만료와 필수 고지

### 6.3 운영·CS

- 접수 채널, 담당자, 대체자, 응답·처리 목표시간
- 환불 사유별 필수 증빙
- 관리자별 승인 금액 한도와 이중 승인 여부
- 자동 처리에서 제외할 위험 신호
- 예외·거절·지연·시스템 장애 고객 안내
- 수기 예외 금액 입력을 허용할지와 승인 절차

- 미결 항목을 개발팀이 임의로 확정하지 않는다.

- 현재 코드에 있는 Top-up gate와 Trial 값도 정책 승인 근거로 간주하지 않는다.
- 승인된 규칙이 없는 환불 branch는 자동화하지 않는다.
- 법무·세무회계·운영CS 확인이 필요한 내용을 전략팀 회신만으로 확정하지 않는다.
- 개발은 승인된 범위와 별도 구현 설계 승인 이후 시작한다.
