# 토스페이먼츠 PG 전체 연동 설계

- 작성일: 2026-08-18 (Asia/Seoul)
- 상태: 구현 전 최종 사용자 검토 대기
- 코드 브랜치: 각 대상 저장소의 `feature/toss-payments-pg-integration`
- 문서 저장소: `.codex/main`
- 구현 환경: API·고객 웹 Node 22, 테스트 우선

## 1. 목적

`feat/access-credit-system-replacement`에 구현된 상품·구독·이용 자격·크레딧 구조를 보존하면서, 토스페이 직접 연동을 토스페이먼츠 PG V2로 교체한다.

이 브랜치는 배포 브랜치가 아니라 Clipper의 전체 PG 연동 구현과 테스트를 완성하는 전용 브랜치다. `dev`, staging, 실서비스 반영 여부와 시점은 사용자가 별도로 결정한다.

완성된 브랜치에서는 다음이 함께 동작해야 한다.

- 로그인 사용자용 월간·연간 카드 정기결제
- 추가 크레딧 단건결제
- 카드, 카카오페이, 네이버페이, 토스페이, 계좌이체, 가상계좌
- 결제 성공 후 구독·이용 자격·크레딧의 멱등 지급
- 월별 구독 크레딧 지급
- 다음 결제 취소·취소 철회
- 결제수단 변경
- 갱신 실패 유예·재시도·복구
- 결제 상태 웹훅과 가상계좌 입금 웹훅
- 상품·기능 권한·갱신 실패 정책의 관리자 설정
- 고객 결제내역·영수증·가상계좌 입금정보 확인

익명 PG 심사용 `review mode`는 이 브랜치에서 제거한다. 현재 `dev`와 `dev.clipperstudio.ai`에 배포된 심사용 기능은 이 작업으로 수정하지 않는다.

### 2.1 결정 상태표

이번 대화에서 사용자가 직접 확정한 항목:

- 브랜치 이름과 dev·access-credit worktree 보존
- review mode 없는 실제 회원용 PG 전체 연동
- Basic·Pro 월간 가격과 월 크레딧
- 900원으로 끝나는 Basic·Pro 연간 결제 총액
- 월간·연간 카드 정기결제와 연간 크레딧 월별 지급
- 추가 크레딧 세 상품의 초기 수량·가격·365일 유효기간
- 플랜별 기능 권한을 DB에서 변경하고 `variation`만 Pro 전용으로 시작
- 계약된 모든 단건 결제수단 구현
- 돈 환불 전체 기능 제외, 크레딧 반환·복구는 유지
- 결제 상태·가상계좌 입금·빌링키 삭제 웹훅 구현

구현을 막지 않도록 이번 설계가 합리적인 초기값으로 확정한 항목:

- 구독 크레딧은 다음 월별 지급 기준일에 만료하고 이월하지 않음
- 활성 이용 자격이 있으면 잔액 소진 전에도 topup 구매 허용
- 가상계좌 입금기한 24시간
- 가격은 부가가치세 포함, 면세금액 0원
- 다음 결제 취소 철회 허용과 기간 말까지 빌링키 보존
- Basic→Pro는 같은 주기에서 즉시 차액 결제, 하향·주기 변경은 다음 갱신 적용
- 예약 변경은 갱신 전 취소·교체 가능
- 고객 결제내역·영수증·가상계좌 정보 화면 포함
- 웹훅에서 외부 취소 상태를 기록·경고하되 권한·크레딧을 자동 변경하지 않음

이번 구현에서 의도적으로 결정하지 않고 제외한 항목:

- 돈 환불 요청 경로·산식·승인·실행
- 고객센터·고객문의 채널
- 최종 법률 문구와 데이터 보존기간
- 라이브 배포 환경과 출시 시점
- 무료 체험, 쿠폰, 팀 구독, 복수 결제수단, 법인·해외 결제

두 번째 묶음은 상품·정책 또는 독립된 application policy에 모아 나중에 변경해도 provider와 크레딧 원장을 다시 설계하지 않게 한다.

## 3. 구현 접근법 결정

### 3.1 선택한 방법: 도메인 보존 + PG provider 경계 교체

다음은 재사용한다.

- 상품 카탈로그와 관리자 편집 API
- 한 사용자당 하나의 기본 이용 자격
- 구독 상태와 기간 모델
- 출처별 크레딧 지급 묶음과 불변 원장
- 작업 시작 차감과 실패 시 크레딧 반환·복구
- 결제 주문·이벤트·fulfillment 분리
- 결제 성공 후 fulfillment 재처리
- 갱신 실패 D+3 유예, D+1·D+2 자동 재시도
- 결제수단 변경 요청의 동시성 통제
- 고객 웹·관리자 웹·데스크톱의 이용 자격 계약

다음은 토스페이먼츠 PG V2 기준으로 교체한다.

- `TossPayProvider`, `HttpTossPayProvider`
- `payToken`, `displayId`, `resultCallback` 계약
- 토스페이 직접 빌링키 상태 조회·활성화 callback 기반 복구
- 토스페이 직접 checkout URL 이동
- 토스페이 직접 환경변수와 fixture

새 provider는 아래 공식 PG 계약을 격리한다.

- 일반 결제 승인: `POST /v1/payments/confirm`
- 결제 조회: `GET /v1/payments/{paymentKey}` 또는 주문번호 조회
- 빌링키 발급: `POST /v1/billing/authorizations/issue`
- 빌링 승인: `POST /v1/billing/{billingKey}`
- 빌링키 삭제: `DELETE /v1/billing/{billingKey}`

브라우저 SDK는 공식 `@tosspayments/tosspayments-sdk`와 기존 심사용 `TossPaymentsSdkService`의 격리 패턴을 재사용한다.

### 3.2 선택하지 않은 방법

- 기존 토스페이 adapter의 URL과 DTO만 바꾸는 방법: 브라우저 인증, 승인, 빌링키 발급과 복구 계약이 달라 안전하지 않다.
- 결제·구독·크레딧 전체 재작성: 이미 검증된 access-credit 도메인과 복구 로직을 버리게 되고 범위와 회귀 위험만 커진다.
- 심사용 PG 코드를 그대로 실서비스화: 익명 주문과 review 전용 상태·규칙이 실제 회원 구독에 맞지 않는다.

## 4. 확정 상품과 권한

### 4.1 요금제 초기값

| 등급 | 결제 주기 | 결제 금액 | 지급 크레딧 | 갱신 |
| --- | --- | ---: | ---: | --- |
| Basic | 월간 | 19,900원 | 매월 400 | 매월 자동 갱신 |
| Basic | 연간 | 190,900원 | 매월 400 | 매년 자동 갱신 |
| Pro | 월간 | 39,900원 | 매월 1,000 | 매월 자동 갱신 |
| Pro | 연간 | 382,900원 | 매월 1,000 | 매년 자동 갱신 |

- Basic 연간은 월 결제 합계 238,800원 대비 약 20.06% 할인이다.
- Pro 연간은 월 결제 합계 478,800원 대비 약 20.03% 할인이다.
- 연간 상품은 월 환산액이 아니라 실제 연 결제금액 자체가 900원으로 끝난다.
- 모든 표시 금액은 부가가치세 포함 소비자 결제금액으로 취급하고 `taxFreeAmount`는 0으로 요청한다.
- 3개월 상품과 고정 기간 단건 이용권은 만들지 않는다.

가격과 크레딧은 임시 초기 상품값이다. 코드 상수가 아니라 DB 상품 카탈로그와 초기 seed로 넣는다.

### 4.2 기능 권한 초기값

Basic에서 허용한다.

- `shortform_url`
- `shortform_paste`
- `shortform_prompt`
- `dialog_highlight`
- `dance_highlight`

Pro에서 위 전체와 다음을 허용한다.

- `variation`

즉, 초기값에서는 베리에이션 생성만 Pro 전용이다.

권한은 `plan_plugin_entitlements`에서 관리하고 관리자 API·화면으로 교체 가능해야 한다. 권한 변경은 해당 등급의 기존 구독자와 관리자 부여 사용자에게 즉시 적용한다. 서버 작업 시작 시 다시 검사하므로 UI 숨김만으로 보호하지 않는다.

### 4.3 가격·크레딧과 기능 권한의 변경 적용 차이

- 기존 구독의 결제 가격, 결제 주기, 월 지급 크레딧은 구독 계약 스냅샷을 따른다.
- 카탈로그 가격이나 월 크레딧 변경은 새 구독 또는 사용자가 명시적으로 상품을 변경한 이후부터 적용한다.
- 기능 권한은 현재 등급의 최신 `plan_plugin_entitlements`를 즉시 따른다.
- 결제 주문은 상품명, 가격, 주기, 등급, 월 크레딧을 당시 값으로 영구 스냅샷한다.

## 5. 추가 크레딧 상품

| 상품 | 가격 | 유효기간 |
| --- | ---: | --- |
| 100크레딧 | 5,900원 | 결제 완료일부터 365일 |
| 500크레딧 | 27,900원 | 결제 완료일부터 365일 |
| 1,000크레딧 | 49,900원 | 결제 완료일부터 365일 |

정책은 다음과 같다.

- Basic과 Pro가 같은 상품을 같은 가격으로 구매한다.
- 활성 기본 이용 자격이 있으면 잔액 소진 전에도 구매할 수 있다.
- 결제 성공 확인 전에는 크레딧을 지급하지 않는다.
- 결제 중 이용 자격이 끝났더라도 결제가 성공하면 구매한 크레딧은 지급한다.
- 이용 자격이 없으면 잔액은 보존하지만 사용할 수 없다.
- 이용 자격이 다시 활성화되면 아직 만료되지 않은 잔액을 사용할 수 있다.
- 추가 크레딧은 이용기간이나 플러그인 권한을 부여하지 않는다.

## 6. 구독 크레딧 소멸 기본값

구독과 관리자 요금제로 매월 지급한 크레딧은 다음 월별 지급 기준일 직전에 만료한다. 이월하지 않는다.

예:

```text
1월 31일 지급 -> 2월 말일 만료
2월 말일 지급 -> 3월 31일 만료
연간 결제도 같은 월별 기준일로 12회 지급
```

고정 30일 또는 31일을 더하지 않고 `nextMonthAnniversary()`의 월말·윤년 규칙으로 정확한 다음 혜택 주기를 계산한다. 이로써 짧은 달에 이전 회차와 다음 회차가 겹치는 문제를 막는다.

작업 실패로 반환할 원래 지급 묶음이 이미 만료되었다면 반환 이력과 묶음 잔액은 복구하지만 사용 가능 잔액으로 되살리지 않는다.

## 7. 결제수단별 범위

경영실이 확인한 계약 범위는 다음과 같다.

1. 카드 단건결제 — 추가 크레딧 충전
2. 카드 정기결제
3. 간편결제 — 카카오페이, 네이버페이, 토스페이
4. 가상계좌
5. 계좌이체

구현 매핑은 다음과 같다.

| 결제 목적 | 카드 | 카카오·네이버·토스페이 | 계좌이체 | 가상계좌 |
| --- | --- | --- | --- | --- |
| 월간·연간 구독 | 카드 빌링 | 미지원 | 미지원 | 미지원 |
| 추가 크레딧 | 지원 | 지원 | 지원 | 지원 |

자동결제는 계약 범위에 맞춰 `requestBillingAuth({ method: "CARD" })`만 사용한다. 공식 문서에 계좌 자동결제가 존재하더라도 이번 계약과 구현 범위에는 넣지 않는다.

일반 결제수단 노출은 토스페이먼츠 주문서형 UI와 MID 설정을 정본으로 삼는다. 코드의 결제수단 allowlist도 위 범위로 제한한다. 공급자가 실제로 결제를 승인한 뒤 예상하지 않은 수단으로 확인되는 예외에서는 고객 돈을 받고 지급을 거부하지 않는다. 결제를 정상 반영하고 운영 경고를 남겨 MID 설정을 바로잡는다.

## 8. 사용자 흐름

### 8.1 로그아웃 상태의 요금제 선택

1. `/pricing`은 로그인 여부와 관계없이 Basic·Pro 및 월간·연간 상품을 보여준다.
2. 로그아웃 사용자가 구독 버튼을 누르면 Google 로그인을 시작한다.
3. 로그인 완료 후 선택했던 결제 상품으로 복귀한다.
4. 서버가 상품의 판매 상태와 현재 사용자 이용 자격을 다시 검증한다.
5. 카드 등록·최초 결제로 이동한다.

복귀 URL이나 브라우저 값은 가격과 권한의 정본이 아니다. 서버는 상품 ID만 입력으로 받고 현재 카탈로그를 다시 읽는다.

### 8.2 최초 구독

```text
상품 선택
  -> 서버가 pending subscription과 billing auth attempt 저장
  -> 고객 웹에서 카드 자동결제 인증창 호출
  -> authKey·customerKey가 API success URL로 반환
  -> 서버가 저장값과 대조
  -> 같은 Idempotency-Key로 빌링키 발급
  -> 빌링키 암호화 저장
  -> 같은 주문번호·Idempotency-Key로 최초 결제
  -> Payment DONE 재검증
  -> 구독·이용 자격 활성화
  -> 첫 월 크레딧 한 번 지급
```

- 카드 등록만 성공하고 최초 결제가 실패하면 이용 자격과 크레딧을 지급하지 않는다.
- 안전하게 저장된 빌링키는 짧은 재시도·결과 확인에 사용할 수 있다.
- 사용자는 같은 카드로 최초 결제를 다시 시도하거나 새 카드 등록을 시작할 수 있다.
- 새 카드가 안전하게 저장되기 전 기존 후보 키를 삭제하지 않는다.
- 오래 중단된 미활성 구독과 불필요한 후보 키는 복구 스케줄러가 정리한다.

### 8.3 월간·연간 갱신

- 토스페이먼츠는 스케줄링하지 않으므로 Clipper API scheduler가 `nextBillingAt`에 빌링 승인 API를 호출한다.
- 월간은 한 달, 연간은 열두 달의 결제기간을 연장한다.
- 연간도 크레딧은 한 번에 12개월분을 지급하지 않고 월별로 지급한다.
- 결제일은 최초 결제 승인 시각과 원래 월·일 anchor를 유지한다.
- 월말과 윤년은 원래 anchor 기준으로 마지막 유효 일자를 선택한다.

### 8.4 추가 크레딧 즉시 결제

```text
/app/topup에서 상품 선택
  -> 인증 사용자와 활성 이용 자격 확인
  -> 서버 주문 생성
  -> Clipper checkout에서 주문서형 결제 UI 렌더링
  -> 카드·간편결제·계좌이체·가상계좌 중 선택
  -> success URL에서 orderId·paymentKey·amount 대조
  -> confirm 또는 상태 조회
  -> DONE이면 결제 완료와 topup fulfillment
```

카드, 간편결제, 계좌이체는 `DONE`을 확인한 뒤 즉시 크레딧을 지급한다.

### 8.5 가상계좌

- 기본 입금기한은 발급 후 24시간이다.
- 승인 성공은 계좌 발급 성공이며 주문 상태는 `waiting_for_deposit`다.
- 계좌 발급 시점에는 크레딧을 지급하지 않는다.
- 은행, 마스킹 계좌번호, 예금주, 입금기한을 결제 결과와 결제내역에 표시한다.
- `DEPOSIT_CALLBACK`과 결제 재조회로 `DONE`을 확인한 뒤 한 번만 지급한다.
- 입금기한 만료 또는 입금 전 취소에는 지급하지 않는다.
- 중복 웹훅과 `PAYMENT_STATUS_CHANGED` 중복 도착은 같은 주문 fulfillment 한 번으로 수렴한다.
- 공급자에서 늦은 `DONE`이 확인되면 로컬 만료 추측보다 공급자 결제 상태를 우선하고 지급한다.

계좌이체와 가상계좌 현금영수증 UI·발급은 토스페이먼츠 주문서형 기능을 사용한다. Clipper는 현금영수증 식별번호를 직접 저장하지 않고 안전한 영수증 URL과 발급 결과만 보관한다.

### 8.6 고객 결제내역

마이페이지에서 로그인 사용자가 자신의 주문만 조회한다.

- 상품명과 결제 목적
- 주문번호와 주문·결제 시각
- 금액과 결제 상태
- 결제수단과 간편결제사
- 가상계좌 입금 대기 정보
- 토스페이먼츠가 제공한 영수증·매출전표 URL
- 결제 완료 후 상품 지급 상태

평문 빌링키, `authKey`, Secret Key, 전체 카드번호, 계좌번호는 반환하지 않는다.

## 9. 구독 관리 정책

### 9.1 다음 결제 취소와 철회

- 사용자는 언제든 다음 자동 결제를 취소할 수 있다.
- 현재 결제기간 종료일까지 권한과 예정된 월별 크레딧을 유지한다.
- 취소는 즉시 환불이나 즉시 이용 종료가 아니다.
- 기간 종료 전에는 다음 결제 취소를 철회할 수 있다.
- 철회를 지원하기 위해 빌링키는 실제 기간 종료 전까지 유지한다.
- 기간이 끝나고 미정산 주문이 없으면 빌링키를 삭제한다.

취소 전에 시작된 갱신 결제가 나중에 `DONE`으로 확정되면 결제된 다음 기간을 제공하되 `cancel_at_period_end`를 다음 기간 끝으로 이동하여 그다음 갱신은 하지 않는다.

### 9.2 상향 변경

Basic에서 Pro로의 변경은 즉시 적용한다.

- 현재 결제 주기는 유지한다. 월간 Basic은 월간 Pro로, 연간 Basic은 연간 Pro로 변경한다.
- 현재 Basic 계약 스냅샷과 변경 시점의 Pro 상품 스냅샷으로 남은 기간 가격 차액을 계산한다.
- 계산식은 `ceil(전체 기간 가격 차이 × 남은 시간 / 전체 결제기간)`이며 원 단위로 올림한다.
- 계산액이 공급자 최소 결제금액보다 작으면 즉시 소액 청구하지 않고 다음 갱신 변경으로 예약한다.
- 차액 결제 `DONE` 후에만 Pro로 변경한다.
- 현재 월별 혜택 주기의 남은 비율만큼 `Pro 월 크레딧 - Basic 월 크레딧`을 올림하여 한 번 추가 지급한다.
- 다음 갱신부터 변경 시점에 확인한 Pro 상품 가격·주기·월 크레딧 스냅샷을 사용한다.

### 9.3 하향 변경과 결제 주기 변경

- Pro에서 Basic으로의 변경은 다음 갱신일부터 적용한다.
- 월간과 연간 사이의 변경도 다음 갱신일부터 적용한다.
- 현재 결제기간의 기능 권한과 크레딧 조건을 소급 변경하지 않는다.
- 한 구독에 하나의 예약 변경만 둔다.
- 사용자는 갱신 전까지 예약을 취소하거나 다른 대상 상품으로 교체할 수 있다.
- 다음 결제 취소를 요청하면 예약 상품 변경도 함께 취소한다.
- 예약 당시 사용자에게 표시한 대상 상품 가격을 스냅샷하고 다음 갱신에 사용한다.

## 10. 갱신 실패 정책

기존 구현을 유지한다.

- 최초 실패: `D+0`, 구독은 `past_due`
- 자동 재시도: `D+1`, `D+2`
- 유예 종료: `D+3`
- 유예 중 기존 플러그인 권한과 만료되지 않은 크레딧 사용 가능
- 실패한 새 회차 크레딧 미지급
- 사용자의 직접 재결제는 자동 재시도 순번을 소모하지 않음
- 성공하면 원래 결제 기준일을 유지해 복구
- `D+3`까지 실패하면 `stopped`, 계정·프로젝트·결과물은 보존

이 값은 관리자 DB 정책으로 변경할 수 있고 이미 `past_due`인 회차에는 소급하지 않는다.

PG 오류는 다음처럼 분류한다.

- 잔액·한도·일시 장애: 예정된 재시도 유지
- 삭제·무효 빌링키: 같은 키 자동 청구를 중지하고 카드 재등록 안내
- timeout·5xx·응답 파싱 실패: 결제 조회 또는 같은 멱등키 재시도로 결론을 확인하기 전 새 청구 금지
- `409 IDEMPOTENT_REQUEST_PROCESSING`: 같은 멱등키로 나중에 재확인

## 11. 결제수단 조회·변경의 PG 전환

토스페이먼츠 PG 빌링키는 발급 후 다시 조회할 수 없다. 따라서 토스페이 직접 연동의 `getBillingKeyStatus()`와 `ACTIVE` 재조회 설계를 사용하지 않는다.

새 흐름은 다음과 같다.

```text
현재 빌링키 유지
  -> 변경 attempt와 암호화 authKey·멱등키 선저장
  -> requestBillingAuth(CARD)
  -> 같은 멱등키로 새 빌링키 발급
  -> 빌링키와 마스킹 카드정보를 즉시 암호화·저장
  -> 구독 현재 키를 새 키로 원자적 교체
  -> 과거 키 삭제
```

- 빌링키 발급 응답 자체가 카드 등록 유효성 확인이다.
- 정상 구독의 카드 변경은 즉시 결제하지 않는다.
- `past_due`에서는 상품명·미결제 금액·등록 직후 즉시 재결제를 고지하고 동의받는다.
- 새 카드 결제가 실패해도 새 빌링키는 유지하고 `past_due` 복구를 계속한다.
- 후보 등록 실패·취소 시 현재 빌링키를 유지한다.
- 카드사·마스킹 번호·카드 종류는 발급 응답의 안전한 필드만 저장한다.
- `BILLING_DELETED` 웹훅으로 현재 키 삭제를 감지한다.

### 11.1 빌링키 발급 응답 유실 복구

발급 API 호출 전 다음을 DB에 저장한다.

- 등록 attempt
- 암호화된 `authKey`
- `customerKey`
- 고정된 billing issue `Idempotency-Key`
- attempt 만료 시각

그 뒤 빌링키 발급을 호출한다. 응답을 받은 직후 다른 외부 작업 없이 빌링키와 마스킹 카드정보를 저장하고 `authKey`를 제거한다.

응답 직후 서버가 중단되어도 토스페이먼츠 POST 멱등키는 최초 요청일부터 15일간 같은 응답을 돌려주므로, 복구 worker가 저장된 `authKey`와 같은 멱등키로 발급 요청을 재실행해 동일 빌링키 응답을 회수할 수 있다. 이 방식으로 “빌링키는 다시 조회할 수 없다”는 제약을 정상 복구 흐름으로 바꾼다.

## 12. 결제 상태와 데이터 모델

기존 적용 마이그레이션은 수정하지 않는다. `feat/access-credit-system-replacement`와 최신 `dev`의 마이그레이션을 합친 뒤 새 forward migration으로 PG 전체 의미를 맞춘다.

### 12.1 주문 상태

목표 상태는 다음 의미를 표현한다.

- `created`
- `checkout_ready`
- `authorization_pending`
- `payment_pending`
- `waiting_for_deposit`
- `paid`
- `canceled`
- `expired`
- `failed`
- `reconciliation_required`

`reconciliation_required`는 결제 실패가 아니라 공급자 결과를 아직 확정하지 못한 상태다. 이 상태에서 새 결제를 자동 생성하지 않는다.

### 12.2 주문 목적

- `subscription_initial`
- `subscription_renewal`
- `subscription_upgrade`
- `credit_topup`

`review` 목적과 익명 review 필드는 최종 전환에서 제거한다.

### 12.3 추가·정리할 데이터

결제 주문:

- `payment_key`, `last_transaction_key`
- 사용한 키 세트와 MID 식별 범주
- 결제수단, 간편결제사, 영수증 URL
- 가상계좌 은행·마스킹 계좌·예금주·입금기한·웹훅 secret 암호화값
- confirm·billing issue·billing charge 멱등키
- 공급자 상태와 reconciliation 상태
- 상품·등급·가격·주기·크레딧 스냅샷

구독:

- 무작위 `customerKey`
- 현재 암호화 빌링키와 HMAC lookup fingerprint
- 카드 마스킹 표시정보
- 계약 가격·주기·월 크레딧·크레딧 소멸 스냅샷
- 결제·혜택 anchor
- 예약 변경 상품과 가격·주기·크레딧 스냅샷

등록 attempt:

- 최초 가입 또는 결제수단 변경 목적
- 암호화 `authKey`
- issue 멱등키
- 후보 암호화 빌링키와 fingerprint
- 상태·만료·동의 정보

웹훅 inbox:

- 이벤트 타입과 안전한 공급자 식별자
- dedupe key
- 수신·처리·재시도 상태
- 마지막 오류 범주
- 원문 전체가 아닌 정규화한 최소 payload

## 13. 멱등성·트랜잭션·복구

토스페이먼츠의 모든 POST 호출에 주문 또는 attempt 생성 시 만든 고정 UUID v4 멱등키를 사용한다.

- 최초 요청과 재시도는 같은 API 키·URL·HTTP 메서드·payload·멱등키를 사용한다.
- 에러가 왔다고 멱등키를 바꿔 같은 논리 결제를 재전송하지 않는다.
- 15일이 지난 미확정 결제는 자동으로 새 키를 만들어 청구하지 않고 관리자 확인 대상으로 둔다.
- 공급자 네트워크 호출 중 DB 트랜잭션을 열어두지 않는다.
- 주문 claim, 공급자 호출, 결제 결과 저장, fulfillment를 각각 짧은 단계로 분리한다.
- 결제 성공 저장과 상품 지급 성공을 분리한다.
- 결제 성공 후 fulfillment 실패는 결제를 다시 하지 않고 지급만 재시도한다.

서버가 결론을 확정하는 조건:

- DB 주문번호와 공급자 `orderId` 일치
- DB 금액과 공급자 `totalAmount` 일치
- 기대한 주문 목적에 맞는 공급자 `type`과 결제수단
- 즉시 결제는 `DONE`
- 가상계좌는 `DONE` 전까지 미지급

## 14. 웹훅

한 HTTPS 엔드포인트에서 다음 이벤트를 받는다.

- `PAYMENT_STATUS_CHANGED`
- `DEPOSIT_CALLBACK`
- `BILLING_DELETED`

### 14.1 공통 원칙

- 일반 결제 웹훅에는 서명 헤더가 없으므로 body만 신뢰하지 않는다.
- 필요한 식별자만 inbox에 저장하고 결제 조회 API로 실제 상태를 재확인한다.
- `DEPOSIT_CALLBACK.secret`은 결제 승인 응답에서 저장한 secret과 안전하게 비교한 뒤 다시 조회한다.
- `PAYMENT_STATUS_CHANGED`와 `DEPOSIT_CALLBACK`을 모두 등록하면 가상계좌 변경이 중복 전달될 수 있으므로 dedupe와 멱등 fulfillment를 전제로 한다.
- 웹훅 원문의 카드·계좌·빌링키를 로그나 `payment_events.payload`에 보존하지 않는다.

### 14.2 빌링키 삭제 상관관계

`BILLING_DELETED`에는 평문 빌링키가 온다. 요청 처리 중 메모리에서 HMAC fingerprint를 계산하여 현재·후보·과거 빌링키 fingerprint와 비교한다. 평문은 저장하거나 로그에 남기지 않는다.

현재 구독 키 삭제가 확인되면:

- 자동 청구를 중지한다.
- 결제수단 재등록 필요 상태를 표시한다.
- 이미 시작된 결제 조회와 fulfillment는 끝까지 수행한다.

과거 또는 후보 키 삭제라면 현재 구독을 중지하지 않고 해당 키 정리 완료만 기록한다.

### 14.3 결제 취소 상태와 현재 환불 비범위

`CANCELED` 또는 `PARTIAL_CANCELED`가 외부에서 감지되면 결제를 재조회하고 주문·감사 기록을 갱신하며 운영 경고를 만든다. 그러나 이번 범위에서는 이용 자격이나 크레딧을 자동 회수하지 않고 토스 취소 API도 호출하지 않는다.

이는 돈 환불 기능을 구현한 것이 아니라, 토스와 Clipper DB의 불일치를 감지하는 안전망이다.

## 15. 돈 환불과 크레딧 반환의 용어·범위

### 15.1 이번 범위에서 제외하는 돈 환불

다음을 모두 구현하지 않는다.

- 사용자 환불 요청 페이지
- 고객센터·고객문의 기능
- 관리자 환불 요청 목록
- 환불 가능 금액 산식
- 운영자 검토·super-admin 승인
- 토스페이먼츠 결제 취소 API
- 전액·부분 환불 실행
- 돈 환불에 따른 이용 자격 종료 또는 크레딧 회수

환불 요청 경로, 약관, 청약철회, 사용기간·크레딧 사용량 산식, 승인 권한이 정책적으로 정해진 뒤 별도 설계한다.

### 15.2 계속 구현하는 크레딧 반환·복구

AI 또는 렌더 작업이 실패하여 이미 차감한 서비스 내부 크레딧을 원래 지급 묶음으로 돌려주는 기능은 유지한다. 이것은 사용자가 결제한 돈을 돌려주는 환불이 아니며 문구도 `크레딧 반환` 또는 `크레딧 복구`를 사용한다.

## 16. 관리자 기능

기존 관리자 기능을 유지·보완한다.

- Basic·Pro, 월·연 상품, 가격, 월 크레딧, 판매 활성 상태 관리
- 플랜별 `plugin_key` 권한 교체
- 추가 크레딧 상품 수량·가격·유효기간·활성 상태 관리
- 사용자 표준 요금제 부여·변경·회수
- 관리자 크레딧 지급·회수
- 갱신 실패 유예·재시도 정책 관리
- 결제 주문·웹훅·fulfillment·reconciliation 상태 조회
- 실패한 fulfillment 재처리
- 결제 상태 불일치와 빌링키 삭제 경고 확인

이번 범위에는 돈 환불 실행 버튼을 만들지 않는다.

기존 `operator`와 `super-admin` 역할 모델을 재사용하고 새 역할 체계를 만들지 않는다. 현재 운영 기능의 권한은 기존 guard를 유지하되, 시크릿·키 원문 조회 API는 어떤 역할에도 제공하지 않는다.

## 17. 보안

- 일반 결제와 빌링의 Client Key·Secret Key를 분리한다.
- Client Key만 checkout session으로 브라우저에 전달한다.
- Secret Key는 API 서버 환경변수에만 둔다.
- API base URL은 `https://api.tosspayments.com`으로 고정한다.
- `customerKey`는 이메일, 전화번호, DB 순차번호, 사용자 ID를 사용하지 않고 충분히 무작위로 만든다.
- 빌링키와 짧게 필요한 `authKey`, 가상계좌 webhook secret은 `SecretCipher`로 암호화한다.
- 빌링키 검색은 keyed HMAC fingerprint로만 수행한다.
- 전체 카드번호, CVC, 카드 비밀번호, 생년월일, 전체 계좌번호를 수집·저장하지 않는다.
- provider 오류 원문은 길이와 문자를 제한해 내부 오류 범주로 변환한다.
- receipt token은 256비트 무작위 값이고 DB에는 SHA-256 hash만 저장한다.
- 로그인 API는 주문·구독 소유권을 항상 재검증한다.
- 금액·상품·크레딧은 서버 카탈로그와 주문 스냅샷만 신뢰한다.
- 로그와 감사 payload에 API 키, 평문 키, 민감한 provider 응답을 남기지 않는다.
- 고객 웹 CSP와 인프라 proxy는 공식 SDK·리다이렉트·웹훅에 필요한 최소 origin만 허용한다.

## 18. 환경변수

API 서버에 다음을 사용한다.

```text
TOSS_PAYMENTS_WIDGET_CLIENT_KEY
TOSS_PAYMENTS_WIDGET_SECRET_KEY
TOSS_PAYMENTS_BILLING_CLIENT_KEY
TOSS_PAYMENTS_BILLING_SECRET_KEY
TOSS_PAYMENTS_RETURN_BASE_URL
WEB_BASE_URL
TOSS_PAYMENTS_BILLING_KEY_HMAC_SECRET
```

- API 키 버전은 개발자센터에서 `2024-06-01`로 맞추고 응답 fixture도 이 계약을 사용한다.
- `TOSS_PAYMENTS_REVIEW_MODE`와 토스페이 직접 환경변수는 새 feature 브랜치의 실제 기능에서 사용하지 않는다.
- 환경변수 변경은 서버 런타임 설정이므로 API 컨테이너 재생성이 필요하다.
- 고객 웹 번들에는 키를 하드코딩하지 않으므로 키 교체만으로 고객 웹 이미지를 다시 빌드하지 않는다.

## 21. 브랜치·worktree·보존 규칙

대상 코드 저장소:

- `web/clipper_web_api`
- `web/clipper_web_client`
- `web/clipper_web_admin`
- `web/clipper_infra`
- `desktop/clipper_angular`
- `desktop/clipper_electron`
- `desktop/clipper_nestjs`

각 저장소에서 다음 순서를 지킨다.

1. 로컬 `feat/access-credit-system-replacement`의 정확한 HEAD를 원격에 push해 보존한다.
2. 그 HEAD에서 `feature/toss-payments-pg-integration`을 만든다.
3. 새 branch용 격리 worktree를 만든다.
4. 새 branch 안에서만 최신 `origin/dev`를 merge한다.
5. 충돌을 해결하며 access-credit 도메인과 dev의 PG V2 review adapter 선례를 합친다.
6. 기존 `feat/access-credit-system-replacement` branch와 worktree는 수정·rebase·reset·삭제하지 않는다.
7. 기존 `dev` branch와 review 배포도 수정하지 않는다.

`.codex`는 `main`에서 이번 설계와 인계 문서를 관리한다.

## 22. 의도적으로 제외하거나 나중에 확정할 항목

구현 범위에서 제외한다.

- 돈 환불 전체 기능
- 고객센터·고객문의
- 이메일·SMS·알림톡
- 무료 요금제·무료 체험
- 쿠폰·프로모션 코드
- 팀·워크스페이스 구독
- 복수 저장 결제수단과 예비 카드 자동 대체
- 법인 계약·세금계산서·해외 통화
- 모바일·상품권·해외 결제수단
- legacy 테스트 데이터 이관과 dual-write
- 계정 삭제와 활성 구독의 결합 정책

구현을 막지 않는 외부 운영 확인으로 남긴다.

- 라이브 MID와 실제 계약 키
- 토스 관리자에서 카카오·네이버·토스페이만 노출되는지 확인
- 가상계좌 에스크로 설정이 최종 계약과 일치하는지 확인
- 최종 이용약관·자동결제 고지·개인정보 문구 법률 검토
- 회계·법률상 결제·웹훅·동의 데이터 보존기간

이 항목은 feature 브랜치의 테스트키 구현을 막지 않는다.

## 23. 구현 전 추가 결정 여부

구현을 시작하기 위해 추가로 사용자에게 받아야 하는 필수 정책 결정은 없다.

이번 문서에서 임시 초기값으로 정한 항목은 모두 데이터 또는 정책 경계에 두어 변경 가능하게 만든다.

- 요금제 가격·월 크레딧
- 연간 할인 가격
- 플랜별 기능 권한
- 추가 크레딧 수량·가격·유효기간
- 갱신 실패 유예·재시도 일정
- 상품 판매 활성 상태

돈 환불처럼 요청 경로와 법률·운영 정책이 먼저 필요한 기능은 추상화만 만들어 임의 구현하지 않고 범위에서 완전히 제외한다.

## 24. 완료 기준

- `feature/toss-payments-pg-integration`에 review mode 없는 실제 회원 PG 흐름이 있다.
- Basic·Pro 월간·연간 카드 구독이 테스트키로 완료된다.
- 추가 크레딧을 계약된 모든 단건 수단으로 테스트할 수 있다.
- 가상계좌는 입금 전 미지급, 입금 완료 후 한 번 지급된다.
- 결제·구독·이용 자격·크레딧이 중복 요청과 장애 후에도 일관된다.
- 빌링키 발급 응답 유실이 같은 멱등키로 복구된다.
- 웹훅은 provider 조회로 검증되고 중복·역순 전달에 안전하다.
- 가격·크레딧 스냅샷과 즉시 적용 기능 권한이 분리된다.
- 돈 환불 기능은 들어있지 않지만 외부 취소 상태는 기록·경고된다.
- 기존 무통장·legacy license 구조가 feature 브랜치에서 제거된다.
- API·고객 웹은 Node 22 전체 테스트와 빌드가 통과한다.
- 관련 관리자·데스크톱 저장소도 각 프로젝트 기준 테스트와 빌드가 통과한다.
- 기존 access-credit 및 dev worktree는 변경되지 않는다.

- 토스페이먼츠는 정기결제 스케줄링을 제공하지 않는다.
- 가상계좌 승인 시 실제 결제가 아니라 계좌가 발급되고, 입금 완료는 웹훅·결제 조회로 확인해야 한다.
- 일반 결제 웹훅은 서명 헤더가 없으므로 Payment 조회로 재검증해야 한다.
- `PAYMENT_STATUS_CHANGED`와 `DEPOSIT_CALLBACK`을 함께 쓰면 가상계좌 이벤트가 중복될 수 있다.
- `BILLING_DELETED`로 삭제된 빌링키를 확인할 수 있다.
